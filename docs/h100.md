# Linux and a datacenter GPU — an H100 NVL MIG instance (2026-10-26 – 29)

*Korean version: [문서/H100.md](../문서/H100.md).*

GeulPU 0.12.1 was built from source and run on a university server of a collaborating researcher. It was the first run on native
Linux and on a datacenter GPU. Three things are recorded here:

1. **Build** — the geul compiler and Python 3 were all it took; no CUDA toolkit, C compiler or cmake.
2. **Reproducibility** — the kernel modules were byte-identical to the ones built on Windows, and the generated tokens of 24
   conversations were all identical to an RTX 4070 Ti's on Windows. In a follow-up run the next day, the app's two reproducibility
   checks (file pair and R1 cross-check) were identical too, down to the logit hash at every step (2.1).
3. **Speed** — compared with llama.cpp b11900 and vLLM 0.32.0 over the same HTTP requests. The follow-up run measured the tensor-core
   peaks and the per-kernel time of prompt processing, to see what limits the matmuls (3.5). A second follow-up on 10-29 measured the
   decoding and prompts of six models kernel by kernel and compared them with their bounds (3.6).

The GPU is a MIG instance of one H100 NVL, profile 3g.47gb (60 of the 132 SMs). The numbers below are this instance's, not those of a
whole H100.

## 1. Build

The reference compiler (Python) of geul 2g-1.4.0 — the version pinned in [시험/글저장소커밋.txt](../시험/글저장소커밋.txt) — builds the
self-hosted compiler once, and that compiler builds GeulPU's three programs:

```
git clone https://github.com/wwoosshh/geul-lang geul-lang-v2
cd geul-lang-v2 && git checkout 2g-1.4.0 && mkdir -p build
GEUL_ROOT=. PYTHONUTF8=1 python3 ref/geulc.py self/컴파일러.gl -o build/geulc
cd .. && git clone https://github.com/wwoosshh/GeulPUv2
cd GeulPUv2 && git checkout v0.12.1 && mkdir -p bin
export GEUL_ROOT=../geul-lang-v2
../geul-lang-v2/build/geulc 백엔드/PTX/PTX.gl -o bin/ptx-backend
../geul-lang-v2/build/geulc 커널/커널생성.gl -o bin/kernel-gen
../geul-lang-v2/build/geulc 엔진/서버.gl -o bin/server-cuda
```

- The three programs are ELF files that import only `libc.so.6` and `libcuda.so.1`; they ran as built on glibc 2.35. On the same
  server, llama.cpp b11900's release CUDA binaries require GLIBC 2.38 and did not run (the comparison used the same tag built from
  source on that server — section 3).
- Follow-up (2026-10-27): five executables built on this server (geulc, ptx-backend, kernel-gen, server-cuda, and jaegi-kernel from
  `엔진/재기_커널.gl`) were byte-identical to the same tag built on Ubuntu 24.04 (glibc 2.39) under WSL2. They import no versioned
  symbols (GLIBC_x.y), so an executable built in one place runs on other distributions without a rebuild. They take the pthread
  functions from `libc.so.6`, which needs glibc 2.34 or later (tested: 2.35 and 2.39).
- A kernel module for each model shape is made with `kernel-gen` → `ptx-backend` (commands in
  [재기/H100/준비.sh](../재기/H100/준비.sh)). The modules' PTX targets sm_80; the driver JIT-compiles it for sm_90 when the server first
  loads it.
- What came up
  - The home directory is NFS (root squash), so git refused the repositories as "dubious ownership". git 2.34 does not read
    `-c safe.directory`, so the setting went into a separate config file: `export GIT_CONFIG_GLOBAL=/tmp/gitconfig`, then
    `git config --global --add safe.directory <repository path>`. The shared account's `~/.gitconfig` stays untouched.
  - tar reports "Cannot change ownership" on NFS, but the files are extracted.

## 3. Speed — the same requests to llama.cpp and vLLM

### Method

- **Engines**
  - **GeulPU 0.12.1** (the build in section 1). Fast mode is the app's default — `--빠른` for Q8_0, `--빠른 --F2` for Q4_K_M (8-bit KV
    cache and fast attention F2). Exact mode is the app's exact module (`--먼`). Speculative decoding off (`--추측끔`).
  - **llama.cpp b11900** (the latest release on the day, commit `74b104c9`). Its release CUDA binaries do not run on this server, so the
    same tag was built from source for sm_90 with conda-forge's CUDA 12.8 (nvcc 12.8.93). Flash attention on; both f16 and q8_0 KV
    caches were measured and the faster one is compared (the README's rule).
  - **vLLM 0.32.0** (PyTorch 2.13, CUDA 13.0). It could not open GGUF files (it tried to read the config as JSON), so only Qwen3-8B was
    measured, in BF16 and in FP8 (converted from BF16 at load — `--quantization fp8`). The official Qwen3-32B-FP8 failed because the
    JIT compilation of the block-FP8 kernels does not match the CUDA 13.0 headers, and was left out. Prefix caching off
    (`--no-enable-prefix-caching`), maximum context 31,232.
- **Models**: Qwen3-8B Q8_0 (8.71 GB) · Qwen2.5-7B-Instruct Q4_K_M (4.68 GB — the same file as the README's RTX 4070 Ti table) ·
  Qwen3-32B Q8_0 (34.82 GB). Sources and SHA-256 in section 5.
- **Requests**: one client ([재기/H100/요청.py](../재기/H100/요청.py)) sends OpenAI-compatible `/v1/completions` requests to all three
  engines — prompts given as token ids (drawn fresh for each request, so no engine's prefix cache matches), greedy, `ignore_eos`.
  Each value is the median of three measurements, and only one engine uses the GPU at a time.
  - Prompt processing: the time to generate 1 token from an L-token prompt.
  - Decoding: at depth D, (time to generate 257 tokens − time to generate 1 token) ÷ 256.
  - Concurrent requests: c requests sent together (each a 512-token prompt and 256 generated tokens); all generated tokens ÷ wall time.
  - Servers: single-request measurements with 1 slot and context 32,768; concurrent requests with 8 slots (GeulPU context 1,024,
    llama.cpp 8,192). vLLM ran both from one server (up to 32 concurrent requests).

### 3.4 Reading the results

1. **Decoding and concurrent requests are faster than llama.cpp.**
   - Over three models and three depths, decoding took 5–22% less time (exact mode 2–20%). Throughput with 4 and 8 concurrent requests
     was 1.7–2.0×.
   - On an RTX 4070 Ti, the decoding ratio for Qwen2.5-7B Q4_K_M was 0.97 and 0.89× at depths 8k and 32k (README — a different
     measurement method). On this instance it was 0.83 and 0.79× at depths 8,192 and 30,720.
2. **Long prompts are the weak spot.**
   - A 30,720-token prompt took 1.7× llama.cpp's time on Q8_0. Fast attention F2 exists only in the k-quant modules, not for Q8_0; on
     Q4_K_M, where F2 is on, the ratio was 1.06×.
   - This is the same place as on the RTX 4070 Ti (attention at long context).
3. **Compared with vLLM (Qwen3-8B).**
   - Single-request decoding was close between the 8-bit setups at shallow depth (depth 64: GeulPU 151, vLLM FP8 155 tokens/s). Deeper,
     vLLM FP8 was 23–25% faster (140 vs 114 at depth 8,192, 113 vs 91 at 30,720).
   - For prompt processing, vLLM FP8 was 3.0–8.6× GeulPU's fast mode. Prompt processing is bound by computation, not memory.
     - Estimating the work per token as 13.9 GFLOP of weight matmuls (without the embedding and output layers) plus causal attention,
       vLLM BF16 used 53–75% of this instance's BF16 peak, and GeulPU's fast mode (int8 matmuls) 6–11% of its int8 peak.
     - The peaks are half (dense) the datasheet's H100 NVL values (with sparsity: BF16 1,671 TFLOPS, INT8 3,341 TOPS) times the SM ratio
       60/132: 380 TFLOPS and 760 TOPS. Clocks were not measured during this run. The follow-up (3.5) measured wgmma s8 at 793 TOPS
       and mma.sync f16 at 252 TFLOPS, with the clock held at 1,785 MHz.
   - vLLM FP8 also led on concurrent throughput (1.5× at 4 requests, 1.6× at 8). vLLM reached 2,733 tokens/s at 32 requests; GeulPU
     has at most 8 slots.
   - vLLM has no determinism contract (output bits can change with the batch). This comparison is about speed only.
4. **Where GeulPU stands on a server GPU.** Single-request decoding is faster than llama.cpp and close to vLLM FP8. On
   computation-bound work (long prompts, many concurrent requests) the gap to vLLM is large; it lies in the tensor-core matmul
   efficiency of prompt processing, long-context attention for Q8_0 (no F2) and the slot count (8).

### 3.5 Per-kernel time of prompt processing and the tensor-core peaks (follow-up, 2026-10-27)

- **Tensor-core peaks** — [재기/H100/mmabench.py](../재기/H100/mmabench.py) loads hand-written PTX through the driver and repeats one
  instruction on several independent accumulators per warp (per warpgroup for wgmma). Median of three runs of about 200 ms.
- **Per-kernel time** — `엔진/재기_커널.gl` (times each launch of the plan between events — median of three). Qwen3-8B Q8_0, fast and
  exact modules, prompts of 512, 2,048 and 8,192 tokens.
- Meanwhile `nvidia-smi` logged the clocks and power every 0.25 s. The SM clock stayed at the maximum (1,785 MHz) throughout.

Matmul throughput — the work is tokens × layers × (D·QKV + D·D + D·2F + F·D) multiply-adds, counted as two ops each.

| GPU · model (fast mode, prompt 2,048) | Four matmuls | Throughput | Per SM per clock | Of the int8 `mma.sync` peak |
|---|---|---|---|---|
| H100 NVL MIG 3g.47gb · Qwen3-8B Q8_0 | 259.2 ms | 109.8 TOPS | 1,025 | 21% (14% of the wgmma peak) |
| RTX 4070 Ti · Qwen2.5-7B-Instruct Q8_0 (record in [2c단계](../문서/2c단계.md)) | 178.6 ms | 149.7 TOPS | 956 (at 2.61 GHz) | 47% (2,044 per SM per clock — [재기/커널요약.py](../재기/커널요약.py)) |

- Per SM per clock, GeulPU's int8 matmuls do about the same work on both GPUs (1,025 and 956 ops). Hopper's tensor-core peak per SM per
  clock is 2.4× higher with `mma.sync` and 3.6× with `wgmma`, but the matmuls did not get faster by that much. The current tiles, tuned
  on the RTX 4070 Ti, appear to be limited on Hopper by the other instructions of the loop body (addressing, unpacking, accumulator
  setup, epilogue), not by the tensor cores.
- At an 8,192-token prompt, attention is 44% of the fast-mode time (Q8_0 has no fast attention F2 — #139).
- Exact-mode matmuls take 1.46–1.47× the fast-mode time (the prompt total 1.30–1.41×).
- So prompt processing on Hopper (#140) is looked at in this order:
  1. Cut instructions from the `mma.sync` tiles' loop body until they are bound by the tensor cores (the remaining items of 2c단계).
  2. `wgmma` tiles (sm_90a), which read operands straight from shared memory and save registers and instructions.
  3. Attention for long prompts.
- The RTX 4070 Ti row is a record from another day and another model (Qwen2.5-7B — D 3,584 · QKV 4,608 · F 18,944 · 28 layers). Its
  matrix sizes are close to Qwen3-8B's (D 4,096 · QKV 6,144 · F 12,288 · 36 layers).

### 3.6 Per-kernel time of decoding and prompts — six models (second follow-up, 2026-10-29)

- **Tool** — `엔진/재기_걸음.gl` (extended after 0.15.0) launches the plan's kernels one by one between events, with no graph, and sums
  the time per kernel function. After two warm-up runs it averages 10 runs for decoding and 2 for prompts. The gaps between launches
  are included, so the kernel sum is a little longer than the graph time.
  - Decoding uses the same plan as the server's decode step: the table step for structures that have one, and the one-row plan for
    those that don't (Qwen3.5, Gemma 4). The server launches the one-row plan kernel by kernel with no graph, so both are recorded: the
    real time including the host's launch cost, and the time of the same plan built into a graph.
  - Prompts are computed from an empty cache in the server's 512-row chunks.
  - [재기/판시간.py](../재기/판시간.py) does the analysis. Weight bytes and elements are counted from the GGUF.
- **Bounds** — for decoding (one row), the time to read the matrices and the output head at the measured copy bandwidth of
  1,808 GB/s (3.2). For the prompt matmuls, the time to do 2 × tokens × elements integer ops at the `mma.sync` s8 peak of 515 TOPS (3.5);
  exact mode has two activation digits and is counted twice.
- **Setup** — the build is 0.15.0 (5ab9c35) with this tool added. The modules are the app's defaults (fast mode, 8-bit KV and F2 for
  k-quants; fast mode for Q8_0 and Qwen3.5; Gemma 4 runs only in exact mode in this version). Maximum length 8,704; the input is fixed
  random tokens (seed 1). Llama-3.1-8B and Qwen3.5-9B were also measured on the RTX 4070 Ti with the same modules (byte-identical) and
  the same input.

- **Prompt matmuls are limited by the SMs' instruction issue.** With the same module, the H100 MIG instance is 1.5× slower than the
  RTX 4070 Ti. Llama-3.1-8B's prompt matmul kernels take 1.54–1.58× the time. Both GPUs have 60 SMs, and the instance's clock
  (1,785 MHz) is lower. This matches the guess in 3.5 (the loop body's instructions). The matmuls take 4.7–7.6× their integer bound
  (#140).
- **Q8_0 decoding is at its bound** (1.16). The k-quant one-row GEMV kernels (`정수줄하나_*`) reach 44–59% of the bandwidth, more for
  larger matrices (70B 59%, 8B 44%). On the RTX 4070 Ti the same kernels reach 80–86% of the 504 GB/s spec bandwidth. On the H100 MIG
  they take 0.43–0.73× the time, so they do not speed up with the bandwidth (3.6×).
- **Qwen3.5 decoding does not use the one-row GEMV kernels.** Without a table step its decode step runs the one-row plan, whose matmuls
  are row-tile kernels (`정수줄타일_*`, `정수아주작은타일선형`). They reach 24–36% of the bandwidth, and with the same file the H100 MIG is
  only 6% faster than the RTX 4070 Ti (row-tile kernels 0.47–1.62×). The host's cost of launching the one-row plan is small (27B: real
  37.60 ms, graph 35.91 ms, 4.5%).
- **Gemma 4**'s one-row plan uses the one-row GEMV kernel (`정수줄하나_Q4_K`) and reaches 50% of the bandwidth. Attention is 24% of its
  decode step at depth 1,024 and 33% at 8,192.
- **Small kernels** (RMS, RoPE, argmax) are bound by the clock and take 1.1–2.5× longer on the H100 MIG. Their share of the decode step is
  small.
- **Attention in an 8,192-token prompt** is 42% for Qwen3-32B Q8_0 (no F2 — #139), 40% for Gemma 4 (exact), 26–28% for Qwen3.5 and
  11–18% for Llama.
- So the next items, in this order: Qwen3.5's decode matmuls on the one-row GEMV kernels, tensor cores for the prompt matmuls (#140),
  HBM bandwidth for the k-quant one-row GEMV kernels, and F2 for Q8_0 (#139).

## 4. Limits and what came up

- One MIG instance was measured. A whole H100 or another datacenter GPU may differ.
- llama.cpp is not the release binary but the same tag built from source for sm_90 only.
- vLLM was measured on Qwen3-8B only. conda-forge's CUDA 13.0 tools (nvcc, headers, ninja) were installed for its JIT compilation
  (FlashInfer), and sampling used the PyTorch path (`VLLM_USE_FLASHINFER_SAMPLER=0`).
- Each value is a median of three. Concurrent requests vary (for example, llama.cpp with the q8_0 KV cache, Qwen3-32B, 4 concurrent
  requests: wall times of 12–19 s).
- The container restarted twice during the measurements (cause unknown). Results and logs were kept in the home directory (NFS), so
  finished configurations were skipped and the measurements continued.
- The follow-up's reproducibility checks ran through an internal script that ports the app 0.12.1's two checks, not through the app
  (2.1).
- This server lets only administrators read the performance counters (`RmProfilingAdminOnly=1`), so Nsight Compute could not be
  used. The "limited by the loop body's instructions" in 3.5 is inferred from the throughput.
- One fix to the tool came after the 3.6 run. That run's tool built the graph of a structure without a table step once, at the first
  depth, and reused it at the next depth. The depth-8,192 graph times (Qwen3.5, Gemma 4) are therefore wrong; they are only in the raw
  data and not in the tables. The tool now builds the graph again at each depth. The RTX 4070 Ti's Qwen3.5-9B decoding was measured
  again with the fixed tool (`4070Ti_Qwen3.5-9B-Q4_K_M_생성_그래프고침.txt`).
- In 3.6 the RTX 4070 Ti's bandwidth was not measured; its spec (504 GB/s) is used.

## 5. Measuring again

The scripts are in [재기/H100/](../재기/H100/). They need Linux, one NVIDIA GPU and conda (mamba). Models, results and logs go into a
work folder `W` (default `~/geulpu-h100`). After an interruption, run the same command again; finished configurations are skipped.

1. Build GeulPU's `bin/` as in section 1.
2. Download the model files into `$W/models` (table below).
3. `W=<work folder> G=<GeulPU's bin> bash 재기/H100/준비.sh` — builds llama.cpp b11900 from source, checks the models' SHA-256 and makes
   GeulPU's six modules.
4. `bash 재기/H100/측정.sh` — GeulPU fast and exact mode and llama.cpp with f16 and q8_0 KV caches, single and concurrent requests.
5. `bash 재기/H100/vllm.sh` — CUDA 13.0 tools, a vLLM virtual environment, the Qwen3-8B (BF16) download, memory bandwidth, vLLM BF16
   and FP8.
6. `python3 재기/H100/정리.py $W/results.jsonl` — the values and ratios in the tables above.

The raw data of this record is [재기/H100/결과.jsonl](../재기/H100/결과.jsonl) (143 lines);
`python -I -X utf8 재기/H100/정리.py 재기/H100/결과.jsonl` prints the values in the tables above.

The follow-up (2.1, 3.5) is measured again like this:

   files in the data folder's `모델/`.

   versioned symbols). jaegi-kernel is `geulc 엔진/재기_커널.gl -o bin/jaegi-kernel`.
