27B 의 값도 실제 파일의 메타데이터다(원격 서버에서 읽었다). 모든 크기에서 RMSNorm eps 10⁻⁶,
`rope.freq_base` 10⁶, 토크나이저는 SentencePiece(`tokenizer.ggml.model` = llama — 엔진이 이미 받는다), 출력은 임베딩과 묶여 있다(`output.weight`
없음). Q4_K_M 파일의 형식: 행렬 Q4_K · Q6_K(`attn_v` · `ffn_down` 의 일부 층 · 임베딩), 정규화 가중치 F32. 4B 이상은 그림 입력(SigLIP —
따로 있는 mmproj 파일)이 있지만 텍스트만 쓴다.

## llama.cpp 의 식 (b12224 — src/models/gemma3.cpp · src/llama-model.cpp)

입력 x = `token_embd`[토큰] × √너비(fp32 의 `sqrtf`). 층 l(입력 x):

1. h = RMSNorm(x; `attn_norm`). q = `attn_q` · h, k = `attn_k` · h, v = `attn_v` · h.
2. q · k 는 헤드마다 RMSNorm(`attn_q_norm` · `attn_k_norm` — 원소는 헤드 크기만큼, 헤드끼리 같은 가중치) → RoPE. v 는 그대로.
3. RoPE 는 NEOX(짝 (i, i + 헤드/2), 헤드 전체). 슬라이딩 윈도 층은 θ = `rope.freq_base_swa`(없으면 10⁴) · 스케일 1, 전체 어텐션 층은
   θ = `rope.freq_base` · 스케일 1 / `rope.scaling.factor`(각 = 스케일 × 위치 × θ_i — `rope.scaling.type` 이 none 이면 스케일 1).
4. q ← q × `f_attention_scale` — 1/√(헤드 크기). 층이 62 개인 27B 만 1/√(너비 / 헤드 수) = 1/√168 이다.
5. 어텐션: 인과 마스크, 슬라이딩 윈도 층은 (질의 위치 − 키 위치 ≥ `sliding_window`)도 가린다. GQA(질의 헤드 j → KV 헤드
   ⌊j / (헤드 수 / KV 헤드 수)⌋). `attn_output`.
6. x ← x + RMSNorm(어텐션; `post_attention_norm`).
7. x ← x + RMSNorm(`ffn_down` · (GELU(`ffn_gate` · h₂) ⊙ `ffn_up` · h₂); `post_ffw_norm`), h₂ = RMSNorm(x; `ffn_norm`) — GELU 는 tanh 근사.

끝: RMSNorm(x; `output_norm`), 로짓 = `token_embd` · x. `final_logit_softcapping` 이 있으면 소프트캡(파일에는 없다).

슬라이딩 윈도 층: l mod P < P − 1 — P = `attention.sliding_window_pattern`(없으면 6, 파일에는 없다). 34 층인 4B 는 층 5 · 11 · 17 · 23 ·
29 가 전체 어텐션 층이다.

## Gemma 4 와 다른 것 — 계약 4.14

| | Gemma 4(계약 4.12) | Gemma 3(계약 4.14) |
|---|---|---|
| 층의 모양 | 슬라이딩 윈도 층 헤드 256 · 전체 어텐션 층 헤드 512, KV 헤드 수도 다르다 | 모든 층이 헤드 256, KV 헤드 수도 같다 |
| 슬라이딩 윈도 층 | 층마다의 배열 | l mod 6 < 5 |
| v | 헤드마다 정규화(가중치 없이), `attn_v` 가 없는 층은 v₀ = k₀ | 정규화하지 않는다 |
| 점수 스케일 | 1 | fp32(1/√256) = 1/16 |
| 전체 어텐션 층의 RoPE | `rope_freqs.weight` 로 나눈다 | 선형 스케일링 8 로 나눈다(4B · 12B) |
| 층 배율 · 소프트캡 | 있다 | 없다 |

나머지(입력 × √너비, RMSNorm, GeGLU, 어텐션 뒤 · FFN 뒤의 정규화, 슬라이딩 윈도의 가림과 병합)는 같다. 그래서 커널은 Gemma 4 의 것을 쓰고
헤드마다의 정규화 커널만 v 를 건드리지 않는 변형이 필요하다. 점수 스케일은 어텐션 커널의 인자, 선형 스케일링은 RoPE 표의 일(계약 4.7 의
2 의 식에 f_i = 8)이다.

## 작은 크기 — 270M · 1B 의 Q8_0 (2026-11-10)

- 270M · 1B 는 너비(640 · 1,152)가 256 의 배수가 아니다. 이 크기의 Q4_K_M 파일은 k-양자화의 블록(256 원소)이 맞지 않는 행렬(`attn_q` ·
  `attn_k` · `ffn_gate` · `ffn_up` 과 `attn_v` 의 절반)이 Q5_0 · Q8_0 로 든 섞인 파일이라 아직 받지 않는다. Q8_0 파일(블록 32 원소)은 받는다 —
  커널생성의 모양 검사가 Gemma 의 Q8_0 모듈에 너비 32 의 배수를 받고([커널/커널생성.gl](../../커널/커널생성.gl)), 엔진의 설정(`젬마설정공통`)이
  k-양자화일 때만 256 의 배수를 요구한다. Gemma 4 의 모듈은 소스가 그대로다.

## 27B — 헤드 128 (2026-11-10)

27B 는 헤드 크기가 128 이다(헤드 32 · KV 헤드 16 · 너비 5,376 · FFN 폭 21,504 · 62 층 — 실제 파일 `gemma-3-27b-it-Q4_K_M.gguf` 의
메타데이터가 위 표와 같다). llama.cpp 는 층이 62 개인 gemma3 의 점수 스케일을 1/√(너비 ÷ 헤드 수) = 1/√168 로 한다 — 헤드 크기의 1/√128 이
아니다(계약 4.14 의 1 · 4, fp32(1/√168) = 0x3D9E01B3).

- **커널**: [커널/생성젬마.gl](../../커널/생성젬마.gl)의 커널은 헤드 크기 D 를 받아 만들어지므로, D = 128 에 새로 쓴 것은 헤드마다의 정규화의
  제곱합 접기뿐이다(계약 4.6 — 간격 64 · 32 는 레인 안에서, 그 뒤는 레인 사이에서). `커널생성 gemma3큰 … --헤드 128` 이 헤드 256 의 커널
  여덟 대신 헤드 128 의 것 여덟(`머리정규화젬마128` …)을 넣는다. 기존 모듈 셋(Gemma 4 12B · Gemma 3 4B · 270M)의 소스는 바이트까지
  그대로다.
- [시험/젬마판.py](../../시험/젬마판.py) `--gemma3 --shape 5376,21504,32,16 --헤드 128`(27B 의 모듈
  `gemma3K_5376x32x16x21504x262208_h128`): 60 가지 모두 CPU 참조와 **불일치 0** — 헤드 32 · KV 헤드 16, 점수 스케일 fp32(1/√168).
- **엔진**: [구조/gemma3/엔진.gl](엔진.gl)의 설정이 헤드 128 · 256(모든 층이 같아야 한다)을 받고, 점수 스케일을 fp32(1/√헤드 크기) —
  층이 62 개면 fp32(1/√(너비 ÷ 헤드 수)) — 로 정한다. 헤드 128 이면 모듈 이름 끝에 `_h128`, 생성기에 `--헤드 128`. 구조/gemma4/엔진.gl 에는
  헤드 128 의 커널 여섯을 얻어 두는 전역과 헤드 크기로 고르는 줄만 더했다 — Gemma 4 와 헤드 256 의 Gemma 3 의 실행은 그대로다(구조 회귀의
  Gemma 경우 다섯이 기준과 같은 요약).
- **헤드 128 시험 파일**: 27B(16.5 GB)는 이 PC 에 들지 않아, 4B 의 층 0 … 5 를 헤드 128 로 읽는 파일을 만들었다
  ([시험/작은젬마.py](../../시험/작은젬마.py) `--헤드 128` — 헤드 수 · KV 헤드 수를 두 배로(16 · 8), `attn_q_norm` · `attn_k_norm` 은 앞 128
  값만. 행렬의 모양은 그대로 맞는다). `시험_7B` 의 실행 경로 다섯이 같은 비트이고, 엔진의 모든 행 로짓 68,436,288 개가 CPU 참조와
  **불일치 0** 이다. [시험/구조회귀.py](../../시험/구조회귀.py)의 경우 `gemma3-작은-h128`. 이 파일은 층이 6 개라 점수 스케일이
  fp32(1/√128)이다 — 62 층의 규칙(1/√168)은 커널 시험과 원격 서버의 실제 파일이 본다.
- **원격 서버**(H100 NVL MIG 3g.47gb · Linux — 실제 파일 `gemma-3-27b-it-Q4_K_M.gguf`): 같은 소스로 만든 모듈의 소스 · PTX 가 이 PC 와
  바이트까지 같다. `시험_7B` 의 경우 넷(프롬프트 24 · 31 · 19 · 1,100 토큰 — 4B · 12B 의 모델 검증과 같은 입력)에서 실행 경로 다섯이 같은
  비트다(오류 플래그 0). 27B 의 채팅 템플릿과 토크나이저 메타데이터(토큰 · 점수 · 종류 · 특수 토큰)는 12B 의 것과 해시까지 같다 — 12B 로
  확인한 채팅 템플릿 = jinja2 · 토크나이저 = llama-tokenize 가 27B 에도 그대로 해당한다.
- **llama.cpp 와의 비교**(원격 서버 — llama.cpp b11871): 수학 참조(fp64)와 llama.cpp 의 다음 토큰 분포는 글 둘 × 256 토큰에서 KL 평균

  llama.cpp 의 그리디 답 100 토큰): 수학 참조의 1위 = llama.cpp 의 그리디 100 %(300 / 300) · KL 평균 8.87 × 10⁻⁴ — **맞음**. 엔진에 같은
  채팅 프롬프트 셋을 넣어 그리디 디코딩으로 낸 답 32 토큰씩이 llama.cpp 의 답과 토큰까지 같다(96 / 96 — "대한민국의 수도는 서울입니다." …).

  낸 '불일치 0'(GLM · Kanana-2 · Gemma 3 4B · 12B)은 엔진의 출력과 수천만 개 값이 비트까지 같은 것이라 이 문제와 상관없이 유효하다.
- **전체 파일의 CPU 참조**(62 층 — 층마다 약 7 분, 원격 서버): 엔진의 로짓 62,405,504 개가 CPU 참조와 **불일치 0** — 프롬프트 24 · 31 · 19
  토큰의 경우는 모든 행(10,488,320 · 12,323,776 · 9,177,280 개), 1,100 토큰의 경우는 행 1,000 부터(30,416,128 개).
- [시험/모듈해시.txt](../../시험/모듈해시.txt) 한 줄(27B 의 모듈), [시험/SASS넘침.txt](../../시험/SASS넘침.txt) 27 줄(공통 커널의 것은 다른

- **정밀 모드의 손실**(원격 서버 — 위 채팅 확인의 답 구간 99 행, 엔진의 로짓은 `시험_7B` 가 남긴 것): 수학 참조(fp64)에서 본 KL 이 엔진은

- **서버의 채팅 확인**(원격 서버 — main 31c6c30 의 리눅스 빌드 `server-cuda`, 2026-11-11): 채팅 질문 셋을 `/v1/chat/completions` 에 온도 0 으로
  보냈다. 서버가 GGUF 의 채팅 템플릿으로 만든 프롬프트 토큰이 llama.cpp 의 것과 같고(28 · 39 · 23 토큰), 답 토큰이 llama.cpp 의 그리디와

## 긴 프롬프트의 어텐션 — 헤드 128 · 256 (2026-11-12)

Gemma 4 와 같은 고침이다 — 새 커널 `타일어텐션젬마D둘`(모듈의 헤드 크기 128 · 256 가운데 하나)을 gemma3 모듈의 맨 끝에 더하고,
`모듈준비젬마3` 이 `둘째판젬마` 를 부른다. 기록은 [구조/gemma4/기록.md](../gemma4/기록.md) 의 '긴 프롬프트의 어텐션'. 27B(H100 — 30,720 토큰
프롬프트): 어텐션 커널 19.18 → 8.11 s, 프롬프트 50.2 → 39.1 s(1.28 배), 출력은 비트까지 그대로다.
