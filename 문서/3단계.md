## 독립 검토 (2026-10-19 06:5x — 판정: 고쳐서 진행)

새 에이전트가 계획 · 엔진 · 서버 · 표 판 코드를 읽고, 실제 출력으로 받아들임을 흉내 셈했다(파일은 고치지 않음 · GPU 안 씀). 요점과 결정:

1. **같은 토큰 보장은 성립한다** — 표 그래프의 판이 모두 행 단위(RoPEKV 표의 위치 · 조각어텐션표의 블록 · 조각접기표 · RMS · 가장큰번호),
   그래프 마디가 사슬이라 층마다 RoPEKV 가 모든 행을 쓴 뒤 어텐션이 돈다, 가림은 −3.0e38 → 정확히 0, B 에 따른 판 선택은 계약 1 · 1.1 ·
   1.2 절이 값을 정한다(32단계 판 시험 · R1 82,673 걸음). 뽑기 · 로그확률 · 해시는 토큰받음 안에서 받은 행마다 — 차례로 넣으면 걸음 번호가
   맞는다. **다만 (a) 넘침**: 조각칸은 큰값(4, 슬롯수) 행, 호스트의 로짓버퍼는 슬롯수 행뿐이라 B = 5 ~ 8 이면 넘친다(CUDA 는 조용히, Vulkan 은
   DEVICE_LOST — 34단계와 같은 종류). **(b)** F1 의 줄타일K 행 1 ~ 8 판 시험과 F1 서버28 결과가 기록에 없다. → 둘 다 고친 뒤에 "보장"이라 쓴다.
2. **되돌리기 없음은 맞다** — 다음 걸음의 행은 받은 길이까지 + 같은 걸음의 앞 행이 먼저 쓴 자리만 읽는다. 낡은 바이트도 지수 바이트가
   유한해 가린 키의 e′ = 0. 조건: 받은 입력만 차례로 캐시에 더하고, 일감이 끝나면 곧 멈춘다.
3. **바꿀 곳**: 표걸음 검사(B ≤ 표최대 · 로짓행, 같은 슬롯은 서로 다른 이어진 위치), 위치가 최대길이 이상이면 서버가 끝나므로 초안을
   p + k ≤ 최대길이 − 1 로 자르기(필수), 조각칸 · 로짓버퍼를 표최대 행으로, 토큰받음을 "정하기"와 "받기"로 나누기(뽑기를 두 번 하지 않게),
   끝내기 · 일감버리기 뒤 해제된 일감을 쓰지 않게(슬롯일 확인), 38f(미룬 로그확률)를 여러 행으로, 요청 · 서버 깃발 · 응답의 기록.
4. **비용 전제가 낡았다** — 1.32 · 1.57 배는 28단계 Q4_0 의 다른 슬롯 넷 · 여덟 걸음이다. 같은 슬롯은 KV 를 한 벌만 읽어 c(B ≥ 2) ≈ 1.03 ~
   1.10 으로 어림(추측 — **먼저 잰다**). 행 2 ~ 8 은 같은 판이라 비용이 평평해 **k 를 줄이는 조절은 효과가 없다** — 조절은 켬/끔과 슬롯 사이의
   행 나눔. 흉내(c = 1.10, 계획 규칙): 코드 · 문서 다시 쓰기 3.71 배, 요약 1.85, R1 수학 1.71, 번역 1.18, 채팅 탐욕 1.20, 채팅 뽑기 1.00
   (한 토큰 찾기를 빼면 1.01). → "반복 많은 일 1.3 배"는 현실적(번역은 그 묶음에서 뺀다), 뽑기 채팅은 한 토큰 찾기를 빼거나 문을 둔다.
5. **비교** — llama.cpp 최신(b11721)의 llama-server 에 `--spec-type`(ngram-simple · ngram-map-k · ngram-mod · ngram-cache, 초안 모델 등)과
   `--spec-default`(ngram-mod)가 있다. vLLM 도 ngram 이 있고, 문서가 추측 켬 · 끔의 출력이 다를 수 있다고 적는다(배치 불변 모드는 베타).
   → "다른 엔진은 보장하지 못한다"를 "기본 설정에서는"으로 좁힌다. 견줌: 추측 없음 · ngram-simple(같은 초안 규칙) · --spec-default.
6. **차례**: c(B) 재기 → 엔진 고침 + 비트 시험 → 서버 통합 + 시험 → 정책 · 기록 → llama.cpp 견주기 → 앱.

- 행 하나를 더할 때마다 정해진 몫(약 0.11 ~ 0.16 ms — 타일 판의 행 몫 · 행마다의 판)과 문맥에 비례하는 어텐션 몫이 든다: 8,184 에서

  슬롯의 행끼리 나눠 읽지 않음) — 검토의 어림 1.03 ~ 1.10 은 문맥 2k 까지만 맞다.
- 그래서 "k 를 줄이는 조절은 효과가 없다"는 긴 문맥에서 맞지 않다 — c 가 평평하지 않으므로 k 는 받아들임과 문맥으로 고른다(아래).
- 뒤의 후보(3b): 같은 슬롯의 행 여럿이 KV 묶음을 한 번만 읽는 어텐션 판(행마다의 셈 차례는 그대로 — 같은 비트). 어림: 8,184 Llama
  B = 8 22.3 → 15 ms 안팎.

**정책(이 값으로 정함)**: 슬롯마다 초안 k 를 G(k) = (1 − aᵏ⁺¹)/(1 − a) / c(k + 1) 이 가장 큰 값으로(G ≤ 1 이면 초안 없음 — 행 하나).
a 는 그 슬롯의 받아들임(초안 토큰 하나가 앞이 맞았을 때 맞을 비율 — 지수 이동 평균, 앞 믿음 0.5 를 의사 수로 섞어 초안을 쉬는 동안
천천히 0.5 로 돌아가 다시 시도한다). c(B) = 1 + (B − 1) · r(n), r(n) = (β + 0.5 κn)/(1 + κn) — κ = 토큰 하나의 KV 바이트 / 가중치
바이트, β = 0.012 × 4.68 GB / 가중치 바이트(위 표에 맞춘 꼴 — 세 모델 · 세 문맥에서 잰 r 과 ±0.006 안, 대개 조금 비관적). 슬롯 여럿이면
행 8 을 나눈다(슬롯마다 행 하나는 늘 — 초안은 남은 행에서).

정책의 세부(엔진/서버몸.gl — 검토 뒤 고친 것):
- **초안 고르기**: 끝 토큰이 나온 자리마다 거꾸로 이어 맞은 길이 m(32 까지)을 재어 가장 길게 맞는 자리(같으면 가까운 것)의 뒤 토큰들.
  처음 판(가장 가까운 3-gram → 2 → 1)보다 코드 고치기가 +9 ~ +11 %(329 → 359 · 356 → 395 토큰/초), 고쳐 쓰기 −4 %, 나머지 같음.
- **받아들임 어림은 일감마다 · m 의 종류마다**(1 · 2 · 3 ~ 7 · 8 이상): a = (맞음 + 앞 믿음) / (해본 + 1), 앞 믿음 0.25 · 0.4 · 0.5 · 0.7.
  걸음마다 맞음 · 해본 = 0.9 × 앞 + 이번(받은 초안 수 · 받은 수 + 거절 1), 초안을 쉬는 걸음은 0.97 배(앞 믿음으로 천천히 돌아가 다시 시도).
- **슬롯 여럿**: 첫째로 슬롯마다(걸음마다 도는 차례로) 바라는 초안을 짓고, 합이 남은 행보다 많으면 도는 차례로 한 행씩 나눈다(슬롯 하나가
  독차지하지 않게). c(B) 는 슬롯 하나의 값으로 어림한다(다른 슬롯의 행이 이미 든 걸음은 B 가 4 → 5 를 넘을 때 판이 바뀌는 모듈이 있어 값이
  조금 다르다).
- 서버가 올릴 때 표 걸음의 그래프를 행 수 1 ~ 8 마다 미리 짓는다(처음 쓰는 행 수의 멈칫 · Vulkan 의 파이프라인을 올림 때로).

빠른 모듈로 돌렸다(빌드/글/*_빠른.ptx — 2c 의 모듈 해시 그대로). 시험_추측의 Vulkan 판은 없고, Vulkan 은 서버 시험(추측3 — NVIDIA)으로

**미룸 — k-양자화 프롬프트의 꼬리 자르기**(2c 에서 이 단계로 미뤘던 것): 이득 어림이 프롬프트의 1 ~ 2 %(o · down 의 마지막 바퀴)인데,
K 타일 판의 열시작(지금 늘 0)을 판 시험에 새로 넣고 Vulkan · 판 기억의 고르는 법 판까지 바꿔야 해서 다음 프롬프트 단계의 후보로 둔다.

## 왜

- 채팅에서 시간의 대부분은 생성이다(프롬프트 1,000 + 답 400 토큰이면 프롬프트는 약 3 % — 2b · 2c 독립 검토). 생성은 이미 메모리 바닥
  가까이다(Qwen2.5-7B Q4_K_M: 걸음당 약 4.4 GB 를 10.03 ms 에 — 504 GB/s 의 약 87 %). 바닥 자체를 바꾸는 길은 한 걸음에 토큰 여럿을
  내는 것(추측 디코딩)뿐이다.
- 이 엔진은 길 · 덩이와 상관없이 같은 비트를 낸다(계약). 그래서 검증 걸음(행 여럿)의 로짓이 하나씩 셈한 로짓과 **비트까지 같고**, 탐욕은
  물론 뽑기(걸음 번호로 정한 난수 — 계약 5)도 같은 토큰을 낸다 — **추측을 켜도 답 · 로그확률 · 연구 패널의 값이 하나도 바뀌지 않는다.**
  다른 엔진(llama.cpp · vLLM)은 일괄 크기에 따라 로짓 비트가 바뀌어 이것을 보장하지 못한다.

## 무엇을 — 프롬프트 찾기 추측(n-gram, 초안 모델 없음)

1. **초안**: 슬롯의 토큰열(프롬프트 + 지금까지의 답)에서 끝의 n-gram(n = 3 → 2 → 1 의 차례로 가장 긴 것)이 앞에 나온 마지막 자리를
   찾고, 그 뒤 토큰 k 개(최대 k = 7)를 초안으로. 찾지 못하면 그 슬롯은 행 하나(지금과 같다).
2. **검증**: 생성 걸음(서버몸.gl 의 생성걸음)이 슬롯마다 [다음 토큰, 초안 1 … k] 를 위치 p … p + k 의 행으로 표걸음에 넣는다
   (엔진표.gl — 같은 슬롯의 이어진 위치는 30단계부터 된다: 층마다 RoPEKV 가 모든 행의 키 · 값을 먼저 쓰고 어텐션이 제 위치까지만 읽는다).
   행 i 의 로짓으로 걸음 s + i 의 토큰을 정한다(탐욕: 가장큰번호, 뽑기: 뽑기(로짓, …, 걸음 s + i)) — 초안 i + 1 과 같으면 받고 다음 행으로,
   다르면 그 토큰을 받고 멈춘다(끝 행까지 맞으면 덤 토큰 하나 더). 받은 토큰마다 지금의 토큰받음(흘려보내기 · 멈춤 조건 · 최대 길이 ·
   로그확률)을 차례로 — 멈추면 나머지는 버린다.
3. **되돌리기 없음**: 받지 않은 위치의 KV 는 다음 걸음이 같은 위치를 먼저 덮어쓰고(RoPEKV 가 어텐션 앞), 어텐션은 제 위치까지만 읽는다 —
   슬롯캐시(토큰 목록)에는 받은 토큰만 더한다.
4. **엔진**: 표걸음의 행 수 한도를 슬롯 수가 아니라 표최대(8)로(같은 슬롯의 행 여럿). 행 수마다의 그래프는 이미 있다(표계획들[B]).
5. **켜고 끄기**: 서버 깃발 · 요청의 `geulpu.speculative`(기본 켬 — 값이 바뀌지 않으므로), 앱의 설정. 초안 k 는 슬롯의 받아들임 비율로
   조절(낮으면 줄이고, 0 이면 끔 — 행 하나의 값과 같아지게).

## 견줄 것 (미리 정함 — 측정 전)

- **A 같음(가장 중요)**: 추측을 켜고 끈 두 실행의 출력 토큰 · 걸음마다 로짓 해시 · 로그확률이 비트까지 같다 — 탐욕과 뽑기(온도 0.7 ·
  top-p 등), 슬롯 하나와 여럿(함께 도는 요청), 멈춤 글 · 최대 길이 · EOS, 연구 패널의 echo 점수. 서버 회귀 시험(시험/서버28.py ·
  로그확률서버38.py)과 교차검증(R1 32 문제 — 앱의 재현성 검증)이 그대로 통과.
- **C 속도**(번갈아 세 바퀴): 생성 토큰/초가 추측 없는 것보다 — 반복이 많은 일(코드 · 문서 다시 쓰기 · 요약 — 프롬프트에 답의 조각이

  llama.cpp 의 llama-server(같은 GGUF — 추측 없음 · `--spec-type ngram-simple` · `--spec-default`)와 견주고, llama.cpp 자신의 추측 켬 · 끔에서
  출력이 달라진 요청 수를 기록한다.
- **D 앱**: 설정 · 상태에 추측이 보이고, 연구 패널의 값이 켜고 끔에 따라 바뀌지 않는다.

1. **c(B) 재기**: F1, 같은 슬롯의 이어진 위치 B = 1 … 8, 문맥 512 · 2048 · 8192 — 걸음 시간(진단몸.gl 의 표 그래프 재기를 같은 슬롯으로 바꿔
   쓰거나 재기 프로그램 하나). 이 값으로 켬/끔의 문턱을 정한다.
2. **엔진 고침**: 조각칸 · 로짓버퍼를 표최대 행, 표걸음 검사(B ≤ 표최대 · 로짓행 · 같은 슬롯의 위치가 서로 다르고 이어짐), 그래프 B = 1 … 8 을
   미리 짓기(권고). **비트 시험**: 판26 `--줄타일만 --빠른`(F1 줄타일K 행 1 ~ 8), 같은 슬롯 B 행 걸음의 로짓 == 한 행씩(새 시험).

   문맥 끝 · 버스트 안의 멈춤 글 · 최대 생성 · EOS · 거절 뒤 캐시 재사용), F1 서버28 · 로그확률서버38(슬롯 1 · 2 · 4 · 8), 교차검증(슬롯 1 또는 2

## 위험

- 뽑기 모드(온도 > 0)는 행마다 로짓(어휘 15 만 × 4 바이트)을 내려받아 CPU 에서 뽑는다 — 행이 여럿이면 그 시간이 이득을 먹을 수 있다
  (재서 보고, 필요하면 GPU 에서 뽑기 — 계약 5 의 식 그대로).
- 행 B 의 걸음 값: B = 1 은 줄 판(정수줄하나), B ≥ 2 는 타일 판(k-양자화)이다 — 행 넷 · 여덟 걸음의 시간이 행 하나의 1.32 · 1.57 배(28 ·
  2b 의 기록)라 받아들임이 낮으면 손해 — 초안 k 를 받아들임에 맞춰 줄인다.
- 슬롯 여럿이 함께 돌 때 행 수 한도(8)를 나눠 써야 한다.
- 초안 모델(예: Qwen2.5-0.5B → 7B)은 받아들임이 더 높지만 서버가 모델 둘을 올려야 한다 — 3b 로 뒤에.
