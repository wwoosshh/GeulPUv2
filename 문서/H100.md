# 리눅스 · 데이터센터 GPU — H100 NVL 의 MIG 인스턴스 (2026-10-26 ~ 29)

*영어판: [docs/h100.md](../docs/h100.md).*

협업 연구자의 대학 서버에서 GeulPU 0.12.1 을 소스로 빌드해 돌렸다. 네이티브 리눅스와 데이터센터 GPU 에서 돈 것은 처음이다. 세 가지를
적는다.

1. **빌드** — 글(geul) 컴파일러와 파이썬 3 만으로 빌드됐다. CUDA 툴킷 · C 컴파일러 · cmake 를 쓰지 않는다.
2. **재현성** — 커널 모듈이 Windows 에서 만든 것과 바이트까지 같았고, 대화 24 개의 생성 토큰이 Windows 의 RTX 4070 Ti 에서 낸 것과
   모두 같았다. 다음 날의 후속 측정에서는 앱의 두 재현성 검사(파일 쌍 · 재현성 검증)도 스텝마다의 로짓 해시까지 같았다(2.1).
3. **속도** — 같은 HTTP 요청으로 llama.cpp b11900 · vLLM 0.32.0 과 비교했다. 후속 측정에서는 텐서 코어의 최고치와 프롬프트 처리의 커널마다
   시간을 재, 행렬곱이 어디에 묶이는지 보았다(3.5). 10-29 의 후속 측정 2 에서는 모델 여섯의 생성 · 프롬프트를 커널마다 재 바닥과
   견주었다(3.6).

GPU 는 H100 NVL 한 장을 나눈 MIG 인스턴스 3g.47gb(SM 132 개 가운데 60 개)다. 아래 숫자는 이 인스턴스의 것이고 H100 한 장 전체의 것이
아니다.

## 1. 빌드

[시험/글저장소커밋.txt](../시험/글저장소커밋.txt) 가 고정한 글(geul) 2g-1.4.0 의 참조 컴파일러(파이썬)로 자체 컴파일러를 한 번 빌드하고,
그 컴파일러로 GeulPU 의 세 프로그램을 빌드했다.

```
git clone https://github.com/wwoosshh/geul-lang geul-lang-v2
cd geul-lang-v2 && git checkout 2g-1.4.0 && mkdir -p build
GEUL_ROOT=. PYTHONUTF8=1 python3 ref/geulc.py self/컴파일러.gl -o build/geulc
cd .. && git clone https://github.com/wwoosshh/GeulPUv2
cd GeulPUv2 && git checkout v0.12.1 && mkdir -p bin
export GEUL_ROOT=../geul-lang-v2
../geul-lang-v2/build/geulc 백엔드/PTX/PTX.gl -o bin/ptx-backend
../geul-lang-v2/build/geulc 커널/커널생성.gl -o bin/kernel-gen
../geul-lang-v2/build/geulc 엔진/서버.gl -o bin/server-cuda
```

- 세 프로그램은 ELF 이고 `libc.so.6` · `libcuda.so.1` 만 가져온다. glibc 2.35 에서 그대로 돌았다. 같은 서버에서 llama.cpp b11900 의 릴리스
  CUDA 바이너리는 GLIBC 2.38 을 요구해 돌지 않았다(비교에는 같은 태그의 소스를 이 서버에서 빌드해 썼다 — 3).
- 후속 측정(2026-10-27): 이 서버에서 빌드한 다섯 실행 파일(geulc · ptx-backend · kernel-gen · server-cuda, 그리고 `엔진/재기_커널.gl` 의
  jaegi-kernel)이 WSL2 의 Ubuntu 24.04(glibc 2.39)에서 같은 태그로 빌드한 것과 바이트까지 같았다. 판(GLIBC_x.y)이 붙은 기호를 하나도
  가져오지 않으므로, 한 곳에서 빌드한 실행 파일을 배포판마다 다시 빌드하지 않고 쓸 수 있다. pthread 함수를 `libc.so.6` 에서 가져오므로
  glibc 2.34 이상이 필요하다(시험한 것은 2.35 · 2.39).
- 모델의 모양에 맞는 커널 모듈은 `kernel-gen` → `ptx-backend` 로 만든다(명령은 [재기/H100/준비.sh](../재기/H100/준비.sh)). 모듈의 PTX 는
  sm_80 대상이고, 서버가 처음 불러올 때 드라이버가 sm_90 용으로 JIT 컴파일한다.
- 겪은 일
  - 홈이 NFS(root squash)라 git 이 저장소를 "dubious ownership" 으로 거부했다. git 2.34 는 `-c safe.directory` 를 읽지 않아, 따로 둔 설정
    파일에 더했다: `export GIT_CONFIG_GLOBAL=/tmp/gitconfig` 다음 `git config --global --add safe.directory <저장소 경로>`. 공유 계정의
    `~/.gitconfig` 는 건드리지 않는다.
  - tar 가 NFS 에서 "Cannot change ownership" 을 알리지만 파일은 풀린다.

## 2. 재현성 — Windows 의 RTX 4070 Ti 와 같은 출력

| 확인 | 결과 |
|---|---|
| 커널 모듈 셋(정밀 모드) — `qwen3Q8_4096x32x8x12288x151936` · `qwen2Q8_5120x40x8x27648x152064` · `qwen3Q8_5120x64x8x25600x151936` | 이 서버의 `kernel-gen` · `ptx-backend` 가 만든 PTX 가 Windows 에서 만든 것과 바이트까지 같다 |
| Qwen3-8B Q8_0(SHA-256 `408b9555…`), 정밀 모드, 그리디 — 도구 호출이 실패한 뒤의 대화 24 개를 끝까지 | 프롬프트 토큰(llama.cpp 의 채팅 템플릿 · 토크나이저로 만든 것) 24/24 같음. 생성 토큰 24/24 대화 · 모든 차례에서 같음 — 대화마다 1 ~ 2 차례, 생성 토큰 모두 1,364 개 |
| Qwen2.5-32B-Instruct · Qwen3-32B Q8_0, 정밀 모드 — 같은 연구의 대화 720 개씩 | 대화의 10 %(72 개)를 두 번 돌려 72/72 · 72/72 같음. 이 PC(12 GB)에 들지 않아 서버 안에서만 비교했다 |

- 이 표에서 비교한 것은 생성 토큰이다. 앱의 두 재현성 검사(스텝마다의 로짓 해시)는 앱이 Windows 전용이라 첫 측정에서 돌리지 못했고,
  다음 날 같은 요청 · 판정의 내부 스크립트로 돌렸다(2.1). 그 밖의 GPU(RTX 3080 Ti · 4070 Ti · 5070 · Radeon RX 9060 XT)는
  [교차검증](../교차검증/)에서 확인했다.
- 정밀 모드의 출력은 OS(Windows · 리눅스), GPU 세대(Ada sm_89 · Hopper sm_90), MIG 와 상관없이 같았다. 그래서 이 PC 에 들지 않는 큰 모델을
  다른 기관의 GPU 에서 돌려도, 이 PC 에서 돌린 작은 모델과의 차이는 실행 환경이 아니라 모델에서 온다고 말할 수 있다.

## 3. 속도 — llama.cpp · vLLM 과 같은 요청으로

### 방법

- **엔진**
  - **GeulPU 0.12.1**(1 의 빌드). 빠른 모드는 앱의 기본과 같다 — Q8_0 은 `--빠른`, Q4_K_M 은 `--빠른 --F2`(8비트 KV 캐시 · 빠른 어텐션
    F2). 정밀 모드는 앱의 정밀 모듈(`--먼`). 추측 디코딩은 껐다(`--추측끔`).
  - **llama.cpp b11900**(측정한 날의 최신 릴리스, 커밋 `74b104c9`). 릴리스의 CUDA 바이너리가 이 서버에서 돌지 않아, 같은 태그의 소스를
    conda-forge 의 CUDA 12.8(nvcc 12.8.93)로 sm_90 용으로 빌드했다. flash attention 을 켜고, KV 캐시 f16 · q8_0 을 둘 다 측정해 빠른 쪽과
    비교한다(README 와 같은 규칙).
  - **vLLM 0.32.0**(PyTorch 2.13, CUDA 13.0). GGUF 를 열지 못해(설정 파일을 JSON 으로 읽으려 했다) Qwen3-8B 만 BF16 과 FP8(BF16 을 불러올
    때 바꿈 — `--quantization fp8`)로 측정했다. 공식 Qwen3-32B-FP8 은 블록 FP8 커널의 JIT 컴파일이 CUDA 13.0 헤더와 맞지 않아 실패해
    뺐다. 접두 캐시는 끄고(`--no-enable-prefix-caching`), 최대 문맥은 31,232 다.
- **모델**: Qwen3-8B Q8_0(8.71 GB) · Qwen2.5-7B-Instruct Q4_K_M(4.68 GB — README 의 RTX 4070 Ti 표와 같은 파일) · Qwen3-32B Q8_0
  (34.82 GB). 주소 · SHA-256 은 5.
- **요청**: 세 엔진에 같은 클라이언트([재기/H100/요청.py](../재기/H100/요청.py))로 OpenAI 호환 `/v1/completions` 를 보낸다 — 토큰 번호로
  준 프롬프트(요청마다 무작위로 새로 만들어 어느 엔진의 접두 캐시도 맞지 않는다), 그리디, `ignore_eos`. 값마다 세 번 측정한 중앙값이고, 한 번에 한
  엔진만 GPU 를 쓴다.
  - 프롬프트 처리: L 토큰의 프롬프트로 1 토큰을 생성하는 시간.
  - 생성: 깊이 D 에서 (257 토큰을 생성하는 시간 − 1 토큰을 생성하는 시간) ÷ 256.
  - 동시 요청: c 개(각 프롬프트 512 · 생성 256 토큰)를 함께 보내, 전체 생성 토큰 ÷ 벽시계 시간.
  - 서버: 한 요청의 측정은 슬롯 1 · 문맥 32,768. 동시 요청은 슬롯 8(GeulPU 문맥 1,024, llama.cpp 8,192). vLLM 은 한 서버로 둘 다(동시
    32 까지).

### 3.4 해석

1. **llama.cpp 보다 생성과 동시 요청이 빠르다.**
   - 세 모델 · 세 깊이에서 생성 시간이 5 ~ 22 % 짧았다(정밀 모드는 2 ~ 20 %). 동시 4 · 8 요청의 처리량은 1.7 ~ 2.0 배였다.
   - RTX 4070 Ti 에서 Qwen2.5-7B Q4_K_M 생성의 비는 깊이 8k · 32k 에서 0.97 · 0.89× 였다(README — 측정 방법이 다르다). 이 인스턴스에서는
     깊이 8,192 · 30,720 에서 0.83 · 0.79× 였다.
2. **긴 프롬프트가 약하다.**
   - 30,720 토큰의 프롬프트 처리는 Q8_0 에서 llama.cpp 의 1.7 배 시간이 걸렸다. 빠른 어텐션 F2 는 k-양자화 모듈에만 있어 Q8_0 에는
     없다. F2 가 켜지는 Q4_K_M 에서는 1.06× 였다.
   - RTX 4070 Ti 에서 알려진 자리(긴 문맥의 어텐션)와 같다.
3. **vLLM 과의 비교(Qwen3-8B).**
   - 한 요청의 생성은 얕은 깊이에서 8비트끼리 비슷했다(깊이 64: GeulPU 151 · vLLM FP8 155 토큰/초). 깊어지면 vLLM FP8 이 23 ~ 25 %
     빨랐다(깊이 8,192 에서 140 · 114, 30,720 에서 113 · 91).
   - 프롬프트 처리는 vLLM FP8 이 GeulPU 빠른 모드의 3.0 ~ 8.6 배였다. 프롬프트 처리는 메모리가 아니라 계산이 한계다.
     - 토큰마다의 계산을 가중치 행렬곱 13.9 GFLOP(임베딩 · 출력층 빼고)에 인과 어텐션을 더해 어림하면, vLLM BF16 은 이 인스턴스의 BF16
       최고 성능의 53 ~ 75 %, GeulPU 빠른 모드(int8 행렬곱)는 int8 최고 성능의 6 ~ 11 % 를 썼다.
     - 최고 성능은 데이터시트의 H100 NVL 값(희소성 기준 BF16 1,671 TFLOPS · INT8 3,341 TOPS)의 절반(밀집)에 SM 비율 60/132 를 곱한
       380 TFLOPS · 760 TOPS 다. 이 측정 때의 클럭은 재지 않았다. 후속 측정(3.5)에서 잰 최고치는 wgmma s8 793 TOPS · mma.sync f16
       252 TFLOPS 였고, 그동안 클럭은 1,785 MHz 를 유지했다.
   - 동시 요청의 처리량도 vLLM FP8 이 앞섰다(4 요청 1.5 배, 8 요청 1.6 배). vLLM 은 32 요청에서 2,733 토큰/초까지 갔고, GeulPU 는 슬롯이
     8 까지다.
   - vLLM 에는 결정성 계약이 없다(배치에 따라 출력 비트가 바뀔 수 있다). 이 비교는 속도만 본 것이다.
4. **서버 GPU 에서의 위치.** 한 요청의 생성은 llama.cpp 보다 빠르고 vLLM FP8 과 가깝다. 계산이 한계인 일(긴 프롬프트 · 많은 동시 요청)에서는
   vLLM 과 차이가 크다. 그 차이는 프롬프트 처리의 텐서 코어 행렬곱 효율, Q8_0 의 긴 문맥 어텐션(F2 없음), 슬롯 수(8)에 있다.

  프롬프트 512 · 2,048 · 8,192 토큰.

  텐서 코어가 아니라 반복 몸통의 다른 명령(주소 · 풀기 · 누산기 준비 · 에필로그)에 묶이는 것으로 보인다.

  1. `mma.sync` 판의 반복 몸통에서 명령을 줄여 텐서 코어에 묶이게 한다(2c단계에 남긴 처방).
  2. `wgmma` 판(sm_90a) — 공유 메모리의 피연산자를 바로 읽어 레지스터와 명령을 던다.
  3. 긴 프롬프트의 어텐션.
- RTX 4070 Ti 의 줄은 다른 날 · 다른 모델(Qwen2.5-7B — D 3,584 · QKV 4,608 · F 18,944 · 층 28)의 기록이다. 행렬의 크기는 Qwen3-8B
  (D 4,096 · QKV 6,144 · F 12,288 · 층 36)와 비슷하다.

### 3.6 생성 · 프롬프트의 커널마다 시간 — 모델 여섯 (후속 측정 2, 2026-10-29)

- **도구** — `엔진/재기_걸음.gl`(0.15.0 뒤에 넓힘): 계획의 띄움을 그래프 없이 하나씩 이벤트 사이에 두고 판(커널 함수)마다 시간을 더한다.
  두 번 데운 뒤 생성은 10 번, 프롬프트는 2 번의 평균이다. 띄움 사이의 틈이 들어가 판의 합은 그래프로 띄운 시간보다 조금 길다.
  - 생성은 서버의 생성 걸음과 같은 계획이다. 표 판이 있는 구조는 표 걸음, 없는 구조(Qwen3.5 · Gemma 4)는 행 하나의 계획이다. 행 하나의
    계획은 서버처럼 그래프 없이 띄움마다 띄우므로, 호스트가 띄우는 비용까지 든 실제 시간과 같은 계획을 그래프로 지어 띄운 시간을 함께 적는다.
  - 프롬프트는 빈 캐시에서 서버와 같은 512 행 덩이로 계산한다.
  - 정리는 [재기/판시간.py](../재기/판시간.py)다. 가중치의 바이트 · 원소는 GGUF 에서 센다.

  GEMV 판의 HBM 대역, Q8_0 의 F2(#139).

## 4. 한계 · 겪은 일

- MIG 인스턴스 하나에서 측정했다. H100 한 장 전체 · 다른 데이터센터 GPU 에서는 다를 수 있다.
- llama.cpp 는 릴리스 바이너리가 아니라 같은 태그의 소스를 sm_90 전용으로 빌드한 것이다.
- vLLM 은 Qwen3-8B 만 측정했다. JIT 컴파일(FlashInfer)에 쓰려고 conda-forge 의 CUDA 13.0 도구(nvcc · 헤더 · ninja)를 넣었고, 샘플링은
  PyTorch 경로다(`VLLM_USE_FLASHINFER_SAMPLER=0`).
- 값마다 세 번의 중앙값이다. 동시 요청은 흔들림이 있다(예: llama.cpp KV q8_0 · Qwen3-32B · 동시 4 의 벽시계가 12 ~ 19 초).
- 측정 중에 컨테이너가 두 번 다시 켜졌다(까닭은 모른다). 결과 · 로그는 홈(NFS)에 남아 있어, 끝난 설정은 건너뛰고 이어서 측정했다.
- 후속 측정의 재현성 검사는 앱이 아니라, 앱 0.12.1 의 두 검사를 옮긴 내부 스크립트로 돌렸다(2.1).
- 이 서버는 성능 카운터를 관리자만 읽게 해(`RmProfilingAdminOnly=1`) Nsight Compute 를 쓰지 못했다. 3.5 의 '반복 몸통의 명령에 묶인다'는
  처리량에서 거꾸로 짚은 것이다.
- 3.6 의 측정 뒤에 도구를 하나 고쳤다. 그 측정의 도구는 표 판이 없는 구조의 그래프를 첫 깊이에서 한 번 지어 다음 깊이에도 썼다. 그래서
  깊이 8,192 의 그래프 시간(Qwen3.5 · Gemma 4)은 틀렸고, 원자료에만 있고 표에는 쓰지 않았다. 지금 도구는 깊이마다 새로 짓는다. RTX 4070 Ti
  의 Qwen3.5-9B 생성은 고친 도구로 다시 쟀다(`4070Ti_Qwen3.5-9B-Q4_K_M_생성_그래프고침.txt`).
- 3.6 에서 RTX 4070 Ti 의 대역은 재지 않고 규격(504 GB/s)으로 셌다.

`~/geulpu-h100`)에 모델 · 결과 · 로그를 둔다. 끊겨도 같은 명령을 다시 돌리면 끝난 설정은 건너뛴다.

1. 1 의 빌드로 GeulPU 의 `bin/` 을 만든다.
2. 모델 파일을 `$W/models` 에 받는다(아래 표).
3. `W=<작업 폴더> G=<GeulPU 의 bin> bash 재기/H100/준비.sh` — llama.cpp b11900 의 소스 빌드, 모델의 SHA-256 확인, GeulPU 의 모듈 여섯 개.
4. `bash 재기/H100/측정.sh` — GeulPU 빠른 · 정밀 모드와 llama.cpp KV f16 · q8_0, 한 요청과 동시 요청.
5. `bash 재기/H100/vllm.sh` — CUDA 13.0 도구 · vLLM 가상환경 · Qwen3-8B(BF16) 받기, 메모리 대역폭, vLLM BF16 · FP8.
6. `python3 재기/H100/정리.py $W/results.jsonl` — 위 표의 값과 비.

이 문서의 원자료는 [재기/H100/결과.jsonl](../재기/H100/결과.jsonl)(143 줄)이다. `python -I -X utf8 재기/H100/정리.py 재기/H100/결과.jsonl` 이
위 표의 값을 낸다.

후속 측정(2.1 · 3.5)은 이렇게 다시 잰다.

1. 재현성 검사 — 리눅스 앱(0.12.1 다음 판)의 `./GeulPU --검사 쌍` · `./GeulPU --검사 재현성`. 모델 파일은 자료 폴더의 `모델/` 에 둔다.
2. 빌드 대조 — 다섯 실행 파일의 `sha256sum` 과 `objdump -T <파일> | grep -o 'GLIBC_[0-9.]*'`(아무것도 나오지 않으면 판이 붙은 기호가
   없다). jaegi-kernel 은 `geulc 엔진/재기_커널.gl -o bin/jaegi-kernel`.
3. 텐서 코어의 최고치 — `python3 재기/H100/mmabench.py --json mma.json`(CUDA 드라이버만 쓴다, numpy 없음).
4. 커널마다 시간 — 재기 입력을 `python3 시험/입력7B.py Qwen3-8B-Q8_0.gguf 재기입력.bin --재기`(numpy)로 만들고
   `bin/jaegi-kernel Qwen3-8B-Q8_0.gguf <모듈 PTX> 재기입력.bin 커널.txt 512 2048 8192`. 모듈은 준비.sh 가 만드는
   `qwen3Q8_4096x32x8x12288x151936`(정밀) · `qwen3Q8_4096x32x8x12288x151936_빠른`(빠른)이다.
