# 소비자 MoE 가설 재기 (2026-10-19 — 계획 · 판정 기준은 재기 전에 정함)

## 가설 (사용자, 2026-10-19)

메모리 부족으로 VRAM 이 귀해져 MoE 모델이 커지고 있다. KTransformers 는 MoE 에 맞춘 CPU/GPU 나눔으로 적은 VRAM 에서 큰 MoE 를
돌렸지만 서버 CPU(AMX)에 맞춰져 소비자 PC 에서는 ollama 와 차이가 작았다. 소비자 MoE 는 아직 시장 증명이 부족하니 GeulPU 가 노릴 수 있다.

제 풀이(직전 답): 소비자 PC 의 벽은 CPU 셈이 아니라 RAM · PCIe 대역폭이다 → 길은 VRAM 을 전문가 캐시로(한 사람의 쓰임에 맞춰).

## 재기 전에 바뀐 것 — llama.cpp 가 이미 같은 길에 있다

받을 판(b11727)의 llama.h 에서 `moe_cache_size` 를 보고 찾았다.

- **#29887 (2026-10-07 합쳐짐)** `--moe-cache-mib N`: 호스트 메모리의 전문가를 GPU 의 LRU 캐시로, 놓친 것만 올림(작은 일괄 ≤ 32 토큰만,
  큰 일괄은 예전 길). 보고: 93.7 GiB 모델, RTX 4090 25.0 → 40.7 토큰/초(1.62 배, 적중 77 %), RTX 5090 30.8 → 67.8(2.20 배, 적중 89 %).
- #30112 (합쳐짐) GPU 여럿. **#30594 (열림)** 프로필로 캐시 미리 채우기 + 놓친 전문가는 CPU 가 함께 셈(PCIe 를 기다리지 않음).
  #30593 (닫힘) 캐시 층의 top-k 줄이기(값이 바뀜) — 적중률 92 → 94 % 보고. #29963 (열림) 호스트 전문가와 파이프라인 병렬.

그래서 질문을 바꾼다: **"llama.cpp 가 캐시를 켰을 때보다, 어떤 캐시 정책으로도 더 얻을 몫이 남는가."**

## 판정 (미리 정함)

- **구조의 몫이 있다**: Belady 정책의 바닥으로 낸 생성 속도 × 0.87(GeulPU 가 밀집 모델 생성에서 낸 대역폭 효율) ≥ **1.5 ×** llama.cpp 의
  최선(캐시 켬, 추측 없음)의 잰 생성 속도 — 깊이 16k · 32k 둘 다에서. 같은 VRAM 예산(llama.cpp 가 전문가에 쓴 VRAM 과 같게)으로 견준다.
- 아니면 **"소비자 MoE 캐시만으로는 GeulPU 의 구조적 우위가 되지 않는다"**로 적고 멈춘다.
- 함께 적는 것: 구현의 몫(LRU 바닥 대 llama.cpp 의 잰 값), 정책의 몫(Belady 대 LRU), 프로필(한 사람)의 몫(자기 작업 프로필 대 다른 글
  프로필), MTP 를 켠 llama.cpp, 에이전트 작업에서 프롬프트를 처음부터 다시 셈한 몫(직전에 제안한 문맥 저장소의 근거).

### 7. 해석 — 넘은 몫은 어디서 오나

- **정책의 몫은 작다.** 실용 정책(SLRU)은 LRU 보다 +0.3 ~ 0.9 %p. Belady 와의 차이(놓침 50 → 21)는 앞날을 알아야 얻는다(2026 년의
  연구에서도 라우터로 미리 읽기는 0.3 ~ 5 %).
- **'한 사람에 맞춘 캐시'의 몫은 없다.** 프로필로 채운 LRU = LRU, 고정 프로필은 LRU 보다 13 ~ 17 %p 나쁘다. 코딩과 코딩 아닌 글은 쓰는
  전문가가 크게 다르지만(대조 글 프로필 37 ~ 45 %), 코딩 안에서는 '최근에 쓴 것'이 '자주 쓰는 것'보다 낫다.
- **몫의 대부분은 실행(구현)이다.** 가) 에서 llama.cpp 는 같은 LRU 바닥의 약 60 ~ 70 %(층마다 호스트 동기 40 번, 미리 읽기 없음) —
  1.24 ~ 1.49 배. 나) 의 2 배 남짓은 놓친 전문가를 CPU 가 겹쳐 셈하는 몫인데, llama.cpp 의 열린 PR #30594 가 바로 이것이다.
- 그래서 기준은 넘었지만 **그 몫은 llama.cpp 도 같은 길로 메우고 있는 구현의 몫**이다. GeulPU 가 하려면 MoE · Gated DeltaNet · MTP 지원과
  글(geul) 컴파일러의 SIMD(지금은 실수 하나짜리 명령만)가 먼저 필요하다. 미리 정한 기준이 '정책 · 구조의 몫'과 '구현의 몫'을 나누지 않은
  것은 기준의 허술함이다.
- **더 큰 낭비가 따로 보였다**: 작업 시간의 38 ~ 43 % 가 프롬프트 처리이고, 그 58 ~ 64 % 가 되풀이되는 긴 프롬프트를 처음부터 셈한 것이다.
  문맥 저장소(셈한 상태를 토큰열 이름으로 VRAM · RAM · SSD 에 두고 다시 씀)의 몫(어림): 같은 프로젝트의 새 작업이면 첫 요청 약 30 초 →
  거의 0, 다른 프로젝트여도 같은 앞 8,963 토큰(약 16 초). 하위 에이전트로 슬롯이 덮인 뒤 되돌아오는 것도 마찬가지.
