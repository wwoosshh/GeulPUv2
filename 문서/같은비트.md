# 같은 비트인가 — 같은 요청을 혼자, 그리고 동시 요청 안에서

*English version: [docs/same-bits.md](../docs/same-bits.md).*

[`도구/same_bits.py`](../도구/same_bits.py) 는 OpenAI 호환 서버에 요청 하나를 — temperature 0, 고정 시드, `cache_prompt: false` 로 — 먼저
혼자, 그다음 다른 프롬프트 일곱 개와 동시에, 다섯 번 보내고 모든 답을 첫 답과 견준다: 토큰과, 서버가 주면 토큰마다의 로그 확률까지.
파이썬 표준 라이브러리만 쓰고, `/v1/chat/completions` 를 말하는 서버면 어느 것이든 된다 — GeulPU · llama.cpp · vLLM · SGLang · Ollama.

```
python 도구/same_bits.py --url http://127.0.0.1:44544/v1 --label GeulPU
python 도구/same_bits.py --url http://127.0.0.1:8080/v1 --label llama.cpp
```

옵션: `--rounds 5` · `--batch 8`(탐침 하나 + 채움 프롬프트 일곱) · `--max-tokens 160` · `--seed 42` · `--prompt "…"` · `--fillers 파일`(줄마다
채움 프롬프트 하나) · `--strict`(하나라도 다르면 종료 1). 마지막 줄이 판정이다:
`<이름>: alone N/N identical · in a batch of B M/N identical · first fork at token k`.

## 읽는 법

- **혼자 보내면 두 엔진 다 같은 답을 되풀이한다.** 요청 하나만 돌 때는 커널이 늘 같은 일을 같은 차례로 한다. llama.cpp 는 배치 불변을 목표로
  하지 않는다고 밝히고 있고, 슬롯 하나에 프롬프트 캐시가 없으면 결정적이다 — `alone` 줄이 그것이다.
- **동시 요청 안에서는 llama.cpp 의 수가 움직인다.** 다섯 라운드 모두 토큰마다의 로그 확률이 바뀌었고(가장 큰 차이 0.04 ~ 0.08 nat), 3 라운드에서는
  답 자체가 66 번째 토큰에서 갈렸다 — 1 · 2 위 후보가 가까운 자리에서 `S` 가 `Revenue` 가 됐다. 어느 라운드가 갈리는가는 함께 든 요청에 달려
  있어 다른 PC · 빌드 · 프롬프트에서는 수가 다르다. 로그 확률이 라운드마다 움직이는 것이 변하지 않는 부분이다.
- **GeulPU 의 토큰과 로그 확률은 열 답 모두 같은 비트였다.** 정밀도 계약이 더하는 차례를 무의미하게 만든다 — 곱의 합은 정수로 정확히 더하고 남은
  반올림 자리는 모두 적혀 있다([계약](../계약/계약.md)) — 그래서 배치가 결과를 바꿀 수 없다. 프롬프트 캐시(디스크에서 되살림 · 다시 셈), 추측
  디코딩, 정밀 모드에서는 GPU 제조사가 바뀌어도 같다([사용 안내 — 무엇이 다른가](../사용안내.md)).
- **에이전트 규모**에서는 cache-divergence-study 하네스의 80 에피소드로 같은 것을 쟀다: llama.cpp 는 프롬프트 캐시를 켜고 끄는 것만으로 80 중 64 가
  갈렸고 GeulPU 는 어느 비교에서도 0 이었다([프롬프트캐시재현성.md](프롬프트캐시재현성.md), 자료 [doi:10.5281/zenodo.23631969](https://doi.org/10.5281/zenodo.23631969)).

## 한계

- PC 하나, 모델 하나, 프롬프트 하나, 다섯 라운드. 도구는 서버를 그 서버의 첫 답과 견준다 — 엔진끼리 견주지 않는다(GeulPU 와 llama.cpp 의 답은
  셈이 달라 서로 다르다).
- llama.cpp b11721 은 2026-10-30 에 이 PC 에 있던 빌드이지 최신 릴리스가 아니다. 최신 빌드로 다시 돌리는 데 2 분이면 된다.
- 앱의 화면이 아니라 스크립트다 — 두 번째 서버와 터미널이 필요하다.
