## 1. 기능 목록의 형식 — `geulpu-operations/1`

파일은 `앱/data/operations.json`(앱 꾸러미에 함께 들어가, 앱과 단계 C 의 CLI 가 실행 중에 읽는다). 맨 위는
`{"format": "geulpu-operations/1", "result_types": {…}, "operations": […]}`.

| 기능의 필드 | 뜻 |
|---|---|
| `id` | 화면 언어와 상관없는 이름 `묶음.동작`(예: `run.branch` · `debug.record.start`). 기록 · 이벤트 · CLI 가 이 이름을 쓴다 |
| `title` · `description` | `{ko, en}` |
| `status` | `exists`(지금 있음) 또는 `planned`(앞으로 — `stage` 필수, 예: `C` · `실험대 3`) |
| `http` | `{method, path}` — 그 기능이 부르는 경로(앱 API · 서버 API · 기록기로 전달). `planned` 이면 없어도 된다 |
| `params` | `[{name, type, required, default, description{ko, en}}]` — 서버 API 의 GeulPU 필드도 인자로 적는다 |
| `result` | 결과 형식의 이름(`result_types` 의 열쇠) |
| `job` | 오래 걸리는 일인가(참이면 일 번호를 돌려준다 — `/api/job/*`) |
| `records` | 실험 기록에 적는 것(`none` · `run` · `branch` · `score` · `lens` · `comparison` …) |
| `cli` | `{ko, en}` — 명령 이름(예: `{"ko": "실행 분기", "en": "run branch"}`). 단계 C 의 CLI 가 이것으로 만들어진다 |
| `gui` | `{view, note}` — 그 기능이 있는 화면(기능지도의 화면 열). 화면이 아직 없으면 `{"planned": "<단계>"}` |
| `internal` · `reason` | 사용자 기능이 아닌 것(예: `/api/ping` · `/api/hello`) — 까닭 필수. 동등성 점검에서 빠진다 |

`result_types` 는 결과 형식마다 `{gui_view, description{ko, en}}` — 모든 결과 형식에 그것을 보여 줄 화면이 있어야 한다.

**하나의 경로가 GET · POST 로 다른 일을 하면 기능 둘로 적는다**(예: 기록기 설정 읽기 · 쓰기). 앱은 요청 하나를 `앱/관리자.gl` 의
`관리나눠주기` 한곳에서 메서드와 경로로 나눠 처리하므로, B3 의 이벤트도 그 자리에서 낸다.

## 2. 첫 판의 범위

- **앱 API** — 기능지도 2 절의 경로 61 개(메서드마다 하나씩).
- **전달 경로(proxy) 둘** — 기능지도에 빠져 있던 것: `/v1/*`(와 `/tokenize` · `/detokenize` · `/tokenizer_info`)를 추론 서버로, `/llama/*` 를 사용자의
  llama-server 로(llama.cpp 재현의 기록기). 기능지도 3 절에 함께 적는다.
- **서버 API** — 생성(`/v1/chat/completions` · `/v1/completions` · `/v1/messages` · `/v1/responses`) · 점수(echo) · 분기(`step_offset`) · 렌즈(`layer_lens` ·
  `jacobian`) · 토큰화 · 모델 목록 · 건강 확인. 기능지도 3 절의 GeulPU 필드 15 개는 이 기능들의 인자로.
- **화면 밖 기능 다섯과 연구 패널 기록** — `planned`(단계 표시): GPU 없는 재현 확인(`도구/repro_check.py`), 같은 비트 확인(`도구/same_bits.py`),
  Jacobian lens 의 J 파일 맞추기(`도구/jlens_fit.py`), llama.cpp 실행의 설정 반사실, 연구 패널 기록의 앱 API. 요청 필드 `geulpu_tool_errors` 는
  생성 기능의 인자로(화면은 `planned`).
- **실험 기록** — `experiment.*`(만들기 · 목록 · 보기 · 점검)를 `planned`(단계 C)로. 형식은 B2.

## 3. 점검 도구 — `시험/기능목록점검.py`(GPU 없이)

1. 형식: 필드 · 형 · `id` 의 형식, `status` 와 `stage`, `cli` 의 두 언어.
2. 경로 대조: 앱의 글(geul) 코드가 처리하는 `/api/…` 경로(메서드와 함께)와 기능 목록의 경로가 같다 — 코드에만 있는 것 0, 목록에만 있는 것 0.
3. CLI: 내부용이 아닌 모든 기능에 CLI 이름(한국어 · 영어)이 있고, 같은 언어 안에서 겹치지 않는다.
4. 화면: 내부용이 아닌 모든 기능에 `gui` 가 있고, 모든 결과 형식에 `gui_view` 가 있다.
5. 웹 코드: `앱/web/*.js` 가 부르는 `/api/…` 경로가 모두 기능 목록에 있다(화면이 목록 밖의 경로를 부르지 않는다).
6. 인자: 경로를 처리하는 코드 블록이 직접 읽는 요청 키(몸의 JSON 키 · 질의)가 모두 그 기능의 `params` 에 있다.
7. `--자체시험`: 임시 사본에 잘못을 하나씩 넣어 모두 잡는지 본다 — 코드에만 있는 경로 · 목록에만 있는 경로 · CLI 이름 없음 · CLI 이름 겹침 ·
   화면 없는 결과 형식 · 웹 코드가 부르는 목록 밖 경로 · 코드가 읽는데 `params` 에 없는 키.

빠른 점검(`시험/빠른점검.py`)에 단계 하나로 넣는다. 전체 점검 경로(`커널/` · `백엔드/` · `시험/모듈점검.py` 등)는 건드리지 않아 CI 는 빠른 방식 그대로다.

## 4. B1 의 판정(구현 전에 적음)

1. **형식:** `앱/data/operations.json` 이 `geulpu-operations/1` 이고, 점검 도구의 형식 오류가 0 이다.
2. **범위:** 코드의 앱 API 경로 61 개가 메서드마다 모두 목록에 있고 목록의 경로가 모두 코드에 있다(빠짐 0 · 남음 0). 전달 경로 둘, 서버 API 의
   경로 10 개와 GeulPU 필드 15 개가 모두 기능의 경로 · 인자로 있다. 화면 밖 기능 다섯과 연구 패널 기록이 `planned` 로 있다.
3. **동등성 점검:** 3 절의 3 ~ 6 이 모두 통과한다.
4. **자체 시험:** 3 절 7 의 잘못 일곱을 모두 잡는다(7/7).
5. **CI:** 빠른 점검 안에서 GPU 없이 5 초 안에 끝나고, CI 는 빠른 방식 그대로다. 앱 코드와 모듈 해시는 바뀌지 않는다.

## 5. B2 · B3 의 판정(안 — 그 묶음을 시작할 때 확정)

- **B2:** 점검 도구가 `_template/` 을 통과시키고, 잘못 셋(포함 파일의 해시 틀림 · 압축 5 MB 넘음 · 필수 필드 빠짐)을 모두 잡는다. CI 에서 GPU 없이.
- **B3:** 기능 목록의 경로를 부를 때마다 시작 · 끝 이벤트가 하나씩 차례대로 나오고, 출처(`gui` · `python` · 그 밖은 `unknown`)가 적힌다. 기존 API
  응답은 바이트까지 그대로다. 내보내기는 지금의 요청 · 응답 형식에 맞춘 긴 폴링(`/api/events?after=<번호>&wait=<ms>`)으로 한다 — 앱의 HTTP 층에
  흘려보내기(SSE)가 없다. SSE 는 뒤에 필요하면 더한다.
