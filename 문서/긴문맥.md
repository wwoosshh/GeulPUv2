## ③a 위치 늘이기 — 자세히(이번 승인 대상)

### 어떻게

- **YaRN**(Qwen2.5 · Qwen3 의 모델 카드 · config 의 `rope_scaling: {type: yarn, factor: 4, original_max_position_embeddings: 32768}` —
  transformers · vLLM · llama.cpp 의 같은 식):
  - 주파수: 짝 i 마다 θ_i = base^(−2i/d). 원래 문맥에서 도는 바퀴 수로 정한 두 경계(β_fast 32 · β_slow 1 — low · high 짝)
    사이를 곧은 경사 r_i 로 섞어 θ′_i = θ_i · ((1 − r_i)/s + r_i) — 높은 주파수는 그대로, 낮은 주파수는 1/s. 이것은 계약 4.7 (2)의
    θ′_i = θ_i / f_i 형태(f_i = 1 / ((1 − r_i)/s + r_i))라 **이미 있는 Llama 3.1 의 계산 경로에 인자만 더한다**.
  - 크기: cos · sin 에 mscale = 0.1 · ln(s) + 1 을 곱한다(q · k 둘 다 — 어텐션 온도). 표의 값이 바뀔 뿐 커널은 그대로.
  - **계약 4.7 (2′)**: f_i 와 mscale 의 계산(fp64 — 경계는 transformers 의 find_correction_range 와 같은 floor · ceil), 표 값 =
    fp32(mscale × cos(위치 · θ′_i))를 바른 반올림으로(fp64 계산 — 지금 표와 같은 방법). CPU 참조(계약/정수계약.py)가 같은 식.
- **켜는 때**: 설정의 문맥이 모델의 원래 길이(32,768)를 넘을 때만 s = 4(Qwen 공식 — 짧은 글에서 조금 손해가 있어 원래 길이 안에서는
  끈다, vLLM · llama.cpp 의 정적 YaRN 과 같은 판단). Qwen2.5 · Qwen2.5-Coder · Qwen3 만(모델 이름이 아니라 구조 qwen2 · qwen3 이고
  GGUF 에 rope 늘이기가 없을 때). 그 밖은 그대로.
- **앱**: 모델 화면의 "문맥 최대"를 YaRN 을 켤 수 있는 모델은 131,072 로 보이고, 켜진 때를 모델 불러오기 기록에 남긴다("YaRN — 32,768
  → 131,072").

### 맞음(미리 정함)

1. **계약**: RoPE 표(위치 0 ~ 131,071)가 엔진 · CPU 참조에서 비트까지 같다. 머리128 의 긴 경우 · 엔진/시험_긴문맥을 65,536 · 98,304 ·
   131,072 근처까지(프롬프트 길 · 표 스텝 행 1 · 행 8 · 그래프가 같은 비트, CPU 참조와 같음).
2. **식이 맞는가** — llama.cpp 최신(b11724, `--rope-scaling yarn --rope-scale 4 --yarn-orig-ctx 32768`)과 같은 64k 글의 다음 토큰
   분포를 비교한다(엔진이 달라 비트는 아니고 KL · 첫째 일치 — 지금 32k 안의 차이와 같은 급이면 맞다).
3. **NIAH 테스트(needle-in-a-haystack)**: 긴 글(측정 입력의 긴 글을 되풀이) 속 깊이 10 · 50 · 90 % 에 숨긴 문장("비밀 번호는 7429")을 32k · 64k · 96k 문맥에서
   묻는다 — Qwen2.5-7B · Coder-7B, llama.cpp 와 맞은 수를 비교한다.
4. **이 PC 의 최대 문맥** 표를 다시(Qwen2.5-7B · Coder-7B · Qwen3-8B), 그 문맥에서 코딩 에이전트(Qwen Code) 일 하나.
5. **그대로인 것**: 원래 길이 안(32,768 이하)은 바이트까지 그대로 — 교차검증 R1 32/32 · 모듈 해시 · 빠른점검. 커널 · 모듈은 바뀌지 않는다.
6. 속도(참고): 64k · 96k 의 빈 프롬프트 · 깊이마다 생성 — ③c 의 출발점으로 적는다(이 단계의 목표는 아님).

### 받을 것(승인 필요)

- 받은 것 · 시험 모델 복사본은 E:(SSD)에, 끝나면 지운다.

### 위험

- YaRN 은 모델이 늘인 위치를 '배운' 것이 아니라 끼워 맞추는 것 — 긴 글의 질은 모델의 몫(NIAH 테스트로 잰다). Qwen 이 공식으로 권하는 값이라
  다른 엔진과 같은 질이어야 한다.

## ③b 8비트 KV(F1A′) — 자세히 (사용자 승인 2026-10-20)

**무엇**: 빠른 모드(F1)의 K · V 캐시를 8비트 정수와 값 32개마다의 fp32 스케일(scale) s = 블록 최댓값 / 127 로 둔다. llama.cpp 의 q8_0 KV 와
같은 형식이다(스케일만 fp16 이 아니라 fp32). 정밀 모드 · Vulkan 은 그대로다. 처음에는 설정에서 고르는 옵션으로 두고 기본은 끈다 — 지금
모드들의 출력 비트가 그대로라 버전 규칙의 MINOR 다.

- KV 바이트: 블록마다 지금 64 B + 지수 1 B → 32 B + 스케일 4 B(0.55 배). 프롬프트 캐시의 청크도 같은 비(7B 14.9 → 8.3 MB).
- 2b-1 의 F1A(2 의 거듭제곱 스케일)는 Qwen 계열 · Q8_0 에서 못 미쳤다 — 블록 최댓값을 정확히 담지 못해서다(문서/2b단계.md). F1A′ 는
  최댓값을 ±127 로 담는다.
- 단계: ③b-1 품질 먼저(에뮬레이션) → ③b-2 실제 8비트 커널 · 엔진 · 앱(품질을 넘으면, 다시 승인) → ③b-3 측정 · 문서 · CI.

### ③b-1 품질 먼저 — 에뮬레이션(커널의 메모리 배치는 그대로)

- **에뮬레이션(emulation)**: RoPEKV 커널 3개(기본 · CUDA 그래프 · 테이블 스텝 변형)가 키 · 값 블록을 8비트로 양자화했다가 역양자화
  (dequantize)한 값 y 를 지금의 16비트 형식(8비트 자리(digit) 둘)으로 둔다. 블록(값 32개)마다 m = max|x|, s = m / 127(바른 반올림).
  s > 0 이면 n = 가까운정수(x / s)(|n| ≤ 127) · y = n · s, 아니면 y = 0. 모든 fp32 연산은 규칙 R.
- CPU 참조: `정수계약.어텐션한자리` = "kv8"(키 · 값) · "v8"(값만 — 기록용). 커널 생성기 플래그 `--어텐션한자리 KV8 | V8`(`--빠른` 과 함께만,
  시험용).
- 에뮬레이션은 ③b-2 의 실제 8비트 커널과 비트가 같지 않을 수 있다 — y 를 16비트 형식으로 다시 반올림한다(상대 2⁻¹⁴ 급 — 8비트 반올림
  2⁻⁸ 보다 훨씬 작다). 품질 판정에는 같다고 본다. ③b-2 의 계약은 그때 CPU 참조로 다시 정한다.

그대로다. k-양자화 파일에서만 켤 수 있다(Q8_0 · Q4_0 은 막는다 — ③b-1 판정 2).

**계약 F1A′**(계약.md 2.1 절, CPU 참조 계약/정수계약.py)

- 키 · 값 저장: 블록(값 32 개)마다 s = max|x| / 127(fp32 나눗셈, 반올림 하나). s > 0 이면 n 은 fp32 몫 x / s 에 가장 가까운 정수
  (|n| ≤ 127), 아니면 n = 0. 저장은 n(int8)과 s(fp32). 모든 fp32 연산은 규칙 R.
- 점수: 블록 b 마다 u_b = fp32(정확한 정수 합 Σ n_q · n_k). q 는 지금처럼 16비트 형식(8비트 자리 둘 — n_q = 256·D₁ + D₀)이고 |Σ| < 2²⁶ 이라
  int32 에서 정확하며, fp32 로 바꿀 때 반올림 하나다. 점수는 Σ_b (u_b × P_q,b) × s_k,t,b 에 c 를 곱한 값 — b 오름차순, b = 0 은 곱, 그 뒤는
  FMA(지금 계약과 같은 순서 — 2^(E_k − 13) 자리에 s_k 가 온다).
- 가중합: e′_t = e_t × s_v,t,b(반올림 하나)를 키 32 개 블록마다 지금의 16비트 형식으로 바꾸고, u_j,d = fp32(정확한 정수 합
  Σ_t n_e′ · n_v), o_d = fma(u₁, P₁, u₀ · P₀).
- 최댓값 · 지수 함수 · 합 · 타일 · 그룹 병합은 지금 계약 그대로다. ③b-1 에서 본 0 의 부호 차이는 커널의 분기 없는 병합(O = fma(o, B, O · A))이
  행을 타일로 나누는 방식(실행 경로)에 따라 −0 을 +0 으로 바꾸는 것이라, 경로와 관계없는 계약으로는 맞출 수 없다. 엔진이 다음 층에 쓰는
  16비트 형식의 출력은 ±0 이 같은 바이트이므로, 시험용 fp32 출력에서 0 의 부호만 다른 원소는 ③b-1 처럼 따로 센다.
- **키의 블록 크기는 32 그대로** — ③b-2a 진단(2026-10-21, Qwen2.5-7B Q4_K_M, ③b-1 과 같은 텍스트): 같은 엔진 안에서 8비트 KV 만의 차이를
  재면 GeulPU(F1 ↔ F1+KV8) KL 3.85 × 10⁻³ · 1위 일치 96.77 %, llama.cpp(f16 ↔ q8_0 KV) 3.90 × 10⁻³ · 96.83 %(텍스트 4개를 합친 값),
  8,192 토큰 윈도 2.44 대 2.74 × 10⁻³ — 같은 크기다. ③b-1 에서 Qwen 의 키 손실이 llama.cpp 보다 커 보인 것은 두 엔진을 모두 GeulPU 정밀
  모드 기준으로 재어, llama.cpp 의 엔진 차이와 q8_0 차이가 KL 에서 단순히 더해지지 않은 탓이다.
