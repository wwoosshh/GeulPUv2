# 긴 문맥 실사용 재기 (2026-10-19 — 측정 방법 · 결과 · 4b단계 고친 뒤의 생성)

## 왜

지금까지의 프롬프트 재기(재기/견주기2.sh)는 빈 캐시에서 N = 512 · 2,048 · 4,096 · 8,192 토큰을 한 번에 넣는 시간이었다(llama-bench 의
pp N 꼴). 실사용의 세션은 수만 토큰(코딩 작업은 10만 넘게)이 흔하고, 대화의 한 차례는 서버가 앞 대화의 KV 캐시를 다시 쓰므로 새 입력만 넣지만
새 토큰마다 앞의 세션 전체를 어텐션으로 읽는다. 그래서 세션 길이에 따라 커지는 값 셋을 잰다.

## 무엇을 · 어떻게

- 모델: Qwen2.5-7B-Instruct Q4_K_M · Llama-3.1-8B-Instruct Q4_K_M, 두 모델 같은 칸 — N 16k · 32k, d 8k · 16k · 31k(31,744 — 새 입력
  1,024 를 더해 32k 안). 글 엔진은 빠른 모드(F1, 4단계의 모듈 — 앱의 기본), llama.cpp 는 기본 f16 KV.
- **글 엔진의 한계 하나 — 64k 를 재지 못했다**: Qwen2.5-7B 의 GGUF 는 위치 수(문맥)가 32,768 이고 글 엔진은 그 너머를 받지 않는다
  (`최대길이는 64 의 배수, 모델의 위치 수까지` — YaRN 같은 문맥 늘이기가 없다). llama.cpp 는 경고와 함께 넘겨 셈한다. Llama-3.1-8B 는 위치 수
  131,072 이지만 KV 가 토큰당 133 KB(글 · llama.cpp f16 같은 급)라 12 GB 에 32k 남짓까지.
- 입력: 재기 입력의 긴 글(모델마다 그 토크나이저의 토큰 8,192)을 되풀이한 73,728 토큰(빌드/재기입력/재기Q_긴 · 재기L_긴.bin). 셈의 양은
  토큰의 값과 상관없다.
- 앱은 서버의 덩이 512 로 돈다(여기는 1,024 — 견주기2 와 같은 엔진 덩이).
- 글 엔진의 모듈은 4단계(아직 커밋 전)의 빠른 모듈, llama.cpp 는 최신 공식 판 b11721(CUDA). RTX 4070 Ti 12 GB, 2026-10-19.
  재기 다시 하기: `bash 재기/긴문맥.sh 빌드/결과/긴문맥` → `python -X utf8 재기/긴문맥요약.py 빌드/결과/긴문맥`.

- **긴 문맥에서는 글 엔진이 느리다.** 2c 의 짧은 프롬프트(2,048 까지 llama.cpp 보다 빠름 — Qwen 0.906 배)에서 8,192 의 1.07 · 1.15 배로,
  16k 의 1.19 · 1.29 배, 32k 의 1.40 배로 벌어진다. 실사용으로 옮기면 32k 세션을 캐시 없이 처음 넣을 때 Qwen 10.8 초(llama.cpp 7.7 초) ·
  Llama 13.2 초(9.4 초), 31k 세션의 한 차례(새 입력 1,024)가 Qwen 0.54 초(0.35 초) · Llama 0.68 초(0.63 초).
- **지는 몫은 어텐션이다.** 깊이 1k 가 늘 때 새 입력 1,024 의 시간이 느는 양(ms / 1k — 8k → 16k · 16k → 31k): 글 Qwen 13.0 · 12.8,
  Llama 17.0 · 16.7 / llama.cpp Qwen 5.5 · 6.5, Llama 9.0 · 21.6. 글의 기울기는 llama.cpp(8k → 16k)의 **2.4 배(Qwen) · 1.9 배(Llama)**다.
  글의 기울기는 곧은 줄이고 두 모델의 비 1.31 이 (층 × q 머리)의 비(1,024 / 784 = 1.31)와 같다 — KV 를 읽는 양(층 × KV 머리의 비 2.29)이
  아니라 셈이 한도다(두 자리 정수 어텐션). llama.cpp 의 Llama 는 16k → 31k 에서 기울기가 2.4 배로 뛴다(Qwen 은 1.2 배) — 까닭은 보지
  않았다(VRAM 이 빠듯한 칸). 그래서 Llama 31k 의 비 1.084 는 llama.cpp 쪽이 느려진 값이다.
- **생성은 깊이 31k 까지 llama.cpp 와 같은 급이고 조금 느리다** — Qwen 1.013 · 1.028 · 1.047 배, Llama 1.058 · 1.061 · 1.060 배(깊이
  8k · 16k · 31k). 글의 값은 그래프만 50 번 돌린 시간이라(토큰마다의 호스트 맞추기 · 고르기 없음) llama.cpp 의 tg128 보다 1 ~ 3 % 유리하게
  잰 값이다 — 실제 차이는 이보다 조금 크다. 추측 검증의 행 8 걸음은 깊이 31k 에서 행 1 의 3.3 · 4.4 배라(행마다 KV 를 따로 읽음) 긴 세션에서는
  추측 디코딩의 이득이 줄어든다.
- 공정함의 나머지: llama.cpp 는 프롬프트에서 마지막 층의 FFN · 출력을 출력 행에만 셈한다(글은 모든 행 — 글에 1 ~ 2 % 불리, 글도 값을
  바꾸지 않고 따라 할 수 있다). llama.cpp 는 ub 셋 가운데 가장 빠른 것을 골랐고 글은 덩이 1,024 하나다. 같은 셈을 두 번 잰 Llama 의 글 값은
  1 % 안팎으로 같았다(가장 큰 차이가 깊이 16,384 새 입력 418.4 · 422.6 ms).
- **64k 이상(코딩 세션의 100k)은 이 PC 에서 글 엔진이 받지 못한다**: Qwen2.5-7B 는 GGUF 의 위치 수 32,768 너머를 받지 않고(YaRN 없음),
  Llama-3.1-8B 는 KV 가 토큰당 133 KB 라 12 GB 에 33k 남짓까지다(KV 를 줄이는 것은 계약의 문제).

## 함께 찾은 결함 — 생성 길의 접기는 10,240 토큰까지만 맞았다 (4b단계에서 고침)

첫 재기에서 깊이 16,384 의 생성 걸음(행 8 54.2 ms — 8,192 의 2.3 배)이 튀었고, 엔진/시험_긴문맥(같은 토큰을 프롬프트 길 · 생성 길로
셈해 로짓을 견줌 — 계약상 비트까지 같아야 한다)으로 보니 생성 길이 틀렸다. Qwen2.5-7B Q4_K_M 빠른 모듈 · 최대길이 32,768:

| 문맥 n | 4,000 | 8,000 | 10,200 | 10,300 | 12,000 | 16,300 | 16,500 | 20,000 | 31,000 |
|---|---|---|---|---|---|---|---|---|---|
| 다른 로짓 칸(/ 152,064) | 0 | 0 | 0 | 152,064 | 152,064 | 152,064 | 152,064 | 152,064 | — |
| 가장 큰 번호(프롬프트 길 · 생성 길) | 같음 | 같음 | 같음 | 87549 · 87549 | 803 · 787 | 315 · 106791 | 13 · 304 | 8597 · 74619 | CUDA 700 (메모리 접근 오류) |

- **까닭**: 생성 길의 접기 정수조각접기128(커널/생성줄128.gl — 생성 그래프의 정수조각접기넓칸, 서버 생성 · 추측 검증의 표 걸음
  정수조각접기넓표, 정수조각접기)이 조각(64 토큰)마다의 M · L · 배율을 공유 판의 고정 칸에 둔다 — 판[c] M · 판[160 + c] L ·
  판[320 + c] · 판[480 + c] 배율 · 판[640 + 묶음] … 그래서 조각 160 개(**10,240 토큰**) · 묶음 16 개까지만 칸이 겹치지 않는다. 그 너머는
  칸이 서로 덮여 값이 틀리고, 넓 판은 묶음 몫 O 를 판[720 + 묶음 · 128 + d] 에 두어 18 번 묶음(위치 18,432)부터 공유 12 KB 를 넘는다.
- **미치는 곳**: 머리 128 모델의 생성 모두(그래프 생성 · 표 걸음), 정밀 · 빠른 모듈 모두(어텐션은 두 모드에서 같은 판), CUDA · Vulkan
  (같은 커널 글). 프롬프트 길(정수어텐션묶음 · 정수묶음접기)은 맞다 — 4b단계에서 32,768 까지 CPU 참조와 비트까지 같음을 보았다. 머리 64
  모델의 접기(커널/생성조각.gl 의 정수접기)는 조각 256 개씩 무리로 돌며 앞 무리들의 최댓값을 판[CM] 으로 이어 가는 꼴이라 이 한도가 없다
  (GeulPU 의 합성 긴 모델(위치 102,400)이 머리 64 라 머리 128 판의 한도가 드러나지 않았다).
- **앱에서**: 설정 문맥의 기본이 8,192 라 기본 설정에서는 닿지 않았다. 설정에서 문맥을 10,240 넘게 올리면(앱은 131,072 까지 받는다)
  대화가 10,240 토큰을 넘는 순간부터 생성 토큰이 오류 표시 없이 틀렸고(계약 위반), 더 길면 서버가 죽을 수 있었다(4b단계 앞까지).
- **GeulPU 0.5.0(공개판)**도 같은 커널 글이다(판[160 + c] · 공유판12 · 공유판4 — 읽어서 확인, 돌려 보지는 않음). 앱의 문맥 설정도 같다.
- **고침(4b단계 — 문서/4b단계.md)**: 접기를 무리(조각 128 개 = 묶음 여덟)마다 한 바퀴로 돌며 앞 무리들의 묶음 최댓값(이음M)과 누적
  (L, O)만 들고 간다. 식과 차례(묶음 안을 차례로, 그다음 묶음끼리 차례로)는 그대로라 위치 8,191 까지는 셈이 한 글자도 다르지 않고, 길이의
  한도는 최대길이뿐이다. 맞음: 커널 판 대 CPU 참조(머리128 — 32,768 까지 경계 다섯, 프롬프트 판 · 생성 판 넷 — 모든 칸 같음), 모델 끝에서
  끝(시험_긴문맥 — 32,760 까지 열여섯 위치 × 표 걸음 행 1 · 행 8 · 생성 그래프, Qwen 빠른 · 정밀 · Llama 빠른 — 모두 같음), 서버(추측 켬 ·
  끔 · echo — 32,700 까지, CUDA 빠른 · 정밀 · Vulkan 정밀, CUDA ↔ Vulkan 같음), 교차검증 R1 32/32 · Vulkan 빠른 확인.
