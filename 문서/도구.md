# 로컬 tools — 코딩 에이전트가 GeulPU 로 일할 수 있게 (계획 2026-10-19 — 승인됨, 받을 것 둘 받음)

## 왜

- 지금 서버는 OpenAI 요청의 `tools` 를 400("tools 는 받지 않는다")으로 거절하고 `role: tool` 메시지도 받지 않는다 → OpenCode ·
  Qwen Code · Continue · Cline 같은 코딩 에이전트의 에이전트 모드(파일 읽기 · 쓰기 · 명령 실행)가 이 엔진으로는 돌지 않는다.
- 문맥을 넘은 400 에는 숫자도, OpenAI 호환 `code` 도 없어 에이전트가 알아채고 스스로 줄이지 못한다. `/v1/models` 에 문맥 길이가 없다.
- 목표: 에이전트가 `http://127.0.0.1:44544/v1`(앱이 서버로 넘겨주는 길)에 붙어 도구를 부르며 일할 수 있게 한다. 도구를 낀 요청도
  GGUF 의 공식 채팅 템플릿과 바이트까지 같은 프롬프트가 되고(같은 요청 → 같은 토큰), 엔진의 계약(같은 답)은 그대로다.

## 범위

- **서버(엔진/서버몸.gl · 제이슨.gl)와 문서**. 커널 · 모듈 · 앱 화면은 그대로 — 앱의 채팅은 도구를 쓰지 않고 요청 몸도 그대로라 연구
  패널의 해시도 그대로다.
- 서버 실행 파일이 바뀌므로 교차검증 기준의 서버 빌드 해시를 고치고 R1 32 문제 · Vulkan 빠른 확인을 다시 돈다 — 도구 없는 요청의
  출력은 바이트까지 같아야 한다.

## 모델마다

| 모델 | 도구 | 꼴(GGUF 의 채팅 템플릿 그대로) |
|---|---|---|

| R1-Distill-Qwen | 안 함 | 틀에 도구가 없다 → 400(같은 말) |

## 어떻게

### 1. 요청

- `tools`(type function), `tool_choice`: `"auto"`(기본) · `"none"`(도구 없이 그림). `"required"` · 함수 지정은 400 — 지킬 수단(제약
  생성)이 없다(나중). `parallel_tool_calls`: 거짓이면 첫 호출에서 끝낸다.
- messages: `role: tool`(content 글 · 조각, `tool_call_id` 는 틀이 쓰지 않는다), assistant 의 `tool_calls`(content null 허용).
- `/tokenize` 도 `tools` · `tool_choice` 를 받는다(앱 · 시험이 같은 틀로 잰다).

### 2. 채팅 템플릿 — 공식 템플릿과 바이트까지

- GGUF 의 `tokenizer.chat_template` 을 transformers 의 `tojson`(ensure_ascii=False, 구분 `", "` · `": "`, 키 순서 그대로)으로 그린 글과
  같게. 서버에 파이썬 `json.dumps` 꼴 쓰기를 새로 둔다 — 들여쓰기 4(Llama), 글의 탈출(`\b` · `\f` 포함), 실수는 파이썬 repr 과 같은
  가장 짧은 꼴(유효 자리 1 ~ 17 에서 되돌아오는 가장 짧은 것 + 지수 꼴 규칙).
- `arguments` 가 글(OpenAI 호환)이면 JSON 으로 풀어 그린다(vLLM · llama.cpp 와 같음). Qwen3 틀은 글이면 그대로 넣는다(틀 그대로).
- **Qwen2.5 · Coder**: 도구가 있으면 시스템 = (시스템 말 또는 기본 시스템 말) + `\n\n# Tools …<tools>` + 도구마다 `\n` + tojson + 끝맺음
  글. 호출 있는 assistant 는 `\n<tool_call>\n{"name": "…", "arguments": …}\n</tool_call>` 를 차례로, 연이은 tool 결과는 user 차례 하나에
  `\n<tool_response>\n…\n</tool_response>` 로.
- **Qwen3**: 시스템이 없으면 도구 글만(기본 시스템 말 없음). 앞 답의 생각을 떼는 기준인 '마지막 질문'은 `<tool_response>` 를 담은 user
  말을 건너뛴 마지막 user(틀의 multi_step_tool). 호출 앞의 줄바꿈은 틀 그대로(content 가 있을 때만 · 둘째부터).
- **Llama 3.x**: `Environment: ipython\n`, 도구는 첫 user 말에 안내 글 + 도구마다 tojson(indent=4) + `\n\n`, 호출은
  `{"name": "…", "parameters": …}`, tool 결과는 `ipython` 차례(글도 tojson — 틀이 글을 iterable 로 보아 따옴표째 넣는다). 호출이
  둘 이상인 assistant 말은 400(틀이 받지 않는다).

### 3. 답에서 도구 호출 읽기

- **Qwen**: `<tool_call>`(토큰 151657) ~ `</tool_call>`(151658) 사이의 글을 내용에서 떼어 JSON 으로 풀어 호출 하나로. 여럿이면 차례대로.
- **Llama**: 도구가 있고 답의 첫 글자가 `{` 이거나 첫 토큰이 `<|python_tag|>` 면 끝까지 모아 `{"name", "parameters" 또는 "arguments"}`
  로 풀어 호출 하나로(틀이 하나만 받으므로 하나만).
- 풀기는 관대하게 — 글 안의 날 줄바꿈 · 탭은 받아 준다(7B 가 코드를 인자에 쓸 때 자주 틀린다). 그래도 못 풀면 그 글을 content 로
  돌려준다(잃지 않게).
- **생각(Qwen3)**: 도구 요청에서 `geulpu.special` 이 없으면 `<think>…</think>` 를 `reasoning_content` 로 뗀다(llama-server · DeepSeek API
  와 같은 키). 앱은 지금처럼 special 이라 그대로.
- 응답: `message.tool_calls = [{id: "call_…", type: "function", function: {name, arguments: JSON 글}}]`, content 는 없으면 null,
  finish_reason `"tool_calls"`. 스트리밍: 내용은 지금처럼 흘리고, 호출 하나가 끝나면 `delta.tool_calls` 조각 하나(이름 · 인자 통째), 생각은
  `delta.reasoning_content`.
- `arguments` 글은 파이썬 꼴(`", "` · `": "`) — 다음 차례에 틀이 다시 그린 글이 모델이 쓴 글과 같아 슬롯의 캐시가 이어진다.
- 끝 토큰 · 최대 길이 · 멈춤 글은 지금 그대로(멈춤 글은 content 에만). 호출 중간에 최대 길이에 닿으면 그 글을 content 로.

### 4. 오류 · 모델 정보

- 문맥 넘침 400: 말에 숫자와 OpenAI 호환 영어 문장을 붙이고(`프롬프트가 슬롯의 문맥보다 길다 — 프롬프트 N 토큰 · 문맥 L 토큰. This model's
  maximum context length is L tokens. However, your messages resulted in N tokens.`), `code: "context_length_exceeded"` — 에이전트가
  알아채고 스스로 줄인다. 앱의 오류 카드 분기(`/슬롯의 문맥보다 길다/`)는 그대로 맞는다.
- `/v1/models` 의 모델에 `"max_model_len": L`(vLLM 과 같은 키).

### 5. 문서

- README(한 · 영)에 "코딩 에이전트에 연결하기": 주소 `http://127.0.0.1:44544/v1`, 모델 이름(불러 둔 모델 — 이름은 아무거나), 도구를
  받는 모델 표, 앱에서 모델을 먼저 불러 둘 것, 시험한 에이전트의 설정 예.
- **문맥은 될 수 있는 한 크게**(사용자 기준, 2026-10-19): 기능 단위 개발(예: 로그인 기능 — 계획 · 검토 · 구현 · 보고를 압축 없이)에는
  **100k 이상**이 목표다. 32k 를 '충분'하다고 쓰지 않는다. 지금 이 PC(12 GB)에서 모델마다 실제로 되는 최대 문맥(모델의 최대 · 그래픽
  메모리)을 표로 따로 보인다. 100k · 200k(실험적으로 1M)를 돌리는 길은 ③(긴 문맥)의 목표 — 8비트 KV, KV 나눠 두기, Qwen 의 32k 너머
  RoPE 늘이기(YaRN), 100k 넘는 자리의 어텐션 속도.
- 이번 단계도 긴 문맥에 고정 한계를 두지 않는다: 요청 몸(지금 16 MB)과 관리자의 넘겨주기가 1M 토큰 대화(수 MB)를 받는지 확인하고,
  도구 호출 · 생각을 모으는 칸은 늘어나는 바이트열로.

## 위험

- 7B 의 도구 쓰임 자체가 약할 수 있다(틀린 JSON · 엉뚱한 호출) — 엔진이 고칠 수 없는 몫. 관대한 풀기 · content 되돌림으로 막고,
  모델마다 결과를 적는다.
- 에이전트의 시스템 프롬프트가 크다(수천 ~ 1만 토큰 넘게) — 기본 문맥 8,192 로는 바로 넘친다. 기능 단위 일은 100k 이상이 필요하다
  (위 5) — 지금 PC 에서는 모델 · 메모리가 그만큼을 못 받는 경우가 많고, 긴 프롬프트의 속도 · 메모리는 ③(긴 문맥)에서.
- 앱에 모델을 불러 두지 않으면 `/v1` 이 503 — 문서에 적는다. 요청의 model 로 저절로 불러오기는 나중.
- 파이썬 repr 과 같은 실수 쓰기 — 지수 꼴 · 큰 수까지 시험한다(도구 스키마에 실수는 드물다).

## 이번에 하지 않음

  도구 쓰기.

## 구현에서 바뀐 것(시험에서 찾음)

- **Llama 3.1 은 호출을 ';' 로 이어 쓴다**(`{…}; {…}; {…}` — 쓰고 · 실행하고 · 다시 실행). 처음 풀기는 JSON 하나만 기대해 셋 다 content
  로 돌렸다 → 앞에서부터 값을 하나씩 풀도록(제이슨.gl 의 제앞풀기). Llama 3 은 첫 호출만 돌려준다 — 틀이 assistant 말 하나에 호출 하나만
  받아, 여럿을 돌려주면 에이전트가 그대로 되보낸 다음 요청이 400 이 된다. 남은 호출은 결과를 본 모델이 다음 차례에 다시 부른다.
- **Qwen3 의 생각 뒤 빈 줄**: 생각을 뗀 답이 '\n\n' 으로 시작해 호출만 있는 답의 content 가 null 이 아니었다 → 생각을 뗀 답의 맨 앞
  줄바꿈을 뺀다(틀의 content.lstrip('\n') 과 같은 몫).
- **tool_choice none 의 생각**: 도구를 보냈으나 none 이면 생각이 content 에 섞였다 → 생각 떼기의 조건을 'tools 를 보낸 요청'으로.
- **문맥을 크게 두면 Qwen 이 불러와지지 않던 결함**(전부터 있던 것 — 이 PC 의 최대 문맥을 재다 찾음): 설정의 문맥을 모델의 위치 수보다
  크게(예: 131072) 두면 서버가 "최대길이는 64 의 배수, 모델의 위치 수까지"로 끝나 Qwen 넷이 모두 불러와지지 않았다(장치 메모리는 줄여
  주면서 모델의 최대는 줄여 주지 않았다) → 엔진.gl 이 모델의 위치 수(와 131072)에 맞춰 줄이고 그 말을 남긴다("모델의 위치 수에 맞춰
  문맥을 131072 → 32768 로 줄였다" — 앱의 영어 화면 번역도). 131072 라는 엔진의 위쪽 한계는 ③(긴 문맥)에서 다시 본다(1M 실험).
