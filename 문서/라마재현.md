# llama.cpp 실행의 비트 재현

이 문서는 단계마다 계획과 판정 기준을 결과보다 먼저 적는다. 결과가 나오면 상태 칸만 고친다.

## 목적

엔진을 바꾸지 않은 llama.cpp 의 실행을 GeulPU 의 GPU 커널로 비트까지 다시 계산한다. 1단계는 생성 걸음(토큰 하나), 2단계는
프롬프트 경로(여러 토큰의 ubatch)의 커널을 글(geul) 언어로 만들어 RTX 4070 Ti(CUDA)에서 돌린다.

- 앞선 일: CPU 참조 구현(Python, GeulPU 밖 — `E:\geulpu-work\xreplay`)이 같은 실행을 프롬프트 토큰만으로 처음부터 비트까지 다시
  계산했다(2026-11-05, 프롬프트 2,548토큰 + 생성 2걸음, 값 4,972,032개 불일치 0). 재현 커널은 그 참조의 연산 순서를 그대로 옮긴다.
- 대상(고정): llama.cpp b12008 공식 Windows CUDA 13 빌드 · RTX 4070 Ti(sm_89, SM 60) · Qwen3.5-9B Q4_K_M ·
  `llama-server -np 1 -fa on --no-cache-prompt --cache-ram 0 -c 8192 -ngl 99`, 온도 0.

## 원리

- llama.cpp 의 CUDA 커널은 `-use_fast_math` 로 빌드됐다: 짧은실수 연산은 비정규수를 버리고(.ftz), 나눗셈 · 역수 · 제곱근 역수 · 지수 ·
  로그 · 사인 · 코사인은 GPU 의 근사 명령(MUFU)이다. 컴파일러가 곱셈과 덧셈을 FMA 로 합친 자리는 SASS 에서 읽었다.
- 재현 커널은 같은 PTX 근사 명령을 쓰고, FMA 의 자리를 `곱해더하기` 로 정확히 둔다(GeulPU 의 PTX 뒷단은 `mul.rn` · `add.rn` 을
  내므로 ptxas 가 합치지 않는다). 더하는 차례(워프 butterfly · 블록 합 · 병렬 블록의 합치기)도 llama.cpp 그대로다.
- 텐서 코어(mma)는 같은 GPU 에서 같은 명령을 같은 피연산자로 부르면 같은 비트를 낸다. 재현 커널은 llama.cpp 가 명령 하나에 넣는
  k 묶음(16개)과 누적 차례를 그대로 둔다. 정수 mma 의 합은 정확하므로 그 뒤의 부동소수점 연산 차례만 맞추면 된다.
- 가중치는 GGUF 파일의 블록 그대로 장치에 둔다(llama.cpp 의 MMVQ 가 읽는 바이트와 같다).
- GeulPU 의 정밀도 계약 · 기존 모듈 · 출력 비트는 바꾸지 않는다. 재현 모듈은 따로 만든다.

## 2단계 — 프롬프트 경로(CUDA)

프롬프트 토큰만 가지고 상태 0 에서 시작해, llama.cpp 가 프롬프트를 처리한 계산과 그 뒤의 생성 걸음을 모두 GPU 커널로 다시 계산한다.

- 서버가 프롬프트를 나누는 모양: 체크포인트를 위해 끝에서 4 + 512토큰 · 4토큰 앞에서 끊고, 한 덩어리는 2,048토큰을 넘지 않는다.
  덩어리 안에서 ubatch 는 512토큰씩이다. 예: 2,548토큰 → (0–2032: 512 · 512 · 512 · 496) · (2032–2544: 512) · (2544–2548: 4).
- 토큰이 9개 이상인 ubatch: 행렬곱은 MMQ, gated delta net 은 64개 이상이면 덩어리 판(토큰 16개씩), flash attention 은 mma 판.
  8개 이하: 행렬곱은 열마다 MMVQ, gated delta net 은 토큰 차례로, flash attention 은 mma 의 4토큰 설정(3–4개).
- 마지막 ubatch 의 마지막 층은 출력 행 하나만 FFN 으로 보내고, 출력 행이 없는 ubatch 의 마지막 층은 KV 캐시만 채운다(그래프의 `get_rows`).

### 알게 된 것

- MMQ 의 열 타일 폭 J 는 8 씩 모두가 아니라 설정표(`mmq-config-ampere.cuh`)에 있는 폭만 후보다: 8 · 16 · 24 · 32 · 40 · 48 · 64 · 80 ·
  96 · 112 · 128(가중치 행이 128 의 배수가 아니면 8 · 16 · 32 · 64 · 128). 처음에 8 씩 모두로 읽어 464 · 396 · 306 토큰에서 120 · 104 를
  골랐고(llama.cpp 는 128 · 112), 열이 다른 타일에 들어가 stream-k 경계가 달라졌다.
- 서버(콜백 없음)는 FFN 의 gate · up 행렬곱과 SwiGLU 를 MMQ 하나로 합친다 — 두 가중치의 형식 · 모양이 같고, 합친 판의 타일(행 64 × 열 J)로
  센 효율이 90 % 이상일 때(`ggml_cuda_mmq_fusion_is_efficient`). 합친 판은 타일마다 블록 하나라 K 를 나누지 않는다. 153 · 248 토큰은
  합친 판의 효율이 91 % 라 합치고, 합치지 않은 판은 80 % 라 stream-k 로 K 를 나눠 비트가 달라졌다. 합친 판의 SwiGLU 는 up · silu(gate) —
  따로 도는 판(silu(gate) · up)과 값이 같다.
- 노드 기록(cb_eval)을 켜면 그 노드는 합치기에서 빠진다. 그래서 커널마다의 대조(2-1)는 합치지 않은 판과, 끝에서 끝(2-2 · 2-3)은 서버와 같은
  합친 판과 견준다. 진단 때 0 · 3층을 기록하며 돌린 하네스의 로짓이 서버와 달랐던 것도 기록한 층이 합치기에서 빠졌기 때문이다.
- 생성 걸음의 flash attention vec 병렬 블록 수는 KV 길이에 따라 바뀐다(launch_fattn: ntiles_KV = ⌈nkv / 256⌉, SM 당 2 블록, 파도 효율이
  가장 좋은 첫 값 — 2,560 → 7, 3,840 이상 → 15).
- llama.cpp 는 날을 넘겨서도 같은 비트를 낸다: 11-05 에 다시 기록한 코딩 요청의 앞 9줄이 11-04 의 하네스 A 와 같다.

## 3단계 — 다른 제조사(Vulkan)

RTX 4070 Ti 에서 돈 llama.cpp 의 실행을 Vulkan 으로, 다른 제조사의 GPU(이 PC 의 Intel UHD 770)에서 비트까지 다시 계산한다.

- 원리: 재현 커널의 글(geul) 소스는 그대로 둔다(소스 하나, 뒷단 둘, 같은 비트). PTX 뒷단은 4070 Ti 의 명령을 그대로 내고, SPIR-V
  뒷단은 그 명령의 셈을 기본 연산 · 정수 연산으로 흉내 낸다. 짧은실수의 기본 연산(비정규수 버림 · FMA 의 자리)은 SPIR-V 뒷단이 이미
  규칙 R 로 PTX 와 같게 낸다. 호스트도 그대로 — `쿠다.gl` 대신 `벌칸.gl` 을 포함한 판을 하나 더 빌드한다.
- 흉내 낼 것:
  - 근사 명령(MUFU, .approx.ftz.f32): ex2 · rcp · rsqrt · lg2 · sin · cos — 공개 비트 모델 ptx-math(MIT)의 표와 정수 셈. sm_89 에서
    입력 2^32 개 모두가 맞는 것은 타당성 시험 ②에서 확인했다. sin · cos 의 범위 줄이기는 64비트 실수 셈이라(UHD 770 의 Vulkan 에는
    64비트 실수가 없다) 정수 셈으로 옮긴다.
  - 0 쪽 반올림 덧셈(add.rz) · f32 → f16 / bf16 변환(가장 가까운 짝수 쪽) · f16 → f32.
  - 텐서 코어 mma m16n8k16: f16 곱 · f32 누적, f16 곱 · f16 누적, bf16 곱 · f32 누적 — 공개 비트 모델 MMA-Sim(MIT)의 Ada 모델(곱 8 개 +
    c 를 최대 지수에 맞춰 24비트로 0 쪽 자르기 → 정확한 합 → 출력 형식으로 반올림, k 16 은 8 개씩 두 번). 피연산자는 서브그룹 셔플로
    모은다(정수 mma 는 이미 그렇게 흉내 낸다 — 합이 정확하다).
- UHD 770 의 공유 메모리는 32 KB 라 gated delta net 덩어리 판(36 KB)을 그 안으로 줄인다(셈은 그대로).

### 알게 된 것

- 흉내는 Intel UHD 770 에서도 맞는다: 3-1 · 3-2 를 마지막 판으로 UHD 770 의 Vulkan 에서도 돌려 4070 Ti 의 CUDA 와 견주었다 — 근사 명령 ·
  e^x · f16 · bf16 변환 · 반실수아래 · 반실수위는 2^32 개 모두, mma 세 형식은 형식마다 출력 134,217,728 개가 같다. 영쪽더하기의 시험 판은
  마지막 판에서 드라이버의 컴파일러가 0 으로 나누기로 멈춰 보지 못했다(앞 판의 버퍼 입력 판은 쌍 16,777,216 개가 같았다 — 재현 커널 안의
  것은 3-4 의 UHD 770 이 덮는다). 다른 것은 f16 → f32 의 NaN 하나: 기존 fpext 의
  낮춤(GLSL UnpackHalf2x16)이 UHD 770 에서는 NaN 의 가수를 지키고(0x7FFFE000) sm_89 는 늘 0x7FFFFFFF 를 낸다. 재현 커널의 반실수아래 ·
  반실수위는 정수 셈이라 같고, 기존 모듈을 바꾸지 않으려고(3-5) fpext 는 그대로 둔다 — NaN 이 나오는 실행이 아니면 닿지 않는다.
- UHD 770 의 셰이더 컴파일러(드라이버 32.0.101.7088)가 시험 판 둘을 틀리게 옮겼다: 고리 몸 안에 갈래가 여럿(16 가지 사슬)이고 64 비트
  정수 섞기가 앞에 있는 판에서 갈래를 잘못 탔고(m = 0 인 입력이 m = 1 의 값을 받음 — 작게 줄인 판들은 맞다), 갈래 없이 다시 쓴 판은
  컴파일하다가 0 으로 나누기로 멈췄다. 시험 판은 갈래 없이 쓰고 입력을 버퍼로 주는 판으로 대신 보았다(영쪽더하기 쌍 16,777,216 개 —
  모두 같다). 재현 커널에서 같은 일이 나면 3-4 의 UHD 770 이 드러낸다.
- 재현 커널은 mma 를 펼쳐 쓴다(FA mma 64 열: mma 96 곳, gated delta net 덩어리: 180 곳). 흉내를 자리마다 펼치면 판 하나가 SPIR-V
  낱말 300 만 · 394 만 개라, 흉내를 커널 모듈마다 함수 하나로 두고 부른다. 근사 명령 · 반실수 묶기도 함수로 두어(FA mma 64 열은
  반실수둘묶기를 264 곳에서 부른다) 16 만 · 20 만 개, 모듈 전체는 5.0 → 3.4 MB.
- UHD 770 의 드라이버는 판을 처음 쓸 때 컴파일하는데, DontInline 함수도 부르는 자리마다 펼치는 듯했다 — 흉내 함수의 몸이 펼친
  셈(명령 3,700 개쯤)일 때는 FA mma 64 열 판 하나가 한 시간을 넘겨도 끝나지 않았다(셔플을 부르는 자리로 옮겨도 같았다). 몸을
  펼치지 않는 SPIR-V 고리와 함수 변수로 다시 쓰자 FA mma 16 열 30 초 · 64 열 69 초에 끝난다. mma 흉내 자체도 UHD 770 에서 5 배
  빨라졌다(3-2 의 형식마다 7.5 → 1.4 초, 4070 Ti 의 Vulkan 은 0.4 초 그대로).
- UHD 770 에서 multi_turn 이 생성 9걸음(위치 1189)부터 틀렸다(프롬프트 끝 · 1–8걸음은 0). 9걸음의 llama.cpp 노드 값을 기록해 커널마다
  견주니 생성 걸음 flash attention(vec)만 달랐고, 같은 입력으로 두 GPU 를 견주니 최댓값 · 합은 같고 V 를 쌓는 부분 합만 — 8 개 묶음의
  첫 차원에서 — 마지막 비트가 달랐다(부분 합 28,672 개 가운데 322 개). 까닭은 SPIR-V 뒷단: 곱해더하기를 GLSL Fma 로 내면서 NoContraction
  을 달지 않았고, 그러면 GLSL.std.450 은 a · b + c 의 정밀도만 요구해 드라이버가 곱 · 합을 따로 반올림해도 된다. NVIDIA 의 드라이버는
  늘 한 번에 셈하고 UHD 770 은 몇 자리를 나눠 셈했다. 달면 그 판은 0 — 뒷단의 고침은 따로 #254(모든 모듈의 SPIR-V 가 바뀌고, 4070 Ti 의
  Vulkan 은 앱의 재현성 검증 32/32 · 32/32 그대로). 이 단계의 판정은 그 고침 위에서 한다.
- UHD 770 의 컴파일: 모듈이 바뀌면 처음 한 번 판 31 개에 3 분쯤(FA mma 둘 · GDN 덩어리가 1 분 안팎씩). 같은 프로그램의 다음 프로세스는
  드라이버의 디스크 캐시가 건너뛰고, 파이프라인 캐시(`GEULPU_VULKAN_CACHE`)를 주면 다른 프로그램끼리도 나눈다(같은 판 31 개 183 → 0.9 초,
  math 의 프롬프트 246.7 → 48.1 초 — 비트는 같다).
- gated delta net 덩어리 판을 32 KB 로 다시 짠 뒤 CUDA 에서도 2-1 의 그 판 · 2-3 의 요청 10개(601,182,720 값)를 다시 돌려 불일치 0.
- 4070 Ti 에서 Vulkan(흉내)의 속도(기록만): 마지막 판으로 프롬프트는 llama.cpp 의 158–476 배, 생성 걸음은 1.66–1.71 배(23.9–25.0 ms).
  mma 흉내의 몸을 펼친 판은 프롬프트가 25–93 배였다 — 고리 몸은 UHD 770 이 판을 컴파일할 수 있게 한 대신 함수 변수가 지역 메모리로
  가 NVIDIA 에서 느리다. 프롬프트의 시간은 거의 모두 텐서 코어 흉내다(재현 자체는 CUDA 에서 llama.cpp 의 3–4 배).

## 4단계 — 영수증과 검증 도구(앱)

llama.cpp 를 쓰는 사람이 고치지 않은 llama-server 로 요청을 돌리며 기록(영수증)을 남기면, 나중에 GeulPU 앱이 그 영수증만으로 다시 계산해
서버가 낸 토큰과 로그 확률이 비트까지 같은지 판정하고, 다시 계산한 실행을 앱의 디버거에서 본다. 대상은 3단계까지의 설정 그대로(b12008
CUDA · 4070 Ti · Qwen3.5-9B Q4_K_M · 한 슬롯 · 프롬프트 캐시 끔 · 온도 0 · `/completion`)이고, 윈도에서 돈 서버의 영수증을 윈도에서
재현한다(서버의 로그 확률은 그 OS 의 C 런타임으로 셈한다). 설정 · 모델 · 엔진 · GPU 를 넓히는 일은 5단계부터.

- 영수증(`geulpu-llama-receipt/1`, JSON 파일 하나):
  - 엔진: llama-server 의 `build_info`(`/props`) · 백엔드 · OS.
  - 장치: 이름 · SM 수 · compute capability — 일 나누기가 SM 수에 따른다(앱의 장치 확인, 같은 컴퓨터).
  - 모델: 경로 · 크기 · SHA-256.
  - 서버 설정: 문맥 · 슬롯 수(`/props`), n_batch · n_ubatch · flash attention · 프롬프트 캐시(서버를 띄운 명령줄 — 앱 설정에 적는다).

### 알게 된 것

- llama-server 의 로그 확률 칸(`completion_probabilities`)은 생성 걸음마다가 아니다. 생성한 글이 UTF-8 글자 가운데서 끝나는 걸음은 칸이
  없고(server-context.cpp `process_token` — `validate_utf8` 가 글이 덜 끝났다고 하면 `add_token` 을 부르지 않는다), 그 바이트는 다음 칸의
  `token` · `bytes`(보낸 글 `text_to_send`)에 합쳐진다. 그 칸의 `id` 와 로그 확률은 글자를 끝낸 토큰의 것이다. 요청 10개 가운데
  ko_translate(칸 254 / 걸음 256)와 json_extract(251 / 256)가 그렇다 — 처음에는 칸을 걸음 차례로 맞대어 그 걸음부터 '다름'으로 나왔다.
  대조는 모델 파일의 어휘로 토큰마다의 바이트를 llama.cpp 와 같이 셈해(`token_to_piece`, special = false — 보통 토큰은 GPT-2 바이트 표를
  되돌리고 사용자 정의 토큰은 글 그대로, 제어 토큰은 빈 조각) 서버의 규칙으로 칸을 맞춘다. 칸이 없는 걸음은 토큰만 견준다.
  `시험/라마영수증.py --칸` 이 영수증 10개 모두에서 칸 수 · 번호가 서버와 맞고 이은 바이트가 응답의 글과 같음을 본다.
- 다시 계산한 값은 CUDA 와 Vulkan(4070 Ti)에서 같다 — 칸을 잘못 맞댄 대조에서도 두 층의 다른 값 수가 같았다(ko_translate 2,709).
- 요청에 `n_probs` 가 있으면 온도 0 이어도 서버의 고르기 사슬 끝은 greedy 가 아니라 dist(seed)다(common/sampling.cpp — 확률을 달라는
  요청에서는 분포 고르기를 둔다). 온도 0 은 사슬 차례(top_k 의 MSVC partial_sort)에서 처음 만난 가장 큰 logit 만 남기므로, 맨 위 logit 이
  정확히 같은 후보가 둘이면 서버는 그 차례의 앞을 고르고 이 대조는 작은 번호를 본다 — 요청 10개에는 없었고, 5단계의 사슬 흉내가 온도 0 도
  같은 길로 본다.
- 기록기가 더하는 것(`n_probs` 20 · `return_tokens` · `cache_prompt` false)은 실행 조건을 바꾼다(30단계에 바로잡음 — 앞에는 "토큰을
  바꾸지 않는다"고 적었다): 요청에 `n_probs` 가 있으면 온도 0 에서도 고르기 사슬 끝이 greedy 가 아니라 dist 라(위), 맨 위 logit 이 정확히
  같은 후보가 둘인 걸음에서는 기록기가 없을 때와 다른 토큰을 고를 수 있다. 4-1 이 보인 것은 이 요청 10개에 그런 걸음이 없었다는 것과,
  기록기를 거친 응답이 `n_probs` 를 준 직접 요청(2단계의 기록)과 같다는 것이다 — `n_probs` 를 주지 않은 요청과 같다는 것은 아니다.
- 검증 한 번에 걸린 시간(요청 하나 — 모듈은 처음 한 번만 만든다): CUDA 5 ~ 12 초, Vulkan(4070 Ti) 18 ~ 540 초(long_doc 의 프롬프트 6,396
  토큰이 가장 길다), Intel UHD 770 293 ~ 769 초(짧은 요청 셋 — 처음 요청은 셰이더 컴파일까지).
- 4-3 의 n_ubatch 256 은 로짓의 비트를 첫 걸음부터 거의 모두 바꾸지만(다른 값 5,339 / 10,752) 고른 토큰은 하나만 바꾼다 — 토큰만 견주는
  재현성 검사로는 놓칠 차이를 비트 대조가 가려낸다.

## 5단계 — 설정 넓히기: 온도 > 0(시드를 준 요청)

실제 쓰임의 요청은 대개 온도 > 0 이다. llama-server b12008 은 토큰 고르기를 CPU 에서 한다(`--backend-sampling` 은 기본 끔). 로짓은
4단계까지로 비트 그대로이니, 서버의 고르기 사슬을 그대로 옮기면 영수증의 토큰이 그 사슬과 시드가 고른 것인지 판정할 수 있다.

- 사슬(서버의 기본 `samplers` — 응답의 `generation_settings` 가 실제 값을 적는다): penalties · dry · top_n_sigma · top_k · typ_p · top_p ·
  min_p · xtc · temperature → dist(seed). 기본값이면 penalties(repeat 1 · freq 0 · present 0) · dry(0) · top_n_sigma(−1) · typ_p(1) ·
  xtc(0)는 아무것도 하지 않는다. 그 앞에 reasoning budget(기본 끔) · logit_bias(요청의 것과 어휘의 suppress 토큰 — 있으면).
  - top_k(k): `llama_token_data_array_partial_sort_inplace` — k ≤ 128 이면 MSVC `std::partial_sort`(logit 큰 차례 — 4단계의 흉내와 같은
    비교), 크기를 k 로, 정렬됨.
  - top_p(p): softmax(맨 앞이 최댓값, float 의 expf · 합 · 나눗셈) → 차례대로 float 누적이 p 이상이고 min_keep 이상인 첫 자리까지.
  - min_p(p): 정렬된 갈래 — 맨 앞 logit + logf(p) 보다 작고 min_keep 이상인 첫 자리에서 자른다.
  - temperature(T): logit /= T(0 이하면 처음 만난 가장 큰 logit 만 남김).
  - dist(seed): 맨 앞이 최댓값, float 의 expf, double 합, `std::uniform_real_distribution<double>(0, 1)` 한 번(std::mt19937 을 두 번
    뽑음)으로 누적이 합 × 난수 이상인 첫 자리. 후보가 하나여도 난수는 한 번 쓴다.
  - 요청에 `n_probs` 가 있으면 온도 0 이어도 사슬 끝은 dist 다(4단계의 '알게 된 것') — 그래서 온도 0 의 영수증도 이 사슬로 견준다(맨 위
    동점이면 서버처럼 정렬 차례의 앞).
- MSVC 의 `generate_canonical<double, 53>`: VS 2022 17.12 부터(P0952R2 — microsoft/STL #4740 · #4850) S = (g2 << 21) + (g1 >> 11),
  결과 S × 2⁻⁵³. 그 전에는 double 로 g1 + g2 · 2³² 를 더해 2⁶⁴ 로 나눴다. 둘의 차이는 2⁻⁵³ 안이라 누적의 경계가 그만큼 가까운 걸음에서만
  고른 토큰이 갈린다 — 지금의 MSVC(17.12 부터)를 따른다.
- 시드: 요청의 `seed` 가 있어야 한다(없으면 서버가 random_device 로 고른다 — 재현할 수 없다고 판정한다).
- 받지 않는 것(시작 전에 까닭과 함께): 사슬의 차례 · 값이 기본과 다른 것(penalties · dry · top_n_sigma · typ_p · xtc · mirostat ·
  dynatemp · adaptive-p), top_k 가 1 … 128 밖(정렬되지 않은 갈래), logit_bias · ignore_eos · grammar, 어휘의 suppress 토큰.

### 알게 된 것

- 고르기의 값을 바꾼 영수증에서 다름은 고른 토큰에만 나온다 — 로그 확률은 서버가 날 로짓에서 셈하므로(`post_sampling_probs` 끔)

## 6단계 — 모델 넓히기: 같은 구조의 다른 크기(Qwen3.5-4B)

5단계까지는 Qwen3.5-9B 하나였다. 같은 구조(qwen35)의 다른 크기는 행렬의 모양이 달라 llama.cpp 의 일 나누기(MMQ 의 타일 · stream-k,
MMVQ, RMSNorm 의 블록)가 달라지는지, 재현 호스트에 9B 의 모양이 박힌 곳이 없는지를 본다. 미리 본 실험(11-06)에서 4B · 0.8B 영수증은
기록되었지만 호스트가 시작에서 멈췄다 — 작은 모델은 출력층을 따로 두지 않는다(tied — `output.weight` 없이 `token_embd.weight` 를
쓴다, llama.cpp 의 `TENSOR_DUPLICATED`).

- 4B 와 9B 의 차이(GGUF): 폭 2560(9B 4096) · FFN 9216(12288) · 출력층 tied · `token_embd` 가 Q6_K(9B Q4_K). 주의(머리 16/4 × 256) · GDN
  (inner 4096 · 무리 16 · 상태 128 · dt 32) · 층 32 · 주의 간격 4 는 같다. 0.8B 는 머리 8/2 · SSM 2048/16 · 24 층 · Q8_0 이라 그다음.
- 바꿀 것:
  - 토큰 임베딩은 CPU 의 get_rows(입력층은 `-ngl 99` 에서도 CPU) — Q6_K 의 `dequantize_row_q6_K`: d · sc · (q − 32)(곱은 정확 — 유효
    자리 11 + 7 + 6 ≤ 24). 판 `라마임베딩Q6_K` 를 더한다.
  - RMSNorm 의 블록: llama.cpp 의 벡터 판은 n4 = 열 / 4 로 고른다(≤ 32 → 32, ≤ 128 → 128, ≤ 256 → 256, ≤ 512 → 512, ≤ 1024 → 1024 …). 호스트가
    열 4096 일 때만 1024 를 골랐다 — 폭 2560 도 1024(스레드 640 개가 값을 읽음). 9B 의 고름은 그대로다.
  - 출력층이 없으면 `token_embd.weight` 를 출력 행렬로(어휘 · 폭도 거기서).
  - (해 보고 더한 것) 행렬-벡터 곱(MMVQ)의 반복을 llama.cpp 의 꼴로 — 아래 '알게 된 것'.
  - (해 보고 더한 것) 활성값 양자화(MMQ)에서 amax 가 0 인 묶음을 llama.cpp 처럼 — 아래 '알게 된 것'.

### 알게 된 것

- 4B 에서 처음 어긋난 것은 행렬-벡터 곱(MMVQ)이었다 — 첫 검증에서 요청 10개가 모두 0 걸음부터 달랐다. llama.cpp 의 mul_mat_vec_q 는 행의
  블록을 `kbx = tid / (qi / vdr)` 부터 `blocks_per_iter`(Q4_K · Q5_K · Q6_K 8, Q8_0 32)씩 건너며 `kbx < blocks_per_row` 까지 돈다. 9B 의 행
  (폭 4096 = 슈퍼블록 16 개)은 8 의 배수라 반복 수를 정해 둔 판도 같았지만, 4B 의 폭 2560(슈퍼블록 10 개)에서는 뒤 반복의 스레드가 다음
  행의 블록을 읽었다. 반복을 llama.cpp 의 꼴로 바꾸니 7개가 같았다.
- 남은 셋은 셈이 아니라 범위 검사였다. 프롬프트가 여러 ubatch 로 나뉘며 토큰 수가 홀수인 ubatch 가 생기는 요청(multi_turn 1,181 토큰 →
  512 · 153 · 512 · 4)에서, 활성값 양자화(quantize_mmq_q8_1)의 스레드 수 N · K / 4 = 153 · 640 이 블록(256)의 배수가 아니다. 마지막 블록의
  일 없는 스레드가 0 을 읽어 amax = 0 → 127/0 · 0 = NaN 을 정수로 바꾸며 글(geul) 언어의 범위 검사(모듈의 오류 칸)를 켰다 — 쓰기는 막혀
  있어 출력은 같았다. 9B 는 K = 4096 이라 N · 1024 가 늘 256 의 배수였다. llama.cpp 에서도 값이 모두 0 인 묶음은 q = 0(NaN 의 정수 바꿈),
  d = 1/∞ = 0 이므로, 판이 amax = 0 이면 q 의 셈에만 0 을 곱한다(같은 0 — d 는 그대로 rcp(∞) = 0).
- 재현 호스트에 디버그를 두었다: 환경 변수 `GEULPU_LLAMA_CHECK` 가 있으면 띄울 때마다 맞추고 모듈의 오류 칸을 봐서, 처음 켠 판의 이름 ·
  격자 · 층을 알린다(위의 셋을 이것으로 찾았다 — 1,984 번째 띄움, 둘째 ubatch 의 0층 qkv).

## 7단계 — 설정 넓히기: 기본 설정의 서버(슬롯 4 · 통합 KV · 프롬프트 캐시)

6단계까지의 검증은 슬롯 하나(-np 1)에 프롬프트 캐시를 끈(--no-cache-prompt) 서버만 받았다. llama-server b12008 의 기본은 다르다: -np
를 주지 않으면 슬롯 4 · 통합 KV(tools/server/server.cpp), 프롬프트 캐시 켬, 슬롯마다 체크포인트 32 개 · 최소 간격 8192, RAM 프롬프트
캐시 8 GiB(--cache-ram), 새 작업을 띄울 때 쉬는 슬롯을 RAM 캐시로 옮김(--cache-idle-slots). 에이전트처럼 한 대화를 이어 보내면 서버는 앞
요청이 남긴 KV · RS 상태에서 이어 셈한다 — 그 요청의 로짓은 앞 요청들의 셈(프롬프트 덩어리 · 생성 걸음 · 되살린 체크포인트)에 매인다.

- 서버의 캐시 셈(server-context.cpp): 새 요청의 n_past 는 슬롯의 토큰(앞 프롬프트 + 셈한 생성 토큰)과 겹치는 앞이다. 하이브리드
  메모리(qwen35)는 RS 를 되돌릴 수 없어, 겹침이 슬롯의 토큰보다 짧으면 체크포인트에서 되살린다 — 체크포인트는 프롬프트 끝에서
  4 + n_ubatch · 4 토큰 앞의 덩어리를 셈하기 전의 상태다. 겹침이 슬롯의 토큰 전부면 되살리지 않고 이어 간다. 응답의 timings.cache_n 이 그
  n_past 다.
- 미리 본 실험(11-06, 4B): 기본 설정 서버(-fa on · -c 16384)에 한 대화의 요청 다섯(잇기 둘 · 같은 프롬프트 · 생성 잇기)을 보냈다. 파이썬으로
  옮긴 서버의 셈이 다섯 모두의 cache_n · tokens_cached 를 맞혔다. 그 셈이 짓는 ubatch 사슬로 재현 호스트를 돌리니 요청마다 토큰 · 상위 20
  로그 확률이 비트까지 같았다(값 12,997 · 다른 값 0). 앞 요청의 생성 걸음은 사슬에서 토큰 하나의 ubatch 가 된다. 재현 호스트는 고치지 않는다.
- 더하는 것:
  - `앱/라마사슬.gl` — 한 슬롯의 캐시 셈(슬롯 고르기의 LCP 비율 · 남기는 몫, n_past, 체크포인트 되살리기 · 지우기 · 만들기, 덩어리 나눔,
    생성 걸음). GPU 없는 시험 `엔진/시험_라마사슬.gl` · `시험/라마사슬.py`(빠른 점검 4w).
  - 기록기: cache_prompt 를 더 이상 끄지 않는다(요청 · 서버 그대로). /slots 의 슬롯 상태, 슬롯 · 캐시 설정(통합 KV · 체크포인트 · RAM
    캐시 · LCP 비율 · 캐시 조각 재사용 · -fa), 기록 차례(recorder.seq)를 적는다.
  - 검증: 캐시를 쓴 영수증(cache_n > 0)은 같은 서버 · 같은 슬롯의 앞 영수증을 기록 차례로 모은다. 처음 요청(cache_n 0)부터 셈을 흉내
    내고, 영수증마다 흉내의 cache_n · 슬롯 토큰 수가 서버와 같을 때만 그 사슬로 다시 셈한다.
  - 받지 않는 것(까닭과 함께): 다른 슬롯도 쓰인 서버(통합 KV 의 KV 칸 자리 · RAM 캐시가 달라짐), 슬롯마다 KV 를 따로 둔 서버(-np N ·
    --kv-unified 없음), --cache-reuse, 슬롯 캐시의 절반 넘게 버리는 요청(RAM 캐시 저장 · 불러오기), 같은 슬롯의 처음 요청이 영수증에 없는
    사슬, 흉내와 서버가 다른 사슬.
  - -fa auto(기본)를 받는다 — 이 모델 · GPU 에서 켜지는지 서버 로그로 확인한다(7-1).

- 서버 로그의 슬롯 고르기 값이 흉내와 같다: c2 · c3 · c5 는 LCP 비율 0.98 · 0.984 · 0.999(남기는 몫 1.0)로 되살리지 않고 이어

  서버의 기본 로그 수준에는 그 고름이 찍히지 않는다.
- 통합 KV 에서 새 작업을 띄우면 서버는 쉬는 슬롯을 RAM 캐시에 저장하고 비운다(--cache-idle-slots, 기본 켬). 한 대화만 쓰는 동안은 쉬는
  슬롯이 비어 있어 아무 일도 없지만, 다른 대화가 끼면 앞 대화의 상태가 RAM 캐시를 거쳐 다시 올라오고 KV 칸의 자리가 바뀐다 — 그래서
  다른 슬롯이 쓰인 서버는 아직 받지 않는다.
- 같은 기록 때 · 차례의 영수증 사본(7-2 의 바꾼 영수증)이 자료 폴더에 함께 있으면 사슬이 사본을 고를 수 있다 — 흉내가 서버와 달라
  받지 않게 될 뿐 "같음"을 잘못 내지는 않는다. 7-2 뒤에 사본을 폴더 밖으로 옮기고 7-4 를 돌렸다.

## 8단계 — 모델 넓히기: 머리 수가 다른 크기(Qwen3.5-0.8B)

6단계의 4B 는 주의 · GDN 의 머리 수가 9B 와 같았다. 0.8B 는 머리 수가 다르다 — 주의 머리 8/2(9B · 4B 16/4) × 256, GDN 의 v 머리 16(9B · 4B
32) · k 무리 16(같음). 폭 1024 · FFN 3584 · 층 24 이고, 모든 텐서가 Q8_0(token_embd 포함)이며 출력층은 tied 다. 영수증 10개는 6단계를 앞두고
미리 기록해 두었다(슬롯 하나 · 캐시 끔 · 온도 0).

- 바꿀 것(재현 커널 · 호스트에 9B 의 머리 수가 박힌 곳):
  - flash attention — 벡터 판 · mma 판 · 두 합치기 판의 KV 줄 걸음(KV 머리 × 256)과 q · 출력의 머리 걸음을 인자(q 머리 수)로. 정수
    주소 셈만 바뀌고 실수 셈의 차례는 그대로다.
  - 호스트 — 벡터 판의 병렬 블록 수(launch_fattn 의 ntiles_dst = q 머리 수), mma 판의 타일 수(KV 머리 × 토큰 타일), KV 캐시의 크기.
  - GDN 덩어리 판 — v 머리 수 · k 무리 수를 인자로(g · beta · 출력의 걸음, q · k 의 머리 짝 h % k 무리).
  - RMSNorm 블록 256(n4 = 256 — 폭 1024)의 판 `라마RMS256`(같은 생성기에 블록 수만).
  - Q8_0 토큰 임베딩 `라마임베딩Q8_0` — CPU 의 dequantize_row_q8_0(q · d, 곱은 정확).
- 그대로인 것: MMVQ 의 작은 K 갈래(블록 수 < nwarps × blocks_per_iter — Q8_0 은 32 블록 미만)는 0.8B 의 K 1024 = 32 블록이라 들지 않는다.

## 9단계 — 설정 넓히기: 채팅 API(/v1/chat/completions)

에이전트 · 채팅 앱은 /completion 이 아니라 OpenAI 꼴의 채팅 API 를 쓴다. 서버는 채팅 템플릿으로 메시지를 프롬프트로 짓고, 프롬프트 캐시의
셈에 메시지 자리를 더 쓴다(server-context.cpp 4502 · 4541 · 4560 · 4578): 덩어리를 사용자 메시지 앞에서 끊고(마지막 사용자 메시지,
체크포인트가 없을 때, 마지막 체크포인트 + 최소 간격 뒤), 사용자 메시지에서 시작하는 덩어리는 프롬프트 가운데여도 체크포인트를 만든다.
메시지 자리는 템플릿 분석의 구분 글이 프롬프트 토큰에서 처음 맞는 자리다(common_chat_msg_delimiters::split — 구분 토큰열의 첫 토큰).
ChatML(Qwen)의 사용자 구분 글은 `<|im_start|>user` 다(chat-diff-analyzer.cpp detect_user_start_marker — 앞 턴의 끝 표지와 빈칸을 건너뛴다).

- 응답: 요청에 llama.cpp 의 `verbose` · `return_tokens` 를 더하면 OpenAI 꼴 응답의 `__verbose` 에 /completion 과 같은 꼴(생성 토큰 · 로그
  확률 · 고르기 값 · timings · id_slot · tokens_cached · 템플릿을 적용한 프롬프트)이 실린다. 로그 확률은 OpenAI 의 `logprobs` ·
  `top_logprobs`(20).
- 미리 본 실험(11-06, 4B): 기본 설정 서버에 채팅 API 로 한 대화 다섯(잇기 둘 · 같은 대화 · 앞을 고침)을 보냈다. 메시지 자리를 넣은 흉내가
  다섯 모두의 cache_n · tokens_cached 를 맞혔다 — 앞을 고친 요청은 사용자 메시지 시작(82)의 체크포인트로 되살렸다. 그 사슬로 재현하니
  토큰 · 로그 확률이 비트까지 같았다(값 9,881 · 다른 값 0).
- 같은 실험에서 RAM 프롬프트 캐시의 갈래도 보았다: 앞을 고친 요청은 슬롯 캐시의 절반 넘게 버려(남기는 몫 0.337) 서버가 슬롯을 RAM 캐시에
  저장했다가 불러오기를 찾았지만, 더 맞는 저장본이 없어 슬롯이 그대로였다(server_prompt_cache::load — 남기는 몫 · LCP 비율이 둘 다
  엄격히 커야 불러온다). 7단계는 이 갈래를 받지 않았다. 이제 사슬에서 저장했을 상태들 가운데 더 맞는 것이 없으면 받는다.
- 더하는 것:
  - `앱/라마사슬.gl` — 사용자 메시지 자리(끊기 · 체크포인트), RAM 캐시 고침의 흉내, 슬롯이 하나인 서버의 LRU 갈래(같은 슬롯).
    GPU 없는 시험 4w 에 메시지 자리 · 슬롯 하나의 사례.
  - 기록기: POST /llama/v1/chat/completions 를 넘기며 `logprobs` · `top_logprobs` · `return_tokens` · `verbose` 를 더한다. 영수증의 응답은
    `__verbose`, 프롬프트 토큰은 그 프롬프트를 /tokenize 로 짓는다. 템플릿의 사용자 구분 글은 /apply-template 로 그린 대화(사용자 · 도우미 ·
    사용자)에서 llama.cpp 의 분석과 같게 찾아 토큰으로 적는다.
  - 검증: 채팅 영수증의 사용자 메시지 자리를 프롬프트 토큰에서 찾아 사슬에 넣는다. 스트리밍 응답 · 도구(grammar) · 구분 글을 찾지 못한
    템플릿은 까닭과 함께 받지 않는다.

### 알게 된 것

- 채팅 API 의 응답은 llama.cpp 의 `verbose` 를 주면 /completion 과 같은 꼴을 `__verbose` 에 함께 싣는다 — 기록기는 그것을 영수증의 응답으로
  쓰고, 검증은 /completion 의 길을 그대로 탄다. 프롬프트 토큰은 `__verbose` 의 프롬프트(템플릿을 적용한 글)를 다시 토큰으로 지은 것으로,
  수가 서버의 tokens_evaluated 와 모두 같았다.
- 메시지 자리가 셈을 바꾼다: 첫 요청부터 덩어리가 사용자 메시지 앞(25 · 82 · 165 …)에서 끊기고, 앞을 고친 요청은 끝에서 4 토큰 앞이 아니라
  사용자 메시지 시작의 체크포인트로 되살린다. /completion 의 흉내만으로는 채팅 영수증을 맞힐 수 없다.
- RAM 캐시 갈래는 드물지 않다 — 앞을 고친 요청 하나가 슬롯 캐시의 절반 넘게 버렸다(남기는 몫 0.42). 서버는 슬롯을 저장하고 더 맞는
  저장본을 찾지만 그 사슬에는 없어 슬롯을 그대로 썼다.

## 10단계 — 모델 넓히기: 다른 구조(dense Qwen3-8B)

Qwen3.5 는 GDN 층 셋에 게이트 어텐션 층 하나가 되풀이되는 하이브리드 구조다. Qwen3(qwen3)은 GDN 이 없는 dense 구조로 Llama · Mistral ·
Qwen2.5 와 같은 꼴이다: 모든 층이 어텐션(머리 32/8 × 128 — GQA 4) · 머리마다 Q · K 의 RMSNorm · NEOX RoPE(회전 차원 = 머리 차원 128,
θ 1,000,000) · SwiGLU FFN · 출력층 따로(tied 아님). 대상은 Qwen3-8B Q4_K_M(36 층 · 폭 4096 · FFN 12288). 영수증 10개는 2단계의 프롬프트를
기록기로(슬롯 하나 · 캐시 끔 · 온도 0) 남겼다.

- 머리 차원 128 이 바꾸는 것(llama.cpp b12008):
  - flash attention vec(생성 걸음) — 레인마다 원소 D/8, 공유 판 · 합치기의 걸음 D, 병렬 블록 수의 KV 묶음 = D(launch_fattn 의
    nbatch_fa), SM 당 블록 3(D 256 은 2 — vec 커널의 레지스터).
  - flash attention mma(프롬프트) — sm_8x 설정표의 (128, 열): 스레드 128, KV 묶음 128(열 8) · 64(열 16 · 32 · 64). D 256 과 무리
    나눔이 다르다(열 8 은 얇은 타일에 워프 4 개가 KV 를 16 개씩 번갈아, 열 16 은 넓은 타일에 워프 4 개, 열 32 는 워프 둘씩). CPU 참조
    (fa_mma.py)를 D · 열로 일반화해 덤프와 맞춘 뒤 생성기로 옮겼다. 덤으로 D 256 의 열 8(토큰 2)도 옮겼다(열 32 는 공유 판이 32 KB 를
    넘어 아직).
  - RoPE — NEOX 의 셈은 지금 판과 같아 머리 크기(블록)만 인자로.
- 호스트(재현 호스트 — llama.cpp 의 src/models/qwen3.cpp 그대로): general.architecture 로 구조를 고르고, qwen3 은 모든 층을 게이트
  없는 어텐션 층으로(FFN 앞 정규화는 ffn_norm). 상수는 qwen3.* 열쇠로(rope.dimension_count 가 없으면 key_length).
- 프롬프트 캐시의 흉내(앱/라마사슬.gl): dense 모델의 메모리는 아무 자리에서나 되돌릴 수 있어(서버의 COMMON_CONTEXT_SEQ_RM_TYPE_PART)
  서버가 체크포인트를 만들지 않는다 — 프롬프트를 끝에서 4 · 4 + n_ubatch 토큰 앞에서 끊지 않고 n_batch 로만 끊으며, 이어지는 요청은
  n_past = 겹치는 앞(체크포인트 되살리기 없음, 프롬프트 전부가 캐시면 n_past − 1). 앱은 모델 파일의 구조로 이 갈래를 고른다. 캐시의
  끝이 ubatch 가운데인 요청(그 ubatch 를 다 셈한 뒤 되돌려야 한다)은 아직 받지 않는다.

### 알게 된 것

- 노드 대조가 모두 0 이어도 끝에서 끝이 다를 수 있다. 하네스는 cb_eval 로 노드를 하나씩 돌리는데, 그러면 llama.cpp(ggml-cuda)가 노드
  여럿을 한 커널로 엮는 합치기(fusion)가 꺼진다. 서버는 엮어 돈다. qwen3 에서 서버는 Q · K 의 RMS_NORM · MUL · ROPE(K 는 · VIEW ·
  SET_ROWS — KV 캐시 쓰기까지)를 한 커널(rms_norm_mul_rope_f32<256>)로 돌리고, 그 셈이 따로 도는 판들과 비트가 다르다: 정규화의
  제곱합은 스레드마다 한 칸 → 블록 256 의 block_reduce(따로 도는 RMSNorm 은 블록 32 · 스레드마다 float4), RoPE 의 뒤 칸은
  fma(x₁, c, RN(x₀ · s))(따로 도는 rope_neox 는 fma(s, x₀, RN(c · x₁))). Qwen3.5 는 IMRoPE 와 띄엄 q(게이트와 섞인 행)라 이 합치기를
  타지 않았다. 판 둘(`라마RMS한칸256` · `라마RoPE엮음128` / `라마RoPE여럿엮음128`)을 더해 맞췄다.
- 찾는 법: 하네스의 `--only <정규식>` 은 맞는 노드만 묻고 사이의 노드는 한 그래프로 돌려 합치기가 그대로다. 층마다의 출력(l_out)과
  재현 호스트의 층 덤프(`GEULPU_LLAMA_DUMP=<폴더>` — 첫 ubatch 의 층 출력과 0층의 RoPE · FA 출력)를 견주면 처음 갈린 층 · 노드가
  나온다. 이번에는 0층의 두 토큰 행(자리 61 · 68 — Q 가 반실수로 바뀔 때 갈린 것)에서 시작해 RoPE 출력이 위치 0 을 빼고 모두 달랐다.
- 하이브리드에 맞춘 흉내의 끊음(끝에서 516 · 4 토큰 앞)은 dense 서버와 ubatch 모양이 달라(2373 토큰: 서버 2048 + 325, 흉내 6 덩어리)
  값의 절반이 갈렸다. 모델의 메모리 꼴이 프롬프트의 ubatch 를 정한다.
- 넓은 타일 · 무리 4(D 128 의 열 16)의 워프 합치기는 meta 가 레인마다 둘이라 행 합이 fma(cs_k · rs_k 의 첫 곱, RN(둘째 곱)) 뒤 xor 16
  덧셈이다(SASS 는 첫 곱을 FFMA 에 넣는다 — 토큰 3 덤프로 가렸다). 블록 수는 공유 메모리(2 단 KV + 가림, 합치기 판, 블록마다 1 KiB
  예약)로 SM 당 2(열 8 은 1).

## 11단계 — 모델 넓히기: 다른 구조(llama — Llama-3.1-8B)

llama(Llama 2 · 3, Mistral 의 구조 이름)는 가장 많이 쓰이는 dense 구조다. qwen3 과 같은 꼴(모든 층 어텐션 · SwiGLU FFN · 출력층 따로)
이지만 Q · K 정규화가 없고 RoPE 가 보통(NORM — 이웃한 두 칸이 짝)이며, Llama 3.1 은 긴 문맥 늘림(llama3)을 freq_factors 텐서
(`rope_freqs.weight`, 64 칸)로 싣는다. 대상은 Meta-Llama-3.1-8B-Instruct Q4_K_M(32 층 · 폭 4096 · FFN 14336 · 머리 32/8 × 128 — GQA 4,

(셋은 EOS 로 끝남).

- llama.cpp b12008(src/models/llama.cpp)에서 qwen3 과 다른 것:
  - Q 는 따로 도는 rope_norm<forward, ff>, K 는 ROPE · VIEW · SET_ROWS 를 엮은 판(같은 rope_norm 이 반실수로 바로 KV 캐시에) — 셈은 같다.
    정규화가 없어 RMS_NORM · MUL · ROPE 합치기는 없다.
  - rope_norm 의 셈(sm_89 SASS): θ = ((I2F(위치) · ex2((I2F(2j) · 0.5) · lg2(ts))) · rcp(ff[j])) · freq_scale, 짝의 앞 =
    fma(c, x0, −RN(s · x1)), 뒤 = fma(s, x0, RN(c · x1)) — 새 판 `라마RoPE보통128` · `라마RoPE보통여럿128`(ff 인자, 없으면 1).
  - kq_scale 은 attention.scale 이 있으면 그 값, 없으면 1 / sqrt(128). 머리 차원은 key_length 가 없으면(이 GGUF) 폭 / 머리 수.
- 호스트 · 앱: 구조 2(llama) — 모든 층 어텐션 · 정규화 없이 RoPE · ffn_norm. 앱은 llama 를 dense(되돌릴 수 있는 메모리)로 받는다.

## 16단계 — 설정 넓히기: dense 모델에서 캐시의 끝이 ubatch 가운데인 요청

dense 모델(qwen3 · llama · qwen2)의 서버는 이어지는 요청에서 n_past = 겹치는 앞(프롬프트 전부가 캐시면 n_past − 1)부터 셈한다(10단계).
n_past 가 앞 요청의 ubatch 가운데면 서버는 그 ubatch 를 앞 요청 때 다 셈했고, 이번 요청에서 seq_rm(n_past, −1)로 n_past 뒤의 칸을 지운
뒤 n_past 부터 셈한다. 남은 칸 [p0, n_past) 의 K · V 는 그 ubatch(크기 T — 앞 요청의 토큰까지)로 셈한 값이다. 행렬곱 · flash
attention 의 판이 ubatch 의 토큰 수로 갈리므로, n_past 까지만 다시 셈하면 비트가 다르다. 그래서 지금까지는 이런 요청을 까닭과 함께
거절했다 — Llama-3.1-8B 의 대화(7단계와 같은 일곱 요청, 기본 설정 서버)에서 c4(같은 프롬프트 — n_past − 1) · c6(앞을 고침) ·
c7(다른 대화 — 채팅 틀의 앞이 겹쳐 같은 슬롯)이 그랬고, c5(생성 잇기)는 c4 를 앞에 둬서 거절했다.

- 흉내(앱/라마사슬.gl): 이력의 ubatch 마다 위치 · 크기 · 토큰을 남긴다. 되돌릴 수 있는 메모리(dense)에서는 시작이 n_past 앞인 이력을
  차례대로 남긴다(가운데에 걸린 ubatch 도 — 앞 요청의 토큰 그대로). 하이브리드(qwen35)는 그대로(캐시 끝이 ubatch 의 경계 — 체크포인트).
- 재현 호스트: 토큰 파일 방식 4 — ubatch 마다 위치 · 크기와 그 토큰들(방식 2 는 0 부터 이어지는 크기만). 적힌 차례대로 셈하므로 가운데에
  걸린 ubatch 를 다 셈한 뒤 다음 ubatch 가 n_past 부터 그 칸을 덮어 쓴다. 가림 · KV 길이(패드 256)는 서버와 같이 그 ubatch 의 끝까지.
  KV 칸은 사슬의 가장 먼 자리까지.
- 흉내의 참조 대조(시험/라마사슬.py)는 ubatch 마다 위치 · 크기와 사슬 토큰의 합 셈(Σ (i + 1)·(토큰 + 1) mod 1,000,000,007)까지 견준다.

## 17단계 — 모델 넓히기: 폭이 4096 을 넘는 모델(Qwen2.5-Coder-14B)

llama.cpp 의 RMSNorm(norm.cu rms_norm_f32)은 n4 = 폭 / 4 가 1024 를 넘으면(폭 4100 … 16384) 블록 1024 에 스레드마다 float4 넷을 맡긴다
(rms_norm_f32<1024, 4, vec>). 14B 급(폭 5120 — Qwen2.5-14B · Qwen3-14B 등)이 이 판을 쓴다. 대상은 Qwen2.5-Coder-14B-Instruct Q4_K_M
(qwen2 · 48 층 · 폭 5120 → n4 1280 · FFN 13824 · 머리 40/8 × 128 — GQA 5 → ncols2 8 · 출력층 따로). 모델 파일은 공식
Qwen/Qwen2.5-Coder-14B-Instruct-GGUF 의 한 파일과 SHA-256 이 같다(c1e65973…).

- SASS(공식 DLL 의 sm_89 판): 칸 i = tid + 1024·k(k = 0 … 3, i < n4 만)마다 a_k = fma(w, w, fma(z, z, fma(x, x, y·y))), 스레드의 합은
  (((0 + a₀) + a₁) + a₂) + a₃, 그 뒤는 블록 1024 의 block_reduce(워프 합 → 워프마다 공유 메모리 → 다시 워프 합), 눈금 · 출력은 지금 판과
  같다.
- 더하는 것: 판 `라마RMS1024넷`, 호스트의 블록 규칙(n4 ≤ 4096 → 이 판). 나머지 셈(행렬곱 · flash attention · RoPE · 치우침)은 판 그대로.
- 호스트의 flash attention mma 부분 버퍼: 조각(블록마다 걸친 타일 — 부분 결과 하나)은 격자(≤ 2 · SM) + 타일(토큰 타일 ≤ 64 × KV 머리)
  개까지다. 지금까지는 512 개분이었는데, 14B 는 KV 머리 8 · ubatch 512 에서 타일이 512(토큰 타일 64 × 8)라 조각이 632 개까지 나와
  넘쳤다(CUDA 오류 700). 버퍼를 모델의 KV 머리로 잡고(2 · SM + 64 · KV 머리), 넘을 계획이면 까닭과 함께 멈춘다. 셈은 그대로다.

## 18단계 — 설정 넓히기: 스트리밍 응답(stream)

채팅 화면 · 에이전트 대부분은 응답을 스트리밍(SSE — `data: {…}` 조각)으로 받는다. 지금까지 기록기는 스트리밍 응답을 적지 않았다(검증은
거절). llama-server b12008 이 조각에 적는 것(Llama-3.1-8B · Qwen3.5-9B 로 비스트리밍과 견줌):

- /completion: 토큰마다 조각 하나(tokens 하나 · completion_probabilities 칸 하나 · content). 칸은 비스트리밍과 언제나 같다. 다만 글이
  UTF-8 글자 가운데서 끝난 걸음의 토큰은 조각이 없다(server-context.cpp process_token — 그 바이트는 다음 조각에) — 비스트리밍은 tokens 에
  모든 토큰이 있지만 스트리밍은 그 토큰의 번호가 어디에도 없다(한국어 응답 64 토큰 가운데 4). 끝 조각(stop 참)에 tokens_predicted ·
  timings · tokens_cached · generation_settings(tokens 와 로그 확률은 비었다).
- 채팅 API: 글 조각(diff)이 생긴 토큰만 조각에 칸이 붙는다(to_json_oaicompat_chat). 끝 토큰과, Qwen3.5 에서는 생각 뒤의 줄바꿈 몇이
  칸째로 빠진다. 끝 조각의 __verbose(/completion 꼴)에 tokens_predicted · prompt 등.

이렇게 한다:

- 기록기: 받은 SSE 몸의 조각을 모아 응답을 비스트리밍과 같은 꼴로 적는다 — 알려진 토큰(/completion 은 조각의 tokens, 채팅은 칸의 id),
  칸들, 글, 끝 조각의 나머지 값, 그리고 `stream`(조각 수 · 알려진 토큰 수 · 빠진 토큰 수 = tokens_predicted − 알려진 수).
- 검증: 빠진 토큰이 없으면 지금과 같다. 빠진 토큰이 있으면 온도 0 에서만 받는다 — 재현 호스트가 걸음마다 자기 로짓의 가장 큰 토큰(같으면
  작은 번호)을 골라 이어 셈하고(토큰 파일의 −1), 고른 토큰을 앱에 돌려준다. 앱은 그 토큰들로 칸을 맞춘다(/completion 은 지금처럼 글자가
  온전한 걸음마다, 채팅은 칸의 id 를 차례대로). 서버의 고르기 사슬(온도 0 — 정렬 차례에서 처음 만난 가장 큰 logit)이 재현의 로짓에서 고른
  토큰이 호스트가 고른 것과 다르면 다름으로 센다. 빠진 걸음의 로그 확률은 서버가 내지 않으므로 견주지 않는다(토큰만).
- 빠진 토큰이 있는 스트리밍 영수증은 뒤 요청의 사슬(같은 슬롯의 앞 영수증)로는 쓰지 않는다(그 토큰이 슬롯의 상태다).

### 알게 된 것

- 사슬의 흉내는 요청마다 슬롯의 토큰 수를 서버(tokens_cached)와 견준다. 빠진 생성 토큰은 슬롯에는 들어 있으므로 그 수만큼 더해 견준다

- 채팅 영수증의 프롬프트 토큰은 응답의 __verbose.prompt 를 /tokenize 로 다시 나눈 것이다(9단계). 그 글은 서버가 셈한 토큰을 되돌린 글

  Llama-3.1-8B 에서 [128000, 128000, …] · 서버의 tokens_evaluated 보다 하나 많게 나왔다(재현은 다른 입력을 셈해 다름). 채팅은 add_special
  없이 나누게 고쳤고, 검증은 프롬프트 토큰 수가 서버의 tokens_evaluated 와 다르면 까닭과 함께 거절한다.

## 22단계 — 설정 넓히기: 온도 > 0 의 채팅 스트리밍(끝 토큰만 빠진 응답)

채팅 화면의 흔한 설정은 스트리밍 · 온도 0.7 … 1 이다. 채팅 스트리밍은 끝 토큰(EOS)의 조각에 글이 없어 그 칸을 보내지 않으므로(18단계),
끝 토큰으로 끝난 응답은 늘 토큰 하나가 빠지고 — 온도 > 0 이면 지금까지 모두 거절했다. 그런데 끝 토큰은 마지막 생성 토큰이라 재현이
먹이지 않는다: 그 앞의 걸음은 모두 알려진 토큰으로 셈한다. 남는 것은 마지막 걸음에서 서버가 무엇을 골랐는가 하나다.

- 받는 조건: 채팅 API 의 스트리밍 · 빠진 토큰 1 개 · stop_type eos(채팅 스트리밍에서 끝 토큰은 늘 빠지므로 빠진 하나가 바로 그것이다).
- 셈: 걸음마다 서버의 고르기 사슬(5단계 — 같은 시드의 mt19937)을 재현의 로짓으로 돌려 알려진 토큰과 견주고, 마지막 걸음에서 사슬이 고른
  토큰을 끝 토큰으로 놓는다. 그것이 제어 토큰(tokenizer.ggml.token_type 3)이 아니면 다름(서버는 거기서 멈췄다).

## 23단계 — 설정 넓히기: 다른 슬롯도 쓰인 기본 설정 서버

기본 설정의 llama-server(-np 를 주지 않음 → 슬롯 4 · 통합 KV · RAM 프롬프트 캐시 8 GB)는 여러 대화가 슬롯을 나눠 쓴다. 지금까지는 다른
슬롯이 쓰인 서버의 영수증을 모두 거절했다(통합 KV 에서 칸의 자리가 달라지므로). 그런데 이 서버는 `--cache-idle-slots`(기본 켬 — RAM 캐시가
있어야 함)로 새 작업을 띄울 때마다 쉬는 슬롯을 모두 RAM 캐시에 저장하고 통합 KV 에서 비운다(server-context.cpp — TAG_IDLE_SLOT_CLEAR).
그래서 한 요청을 셈하는 동안 KV 에는 그 슬롯의 칸만 있다.

- 캐시를 쓰지 않은 요청(cache_n 0)은 다른 슬롯이 쓰였어도 혼자 셈한 것과 같다 — 받는다.
- 이어지는 요청(cache_n > 0)은 같은 슬롯의 앞 영수증들 사이에 다른 슬롯의 요청이 없을 때만 슬롯의 상태가 그대로다(그 사이에 다른 작업이
  떴으면 이 슬롯은 비워졌고, 상태는 RAM 캐시에서 불러온 것 — 다음 단계). 사이에 다른 슬롯의 요청이 있으면 까닭과 함께 거절한다.
- 같은 때 돈 다른 슬롯(응답 뒤 /slots 의 is_processing)은 연속 배치(한 ubatch 에 여러 시퀀스)라 거절한다.
- `--no-cache-idle-slots` 이거나 RAM 캐시가 0 이면 쉬는 슬롯의 칸이 남으므로 지금처럼 거절한다.

## 24단계 — 설정 넓히기: RAM 캐시에서 불러온 상태로 이은 요청

23단계의 서버에서 다른 대화의 작업이 뜬 뒤 앞 대화로 돌아오면, 그 대화의 슬롯은 이미 비워졌고 서버는 빈 슬롯에 RAM 캐시의 항목을 불러와
잇는다(23단계의 A3 — 슬롯 2, 캐시 749). 불러온 항목은 그 대화의 슬롯을 저장한 사본이라, 그 슬롯의 이력(ubatch)을 다시 셈하면 같은 상태에
이른다.

- 흉내를 서버 단위로(앱/라마사슬.gl 의 라마서버요청 · 시험/라마사슬.py 의 서버): 활성 슬롯(마지막 작업의 슬롯) 하나와 RAM 캐시 항목(슬롯의
  사본 — 토큰 · 이력 · 체크포인트). 요청마다 영수증의 슬롯이 활성 슬롯이면 LCP 비율로 고른 것(남기는 몫 < 0.5 면 캐시 고침 — 저장 후
  불러오기), 다른 슬롯이면 빈 슬롯에 불러오고 쉬던 활성 슬롯을 저장 · 비움. 저장(server_prompt_cache::alloc)은 지금 토큰이 어떤 항목에 다
  들어 있으면 건너뛰고 지금 토큰에 다 들어가는 항목은 지운다, 불러오기(load)는 남기는 몫 ≥ 0.25 이고 남기는 몫 · 유사 비율이 둘 다 나은
  항목을 불러와 캐시에서 지운다. 크기 한도(기본 8 GB)는 흉내 내지 않는다.
- 사슬: 같은 서버의 모든 슬롯 영수증을 기록 차례대로. 서버를 다시 띄웠을 수 있어 시작은 캐시 0 인 영수증 가운데 앞에서부터 — 흉내가 그
  뒤 모든 영수증의 cache_n · tokens_cached 와 맞는 첫 것.

### 알게 된 것

- 다른 슬롯에 RAM 캐시를 불러오는 것은 슬롯 고르기(get_available_slot) 안이고, 쉬는 슬롯을 비우는 것은 그 작업을 띄운 뒤다. 그래서 불러오는
  순간에는 앞 작업의 슬롯 칸이 아직 KV 에 있어, 불러온 상태는 그 뒤의 칸(find_slot — 예: 929 …)에 놓인다. 앞 슬롯이 비워진 뒤 새 토큰은
  다시 0 부터의 칸에 들어간다. 위치 차례와 칸 차례가 달라지고 KV 길이(pad256(쓴 칸의 끝))도 커져, flash attention 의 합 차례 · 나눔이
  처음 셈과 다르다 — 이력을 위치 차례로 다시 셈하는 재현으로는 같은 값이 나오지 않는다(23단계 A3 · 24단계 다섯 모두 걸음 0 부터 다름).
- 그래서 흉내가 "칸 옮김"(다른 슬롯의 칸이 있는 동안 불러온 상태 — 그 상태에서 저장한 항목에도 이어짐)을 표시하고, 그런 요청은 까닭과
  함께 거절한다. 같은 슬롯에서의 캐시 고침(남기는 몫 < 0.5)은 그 슬롯의 칸을 먼저 지우므로 칸이 0 부터 차례대로다(옮김 없음).
- 칸 배치를 따르는 재현(다음 단계): 서버의 칸 고르기(find_slot · head · seq_rm · 상태 되살리기)를 흉내 내 ubatch 마다 토큰의 칸과 KV 길이를
  내고, 재현 호스트가 K · V 를 그 칸에 쓰고(불러올 때는 칸을 옮기고) 칸 → 위치 표로 가림을 지어야 한다.

## 25단계 — 설정 넓히기: 칸 배치를 따르는 재현(RAM 캐시에서 다른 슬롯에 불러온 요청)

24단계에서 거절한 요청 — 다른 슬롯의 칸이 KV 에 있는 동안 RAM 캐시에서 불러와, 위치 차례가 아닌 칸에 놓인 상태 — 을 서버의 칸 배치
그대로 셈한다.

- 서버의 칸 고르기(src/llama-kv-cache.cpp, b12008)를 흉내 낸다(시험/라마사슬.py 의 칸판 · 앱/라마사슬.gl 의 라마칸판): 통합 KV 의 칸마다
  (시퀀스, 위치)와 head. find_slot(cont = false)은 head 부터 빈 칸을 하나씩 모으고(띄엄띄엄 놓일 수 있다), 끝에 닿으면 0 으로 돈다.
  apply_ubatch 는 head = 마지막 칸 + 1, seq_rm 은 처음 비운 칸이 head 앞이면 head 를 그리로. n_kv = min(칸 수, max(256, 쓴 칸의 끝을
  256 의 배수로 올림)). RAM 캐시에서 불러오기(state_read_meta)는 그 슬롯을 지우고 find_slot 으로 칸을 찾아, 저장한 차례(저장할 때의 칸
  차례 — state_write 가 칸을 앞에서부터 적는다)대로 놓는다.
- 흉내의 이력은 항목마다 칸 · 놓은 뒤의 n_kv 를 지니고, 불러오기는 "옮김" 항목(위치 −1 · 크기 = 위치 수 — 위치마다 새 칸)이 된다.
  서버의 차례: 슬롯 고르기 안에서 불러오기(앞 작업의 슬롯 칸이 아직 KV 에 있다) → 작업을 띄운 뒤 쉬는 슬롯을 저장 · 비움 →
  seq_rm [n_past, end) → 프롬프트의 ubatch · 생성 걸음마다 find_slot.
- 재현 호스트의 방식 5: 사슬의 항목마다 [n_kv] [칸들], 걸음마다 [n_kv] [칸]. 호스트는 이 대화의 위치 → 칸을 지니고 K · V 를 적힌 칸에
  쓰며(칸이 이어지는 토막마다), 가림은 이 대화의 칸 가운데 위치가 토큰의 위치 이하인 칸만 연다. 옮김은 어텐션 층마다 K · V 줄을 옛
  칸에서 새 칸으로 복사한다. 이 모양(ubatch ≤ 512)에서 flash attention 은 가림을 보고 KV 를 건너뛰지 않으므로(mask 를 살피는 것은 토큰
  1024 이상), 다른 슬롯의 칸에 무엇이 있든 값은 같다 — 맞출 것은 이 대화의 칸 자리 · 가림 · n_kv 다.
- 앱은 칸이 위치와 같은 사슬(지금까지의 모든 경우)은 방식 4 그대로, 다른 사슬만 방식 5 로 보낸다.

## 26단계 — 설정 넓히기: 쉬는 슬롯을 비우지 않는 서버(--no-cache-idle-slots · RAM 캐시 0)

`--no-cache-idle-slots` 이거나 RAM 캐시가 0 인 서버(슬롯 넷 · 통합 KV)는 작업을 띄울 때 쉬는 슬롯을 비우지 않는다. 대화마다 제 슬롯에
남아 이어 쓰므로, 한 요청을 셈하는 동안 KV 에 다른 슬롯의 칸이 남아 있다. 그래서 새 토큰이 놓이는 칸은 위치 차례가 아니고, n_kv 에는
다른 슬롯의 칸까지 든다. 23단계까지는 이런 서버에서 다른 슬롯이 쓰였으면 거절했다. 25단계의 칸 흉내와 방식 5 로 셈한다.

- 서버 흉내를 모든 슬롯으로 넓혔다(시험/라마사슬.py 의 서버 · 앱/라마사슬.gl 의 라마서버흉내): 슬롯마다 상태와 마지막으로 쓴 때(작업이
  끝날 때 — t_last_used). 슬롯 고르기(server-context.cpp 의 get_available_slot · get_free_slots)는 LCP 비율이 기준보다 크고 가장 큰 슬롯 —
  남기는 몫 < 0.5 면 캐시 고침. 그런 슬롯이 없으면 빈 슬롯을 먼저, 그다음 마지막으로 쓴 때가 이른 슬롯을 고른다(같으면 번호 차례). 이때는
  늘 캐시 고침. 캐시 고침은 RAM 캐시가 있을 때만 — 그 슬롯을 저장하고 더 나은 항목을 불러온다. 쉬는 슬롯을 비우는 서버(23 · 24단계)는
  그 뒤 다른 슬롯을 번호 차례로 저장하고 비운다. 흉내가 고른 슬롯이 영수증의 슬롯과 다르면(기록되지 않은 요청 등) 까닭과 함께 셈하지
  않는다.
- 슬롯보다 대화가 많으면 칸이 있는 슬롯을 다시 쓴다: 다른 대화의 상태가 남은 슬롯에서 앞이 겹치는 몫(채팅 틀의 시스템 머리 — Llama 는
  30 토큰)만 이어 쓰거나(RAM 캐시 0), 그 슬롯을 RAM 캐시에 저장하고 맞는 항목을 불러온다.
- 앱은 슬롯이 여럿인 통합 KV 서버의 영수증을 모두 서버 단위 사슬로 짓는다(같은 때 돈 다른 슬롯 — 연속 배치 — 는 그대로 거절).

## 27단계 — 설정 넓히기: 슬롯마다 KV 를 둔 서버(-np N)

`-np N` 을 주면 통합 KV 가 꺼져(`--kv-unified` 를 함께 주지 않으면) KV 가 슬롯마다 흐름 하나씩이 된다. 흐름의 크기는 n_ctx_seq —
pad256(n_ctx / N)이고, 영수증의 n_ctx(/props 의 슬롯 문맥)가 이것이다. 슬롯의 칸은 제 흐름 안에만 있어 다른 슬롯과 섞이지 않는다.
`--cache-idle-slots`(기본 켬)는 작업을 띄울 때 쉬는 슬롯을 RAM 캐시에 저장만 하고 비우지 않는다(server-context.cpp —
TAG_IDLE_SLOT_CLEAR 는 통합 KV 일 때만). 지금까지는 이런 서버의 영수증을 모두 거절했다.

- 흉내의 칸판을 흐름마다(슬롯 번호) 하나씩 두고, RAM 캐시에서 불러올 때는 그 슬롯의 흐름에 놓는다. 쉬는 슬롯은 셋 가운데 하나다:
  그대로(--no-cache-idle-slots · RAM 캐시 0), 저장만(슬롯마다 KV), 저장하고 비움(통합 KV — 23 · 24단계). 서버 기록의 find_slot 은 흐름
  번호(stream[i])까지 견준다.
- 앱은 슬롯이 여럿인 서버의 영수증을 모두 서버 단위 사슬로 짓는다. `--kv-unified-per-slot`(슬롯의 문맥만 줄임 — n_ctx 가 KV 의 크기가
  아니다)은 까닭과 함께 거절한다.

## 28단계 — 겹친 요청 알아보기(연속 배치)

### 조사(2026-11-06)

같은 서버에 요청이 겹치면 llama-server 는 여러 대화의 토큰을 한 ubatch 에 묶어 셈한다(연속 배치 — server-context.cpp
update_slots: 생성 중인 슬롯의 토큰을 먼저, 프롬프트를 셈하는 슬롯의 토큰을 n_batch 까지. 묶음은 n_ubatch 씩 차례로 자른다).

- 공식 DLL(b12008)로 대화 A 의 로짓을 견줬다(Llama-3.1-8B · 21 걸음). B 와 한 묶음으로 셈하면 A 는 혼자일 때와 다르다. 같은 모양 · 같은
  위치에서 B 의 토큰 값만 바꾸면 A 는 21 걸음 모두 비트까지 같다. B 의 길이만 바꾸면 A 가 든 ubatch 의 크기나 칸 · n_kv 가 달라지는
  걸음부터 다르다. 그러니 A 의 비트를 정하는 것은 묶음의 모양(ubatch 크기 · 그 안의 A 의 줄)과 칸 배치이고, 다른 대화의 값은 아니다.
- 겹친 두 요청을 실제로 기록했다(A 가 생성하는 동안 B). llama-server 를 `LLAMA_BATCH_DEBUG=1` 로 띄우면 llama_decode 마다 묶음의 토큰 ·
  위치 · 시퀀스 · 출력이 기록에 적힌다. 그 묶음을 공식 엔진으로 같은 차례대로 다시 돌리면 A 300 걸음 · B 48 걸음 모두 영수증과 비트까지
  같다. 연속 배치의 재현에 쓸 것은 서버 기록에 다 있다.
- 지금의 검증은 B(A 가 도는 동안 끝남)는 "다른 슬롯이 같은 때 돌고 있었습니다"로 거절하지만, 늦게 끝난 A 는 혼자 셈해 "걸음 15 에서
  다름"으로 알렸다(겹침을 몰랐다). 이 단계는 겹친 요청을 까닭과 함께 알아본다(연속 배치의 재현은 다음 단계).

### 알아보기

- 기록기는 요청을 넘기기 전에 /slots 를 묻는다(영수증의 slots_before). /slots 는 서버의 우선 작업이라 디코드 가운데에도 곧 답한다. 응답
  바로 뒤의 /slots(slots_after)도 영수증을 마무리하는 스레드가 아니라 응답이 끝난 자리에서 묻는다 — 다음 요청과 엇갈리는 틈을 줄인다.
- 이 영수증만으로: 요청 앞에 다른 슬롯이 돌고 있었거나, 다른 슬롯의 작업 번호(id_task)가 앞뒤로 바뀌었으면(기록기를 거치지 않은 요청도)
  겹쳤다. 끝날 때 다른 슬롯이 돌고 있었으면 겹쳤다(7단계부터).
- 같은 서버의 다른 영수증으로(slots_before 가 없는 지금까지의 영수증에도): 영수증 Q 가 끝날 때 다른 슬롯 j 가 작업 t 를 돌고 있었으면,
  슬롯 j 에서 작업 t 를 셈한 영수증(그 영수증의 slots_after 에서 제 슬롯의 작업 번호 = t)도 Q 와 겹쳤다.
- 서버 단위 사슬은 겹친 영수증이 든 시작을 쓰지 않는다(그 뒤의 슬롯 · KV 칸을 흉내 낼 수 없다).

## 29단계 — 연속 배치의 재현(겹친 요청을 서버 기록의 ubatch 묶음대로)

28단계의 조사대로 겹친 요청의 비트는 묶음의 모양(ubatch 크기 · 그 안의 줄의 자리)과 칸 배치로 정해진다. 그 묶음은 영수증에는 없고
서버 기록(`LLAMA_BATCH_DEBUG=1` · `-v`)에 있다.

- **재현 호스트의 방식 6**: 항목은 ubatch(줄마다 토큰 · 위치 · 칸 · 표시 — 재현하는 대화의 줄 · 그 줄의 로짓을 낸다), 옮김, 지움
  (seq_rm). 다른 대화의 줄은 모양만 맞춘다(가림은 제 칸 하나). RoPE 는 위치가 이어지는 토막마다(한 토큰 판과 몸이 같은 여러 토큰 판),
  K · V 는 적힌 칸에, 가림은 재현하는 대화의 칸 가운데 줄의 위치 이하. 마지막 층은 출력 줄만 FFN 을 지난다(llama.cpp 의
  inp_out_ids) — 출력 줄이 8 개 이하면 llama.cpp 는 MMVQ 라 열마다의 셈이 줄 하나와 같아, 재현하는 대화의 출력 줄마다 따로 셈한다.
  dense 만(qwen35 의 GDN 층은 시퀀스마다 상태가 따로다).
- **서버 기록 읽기(앱/라마묶음.gl)**: 처음 작업을 띄운 줄부터 ubatch 의 줄(모든 대화)을 차례대로 통합 KV 의 칸 흉내(칸판)에 놓고, 이
  영수증의 슬롯 · 작업(slots_after 의 id_task)이 끝날 때까지 그 대화의 줄이 든 ubatch 를 방식 6 의 항목으로 낸다. 그 대화의 앞 작업의
  줄도 싣는다(KV 를 다시 쌓는다 — 로짓은 이 작업의 출력 줄만). memory_seq_rm · prompt_clear 는 지움. 기록의 토큰은 영수증의 프롬프트
  · 생성 토큰과 줄마다 견주고, KV 디버그(`LLAMA_KV_CACHE_DEBUG=1`)가 있으면 흉내의 find_slot(used_max_p1 · used · head)을 기록과 줄마다
  견준다. RAM 캐시에서 상태를 불러온 기록 · 문맥 밀기 · 시퀀스가 여럿인 줄 · 출력 줄이 8 개를 넘는 ubatch · 흐름이 여럿인 KV 는
  까닭과 함께 받지 않는다.
- **앱**: 겹친 요청(28단계의 알아보기)의 영수증은, 그 서버의 명령줄(기록기의 args)에 `--log-file <파일>` 이 있으면 그 기록으로 셈한다.

## 30단계 — 토큰 없는 기록의 검증(요청 · 응답의 글만으로)

29단계까지의 기록기는 관측이 실행에 개입했다. llama.cpp 의 코드 · 모델 · 셈은 그대로지만 실행 조건은 그대로가 아니었다:

- 요청을 바꿨다 — `/completion` 에 `n_probs` 20 · `return_tokens`, 채팅에 `logprobs` · `top_logprobs` 20 · `return_tokens` · `verbose`.
  `n_probs` 가 있으면 온도 0 에서도 고르기 사슬 끝이 dist 라 맨 위 logit 이 같은 걸음에서 토큰이 달라질 수 있다(4단계에 바로잡음).
- 실행 가운데 서버에 물었다 — 넘기기 앞뒤의 `/slots`, 응답 뒤의 `/props` · `/tokenize`(채팅은 `/apply-template` 도), 그리고 서버가 도는
  동안 모델 파일의 SHA-256. 셈을 바꾸지는 않지만 서버의 시간을 쓰고, 요청이 겹치면 어느 요청끼리 묶일지가 시간에 달렸다.
- 클라이언트의 주소를 기록기로 바꾸게 했다.

그래서 검증한 것은 "평소의 실행"이 아니라 "기록기를 거친 실행"이었다. 관측은 실행에 개입하지 않아야 한다. 이 단계는 그 바탕으로,
서버가 기본으로 돌려주는 응답(요청에 아무것도 더하지 않음)만으로 검증하는 길을 만든다. 기록기를 투명하게 바꾸는 것(31단계)과
클라이언트가 원래 남기는 대화 기록에서 검증하는 것(32단계)이 이 길을 쓴다.

- **기본 응답에 있는 것**(b12008 — 시제품의 조사): `/completion` 은 글 · 슬롯 · 캐시 토큰 수(timings.cache_n · tokens_cached) · 고르기
  설정(generation_settings — 시드까지) · 모델 경로 · 프롬프트의 글, 채팅은 글 · 빌드(system_fingerprint) · 캐시 토큰 수 · 토큰 수(usage).
  없는 것은 생성 토큰의 번호와 로그 확률(클라이언트가 요청했을 때만 있다).
- **토큰 없는 영수증**(`geulpu-llama-receipt/2`): 요청 몸 · 응답(서버가 낸 그대로) · 서버의 명령줄과 실행 파일 · 모델 경로 · 크기 · 이 PC 의
  GPU. 프롬프트 토큰 · 생성 토큰 · 슬롯 상태 · 모델 해시를 적지 않는다.
- **프롬프트 토큰**: 검증할 때 llama.cpp 자신의 도구로 다시 만든다 — 영수증과 같은 빌드의 llama-server 를 CPU 로(`--device none` · `-ngl
  0` · `--no-warmup`) 임시 포트에 띄워, `/completion` 은 `/tokenize`(add_special · parse_special 참), 채팅은 `/apply-template` →
  `/tokenize`. 그 서버의 빌드(`/props`)가 영수증과 다르면 받지 않는다. 원래 실행에는 손대지 않는다.
- **생성 토큰**: 재현이 다시 만든다 — 온도 0(서버의 greedy 와 같이 가장 큰 logit, 같으면 작은 번호). 다시 만든 토큰의 조각을 이으면
  응답의 글과 바이트까지 같아야 "같음"이다. 같으면 그 토큰을 적어 두고(자료\영수증\다시만듦), 같은 서버의 뒤 영수증의 사슬이 그것을
  쓴다 — 그래서 토큰 없는 기록은 앞 영수증부터 차례로 검증한다(앞 영수증의 토큰이 아직 없으면 그 영수증을 먼저 검증하라고 알린다).
- **로그 확률**: 클라이언트가 요청해 응답에 있으면 지금처럼 비트까지 견주고, 없으면 견주지 않는다(토큰 · 글 수준의 검증).
- **모델 파일**: 검증할 때 SHA-256 을 셈하고, 크기가 영수증과 같아야 한다.
- 받지 않는 것(까닭과 함께): 온도 > 0 인데 생성 토큰이 없는 기록(고른 토큰 · 시드를 되짚지 못한다), 서버가 답을 나눠 돌려준 채팅(생각 ·
  도구 호출 — 원래 글을 맞대지 못한다), 같은 빌드의 llama-server 실행 파일이 없을 때, 요청이 겹친 토큰 없는 기록(서버 기록에서 이 요청을
  찾을 작업 번호가 없다 — 다음 단계).

### 알게 된 것

- 채팅 응답(OpenAI 꼴)에는 슬롯 번호(id_slot)가 없다. 슬롯이 여럿인 서버의 흉내는 영수증의 슬롯과 흉내가 고른 슬롯이 같아야 했고,
  슬롯을 모르면 받지 않았다. 슬롯 번호가 −1(모름)이면 흉내의 고르기(LCP 비율 · 빈 슬롯 · 가장 오래 쓰지 않은 슬롯)를 그대로 쓴다 —
  고른 슬롯이 틀리면 흉내의 캐시 토큰 수가 서버(timings.cache_n)와 달라져 까닭과 함께 멈춘다. 빠른 점검 4w 에 슬롯을 모르는 서버 사례
  66 개를 더했다(글 · 파이썬 참조 모두 같음).
- 다시 만드는 데 드는 것: 임시 서버는 검증마다 1 ~ 5 초(모델 파일을 메모리에 비추기만 — 셈하지 않는다), 프롬프트 토큰은 다시만듦 파일에
  적어 두고 다음부터는 읽는다.

## 31단계 — 투명한 기록기(기본)

30단계가 토큰 없는 기록을 검증하게 되었으니, 기록기가 실행에 개입할 까닭이 없어졌다. 이 단계부터 기록기의 기본은 **투명**이다.

- **넘기기**: 요청 몸을 바이트 그대로 llama-server 에 보낸다(칸을 더하지 않는다). 응답도 그대로 돌려준다(스트리밍도).
- **실행 중에 서버에 묻지 않는다**: `/slots` · `/props` · `/tokenize` · `/apply-template` 를 부르지 않고, 모델 파일도 읽지 않는다(해시 없음).
- **영수증은 토큰 없는 꼴**(`geulpu-llama-receipt/2`): 요청 몸 · 서버가 낸 응답 그대로(스트리밍은 조각을 모은 글과 끝 조각) · 서버의
  명령줄과 실행 파일 · 모델 경로와 크기 · 이 PC 의 GPU. 빌드는 채팅 응답의 system_fingerprint, 또는 기록기 설정 때 실행 파일의
  `--version`(따로 도는 프로세스 — 도는 서버와 닿지 않는다). 서버의 n_ctx · 슬롯 수 · n_batch · n_ubatch · 캐시 설정은 명령줄에서
  읽고 없으면 b12008 의 기본(-c 4096, -np 자동 → 슬롯 4 · 통합 KV, -b 2048, -ub 512, 체크포인트 32 · 8192, RAM 캐시 8192 MiB)으로
  — `derived: true` 로 표시한다. 슬롯마다 KV 면 슬롯의 문맥은 n_ctx / 슬롯 수를 256 의 배수로 올린 것(27단계).
- **설정**(`자료\영수증\기록기.json`): 포트 · 명령줄 · 실행 파일(exe — 없으면 명령줄의 첫 낱말이 있는 파일일 때 그것) · 방식(mode —
  `transparent` 기본 · `probes`). 저장할 때 실행 파일의 `--version` 으로 빌드를, 명령줄의 `-m` 으로 모델 경로를, 파일 메타로 크기를
  적어 둔다. 찾지 못한 것은 저장 응답의 warnings 에.
- **개입하는 기록(`probes`)은 선택**: 지금까지의 기록기(요청에 확률 · 토큰 칸을 더하고 `/slots` 등을 묻는다 — 토큰이 있는 영수증 /1).
  화면과 설정 응답에 "요청을 바꾸고 서버에 묻는다"고 알린다.
- 검증 쪽: 토큰 없는 영수증에 빌드가 없으면 임시 llama-server 의 `/props` 에서 받고(다시만듦 파일에 적어 둔다), 실행 파일이 없으면 지금
  기록기 설정의 실행 파일(명령줄이 같을 때)을 쓴다.

## 32단계 — 기록기 없이: 대화 기록에서 검증

추론할 때 아무것도 하지 않은 실행을 나중에 검증한다. 사용자가 원래 가진 것만 쓴다 — 클라이언트가 남긴 대화(메시지와 답), 모델 파일,
서버를 띄운 명령줄과 실행 파일. 기록기 · 프록시 · 서버 기록 · 요청 바꾸기가 모두 없다.

- **대화 기록**(JSON — 클라이언트의 기록을 이 꼴로 내보낸다):
  ```
  {"sampling": {"temperature": 0, "max_tokens": 64, "seed": 1},          ← 클라이언트가 보낸 고르기 값(top_k · top_p · min_p 도)
   "request_fields": {"chat_template_kwargs": {"enable_thinking": false}}, ← 요청마다 함께 보낸 다른 칸(없으면 생략)
   "messages": [{"role": "system", "content": "…"}, {"role": "user", "content": "…"}, {"role": "assistant", "content": "…"}, …]}
  ```
  도우미(assistant) 메시지 하나가 요청 하나다 — 그 앞의 메시지들이 요청의 messages, 그 글이 답. 도우미 메시지에 `"sampling"` 을 두면
  그 요청만 덮는다(차례마다 max_tokens 가 다를 때).
- **가져오기**(`POST /api/llama/import` — 화면의 "대화 기록 가져오기"): 서버 설정(명령줄 · 실행 파일 — 31단계의 설정)으로 도우미
  메시지마다 토큰 없는 영수증(/2, `recorder.mode: import`)을 쓴다. 요청 몸은 messages · 고르기 값 · request_fields, 응답은 답의 글
  뿐(생성 토큰 수 · cache_n · 슬롯 · 끝난 까닭을 모른다).
- **검증의 모르는 것들**:
  - 생성 토큰 수: 답의 글을 임시 llama-server 로 토큰화한 수 + 16(max_tokens 가 있으면 그 이하)만큼 다시 만들고, 다시 만든 토큰의 글
    가운데 답과 바이트까지 같은 앞부분을 찾는다. 그 뒤 토큰이 제어 토큰(EOS 등)이면 "끝 토큰으로 끝남", 토큰 수가 max_tokens 면 "한도로
    끝남" — 둘 다 "같음". 답 뒤를 모델이 이어 쓰거나 글이 다르면 "다름"(처음 다른 바이트 · 걸음). 같으면 그 토큰(끝 토큰까지)을
    다시만듦 파일에 적어 뒤 차례의 사슬이 쓴다.
  - 캐시 토큰 수(cache_n) · 슬롯: 흉내의 값을 그대로 쓴다(견줄 서버 값이 없다 — 틀리면 재현이 다른 셈을 해 글이 다르게 나온다).
  - 온도 > 0: 고른 토큰을 되짚을 수 없어 받지 않는다(까닭과 함께).
- 받지 않는 것: 온도 > 0, 도구 호출 · 생각을 따로 돌려받은 답(원래 글을 맞댈 수 없다), 대화 기록에 없는 숨은 요청(제목 짓기 등)이
  서버 캐시를 바꾼 경우(흉내가 어긋나 "다름"으로 나온다 — 그 까닭은 알려 주지 못한다).
- 사슬의 시작: 캐시 토큰 수를 모르는 영수증은 그 서버의 가장 앞의 것만 사슬의 시작이 된다(대화 기록은 서버의 처음부터라고 본다). 뒤의
  것을 홀로 세면 서버의 캐시 상태와 다른 셈이 되므로 — 첫 판의 시험에서 답을 바꾼 A2 뒤의 A3 가 홀로 셈돼 "다름"으로 나왔다 — 앞
  영수증의 토큰이 없으면 "먼저 검증하라"로 거절한다. 캐시를 끈 서버(--no-cache-prompt)의 영수증은 cache_n 을 0 으로 본다.

## 33단계 — 토큰 없는 스트리밍 기록(투명한 기록기 · 스트리밍 클라이언트)

31단계부터 기록기의 기본은 투명이고, 채팅 화면 · 에이전트는 대개 응답을 스트리밍으로 받는다. 그런데 투명한 기록기가 적은 스트리밍
영수증(토큰 없는 /2)은 지금까지 "아직 셈하지 않습니다"로 거절했다 — 기본 설정으로 기록한 흔한 실행이 검증되지 않았다.

- 서버(b12008)가 스트리밍 조각에 적는 것(18단계): /completion 은 조각마다 content, 끝 조각(stop 참)에 tokens_predicted ·
  tokens_evaluated · tokens_cached · id_slot · timings · generation_settings · stop_type. 채팅은 조각마다 choices[].delta(content ·
  reasoning_content · tool_calls), finish_reason 이 있는 조각, 끝 조각에 timings(predicted_n · prompt_n · cache_n), 클라이언트가
  `stream_options.include_usage` 를 주면 usage. 토큰 번호와 로그 확률은 클라이언트가 요청했을 때만.
- 기록기(투명): 31단계는 조각을 모은 글(content)과 마지막 조각(final)만 적었다. 이 단계에서 더 적는 것은 서버가 보낸 조각에서 모은
  것뿐이다(요청 · 서버에는 그대로): 채팅에서 생각(reasoning_content) · 도구 호출(tool_calls) 조각이 있었는가(`split`), finish_reason,
  usage(있으면), 클라이언트가 요청해 조각에 실린 토큰 번호 · 로그 확률 칸.
- 검증: 스트리밍 영수증을 비스트리밍과 같은 꼴로 맞춘다. 글은 모은 글. 생성 토큰 수는 /completion 이 끝 조각의 tokens_predicted,
  채팅이 usage.completion_tokens 또는 timings.predicted_n. 프롬프트 토큰 수는 usage.prompt_tokens 또는 timings 의 prompt_n + cache_n.
  그 뒤는 30단계와 같다 — 프롬프트 토큰은 같은 빌드의 임시 llama-server 로, 생성 토큰은 재현이 다시 만들어 글을 바이트까지 견준다.
  로그 확률 칸이 있으면 비트까지 견준다(채팅 스트리밍의 칸 맞추기는 18단계의 것).
- 31단계의 기록기가 적은 스트리밍 영수증(split 칸 없음)은 생각 · 도구 호출 조각이 없었다고 본다. 있었다면 모은 글이 다시 만든 글과
  달라 "다름"으로 나온다(거짓 "같음"은 나오지 않는다).
- 받지 않는 것(그대로): 온도 > 0 의 토큰 없는 기록(다음 단계), 멈춤 글로 끝난 응답, 서버가 답을 나눈 채팅(split).

### 알게 된 것

- /completion 의 스트림 조각에는 클라이언트가 return_tokens 를 주지 않아도 토큰 번호(tokens)가 실린다. 글자가 덜 끝난 걸음의 토큰만
  빠진다(18단계). 그래서 /completion 스트림의 토큰 없는 영수증은 대개 토큰을 안다.
- 그 때문에 첫 판은 토큰을 아는 영수증의 글을 견주지 않아, 모은 글 한 글자를 바꾼 영수증을 "같음"으로 냈다. 토큰 없는 영수증(/2)은
  토큰을 알아도 응답의 글을 토큰의 글과 견주게 고쳤다 — 글과 토큰이 따로 바뀐 영수증이 "같음"이 되지 않는다.
- 첫 판의 변환은 스트림 응답의 맨 위에서 choices 를 읽어(choices 는 끝 조각에 있다) 앱이 멈췄다 — JSON 의 자식 읽기(제자식)는 없음을
  받지 않는다. 개수를 먼저 보게 고쳤다.
- b12008 의 채팅 스트림은 끝 조각에 usage 를 싣지 않는다(stream_options.include_usage 를 주면 따로 보낸다) — 생성 수는 timings.predicted_n
  으로 셈한다.

## 34단계 — 온도 > 0 의 토큰 없는 기록(시드를 준 요청)

채팅 화면 · 에이전트의 흔한 설정은 온도 0.7 … 1 이다. 지금까지 토큰 없는 기록(투명한 기록기 · 대화 기록)은 온도 0 만 셈했다 — 온도
> 0 이면 서버가 고른 토큰을 글에서 되짚을 수 없다고 거절했다. 그런데 시드가 있으면 서버의 고르기 사슬은 로짓과 시드만으로 정해진다
(5단계). 재현이 로짓을 셈하는 차례대로 같은 사슬을 돌리면 서버가 고른 토큰을 그대로 다시 고른다.

- 재현 호스트에 서버의 고르기 사슬(`엔진/라마고르기.gl` — 5단계에서 서버 토큰 2,391 개를 맞힌 것)을 넣는다. 생성 토큰의 줄마다
  (프롬프트 끝 줄부터) 차례로 사슬을 돌려 난수를 서버의 차례로 쓰고(알려진 토큰의 걸음도), 토큰을 모르는 걸음(토큰 없는 기록은 모든
  걸음, 스트리밍은 글자가 덜 끝난 걸음 · 글 조각이 없는 걸음)은 사슬이 고른 토큰을 넣는다.
- 앱은 사슬이 greedy 가 아닐 때(온도 > 0, 또는 확률을 요청해 사슬 끝이 dist 인 요청) 사슬의 값(top_k · top_p · min_p · 온도 · 시드 ·
  min_keep)을 호스트에 준다. 판정은 30 · 32 · 33단계와 같다 — 다시 만든 토큰의 글이 응답과 바이트까지 같아야 한다.
- 그대로 거절하는 것: 시드가 없는 요청(서버가 random_device 로 고른다), 사슬의 차례 · 값이 기본과 다른 요청(penalties 등 — 다음 단계).
- 받는 것이 넓어지는 곳: 투명한 기록기의 온도 > 0 기록(스트리밍 포함), 대화 기록의 온도 > 0(차례마다 시드), 탐침 기록기의
  스트리밍에서 가운데 토큰이 빠진 온도 > 0 응답(18 · 22단계에서 거절한 것).
