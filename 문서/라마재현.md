# llama.cpp 실행의 비트 재현

이 문서는 단계마다 계획과 판정 기준을 결과보다 먼저 적는다. 결과가 나오면 상태 칸만 고친다.

## 목적

엔진을 바꾸지 않은 llama.cpp 의 실행을 GeulPU 의 GPU 커널로 비트까지 다시 계산한다. 1단계는 생성 걸음(토큰 하나), 2단계는
프롬프트 경로(여러 토큰의 ubatch)의 커널을 글(geul) 언어로 만들어 RTX 4070 Ti(CUDA)에서 돌린다.

- 앞선 일: CPU 참조 구현(Python, GeulPU 밖 — `E:\geulpu-work\xreplay`)이 같은 실행을 프롬프트 토큰만으로 처음부터 비트까지 다시
  계산했다(2026-11-05, 프롬프트 2,548토큰 + 생성 2걸음, 값 4,972,032개 불일치 0). 재현 커널은 그 참조의 연산 순서를 그대로 옮긴다.
- 대상(고정): llama.cpp b12008 공식 Windows CUDA 13 빌드 · RTX 4070 Ti(sm_89, SM 60) · Qwen3.5-9B Q4_K_M ·
  `llama-server -np 1 -fa on --no-cache-prompt --cache-ram 0 -c 8192 -ngl 99`, 온도 0.

## 원리

- llama.cpp 의 CUDA 커널은 `-use_fast_math` 로 빌드됐다: 짧은실수 연산은 비정규수를 버리고(.ftz), 나눗셈 · 역수 · 제곱근 역수 · 지수 ·
  로그 · 사인 · 코사인은 GPU 의 근사 명령(MUFU)이다. 컴파일러가 곱셈과 덧셈을 FMA 로 합친 자리는 SASS 에서 읽었다.
- 재현 커널은 같은 PTX 근사 명령을 쓰고, FMA 의 자리를 `곱해더하기` 로 정확히 둔다(GeulPU 의 PTX 뒷단은 `mul.rn` · `add.rn` 을
  내므로 ptxas 가 합치지 않는다). 더하는 차례(워프 butterfly · 블록 합 · 병렬 블록의 합치기)도 llama.cpp 그대로다.
- 텐서 코어(mma)는 같은 GPU 에서 같은 명령을 같은 피연산자로 부르면 같은 비트를 낸다. 재현 커널은 llama.cpp 가 명령 하나에 넣는
  k 묶음(16개)과 누적 차례를 그대로 둔다. 정수 mma 의 합은 정확하므로 그 뒤의 부동소수점 연산 차례만 맞추면 된다.
- 가중치는 GGUF 파일의 블록 그대로 장치에 둔다(llama.cpp 의 MMVQ 가 읽는 바이트와 같다).
- GeulPU 의 정밀도 계약 · 기존 모듈 · 출력 비트는 바꾸지 않는다. 재현 모듈은 따로 만든다.

## 2단계 — 프롬프트 경로(CUDA)

프롬프트 토큰만 가지고 상태 0 에서 시작해, llama.cpp 가 프롬프트를 처리한 계산과 그 뒤의 생성 걸음을 모두 GPU 커널로 다시 계산한다.

- 서버가 프롬프트를 나누는 모양: 체크포인트를 위해 끝에서 4 + 512토큰 · 4토큰 앞에서 끊고, 한 덩어리는 2,048토큰을 넘지 않는다.
  덩어리 안에서 ubatch 는 512토큰씩이다. 예: 2,548토큰 → (0–2032: 512 · 512 · 512 · 496) · (2032–2544: 512) · (2544–2548: 4).
- 토큰이 9개 이상인 ubatch: 행렬곱은 MMQ, gated delta net 은 64개 이상이면 덩어리 판(토큰 16개씩), flash attention 은 mma 판.
  8개 이하: 행렬곱은 열마다 MMVQ, gated delta net 은 토큰 차례로, flash attention 은 mma 의 4토큰 설정(3–4개).
- 마지막 ubatch 의 마지막 층은 출력 행 하나만 FFN 으로 보내고, 출력 행이 없는 ubatch 의 마지막 층은 KV 캐시만 채운다(그래프의 `get_rows`).

### 알게 된 것

- MMQ 의 열 타일 폭 J 는 8 씩 모두가 아니라 설정표(`mmq-config-ampere.cuh`)에 있는 폭만 후보다: 8 · 16 · 24 · 32 · 40 · 48 · 64 · 80 ·
  96 · 112 · 128(가중치 행이 128 의 배수가 아니면 8 · 16 · 32 · 64 · 128). 처음에 8 씩 모두로 읽어 464 · 396 · 306 토큰에서 120 · 104 를
  골랐고(llama.cpp 는 128 · 112), 열이 다른 타일에 들어가 stream-k 경계가 달라졌다.
- 서버(콜백 없음)는 FFN 의 gate · up 행렬곱과 SwiGLU 를 MMQ 하나로 합친다 — 두 가중치의 형식 · 모양이 같고, 합친 판의 타일(행 64 × 열 J)로
  센 효율이 90 % 이상일 때(`ggml_cuda_mmq_fusion_is_efficient`). 합친 판은 타일마다 블록 하나라 K 를 나누지 않는다. 153 · 248 토큰은
  합친 판의 효율이 91 % 라 합치고, 합치지 않은 판은 80 % 라 stream-k 로 K 를 나눠 비트가 달라졌다. 합친 판의 SwiGLU 는 up · silu(gate) —
  따로 도는 판(silu(gate) · up)과 값이 같다.
- 노드 기록(cb_eval)을 켜면 그 노드는 합치기에서 빠진다. 그래서 커널마다의 대조(2-1)는 합치지 않은 판과, 끝에서 끝(2-2 · 2-3)은 서버와 같은
  합친 판과 견준다. 진단 때 0 · 3층을 기록하며 돌린 하네스의 로짓이 서버와 달랐던 것도 기록한 층이 합치기에서 빠졌기 때문이다.
- 생성 걸음의 flash attention vec 병렬 블록 수는 KV 길이에 따라 바뀐다(launch_fattn: ntiles_KV = ⌈nkv / 256⌉, SM 당 2 블록, 파도 효율이
  가장 좋은 첫 값 — 2,560 → 7, 3,840 이상 → 15).
- llama.cpp 는 날을 넘겨서도 같은 비트를 낸다: 11-05 에 다시 기록한 코딩 요청의 앞 9줄이 11-04 의 하네스 A 와 같다.

## 3단계 — 다른 제조사(Vulkan)

RTX 4070 Ti 에서 돈 llama.cpp 의 실행을 Vulkan 으로, 다른 제조사의 GPU(이 PC 의 Intel UHD 770)에서 비트까지 다시 계산한다.

- 원리: 재현 커널의 글(geul) 소스는 그대로 둔다(소스 하나, 뒷단 둘, 같은 비트). PTX 뒷단은 4070 Ti 의 명령을 그대로 내고, SPIR-V
  뒷단은 그 명령의 셈을 기본 연산 · 정수 연산으로 흉내 낸다. 짧은실수의 기본 연산(비정규수 버림 · FMA 의 자리)은 SPIR-V 뒷단이 이미
  규칙 R 로 PTX 와 같게 낸다. 호스트도 그대로 — `쿠다.gl` 대신 `벌칸.gl` 을 포함한 판을 하나 더 빌드한다.
- 흉내 낼 것:
  - 근사 명령(MUFU, .approx.ftz.f32): ex2 · rcp · rsqrt · lg2 · sin · cos — 공개 비트 모델 ptx-math(MIT)의 표와 정수 셈. sm_89 에서
    입력 2^32 개 모두가 맞는 것은 타당성 시험 ②에서 확인했다. sin · cos 의 범위 줄이기는 64비트 실수 셈이라(UHD 770 의 Vulkan 에는
    64비트 실수가 없다) 정수 셈으로 옮긴다.
  - 0 쪽 반올림 덧셈(add.rz) · f32 → f16 / bf16 변환(가장 가까운 짝수 쪽) · f16 → f32.
  - 텐서 코어 mma m16n8k16: f16 곱 · f32 누적, f16 곱 · f16 누적, bf16 곱 · f32 누적 — 공개 비트 모델 MMA-Sim(MIT)의 Ada 모델(곱 8 개 +
    c 를 최대 지수에 맞춰 24비트로 0 쪽 자르기 → 정확한 합 → 출력 형식으로 반올림, k 16 은 8 개씩 두 번). 피연산자는 서브그룹 셔플로
    모은다(정수 mma 는 이미 그렇게 흉내 낸다 — 합이 정확하다).
- UHD 770 의 공유 메모리는 32 KB 라 gated delta net 덩어리 판(36 KB)을 그 안으로 줄인다(셈은 그대로).

### 알게 된 것

- 흉내는 Intel UHD 770 에서도 맞는다: 3-1 · 3-2 를 마지막 판으로 UHD 770 의 Vulkan 에서도 돌려 4070 Ti 의 CUDA 와 견주었다 — 근사 명령 ·
  e^x · f16 · bf16 변환 · 반실수아래 · 반실수위는 2^32 개 모두, mma 세 형식은 형식마다 출력 134,217,728 개가 같다. 영쪽더하기의 시험 판은
  마지막 판에서 드라이버의 컴파일러가 0 으로 나누기로 멈춰 보지 못했다(앞 판의 버퍼 입력 판은 쌍 16,777,216 개가 같았다 — 재현 커널 안의
  것은 3-4 의 UHD 770 이 덮는다). 다른 것은 f16 → f32 의 NaN 하나: 기존 fpext 의
  낮춤(GLSL UnpackHalf2x16)이 UHD 770 에서는 NaN 의 가수를 지키고(0x7FFFE000) sm_89 는 늘 0x7FFFFFFF 를 낸다. 재현 커널의 반실수아래 ·
  반실수위는 정수 셈이라 같고, 기존 모듈을 바꾸지 않으려고(3-5) fpext 는 그대로 둔다 — NaN 이 나오는 실행이 아니면 닿지 않는다.
- UHD 770 의 셰이더 컴파일러(드라이버 32.0.101.7088)가 시험 판 둘을 틀리게 옮겼다: 고리 몸 안에 갈래가 여럿(16 가지 사슬)이고 64 비트
  정수 섞기가 앞에 있는 판에서 갈래를 잘못 탔고(m = 0 인 입력이 m = 1 의 값을 받음 — 작게 줄인 판들은 맞다), 갈래 없이 다시 쓴 판은
  컴파일하다가 0 으로 나누기로 멈췄다. 시험 판은 갈래 없이 쓰고 입력을 버퍼로 주는 판으로 대신 보았다(영쪽더하기 쌍 16,777,216 개 —
  모두 같다). 재현 커널에서 같은 일이 나면 3-4 의 UHD 770 이 드러낸다.
- 재현 커널은 mma 를 펼쳐 쓴다(FA mma 64 열: mma 96 곳, gated delta net 덩어리: 180 곳). 흉내를 자리마다 펼치면 판 하나가 SPIR-V
  낱말 300 만 · 394 만 개라, 흉내를 커널 모듈마다 함수 하나로 두고 부른다. 근사 명령 · 반실수 묶기도 함수로 두어(FA mma 64 열은
  반실수둘묶기를 264 곳에서 부른다) 16 만 · 20 만 개, 모듈 전체는 5.0 → 3.4 MB.
- UHD 770 의 드라이버는 판을 처음 쓸 때 컴파일하는데, DontInline 함수도 부르는 자리마다 펼치는 듯했다 — 흉내 함수의 몸이 펼친
  셈(명령 3,700 개쯤)일 때는 FA mma 64 열 판 하나가 한 시간을 넘겨도 끝나지 않았다(셔플을 부르는 자리로 옮겨도 같았다). 몸을
  펼치지 않는 SPIR-V 고리와 함수 변수로 다시 쓰자 FA mma 16 열 30 초 · 64 열 69 초에 끝난다. mma 흉내 자체도 UHD 770 에서 5 배
  빨라졌다(3-2 의 형식마다 7.5 → 1.4 초, 4070 Ti 의 Vulkan 은 0.4 초 그대로).
- UHD 770 에서 multi_turn 이 생성 9걸음(위치 1189)부터 틀렸다(프롬프트 끝 · 1–8걸음은 0). 9걸음의 llama.cpp 노드 값을 기록해 커널마다
  견주니 생성 걸음 flash attention(vec)만 달랐고, 같은 입력으로 두 GPU 를 견주니 최댓값 · 합은 같고 V 를 쌓는 부분 합만 — 8 개 묶음의
  첫 차원에서 — 마지막 비트가 달랐다(부분 합 28,672 개 가운데 322 개). 까닭은 SPIR-V 뒷단: 곱해더하기를 GLSL Fma 로 내면서 NoContraction
  을 달지 않았고, 그러면 GLSL.std.450 은 a · b + c 의 정밀도만 요구해 드라이버가 곱 · 합을 따로 반올림해도 된다. NVIDIA 의 드라이버는
  늘 한 번에 셈하고 UHD 770 은 몇 자리를 나눠 셈했다. 달면 그 판은 0 — 뒷단의 고침은 따로 #254(모든 모듈의 SPIR-V 가 바뀌고, 4070 Ti 의
  Vulkan 은 앱의 재현성 검증 32/32 · 32/32 그대로). 이 단계의 판정은 그 고침 위에서 한다.
- UHD 770 의 컴파일: 모듈이 바뀌면 처음 한 번 판 31 개에 3 분쯤(FA mma 둘 · GDN 덩어리가 1 분 안팎씩). 같은 프로그램의 다음 프로세스는
  드라이버의 디스크 캐시가 건너뛰고, 파이프라인 캐시(`GEULPU_VULKAN_CACHE`)를 주면 다른 프로그램끼리도 나눈다(같은 판 31 개 183 → 0.9 초,
  math 의 프롬프트 246.7 → 48.1 초 — 비트는 같다).
- gated delta net 덩어리 판을 32 KB 로 다시 짠 뒤 CUDA 에서도 2-1 의 그 판 · 2-3 의 요청 10개(601,182,720 값)를 다시 돌려 불일치 0.
- 4070 Ti 에서 Vulkan(흉내)의 속도(기록만): 마지막 판으로 프롬프트는 llama.cpp 의 158–476 배, 생성 걸음은 1.66–1.71 배(23.9–25.0 ms).
  mma 흉내의 몸을 펼친 판은 프롬프트가 25–93 배였다 — 고리 몸은 UHD 770 이 판을 컴파일할 수 있게 한 대신 함수 변수가 지역 메모리로
  가 NVIDIA 에서 느리다. 프롬프트의 시간은 거의 모두 텐서 코어 흉내다(재현 자체는 CUDA 에서 llama.cpp 의 3–4 배).

## 4단계 — 영수증과 검증 도구(앱)

llama.cpp 를 쓰는 사람이 고치지 않은 llama-server 로 요청을 돌리며 기록(영수증)을 남기면, 나중에 GeulPU 앱이 그 영수증만으로 다시 계산해
서버가 낸 토큰과 로그 확률이 비트까지 같은지 판정하고, 다시 계산한 실행을 앱의 디버거에서 본다. 대상은 3단계까지의 설정 그대로(b12008
CUDA · 4070 Ti · Qwen3.5-9B Q4_K_M · 한 슬롯 · 프롬프트 캐시 끔 · 온도 0 · `/completion`)이고, 윈도에서 돈 서버의 영수증을 윈도에서
재현한다(서버의 로그 확률은 그 OS 의 C 런타임으로 셈한다). 설정 · 모델 · 엔진 · GPU 를 넓히는 일은 5단계부터.

- 영수증(`geulpu-llama-receipt/1`, JSON 파일 하나):
  - 엔진: llama-server 의 `build_info`(`/props`) · 백엔드 · OS.
  - 장치: 이름 · SM 수 · compute capability — 일 나누기가 SM 수에 따른다(앱의 장치 확인, 같은 컴퓨터).
  - 모델: 경로 · 크기 · SHA-256.
  - 서버 설정: 문맥 · 슬롯 수(`/props`), n_batch · n_ubatch · flash attention · 프롬프트 캐시(서버를 띄운 명령줄 — 앱 설정에 적는다).
  - 요청 · 응답(서버의 JSON 그대로) · 프롬프트 토큰(`/tokenize` — 서버가 `/completion` 에서 쓰는 add_special · parse_special 그대로).
- 기록기: 앱의 길 `/llama/…` 가 사용자의 llama-server(127.0.0.1 의 포트 — 앱 설정)로 넘기고, `/llama/completion` 의 요청 · 응답을
  영수증으로 남긴다. 요청에 `n_probs` · `return_tokens` 가 없으면 더한다(온도 0 에서 셈은 그대로 — 응답에 로그 확률이 붙는다). 스트리밍은
  5단계.
- 재현 · 검증(앱의 작업): 영수증 → 모델 파일 확인(SHA-256) → 받는 빌드 · 장치인지 → 재현 모듈(커널생성 `라마재현` + 뒷단 — 앱의
  모듈 폴더에 한 번) → 재현 호스트(앱 꾸러미의 새 프로그램 둘 — CUDA · Vulkan. 방식 2: 상수를 GGUF 와 llama.cpp 의 셈으로, 프롬프트는
  서버의 덩어리 규칙으로) → 걸음마다 서버의 로그 확률 셈(MSVC `std::partial_sort` 의 자리 옮김 + C 런타임의 expf · logf)을 그대로 해
  영수증과 비트 대조 → 결과 폴더(요약 · 걸음마다의 대조 · 디버거 실행 기록).
- 분석: 결과의 실행 기록을 디버거에서 연다 — 걸음마다 상위 후보 · 로그 확률 · 엔트로피를 재현한 로짓에서, GeulPU 서버를 띄우지 않고.

### 알게 된 것

- llama-server 의 로그 확률 칸(`completion_probabilities`)은 생성 걸음마다가 아니다. 생성한 글이 UTF-8 글자 가운데서 끝나는 걸음은 칸이
  없고(server-context.cpp `process_token` — `validate_utf8` 가 글이 덜 끝났다고 하면 `add_token` 을 부르지 않는다), 그 바이트는 다음 칸의
  `token` · `bytes`(보낸 글 `text_to_send`)에 합쳐진다. 그 칸의 `id` 와 로그 확률은 글자를 끝낸 토큰의 것이다. 요청 10개 가운데
  ko_translate(칸 254 / 걸음 256)와 json_extract(251 / 256)가 그렇다 — 처음에는 칸을 걸음 차례로 맞대어 그 걸음부터 '다름'으로 나왔다.
  대조는 모델 파일의 어휘로 토큰마다의 바이트를 llama.cpp 와 같이 셈해(`token_to_piece`, special = false — 보통 토큰은 GPT-2 바이트 표를
  되돌리고 사용자 정의 토큰은 글 그대로, 제어 토큰은 빈 조각) 서버의 규칙으로 칸을 맞춘다. 칸이 없는 걸음은 토큰만 견준다.
  `시험/라마영수증.py --칸` 이 영수증 10개 모두에서 칸 수 · 번호가 서버와 맞고 이은 바이트가 응답의 글과 같음을 본다.
- 다시 계산한 값은 CUDA 와 Vulkan(4070 Ti)에서 같다 — 칸을 잘못 맞댄 대조에서도 두 층의 다른 값 수가 같았다(ko_translate 2,709).
- 기록기가 더하는 것(`n_probs` 20 · `return_tokens` · `cache_prompt` false)은 온도 0 의 토큰을 바꾸지 않는다 — 기록기로 보낸 응답이
  2단계의 기록과 토큰 · 로그 확률까지 같다(4-1).
- 검증 한 번에 걸린 시간(요청 하나 — 모듈은 처음 한 번만 만든다): CUDA 5 ~ 12 초, Vulkan(4070 Ti) 18 ~ 540 초(long_doc 의 프롬프트 6,396
  토큰이 가장 길다).

## 하지 않는 것(다음 단계)

구조 · 여러 슬롯 · 프롬프트 캐시 · 온도 > 0, 다른 NVIDIA 세대에서 돈 실행의 재현(그 세대의 근사 명령 · 텐서 코어 모델이 필요), 다른
OS(리눅스)에서 돈 서버의 영수증을 윈도에서(C 런타임의 흉내가 필요), 다른 엔진(Ollama · vLLM · SGLang).
