# 리눅스의 Vulkan(#135) — 계획

이 문서는 단계의 계획과 판정 기준을 결과보다 먼저 적는다. 결과가 나오면 상태 칸만 고친다.

## 목적

리눅스에서도 `server-vulkan` 을 빌드하고 돌려, AMD · Intel · Moore Threads 같은 NVIDIA 밖의 GPU 로 GeulPU 를 쓰게 한다. 그리고
그 결과가 Windows 와 같은 비트인지 본다. 연구 서버는 대부분 리눅스다(UPM 연구실의 MTT GPU, 몇 달 뒤의 AMD 클러스터). 그래서 지금은
GeulPU 만의 강점 — 회사가 다른 GPU 끼리 같은 비트 — 을 연구실에서 확인할 길이 없다.

## 지금(2026-11-05, main 458716e)

- Vulkan 을 부르는 자리는 [엔진/벌칸선언.gl](../엔진/벌칸선언.gl) 하나다. Vulkan 로더 `vulkan-1.dll` 의 함수 마흔아홉과,
  `kernel32.dll` 의 `GlobalMemoryStatusEx` 하나를 선언한다. 뒤의 것은 예산 확장이 없는 내장 GPU 의 남은 실제 메모리를 읽는다
  (`벌칸쿠다.gl` 의 `벌실메모리남음`).
- 글(geul) 컴파일러는 리눅스 대상이면 `포함 "X.gl"` 대신 같은 폴더의 `리눅스/X.gl` 을 쓴다(D-50 대상겹침). `엔진/리눅스/` 에는
  파일 · 소켓 · 스레드 · 저장소 파일 · CUDA 선언이 있고 Vulkan 선언은 없다.
- 그래서 리눅스에서 빌드한 `서버V` · `장치V` · `진단V` 는 `vulkan-1.dll` 을 가져오는 ELF 가 되어 돌지 못한다. 빠른 점검의 가져오기
  검사(6)는 이 셋을 보지 않는다.
- Vulkan 층의 나머지(`벌칸.gl` · `벌칸쿠다.gl` · `벌칸여럿.gl` · `벌칸정보.gl`)와 머리 파일 셋에는 다른 체계 호출이 없다.
- [앱/꾸리기.sh](../앱/꾸리기.sh)(리눅스 꾸리기)에 `spirv-backend` · `server-vulkan` · `device-vulkan` · `diag-vulkan` 과 Vulkan
  진단 커널이 없다(#135 라고 적혀 있다).
- 앱은 리눅스에서도 이미 `device-vulkan` 으로 장치를 확인하고, Vulkan 이면 `spirv-backend` 로 모듈을 만든다(`앱/벤치.gl` ·
  `앱/일.gl` — `.exe` 는 리눅스 층의 실행이름이 뗀다). 파일이 없어서 Vulkan 이 빠질 뿐이다(확인은 2단계에서).

## 원리

- SPIR-V 모듈은 체계와 상관없다. 같은 생성기 · 같은 SPIR-V 백엔드가 만든 같은 바이트를 리눅스 드라이버도 받는다. 정밀도 계약의 셈은
  드라이버가 아니라 커널이 정하므로, 같은 장치 조건(서브그룹 32 · 공유 메모리 · 비정규수 처리)이면 같은 비트가 나와야 한다.
- 바꾸는 것은 리눅스판 선언과 꾸리기뿐이다. Windows 실행 파일 · 모듈 · 출력 비트는 바뀌지 않는다.

## 2단계 — 리눅스에서 돌리기(이 PC 의 WSL, GPU 없이)

WSL(Ubuntu 24.04)에는 Mesa 의 Vulkan 드라이버가 이미 있다. CPU 로 도는 lavapipe 도 있다(새로 깔 것 없음). WSL 에서 GPU 를 Vulkan 으로
보는 드라이버(dzn)는 없으므로, 여기서는 CPU Vulkan 으로만 돌린다. 이 단계의 돌림은 WSL 의 CUDA 를 가리고(`CUDA_VISIBLE_DEVICES=`)
낮은 우선순위로 했다 — GPU 에 닿지 않는다.

- 리눅스 꾸러미를 WSL 에서 만들고 `device-vulkan` 으로 lavapipe 를 본다.
- GeulPU 는 서브그룹 크기 32 를 고를 수 있어야 한다. lavapipe 의 서브그룹은 CPU 의 벡터 폭(AVX2 면 8)이라 막힐 수 있다.
  그러면 `LP_NATIVE_VECTOR_WIDTH=1024`(서브그룹 32)로 다시 본다.
- 돌릴 수 있으면 작은 모델(Qwen3-0.6B Q8_0, 정밀 계산)로 요청 몇 개를 보낸다. 스텝마다 로짓 해시를 Windows 의 Vulkan(4070 Ti)과
  CUDA 의 같은 요청과 견준다(파이썬 API). 그다음 앱의 장치 확인이 리눅스에서 Vulkan 을 고르는지(`gpu_layer` vulkan) 본다.

| 번호 | 기준 | 상태 |
|---|---|---|
| 2-1 | 리눅스의 `device-vulkan` 이 lavapipe 를 읽어 JSON 을 쓴다(인스턴스 · 장치 목록 · 속성 · 기능 — 로더 선언이 맞다) | 통과(2026-11-05): llvmpipe(LLVM 20.1.2 · Mesa 25.2.8 · Vulkan 1.4.318)를 읽었다 — 서브그룹 8(AVX2) · 공유 32 KB · 할당 한도 2.15 GB · 협력 행렬 없음 · 비정규수 버림 모드 없음. 막는 것: "서브그룹 크기 32 를 고를 수 없다(8 … 8)" |
| 2-2 | lavapipe 가 GeulPU 의 조건을 채우면: 리눅스 Vulkan 의 로짓 해시가 Windows Vulkan · CUDA 와 모든 스텝에서 같다. 채우지 못하면 그 까닭을 적고 3단계로 | lavapipe 로는 하지 못한다 → 3단계. 서브그룹 32 를 줄 수 없다. Mesa 가 받는 가장 넓은 폭(`LP_NATIVE_VECTOR_WIDTH=512`)에서도 16 이라, 리눅스의 server-vulkan 이 까닭을 알리고 끝난다. 1024 로 억지로 넓히면 속성은 32 를 알리지만, 모델을 올리다 드라이버 안에서 넘친다(디버거: `libvulkan_lvp.so` 가 부른 `__stack_chk_fail`). 기준 쪽(같은 요청 넷 · 점수 하나, Qwen3-0.6B Q8_0 정밀): Windows 4070 Ti 의 Vulkan 과 CUDA 가 모두 같은 비트(0.21.0 앱) |
| 2-3 | 리눅스 앱이 `gpu_layer` vulkan 에서 `server-vulkan` 으로 모델을 불러 답한다 | 일부 통과: CUDA 를 가리면 리눅스 앱이 Vulkan(llvmpipe)을 고르고, 리눅스의 spirv-backend 로 모델 모듈(`qwen3Q8_…_32.spvs`, 44.9 MB)을 9 초에 만든다. 모델을 올리는 데서 2-2 의 드라이버 한계로 멈춘다. 답하는 데까지는 3단계에서 |

## 3단계 — 리눅스의 실제 GPU(사용자가 고르고 승인한 기계)

후보(어느 것을 쓸지는 사용자가 정한다):
1. 이 PC 를 리눅스로 켠다(USB 의 Ubuntu 등). NVIDIA 4070 Ti 와 Intel UHD 770 을 둘 다 리눅스 드라이버로 볼 수 있다. 사용자가 해야 한다.
2. UPM 연구실의 워크스테이션 GPU(A6000 · Ada · A100). JupyterHub 의 H100 은 MIG 조각이라 Vulkan 이 없을 수 있다. 먼저
   `device-vulkan` 으로 본다. 원격 서버는 사용자의 승인 뒤에만 쓴다.
3. MTT · AMD — 연구실의 협력자 · AMD 프로그램이 열리면.

| 번호 | 기준 | 상태 |
|---|---|---|
| 3-1 | 리눅스 GPU 에서 `GeulPU --check r1`(CUDA · Vulkan 모듈 둘 다)이 32/32 — 기준 PC 와 같은 비트 | UPM 의 H100(2026-11-05, 2-2 의 요청 넷 · 점수 하나 — 이 가지의 리눅스 빌드): CUDA 는 Windows 4070 Ti 의 기준과 모두 같은 비트. Vulkan 은 쓸 수 없다 — GPU 가 MIG 모드라 NVIDIA 의 Vulkan 드라이버(595.71.05)가 인스턴스를 만들지 않는다(로더 1.3.204 와 ICD 파일을 우리 폴더에 두어 드라이버를 열었지만 `vk_icdGetInstanceProcAddr` 가 `vkCreateInstance` 를 주지 않는다. MIG 에는 그래픽 API 가 없다). NVIDIA 의 리눅스 Vulkan 은 MIG 가 아닌 GPU 에서 |
| 3-2 | NVIDIA 밖의 리눅스 GPU(Intel ANV · AMD RADV · MTT) 하나 이상에서 같은 검사 32/32 | 이 PC 를 리눅스로 켜서(Intel UHD 770 — ANV, NVIDIA 4070 Ti — NVK 가 있으면) 같은 요청으로 본다 |
| 기록 | 리눅스 드라이버가 알리는 한계(공유 메모리 · 한 번 할당 · 협력 행렬 모양)와 고른 모듈판(보통 · 공유32) — 판정에 쓰지 않는다 | |

## 4단계 — 릴리스(사용자가 판을 낼 때)

리눅스 꾸러미 · 휠에 Vulkan 이 든다. 사용자 문서(README · 사용안내 · user-guide 의 리눅스 절과 지원 표), 릴리스 노트의 문구
("리눅스는 NVIDIA 만")를 그 판의 릴리스 PR 에서 고친다.

## 재현 연구 3단계와의 겹침

재현 연구 3단계(llama.cpp 재현 커널을 이 PC 의 Intel UHD 770 에서 Vulkan 으로 — 다른 세션)는 SPIR-V 백엔드, `커널/생성라마*`,
`엔진/라마재현*`, 모듈 해시의 재현 행을 고친다. 이 일과 같은 파일은 없다. 맞출 곳은 하나다: 3단계가 `엔진/벌칸선언.gl` 에 Vulkan
함수를 더하면 리눅스판에도 같은 줄을 넣는다. 나중에 병합하는 쪽이 맞춘다. GPU 는 둘 다 GPU 줄을 선다.

## 하지 않는 것

재현 모듈의 리눅스 Vulkan(재현 연구의 일), WSL 의 dzn 드라이버 설치, macOS, Windows 쪽의 바꿈.

## 드는 시간(어림)

1단계: 고치기 1–2 시간과 CI 한 바퀴(20–30 분). 2단계: WSL 빌드와 lavapipe 확인 1–2 시간. 작은 모델은 CPU 라 요청마다 몇 분이 걸린다.
3단계: 기계에 달렸다(검사 하나에 수십 분).
