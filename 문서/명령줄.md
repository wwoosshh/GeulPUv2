# AI 용 CLI — 앱 리디자인 단계 C (계획과 판정, 2026-11-08)

[앱리디자인.md](앱리디자인.md) 의 단계 C. 기능 목록(`앱/data/operations.json`, [기능목록.md](기능목록.md))에서 명령을 만들어, AI 나 사람이 자기
터미널에서 GeulPU 의 모든 기능을 부르고, 그 호출이 앱의 이벤트([기능목록.md](기능목록.md) §7)에 세션 이름과 함께 나오게 한다. 앱리디자인.md §6
의 결정대로 CLI 는 GeulPU 실행 파일의 하위 명령(subcommand)이고 글(geul) 언어로 쓴다 — 파이썬 없이 어느 설치에서나 돈다. `geulpu` 파이썬 명령은
지금처럼 인자를 그대로 전달하므로 `geulpu <명령> …` 도 같다. 명령은 한국어 · 영어 이름을 모두 받는다. 묶음마다의 판정은 그 묶음을 구현하기 전에 이
문서에 적는다.

## 1. C1 — 명령의 모양

```
GeulPU <명령> [--<인자> <값> …] [--json <본문>|@<파일>] [--wait] [--out <파일>] [--port <번호>] [--session <이름>] [--timeout <초>] [--dry-run]
```

- **명령:** 기능 목록의 `cli.en`(예: `run branch`) · `cli.ko`(예: `실행 분기`) · 기능 id(`run.branch`) 가운데 하나. 첫 인자가 `-` 로 시작하지
  않으면 명령으로 읽는다 — 앱을 띄우는 지금의 쓰임(`GeulPU` · `GeulPU --port 44639 …`)은 그대로다. 내장 명령은 둘: `ops`(`기능 목록`)는 부를 수 있는
  모든 기능과 인자를 JSON 으로 내고(AI 가 스스로 찾는 길), `help <명령>`(`도움말`)은 기능 하나의 설명 · 인자 · 쓰는 법을 낸다.
- **인자:** 기능 목록의 인자 이름 그대로(`--max_tokens 8` · `--geulpu.step_offset 3` · `--max_tokens=8`). 값은 목록의 형(type)으로 읽는다 —
  integer · number 는 수, boolean 은 `true` · `false`(값 없이 쓰면 참), string 은 문자열, array · object 는 JSON. 점이 든 이름은 안쪽 객체가
  된다(`geulpu.step_offset` → `{"geulpu":{"step_offset":3}}`). POST 기능은 요청 본문(JSON), GET 기능은 쿼리 문자열로 보낸다. 목록에 없는 인자는
  사용법 오류다(오타를 잡는다). 목록에 없는 필드까지 쓰려면 `--json` 으로 본문 전체를 준다 — 이때는 인자를 함께 쓰지 않는다. 목록이 `required` 로
  적은 인자가 없어도 사용법 오류다.
- **결과:** 표준 출력에 앱의 JSON 답을 그대로 낸다. `--out <파일>` 이면 답을 그 파일에 쓰고 `{"ok":true,"file":…,"bytes":…}` 를 낸다. 스트리밍
  (`stream: true`)은 받지 않는다 — CLI 는 답 전체를 낸다.
- **오류:** 표준 출력에 `{"error":{"message":…,"status":…,"op":…,"next":…}}`. `message` 는 앱이 준 까닭 그대로, `next` 는 다음에 할 일(모델이
  없으면 `GeulPU model load --model <id> --wait`, 다른 작업이 돌면 `GeulPU system state` 로 기다리거나 `GeulPU job cancel`, 앱이 없으면
  `GeulPU --no-open` 으로 띄우기, 사용법 오류면 `GeulPU help <명령>`).
- **종료 코드:** 0 성공 · 1 기능 실패(HTTP 4xx · 5xx, 기다린 작업의 실패 · 취소) · 2 사용법 오류 · 3 앱에 닿지 못함.
- **오래 걸리는 작업(job):** 앱의 답(`{"ok":true,"job":N}`)을 그대로 낸다. `--wait` 이면 `/api/state` 로 그 작업이 끝나기를 기다려(0.5 초마다)
  작업의 JSON(`state` · `summary` · `result` · `reason` …)을 낸다.
- **출처:** 모든 요청에 `X-GeulPU-Source: cli`. `--session <이름>`(또는 환경 변수 `GEULPU_SESSION`)이면 `X-GeulPU-Session: <이름>` 도 보낸다.
  앱의 이벤트에 `source: "cli"` 와 `session` 이 적힌다 — 이름은 `[A-Za-z0-9._-]` 로 64 자까지이고, 다른 글자가 들면 이름을 적지 않는다.
- **앱의 자리:** `--port`(또는 `GEULPU_PORT`, 기본 44544)의 127.0.0.1. CLI 는 앱을 새로 띄우지 않는다 — 사용자가 보는 그 앱을 부른다.
- **`--dry-run`:** 보내지 않고 보낼 요청(`op` · `method` · `path` · `body`)을 낸다 — 시험과 AI 의 확인용.
- **기능 목록의 한국어 이름:** CLI 명령이 되므로 [용어.md](용어.md) 의 표준 용어로 고쳤다(예: 평가 견주기 → 평가 비교, 실행로그 들여오기 → 실행 로그
  가져오기, 저장소 비우기 → 프롬프트 캐시 비우기, 일 취소 → 작업 취소). 영어 · 한국어 이름 174 개가 모두 겹치지 않는다.
- **하지 않는 것(C1):** 사람용 `--text`(사람의 자리는 GUI — 명령 창의 사람용 표시는 단계 E 에서 함께), 스트리밍 결과, 앱 띄우기, 대화형 입력.

## 2. C1 의 판정(구현 전에 적음)

1. 부를 수 있는 모든 기능이 세 이름(`cli.en` · `cli.ko` · id)으로 같은 기능에 닿고, `--dry-run` 이 기능 목록과 같은 방법 · 경로와, 준 인자대로의
   요청 본문 · 쿼리 문자열을 낸다. 모든 기능을 자동으로 확인하는 점검을 빠른 점검(CI)에 넣는다 — GPU 없이.
2. 사용법 오류 다섯(없는 명령 · 목록에 없는 인자 · 빠진 필수 인자 · 형이 틀린 값 · `--json` 과 인자를 함께 씀)이 모두 종료 코드 2 와 오류 JSON 을
   낸다. 앱이 없는 포트로 부르면 3.
3. 시험 인스턴스에서 실제 호출: GET 셋 · POST 둘 · 작업 하나를 `--wait` 로 부르면 앱의 답(작업이면 끝난 작업의 JSON)과 종료 코드 0 을, 모델 없는
   `run chat` 은 503 의 까닭과 `next` 가 든 오류 JSON 과 종료 코드 1 을 낸다.
4. CLI 의 호출이 앱의 이벤트에 `source: "cli"` 와 `--session` 의 이름으로 나오고, 세션 이름에 허용되지 않은 글자가 들면 `session` 이 없다.
5. 앱을 띄우는 지금의 쓰임과 기존 API 응답은 그대로다 — 바꾸기 전 앱과 같은 요청의 응답을 바이트까지 대조한다.
6. 기능 목록 점검과 빠른 점검이 통과한다.

## 3. C2 — 실험 맥락 (설계와 판정, 2026-11-08 확정)

실험 기록(형식 `geulpu-experiment/1`, [기능목록.md](기능목록.md) §6 · `experiments/README.md`)을 앱의 기능으로 만들고, 명령을 실험의 작업 기록으로
남긴다.

- **실험의 자리:** 실험 폴더들을 담는 폴더(root). 기본은 데이터 폴더의 `experiments`, 기능마다 `root` 로 바꾼다(저장소의 `experiments/` 처럼
  어디든). 실험 하나는 `<root>/<YYYY-MM-DD>-<이름>/`.
- **기능 넷(기능 목록의 planned → exists):**
  - `experiment.create` — POST `/api/experiments/create` `{name, title, question, root}`. 템플릿(앱 꾸러미의 `data/experiment-template/`)에서
    폴더를 만들고 `experiment.json` 의 `id`(날짜 + 이름) · `title` · `question` · `created` · `geulpu.version`(앱 버전)을 채운다. `plan.md` ·
    `results.md` 의 제목 줄에도 제목을 넣고, root 의 `index.md` 에 한 줄을 더한다(없으면 만든다). 답 `{"id","path"}`. `name` 은
    `[a-z0-9][a-z0-9-]*`(64 자까지), 이미 있으면 409.
  - `experiment.list` — GET `/api/experiments?root=` → `{"root","experiments":[{"id","title","status","created","path"}]}`
    (`experiment.json` 이 있는 폴더만, 이름 차례).
  - `experiment.show` — GET `/api/experiments/show?path=` → `{"path","experiment":<experiment.json>,"plan":…,"results":…,"commands":<줄 수>}`.
    `path` 는 폴더 경로 또는 기본 자리 안의 실험 id.
  - `experiment.check` — POST `/api/experiments/check` `{path}` → 작업(job). 꾸러미의 `data/experiment_check.py`(= `도구/experiment_check.py`,
    B2 의 점검 도구 그대로)를 파이썬으로 돌려 판정과 문제 목록을 작업의 요약에 둔다. 점검 도구가 하나라 GUI · CLI · CI 의 판정이 같다. 파이썬
    3.10 이상이 필요하다(모델 평가와 같은 찾기 — `py -3` · `python` · `python3`).
- **명령 기록:** CLI 의 `--experiment <경로|id>`(또는 환경 변수 `GEULPU_EXPERIMENT`)는 보내기 전에 `experiment show` 로 실험인지 확인하고(아니면
  사용법 오류 2), 요청에 `X-GeulPU-Experiment: <경로>` 를 붙인다. 앱은 그 호출이 이벤트를 남기는 기능(§ B3 — POST)이면 끝날 때
  `<경로>/records/commands.jsonl` 에 한 줄을 쓴다: `{"time","op","method","path","params":<요청 본문 그대로>,"source","session","status","ms"}`
  — 앱리디자인.md §3 의 정한 것 6(기능 id 와 인자, 화면 언어와 상관없음). 앱이 쓰므로 GUI 도 같은 머리로 같은 기록을 남길 수 있다(단계 E).
  경로에 `experiment.json` 이 없으면 쓰지 않는다.
- **꾸러미:** `experiments/_template/` → `data/experiment-template/`, `experiments/experiment.schema.json` · `도구/experiment_check.py` → `data/`.
  점검 도구는 스키마를 자기 옆에서 먼저 찾고, `--json` 으로 기계가 읽는 판정을 낸다.
- **하지 않는 것(C2):** 기록한 명령으로 다시 실행하기(실험대 단계), `index.md` 의 상태 · 결론 갱신, `files` 목록 자동 갱신(`--files` 그대로),
  `panel.records`(연구 패널의 기록 — 화면을 바꾸는 단계 E 로) · `lens.jacobian_fit`(실험대 단계로) — 기능 목록의 단계를 옮긴다.

**C2 의 판정(구현 전에 적음)**
1. CLI 로 만든 실험(`experiment create`)이 B2 의 점검 도구를 통과하고, `experiment list` · `show` 가 그 실험을 보여 준다.
2. `--experiment` 로 부른 POST 기능 셋(하나는 모델 없는 503)이 `records/commands.jsonl` 에 호출마다 한 줄 — 기능 id · 요청 본문 그대로 · 출처 ·
   세션 · 상태 — 로 남고, GET 과 `--experiment` 없는 호출은 남지 않는다. 실험이 아닌 경로는 CLI 가 종료 코드 2 로 막는다.
3. `experiment check --wait` 가 올바른 실험은 통과(종료 0), 포함 파일의 해시가 틀린 실험은 그 문제를 요약에 담아 실패(종료 1)로 낸다 — 점검 도구를
   직접 돌린 판정과 같다.
4. 기존 API 응답은 바이트까지 그대로다(main 에서 빌드한 앱과 대조).
5. 기능 목록 점검(실험 기능 넷이 exists) · 명령줄 점검 · 빠른 점검이 통과한다.
