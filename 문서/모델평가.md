## 0. 왜

- **방향(사용자, 2026-11-02)**: 학습은 다른 도구(PyTorch · Unsloth · Axolotl 등)에 맡기고, GeulPU 는 만들어진 GGUF 를 시험하는 곳이
  된다. 연구자가 GGUF 초안을 만들고, 그 상태를 알고, 고치고, 고친 결과를 이해하기까지를 앱 하나에서 잇는다.
- **지금의 문제(사용자)**: 연구 기능이 "장난감 수준"이고 쓰는 법이 어색하다 — 연구 패널은 답 하나를 토큰마다 보는 데 그치고, 디버거는
  어떻게 쓰는지 · 무엇을 보여 주는지 알기 어렵다.
- **사람들이 GGUF 를 시험하는 방법(조사 2026-11-02)**:
  1. **변환 확인** — llama.cpp 의 `examples/model-conversion`: 원래 모델(transformers)과 변환한 GGUF 의 로짓을 비교한 뒤 양자화하고
     perplexity 를 측정한다. 개발자용 Makefile 이고, 생성에는 상관없는 작은 수치 차이로도 실패할 수 있다고 적혀 있다.
  2. **분포 비교** — `llama-perplexity --kl-divergence`: 기준(FP16) 모델의 로짓을 파일로 남긴 뒤 양자화한 파일과 비교해 KL divergence
     평균 · PPL 비 · Δp · RMS Δp · "Same top p"(top-1 일치율)를 낸다. 기준 파일이 크다(wikitext-2 에서 Llama 3 8B 가 37 GiB).
  3. **대화 데이터의 KL divergence · top-1 일치율** — Unsloth(보지 않은 프롬프트로 Wikipedia 과적합을 피한다. top-1 일치율만으로는 생성
     경로의 차이를 놓친다고 적었다), localbench(BF16 GGUF 기준, 여섯 분야 약 25 만 토큰을 공식 채팅 템플릿으로 — 프롬프트의 로그확률을
     얻으려고 llama.cpp 를 고쳐 썼다).
  4. **과제 점수** — Kaitchup: MMLU-Pro · GPQA · LiveCodeBench · Math-500 을 온도 0 으로 원래 모델과 비교한다. PPL · KL divergence 가
     조금 바뀌어도 과제 점수가 크게 떨어진 경우가 있어 둘 다 본다. GGUF 하나에 H200 으로 10 ~ 20 시간 걸렸다.
  5. **미세조정 모델의 고장** — 가장 흔한 까닭은 채팅 템플릿, 그다음이 EOS 토큰(끝나지 않는 답)이다(Unsloth 의 문제 해결 안내).
     ggufdoctor 는 템플릿을 렌더링해 보는 린터(linter)이고 모델을 돌리지 않는다.
- **GeulPU 가 이 일에 맞는 까닭**:
  - echo 스코어링이 엔진에 있다 — 프롬프트 · 답의 로그확률을 엔진을 고치지 않고 얻고, 생성할 때와 비트까지 같다.
  - 결과가 함께 도는 요청 · 캐시 · GPU 에 따라 바뀌지 않는다 — 평가를 동시 요청으로 빠르게 돌려도 같은 값이고, 같은 파일 · 같은
    설정이면 언제 다시 재도 같다. 그래서 v2 → v3 의 차이는 파일을 바꾼 것에서만 온다(llama-server 는 함께 돈 요청에 따라 12 경우 중
    11 에서 그리디 답이 바뀌었다 — [개발.md](개발.md)).
  - 채팅 템플릿을 jinja 해석기로 그대로 실행한다 — 원래 모델의 템플릿과 GGUF 안의 템플릿을 같은 해석기로 렌더링해 비교할 수 있다.
  - 디버거의 처음 갈라진 스텝 · 분기 · 층 렌즈(logit lens) — 답이 어디서 달라졌는지 볼 수 있다.

## 3. 설계

### 3.1 작업 공간과 버전

- 작업 공간(workspace) 하나 = 모델 하나의 작업. 데이터 폴더의 `평가\<작업 공간>\workspace.json`(형식 `geulpu-eval-workspace/1`):
  - 원래 모델(선택) — Hugging Face 저장소 · 리비전, 또는 로컬 폴더.
  - 기준 모델 — GGUF 의 경로 · SHA-256 · 형식 · 계산 방식.
  - 버전 `v1` … — GGUF 의 경로 · SHA-256 · 크기 · 형식, 만든 방법(`imported` 가져옴 · `metadata` 메타데이터만 고침 · `quantized` 다시 양자화 ·
    `converted` 변환 — 부모 버전, 설정, 쓴 도구와 그 버전), 만든 시각, 결과 목록. 그리고 지금 버전.
- 버전은 파일의 SHA-256 으로 가린다(같은 파일을 두 번 더하지 않는다). 파일은 옮기지 않고 앱의 모델 목록과 같은 파일을 가리킨다.
- '가진 GGUF 파일로 시작' = 내 모델에서 고르거나 파일을 열어 v1 로.

### 3.2 기준 모델

- 같은 모델의 BF16 · F16 GGUF 를 엔진이 받고 GPU 에 들어가면 그것을 쓴다(정밀 모드 — 0.12.0 부터 이 파일들의 기본). gemma4 는 16비트 행렬을
  받지 않고, 이 PC(12 GB)에서 BF16 이 들어가지 않는 크기(약 5B 넘음)도 있다 — 그때는 Q8_0 이 기준이고 결과의 기준 칸에 형식을 적는다.
- 원래 모델(transformers)을 기준으로 하는 비교는 2단계의 보조 스크립트가 같은 형식의 기준값 파일을 만들어 한다.
- 기준 모델과 평가할 모델은 같은 계산 방식으로 돈다 — 기본은 정밀(엔진의 근사를 섞지 않는다). 빠른 모드는 'GeulPU 의 빠른 모드로 쓸 때'를
  묻는 옵션이다.

### 3.3 측정 — 같은 토큰열의 분포 비교와 저마다의 생성 비교

**(가) 분포 비교** — 기준 모델이 자기 채팅 템플릿으로 그리디 생성한 답을 두 모델이 echo 스코어링한다. 두 모델이 같은 토큰을 받으므로 차이는
가중치에서만 온다. 답의 위치마다:

- **KL divergence** KL(P기준 ‖ P평가) — 기준 모델의 상위 K 개 토큰과 나머지 확률 하나로 계산한다(나머지를 하나로 합치면 KL 의 아래쪽
  값(lower bound)이 된다 — 1-0 에서 모든 어휘의 값과 비교해 K = 64 로 정했다). 평균 · 99 백분위수 · 최댓값. 결과에는 K 와 기준
  모델의 상위 K 밖의 평균 확률을 함께 적는다.
- **top-1 일치율** — 두 모델의 1위 토큰이 같은 위치의 비율.
- **Δp** — 기준 모델이 고른 토큰의 확률 차(기준 − 평가). 평균 · RMS.
- **PPL 비** — 기준 토큰의 평균 음의 로그확률 차를 exp 로.

**(나) 생성 비교** — 두 모델이 같은 대화를 저마다의 GGUF 채팅 템플릿으로 받아 그리디로 답한다. 채팅 템플릿 · EOS 토큰의 고장은 여기서
드러난다.

- **답이 달라진 대화** — 답의 토큰이 다른 대화 수, 처음 갈라진 스텝, 그 스텝에서 기준 모델의 마진(디버거의 '마진이 작은 스텝' 기준 0.05 nat
  보다 작으면 '근소한 차이에서 시작').
- **끝난 까닭**(EOS · 최대 길이)과 답 길이.
- 두 템플릿이 같으면 (나)의 처음 갈라진 스텝은 (가)에서 1위가 처음 다른 위치와 같아야 한다 — 서로의 확인.

어휘가 다른 두 파일(토큰 수나 토큰 문자열이 다름)은 (가)를 하지 않고 까닭을 적는다 — (나)는 텍스트로 비교한다. 지표는 분야마다와 전체로 낸다.
**텍스트 모드**(llama.cpp 와 같은 방식의 수가 필요할 때): 텍스트 파일을 토큰으로 나눠 문맥 512 의 청크마다 뒤쪽 절반을 점수 매긴다 — llama-perplexity
의 방식.

### 3.4 서버에 더할 것

- `/v1/completions` 의 echo 에서 위치마다 지정한 토큰들의 로그확률: 요청 `geulpu.token_ids_logprob`(echo_from 부터 위치마다 토큰 id 목록) →
  응답의 같은 이름(위치마다 값). 값은 계약 5.2 의 로그확률 그대로다 — 같은 위치의 `prompt_top_logprobs` 와 겹치는 토큰에서 비트까지 같아야
  한다. SGLang 의 같은 이름(모든 위치에 같은 목록)을 위치마다의 목록으로 넓힌 것이다.
- 상위 로그확률의 수를 `geulpu` 쪽에서만 128 까지 늘린다 — 1-0 에서 기본 K 가 64 로 정해졌다(요청 `geulpu.top_logprobs`, 응답의
  `prompt_top_ids` · `prompt_top_logprobs` · `top_ids` · `top_logprobs` 가 그 수만큼). OpenAI 호환의 `logprobs` 는 20 그대로.
- 지표의 계산은 앱(글(geul) 코드)이 한다 — 서버는 값만 준다.

  2. 평가할 버전마다 서버를 띄워 (가) · (나).
  3. 집계.
- 서버는 교차검증처럼 포트 18092 부터, 슬롯 8 · 동시 요청 8 — 결과는 동시 요청 수와 상관없다.

  (위치마다 KL · top-1 · Δp · 음의 로그확률 둘 · 꼬리 — 다시 계산과 시험에 쓴다) · `run-<버전>.jsonl`(생성한 답의 실행 로그), 덤프를 켜면
  `cand.bin`(위치마다 평가할 모델의 값). 기준 모델의 실행 로그는 기준값 폴더의 `run-ref.jsonl`.
- **재현 정보**: 기준 · 평가 파일의 SHA-256, GeulPU 버전 · 서버 빌드 해시 · 모듈 해시, 계산 방식 · 장치, 데이터 SHA-256, 설정, 결과 해시. 같은
  평가를 다시 돌리면 결과 해시가 같아야 한다.
- API(앱): `GET /api/eval`(작업 공간 · 버전 · 결과 목록과 데이터 목록) · `/api/eval/result?workspace=&dir=` · `/api/eval/compare?workspace=&a=&b=`,
  `POST /api/eval/workspace`(`action` create · update · delete — 지우기는 `평가\지운작업공간\` 으로 옮긴다) · `/api/eval/version`(add · delete) ·
  `/api/eval/data/import`(`.jsonl` · `.txt`) · `/api/eval/run`(작업 시작 — 진행 · 취소는 지금의 작업 API).
- 1-3 에서 더함: 결과의 `diverge.jsonl`(답이 다른 대화마다 두 답의 글과 처음 갈라진 스텝 앞뒤 세 스텝의 값 — 기준 토큰 · KL · 두 모델의 로그확률,
  그 스텝에서 기준 모델의 상위 다섯 후보와 평가할 모델이 낸 토큰의 두 로그확률 · 토큰의 글. 보기용이라 결과 해시에 넣지 않는다),
  `GET /api/eval/item?workspace=&dir=&i=`(대화 하나 — items 의 줄 · diverge 의 줄 · 실행 로그의 messages · tools · 답),
  `POST /api/eval/open`(결과 폴더 열기) · `/api/eval/debug`(결과의 실행 로그를 디버거의 실행 목록으로 — `eval-<결과 폴더>`,
  기준 모델의 것은 `…-ref`). 버전 더하기는 작업 공간에 이미 있는 모델(기준 모델 · 버전)을 받지 않는다.

### 3.7 화면의 판정 문장 — 규칙을 먼저 정한다

- **결과**: "대화 N 개 중 n 개의 답이 기준 모델과 달라졌다(그중 m 개는 근소한 차이에서 시작)" + KL divergence · top-1 일치율.
- **모델 비교의 추천**: 답이 달라진 대화가 가장 적은 파일과 비교해 부호 검정(sign test — 같은 대화끼리, p < 0.05)으로 뚜렷한 차이가 없는
  파일 가운데 가장 작은 것. 그런 파일이 없으면 추천하지 않는다.
- **전후 비교**(같은 데이터 · 같은 설정의 두 결과만): 기준 모델과 같아진 대화 c, 새로 달라진 대화 b — c > b 이고 부호 검정 p < 0.05 면
  '나아졌다', 반대면 '나빠졌다', 그 밖은 '뚜렷한 차이가 없다'. GeulPU 의 결과에는 실행의 잡음이 없어 대화 하나하나의 바뀜은 파일을 바꾼 데서
  오지만, 어떤 대화를 골랐나에 따른 차이는 남기 때문에 검정을 쓴다.
- '표현만 다름'은 채점할 수 있는 문항(3단계)에서만 센다 — 답이 같은 정답이고 텍스트만 다른 경우. 채점하지 않는 대화는 '텍스트가 다름'만 말한다.

### 3.8 GGUF 변환 검증과 고치기 (2단계)

- 원래 모델의 작은 파일만 읽는다 — 로컬 폴더, 또는 Hugging Face 의 `config.json` · `generation_config.json` · `tokenizer.json` ·
  `tokenizer_config.json` · `special_tokens_map.json` · `chat_template.jinja`(가중치 없이 수십 MB 안).
- 검사와 판정:
  - **채팅 템플릿**: 정한 대화 경우(시스템 있음 · 없음, 여러 턴, 도구, 생각 켬 · 끔)를 원래 모델의 템플릿과 GGUF 의 템플릿으로 같은 jinja
    해석기에서 렌더링한다 — 바이트까지 같으면 통과, 다르면 문제(처음 다른 위치와 두 텍스트). 앱에 해석기의 실행 부분을 넣는다.
  - **EOS · 특수 토큰**: GGUF 의 eos · eot · bos 와 엔진이 쓰는 끝 토큰(`eog_token_ids`)을 원래 모델의 `generation_config.json` 의 eos 목록 ·
    특수 토큰과 비교한다. GeulPU 는 Qwen 계열에서 GGUF 의 eos_token_id 와 상관없이 `<|im_end|>` 에서 끝내므로, GeulPU 에서 끝난다고 다른
    런타임에서도 끝난다는 뜻이 아니다 — 판정은 GGUF 의 키로 하고, 다른 런타임에서 어떻게 될지는 '확인 필요'로 적는다.
  - **토크나이저**: 어휘 · 병합 · 특수 토큰이 `tokenizer.json` 과 같은가(구조 비교 — 앱 안에서). 텍스트를 실제로 토큰으로 나눠 보는 비교는 HF tokenizers 를
    쓰는 보조 스크립트로(선택).
  - **설정**(#196 로 더함): `config.json`(멀티모달이면 `text_config`)의 하이퍼파라미터 — 층 수 · hidden · FFN · 머리 수 · KV 머리 수 · 머리 크기 ·
    rope 기준값 · RMS eps · 어휘 수 — 가 GGUF 의 `<구조>.*` 키와 같은가. rope 기준값은 transformers 4 의 `rope_theta` 와 5 의
    `rope_parameters.rope_theta` 를 둘 다 읽는다. 다르면 문제(다시 변환 — 메타데이터로 고치지 않는다).
  - **다음 토큰 확률 · 출력**: 3.3 의 (가) · (나) — 기준은 BF16 GGUF 또는 원래 모델(보조 스크립트).
  - **층별 값**: 층 렌즈가 되는 구조에서 처음 갈라진 스텝의 층마다 두 모델의 KL divergence.
- **고치기**: 메타데이터만 바꾼 GGUF 를 새 버전으로 쓴다(채팅 템플릿 · eos 등). GGUF 쓰기를 글(geul)로 짠다 — 텐서 자료는 그대로 복사하고 헤더의 키만
  새로. 확인: 텐서마다 바이트가 같고, 엔진의 모델 확인을 통과하고, 같은 토큰열의 로짓 해시가 원래 파일과 같다.
- **원래 모델의 기준값 보조 스크립트**(파이썬 — torch · transformers, 선택): 같은 대화를 원래 모델로 돌려 기준값 파일을 쓴다. 앱이 파이썬
  환경을 찾으면 부르고, 없으면 까닭과 설치 방법을 보인다.

### 3.9 정확도 평가 (3단계)

- 채점 규칙(데이터의 `grader`): `number`(답의 마지막 수 — GSM8K 의 `####` 뒤 수와), `choice`(객관식의 글자 — 'The answer is (X)'),
  `exact`(정리한 문자열이 같음), `tool_call`(함수 이름과 인자의 JSON 이 같음). 코드를 실행하는 채점은 하지 않는다(따로 격리 환경이 든다).
- 결과에 정답률(95 % 구간 — 부트스트랩)과 기준 모델과의 차이, 전후 비교에 맞음 → 틀림 · 틀림 → 맞음 문항(부호 검정).
- 내장 과제: GSM8K test 1,319 문제(MIT), MMLU-Pro test 의 500 문제(MIT — 분야마다 고르게, 고르는 규칙을 먼저 적음). 처음 쓸 때 받으려 했지만
  원본이 parquet 이라(앱은 JSONL 만 읽는다) JSONL 로 바꿔 앱에 넣는다(사용자 2026-11-02 — '3-2 의 판정').

### 3.10 GGUF 만들기와 개선 (4단계)

- llama.cpp 의 도구를 쓴다 — `convert_hf_to_gguf.py`(파이썬: 2026-11-02 의 requirements 가 torch 2.11.0(CPU) · transformers 4.57.6 · numpy ·
  sentencepiece · gguf · protobuf), `llama-quantize`(형식 · `--imatrix` · `--tensor-type` 행렬별 형식), `llama-imatrix`. 앱이 정한 릴리스를
  받는다(크기 · 출처를 보이고 사용자가 허락한 뒤). llama.cpp 의 도구는 한글 경로를 열지 못하므로 ASCII 경로의 작업 폴더를 쓴다.
- transformers 5 로 저장한 모델 폴더(#196): llama.cpp 는 많은 모델의 토크나이저 때문에 transformers 를 4.57.6 에 묶어 두었고, 4.x 는 5.x 가 쓴
  `tokenizer_config.json`(`extra_special_tokens` 목록)을 읽지 못하며 `config.json` 의 `rope_parameters` 를 몰라 `rope_theta` 의 기본값(10000)을
  쓴다. llama.cpp 관리자의 권고(ggml-org/llama.cpp#24460 — requirements 그대로인 환경 하나, transformers 만 올린 환경 하나)대로 환경을 둘 둔다 —
  `py-convert`(transformers 4.57.6)와 `py-convert-tf5`(transformers 5.22.1 — torch 는 `py-convert` 의 것을 `.pth` 한 줄로 함께 씀). 변환 ·
  원래 모델과 견주기는 원래 폴더의 `config.json` 의 `transformers_version` 이 5 이상이면 둘째를 쓴다.
- 만든 파일은 새 버전이 되고, 변환 검증과 모델 비교가 자동으로 돈다.
- 행렬별 정밀도는 엔진이 받는 섞임 안에서만 고르게 한다 — 표준 구조의 k-양자화 경로는 행렬마다 Q4_K · Q5_K · Q6_K · IQ4_XS · 16비트, gate
  와 up 은 같은 형식, Q8_0 은 섞을 수 없다([형식섞임.md](형식섞임.md) 의 D3 전). qwen35 는 행렬마다 Q8_0 · k-양자화 · IQ4_XS · 16비트(한
  행렬곱 안의 q · k · v 와 gate · up 에서는 Q8_0 과 k-양자화를 섞지 못한다). gemma4 는 파일 전체가 한 형식이다. 제안하기 전에 엔진의 모델
  확인으로 받는지 본다.
- '차이가 큰 곳':
  1. 빠른 보기 — 층 렌즈로 처음 갈라진 스텝들의 층마다 KL divergence(qwen2 · qwen3 · llama · gemma4).
  2. 자세히 측정(선택 · 걸리는 시간을 먼저 보임) — 행렬 종류 × 층 범위마다 그 행렬만 기준 정밀도로 되돌린 파일을 만들어, 작은 데이터에서 KL
     divergence 가 얼마나 줄어드는지.
- 제안은 측정한 값과 파일 크기의 변화로만 보인다 — 효과를 미리 장담하지 않는다(화면의 '예상'은 2 의 측정값).
- 층 렌즈는 요청 하나에 한 위치만 읽는다 — 위치가 많으면 엔진에 여러 위치를 한 번에 계산하는 방법을 더한다([층렌즈.md](층렌즈.md) 의
  '나중').

### 3.11 출력 분석

- 1단계: 답이 달라진 대화의 목록(처음 갈라진 스텝 · 마진 · 분야) → 대화 하나를 열면 두 답을 나란히, 처음 갈라진 스텝 앞뒤의 토큰마다 두
  모델의 확률과 상위 후보, 디버거의 요청 보기로 열기.
