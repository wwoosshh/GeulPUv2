# 문맥 저장소 — 재현 가능한 에이전트 엔진의 첫 단계 (계획 2026-10-19 — 사용자 승인 2026-10-19)

## 왜

- **방향(사용자, 2026-10-19)**: 재현 가능한 로컬 에이전트 엔진. 결정성(같은 입력 → 어느 길 · 장치에서든 같은 비트)을 바탕으로 두고, 그 위에
  사용자가 느끼는 속도와 재현 기능을 쌓는다. 속도 기능만으로는 llama.cpp 가 몇 주 안에 따라온다(문서/MoE재기.md).
- **재 본 낭비**(문서/MoE재기.md — Qwen Code 로 실제 코딩 작업 셋): 작업 시간의 **38 ~ 43 % 가 프롬프트 처리**이고, 그중 **58 ~ 64 % 가
  되풀이되는 긴 프롬프트를 처음부터 셈**한 것이다(새 작업의 시스템 프롬프트 15k 토큰 · 하위 에이전트가 슬롯을 덮은 뒤). 작업끼리 첫
  프롬프트의 앞 8,963 토큰이 같았다.
- **GeulPU 의 지금**: 한 슬롯 안에서는 앞이 같은 만큼 토큰 단위로 다시 쓴다(서버몸.gl 줄넣기하나). 하지만 슬롯 밖은 모두 처음부터다 —
  슬롯(앱 기본 2)보다 많은 대화(앱의 방 · 에이전트 · 하위 에이전트), 서버 다시 켜기, 모델 바꾸기(관리자는 서버 프로세스를 끊는다).
- **GeulPU 만의 것**: 계약상 KV 캐시는 어느 길로 채워도 바이트까지 같다(계약 시험 '캐시 바이트' — 생성 그래프 · 한 번에 · 넷으로 · 한
  행씩 · 다시). 그래서 저장했다 되살린 KV 는 다시 셈한 KV 와 같고, **저장소를 켜도 답 · 로그확률 · 연구 패널의 해시가 하나도 바뀌지
  않는다.** 다른 엔진은 일괄 · 길이 바뀌면 비트가 달라질 수 있어 이것을 보장하지 못한다.

| | llama.cpp | vLLM · SGLang | GeulPU 문맥 저장소 |
|---|---|---|---|
| 다시 쓰는 곳 | 슬롯 + RAM 프롬프트 캐시(기본 8 GiB, 끄면 사라짐), 슬롯 저장은 손으로 | 프로세스 안의 페이지 · 트리(서버용 바깥 층은 LMCache · HiCache) | 256 토큰 덩이의 파일(SSD) — 껐다 켜도, 모델을 바꿨다 돌아와도 |
| 캐시를 켜면 답이 | 바뀔 수 있다 | 결정성 모드에서도 일괄이 바뀌면 어긋날 수 있다 | 계약상 같은 비트(시험으로 확인) |
| 다른 장치 | — | — | 정밀 모드는 CUDA ↔ Vulkan(AMD 포함)이 같은 파일을 쓴다 |

## 쓰임새 — 저장소로 무엇을 이루나 (사용자 2026-10-19 — 구현한 뒤 어떻게 써먹을지)

저장소는 같은 문맥을 기다리는 횟수를 "매번"에서 "한 번"으로 줄인다. 그 속도(다시 셈 없애기)는 남도 따라올 수 있지만, 여기에 **꺼낸 상태 =
다시 셈한 상태(비트)**가 얹히면 재현 · 되감기 · 갈래가 싸고 정확한 일이 된다 — 이것이 GeulPU 만의 몫이다. 쓰임새는 효용이 큰 차례로 쌓는다.

| | 쓰임 | 누가 · 언제 | 판정 숫자 | 2단계에서 잰 것(Qwen2.5-7B — 아래 2단계 결과) | 더 필요한 것 |
|---|---|---|---|---|---|
| ① | **다시 셈하지 않는 에이전트** | 새 작업(같은 시스템 프롬프트) · 하위 에이전트가 슬롯을 덮은 뒤 · 서버를 다시 켠 뒤 | 새 작업의 첫 토큰 · 녹화한 작업 전체 시간 | 새 작업 첫 토큰 4.1 ~ 4.3 초 → 다시 켠 뒤에도 0.29 ~ 0.33 초, 녹화 54 요청의 첫 토큰 합 39 → 5.9 초 | 앱 연결(3단계) |
| ② | **GPU 하나로 에이전트 여럿**(문맥 전환) | 계획 · 구현 · 검토 담당을 번갈아 — 쉬는 쪽의 문맥을 SSD · RAM 으로 내렸다가 차례가 오면 올림 | 주 ↔ 하위 에이전트 전환 비용 | 슬롯 하나로 세 대화를 번갈아: 첫 토큰 합 237 → 52 초. 슬롯 고르기(덮이는 것이 가장 적은 슬롯) · 덮기 전 쓰기 | 이름 붙인 상태로 붙잡아 두기 · 미리 올리기 |
| ③ | **되감고 갈라 보기 · 재생**(GeulPU 만) | 에이전트 실행 취소, 최선 고르기(갈래 여럿), 녹화한 실패의 재현, 붙였다 떼는 검토(아래 다음 1) — 갈래끼리의 차이는 오직 바꾼 것 때문 | 되감은 지점까지 되살린 토큰 · 시간 · 해시가 처음과 같음, 녹화 작업 재생의 해시 같음 | 녹화 54 요청을 다시 켠 서버로 재생 — 걸음 1,728 개 모두 같은 비트 | 상태 저장 · 되감기 · 갈래 API |
| ④ | **세션을 넘는 기억** | 며칠 이어지는 작업, 기계를 넘는 이어 하기, 되돌릴 수 있는 요약(①의 대화 압축 전 갈래를 남김), 기억 팩(문서 · 매뉴얼을 미리 읽은 상태를 앞에) | 재부팅 뒤 32k 세션 다시 열기(OS 캐시 · SSD 따로) | CUDA 가 쓴 저장소를 Vulkan 서버가 읽어도 같은 비트(AMD 실기기는 아직) | 세션 이름 · 기억 팩 API |

**판정 숫자(4단계에서 잰다 — 아래 맞음 · 판정의 실사용과 함께)**: 1. 같은 시스템 프롬프트로 새 작업을 시작할 때 첫 토큰(Qwen Code
14.5k 토큰) 2. 재부팅 뒤 32k 세션 다시 열기 3. 주 ↔ 하위 에이전트 전환 비용 4. 녹화한 실제 에이전트 작업의 전체 시간 5. 저장소에서 꺼낸
상태 = 다시 셈한 상태. 지금 모델은 이 PC 에서 문맥 3만 토큰대라 절대 숫자는 작다 — 몇 분 단위의 체감은 Qwen3.6 · 10만 토큰 이상과 함께
온다. 1판은 "구조가 맞고 비트가 같다"를 확인하는 단계다.

**조건과 한계**

- **앞부분이 토큰까지 같아야** 다시 쓴다. 에이전트 도구가 프롬프트 앞쪽에 시각 · git 상태처럼 매번 바뀌는 것을 넣으면 거기서 깨진다(클라우드
  프롬프트 캐싱도 같은 제약) → **캐시가 깨진 자리**(몇 번째 토큰 · 앞뒤 글 · 까닭)를 응답과 연구 패널에 보여 사용자가 고치게 한다.
- **새 토큰은 셈해야** 한다(도구 결과 · 새로 읽은 파일). 작업 전체로는 다시 셈만 없앤 상한이 약 1.3 배(문서/MoE재기.md 의 시간 나눔 —
  2단계 시험은 생성이 32 토큰뿐이라 더 크게 나온다). 그 위는 프롬프트 · 생성 속도의 몫이다.
- **디스크**: 지금 KV 는 토큰당 7B 58 KB · 8B 130 ~ 146 KB(fp16 과 거의 같은 크기) — 10만 토큰 대화 하나가 5.7 ~ 15 GB. 크기 한도와 오래된
  갈래 정리가 있어야 하고, 8 비트 KV 는 절반으로 줄이지만 KV 의 비트가 바뀌는 계약 변경이라 따로 판단한다. SSD 수명은 작은 문제다(위험).
- **판**: 같은 모델 파일 · 같은 계약 판이어야 한다. 커널이 바뀌어 KV 바이트가 달라지면 형식 판을 올려 예전 덩이는 쓰지 않는다(다시 셈).
- **보안**: KV 는 대화를 되살릴 수 있는 값이다 — 사용자 자료 폴더에만, 지우기 버튼, 암호화(서버가 새 DLL 을 가져오면 서버의 가져오기 표
  규칙이 바뀐다 — 3단계에서 정함).
- **비교의 정직함**: llama-server 에도 슬롯을 파일로 저장 · 복원하는 수동 기능(`--slot-save-path`)이 있다 — 슬롯마다 손으로 부르고, 앞부분으로
  찾아 주지 않으며, 캐시를 쓴 답이 다시 셈한 답과 같다는 보장이 없다. 비교할 때 빼지 않는다.

**무대**: 개인 PC → 개인 GPU 서버(GPU 몇 장 · 회사가 섞일 수 있음 — 한 사람이나 작은 팀의 에이전트 여럿). 데이터센터의 KV 풀(vLLM +
LMCache · SGLang HiCache · NVIDIA Dynamo · Mooncake)은 하지 않는다 — 그 판은 여러 GPU 나눔 · 페이지 KV · 대량 일괄이 먼저다. 그 판에도 없는
것("캐시에서 꺼낸 것 = 다시 셈한 것", 섞인 GPU 사이의 정확한 이어 하기)이 개인 GPU 서버 규모에서 쓸모를 갖는다.

## 무엇을 — 설계

### 단위와 이름

- **덩이 = 위치 256 개**(32 · 64 의 배수 — 값의 32 위치 블록과 어텐션 조각에 맞음). 꽉 찬 덩이만 담는다. 프롬프트가 덩이 중간에서
  갈라지면 마지막 꽉 찬 덩이까지 되살리고 나머지(최대 255 토큰)는 셈한다.
- **이름 = SHA-256 사슬**: h₀ = H("GeulPU-KV/1", 모델 sha256, 모드(정밀 · 빠른), KV 형식 판, RoPE 설정, 덩이 크기),
  hₖ = H(hₖ₋₁, 덩이 k 의 토큰 256 개). 파일 이름은 hₖ. 덩이 k 의 이름이 앞의 모든 토큰을 품으므로 "같은 이름 = 같은 앞부분"이다.
  비트를 바꾸는 것은 모두 이름에 든다(모델 · 모드 · 형식 · RoPE — ③의 YaRN 도 여기로).
- 모델 sha256 은 관리자가 이미 갖고 있다(모델목록.json — 받을 때 확인한 값) → 서버 인자로 넘긴다.

### 담는 것

- 층마다 차례로 키(KV 머리 · 자리 둘의 줄 — 줄마다 256 × 128 B), 키 지수(KV 머리마다 256 × 4 B), 값(KV 머리마다 블록 8 개 —
  8 × 8,192 B), 값 지수(KV 머리마다 256 × 4 B) — 커널/생성머리128.gl 의 배치에서 위치 범위만 떼어 낸 것(장치 쪽은 같은 간격의 줄이라
  층마다 줄 간격 복사 넷). 슬롯 번호 · 최대길이와 상관없는 차례로 담아, 다른 슬롯 · 다른 문맥 설정 · 다른 GPU 층에도 되살린다.
- 머리말(4,096 B): "GKV1", 형식 판 · 덩이 · 층 · KV 머리 · 머리 크기 · 덩이 번호 k · 내용 바이트 · 상태 바이트(지금 0) · 내용 합(64 비트 —
  8 바이트 낱말 네 갈래의 홀수 곱), 씨앗 · 앞 이름 hₖ₋₁ · 이름, 그 덩이의 토큰 256 개. 읽을 때 하나라도 다르면 지우고 다시 셈.
- 덩이 하나의 크기: Qwen2.5-7B 14.9 MB · Llama-3.1-8B · Mistral-7B 34 MB · Qwen3-8B 38 MB · Qwen2.5-14B 51 MB.

### 층

| 층 | 무엇 | 속도(이 PC) |
|---|---|---|
| VRAM | 지금의 슬롯 그대로 | — |
| 다른 슬롯 | 다른 슬롯이 같은 앞부분을 들고 있으면 GPU 안에서 복사 | 429 GB/s |
| RAM | OS 의 파일 캐시(따로 잡지 않음 — 최근에 쓰고 읽은 파일이 그대로 메모리에) + 핀 메모리 중간 칸 하나 | 핀 → GPU 21.5 GB/s |
| SSD | 앱 자료 폴더의 `문맥저장소`(설정으로 위치 · 크기 — 기본 20 GB, SSD 에만) | 990 EVO Plus 약 7 GB/s · P3 약 3.5 GB/s |

어림: Qwen2.5-7B 의 15k 토큰 앞부분 = 0.87 GB → 되살리기 0.1 ~ 0.25 초, 다시 셈 약 3.5 초(16k 빈 프롬프트 3.7 초 — 문서/긴문맥재기.md).

### 읽기 — 일감을 슬롯에 넣을 때(줄넣기하나)

1. 프롬프트의 이름 사슬을 셈(덩이마다 SHA-256 한 번 — 1 KB).
2. 저장소 · 슬롯들에서 가장 긴 같은 앞부분을 찾는다(저장소는 덩이 단위, 슬롯은 지금처럼 토큰 단위). 메아리(점수 매기기)가 있으면 그 앞까지만 —
   지금 규칙 그대로.
3. 고른 슬롯의 앞부분 뒤를 가장 가까운 곳에서 채운다: 다른 슬롯(GPU 안 복사) → 저장소(파일 → 핀 중간 칸 → GPU). CUDA 는 층마다 줄 간격 복사
   (cuMemcpy2D) 넷, Vulkan 은 영역 목록 한 번의 복사. 모델 조각(25단계)은 조각마다.
4. 슬롯 캐시 토큰열을 되살린 데까지 잇고, 나머지만 지금처럼 프롬프트 길로 셈한다. 같은 바이트를 덮어써도 결과는 같다(계약).

### 쓰기 — 일감이 끝날 때, 뒤에서

- 일감이 끝나면 그 슬롯에서 아직 저장소에 없는 꽉 찬 덩이를 핀 중간 칸으로 내리고(15 MB 에 약 1 ms), **오래 사는 일꾼 스레드 하나**가 내용
  해시 · 파일 쓰기를 한다(토큰마다 스레드를 만들면 5 ms — 38f). 에이전트의 한 걸음은 보통 새 덩이 한두 개.
- 관리자는 서버를 끊으므로 일감마다 써 두어야 잃지 않는다. 관리자의 '서버 멈추기'는 끊기 전에 `저장소 비우기 요청`(쓰기 줄을 끝까지)을 짧은
  시간 한도로 보낸다.
- 설정: 쓰기 '모두'(기본) · '슬롯을 비울 때만'(SSD 쓰기를 줄이는 쪽) · 끔.

### 비우기 · 지키기

- 크기 한도를 넘으면 마지막으로 쓴 때가 가장 오래된 덩이부터 지운다(색인 — 시작할 때 폴더를 읽어 메모리에).
- 읽을 때 내용 해시가 다르면(디스크 손상) 버리고 다시 셈한다. 형식 판 · 계약이 바뀌면 이름이 달라져 옛 덩이는 쓰이지 않고 한도 비우기로 사라진다.
- **검증 모드**(시험 · 연구 패널): 되살린 앞부분을 다시 셈해 KV 해시가 같은지 본다 — "답을 바꾸지 않는 캐시"를 사용자가 직접 확인.

### 보이기

- 서버 기록 줄: `프롬프트 N (캐시 a · 저장소 b · 다른 슬롯 c)`, 응답 덧붙임 `geulpu.store`(되살린 토큰 · 걸린 시간), 요청 `geulpu.store: false` 로 끔.
- 앱 설정: 문맥 저장소 켬 · 위치 · 크기 · 쓰기 방식 · 비우기 버튼. 연구 패널: 요청마다 되살린 토큰 · 검증 결과.
- 서버 인자: `--저장소 <폴더>` `--저장소크기 <GB>` `--모델해시 <sha256>` `--저장소쓰기 모두|비울때|끔`.

   ```
   큰 모델 상태 S(계획 · 명세) ── 저장소에

   큰 모델: S + C 로 계속 — 문맥이 부풀지 않고, T 는 언제든 같은 상태로 다시 붙임
   ```
