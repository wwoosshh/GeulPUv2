# 바뀐 것

GeulPU 앱의 판(SemVer). 판은 `앱/판.gl` 하나에 적고, 릴리스 태그 `v<판>` 과 같아야 한다(릴리스 CI 가 견준다). 0.5.0 까지는 연구 저장소
[GeulPU](https://github.com/wwoosshh/GeulPU) 에서 냈고, 이 저장소(GeulPUv2)가 그 소스를 이어 받아 다음 판부터 여기서 낸다. 연구의 단계
기록은 [GeulPU 의 문서/단계기록.md](https://github.com/wwoosshh/GeulPU/blob/main/문서/단계기록.md).

## 다음 판

- **문맥 저장소(2026-10-19 · 20)**: 긴 프롬프트의 KV 를 256 토큰 덩이로 SSD 에 남기고, 같은 앞부분의 요청이 오면 — 앱을 다시 켠 뒤에도,
  모델을 바꿨다 돌아와도, 다른 대화가 슬롯을 덮은 뒤에도 — 다시 세지 않고 되살린다. 답 · 로그확률 · 연구 패널의 값은 끈 것과 비트까지
  같다(계약 — 정밀 모드는 CUDA 가 쓴 덩이를 Vulkan 이 읽어도 같다). 실제 Qwen Code 작업 셋을 녹화한 요청(Qwen2.5-7B)으로 쟀을 때, 서버를
  다시 켠 뒤 작업 첫 요청의 첫 토큰이 4.1 ~ 4.3 초 → 0.29 ~ 0.38 초, 슬롯 하나로 세 대화를 번갈아 보내면 첫 토큰 합이 237 → 52 초, 앱을
  껐다 켠 뒤 같은 대화를 이을 때 16,640 토큰을 0.3 초에 되살렸다. **설정 → 문맥 저장소**: 기본은 저장 위치가 SSD 면 켬 · HDD 면 끔(HDD 에서는
  되살리기가 다시 셈보다 느릴 수 있다), 위치(기본 데이터 폴더\문맥저장소) · 크기 한도(기본 20 GB — 넘으면 가장 오래 쓰지 않은 것부터) ·
  쓰기 방식(모두 · 비울 때만 · 읽기만) · '저장소 지우기'. 앱은 서버를 멈추기 전(모델 바꾸기 · 창 닫기 포함)에 쓰지 않은 덩이를 다 쓰게 한다.
  **연구 패널**: 답마다 프롬프트를 어디서 다시 썼는지(이 슬롯 · 다른 슬롯 · 저장소)와 **캐시가 깨진 자리**(몇 번째 토큰 · 그 앞 글 · 이전 →
  이번 토큰) — 에이전트가 프롬프트 앞쪽에 매번 바뀌는 것(시각 · 작업 폴더 경로 등)을 넣으면 거기서 깨지는 것이 보인다. API: 응답의
  `geulpu.store`, 요청마다 `geulpu.store: false`, 서버 인자 `--저장소` · `--저장소크기` · `--저장소쓰기`, `GET /geulpu/store` ·
  `POST /geulpu/store/flush` · `/clear`([문서/문맥저장소.md](문맥저장소.md)).
- **방 둘을 오갈 때 다시 세지 않음(슬롯 고르기, 2026-10-19)**: 새 대화가 다른 대화가 든 슬롯을 덮지 않고 덮이는 것이 가장 적은 슬롯으로
  가며, 같은 앞부분(시스템 프롬프트 등)은 다른 슬롯에서 GPU 안 복사로 받는다. 지금까지는 앞이 가장 길게 같은 슬롯만 봐서, 앱(슬롯 2)에서
  같은 시스템 프롬프트의 대화 둘을 오가면 둘 다 슬롯 0 으로 가 서로 덮었다(슬롯 1 은 놀았다). 녹화한 두 작업을 번갈아 보낸 요청 10 개의
  첫 토큰 합 44.7 → 11.6 초(답은 비트까지 같음). 응답의 `geulpu.store` 에 이 슬롯 · 다른 슬롯 · 저장소에서 다시 쓴 토큰이 나뉘어 나온다.
- **코딩 에이전트의 도구(tools, 2026-10-19)**: OpenAI 꼴 API 가 도구를 받는다 — 요청의 `tools` · `tool_choice`(auto · none) ·
  `parallel_tool_calls`, `role: tool` 메시지, assistant 의 `tool_calls`. 도구를 낀 프롬프트는 모델 파일(GGUF)의 공식 채팅 틀을 jinja2 로
  그린 글과 토큰까지 같다(Qwen2.5 · Qwen3 생각 켬 · 끔 · Llama 3.1 · 3.2 — 경우 62 개). 답의 호출(Qwen 의 `<tool_call>` · Llama 의 JSON —
  ';' 로 이어 쓴 것까지)은 `tool_calls` 와 finish_reason `tool_calls` 로(흘림이면 `delta.tool_calls`), Qwen3 의 생각은 `reasoning_content`
  로 따로. 모델이 인자를 조금 틀리게 써도(글 안의 날 줄바꿈) 받아 주고, 못 풀면 글로 돌려준다. OpenAI 공식 SDK 로 짠 코딩 에이전트가
  Qwen2.5-7B · Qwen3-8B 로 일 셋을 모두 끝냈고, 실제 에이전트 Qwen Code 가 Qwen2.5-7B 로 파일을 만들고 실행해 확인했다(시스템 프롬프트만
  14,501 토큰 — 문맥은 클수록 좋고, 기능 단위 개발은 100k 이상이 목표). 문맥을 넘으면 400 에 토큰 수와 OpenAI 꼴 `code:
  context_length_exceeded` 를 붙이고, `/v1/models` 에 `max_model_len` 을 넣었다. Mistral · R1 은 이 모델 파일의 틀에 도구가 없어 알기 쉬운
  400([문서/도구.md](도구.md)).
- **문맥을 크게 두면 Qwen 이 불러와지지 않던 결함을 고침(2026-10-19)**: 설정의 '채팅마다 문맥 길이'를 모델의 최대보다 크게(예: 131072)
  두면 Qwen2.5 · Qwen3 이 불러와지지 않았다. 이제 그래픽 메모리처럼 모델의 최대에도 맞춰 줄인다.
- **긴 대화 자동 요약(대화 압축, 2026-10-19)**: 대화가 채팅마다 문맥 길이에 가까워지면 앞의 대화를 같은 모델로 요약해(온도 0 · 생각
  끔 — 같은 대화면 같은 요약) 그 요약과 최근 차례(문맥의 30 %까지 — 글자 그대로)만 보낸다. 지금까지는 문맥을 넘으면 오류 카드로 그 채팅이
  멈췄다. 서버의 프롬프트 캐시가 앞 대화를 갖고 있어 요약 요청에서 새로 세는 것은 지시뿐이다(문맥 2,048 에서 요약 0.4 ~ 1.3 초). 대화가 한
  번에 들지 않으면(문맥을 줄였거나 모델을 바꿈) 덩이로 나눠 차례로 요약한다. 요약은 대화 안에 접힌 카드로 남고(펼쳐 봄), 요약된 앞 메시지는
  흐리게 남는다. 답 아래에 문맥 쓰임("문맥 5,210 / 8,192"), 문맥 끝에서 끊긴 답은 최대 길이 끊김과 나눠 "요약하고 다시 생성". 생성
  설정의 **긴 대화 자동 요약**(켬 — 기본)으로 끈다 — 끄면 문맥 오류 카드에 "요약하고 다시 시도". 다섯 모델(Qwen2.5 · Qwen3 생각 켬 · 끔 ·
  Llama 3.1 · Mistral · R1)에서 시험, 연구 패널의 요청 해시는 요약을 낀 답도 맞는다. 앱만 바뀌었다(엔진 · 서버 · 모듈 그대로 —
  [문서/대화압축.md](대화압축.md)).

## 0.5.1 — Llama 3.1 · 3.2 · Mistral · GeulPUv2 로 옮김 · 빠른 모드 · 추측 디코딩 · 긴 대화의 생성 고침 (2026-10-19)

- **새 버전 알림 · 배포**: 이 판부터 앱의 새 버전 알림은 GeulPUv2 의 릴리스를 본다(0.5.0 까지는 GeulPU). 파이썬의 설치 도구로 깐 앱
  (PyPI 꾸러미 `geulpu` — 꾸리기 결과를 그대로 담은 Windows x64 휠, 명령 `geulpu`)은 PyPI 의 판을 보고, 알림에 앱을 끈 뒤 쓸 업데이트
  명령(`pip install -U geulpu` · `pipx upgrade geulpu` · `uv tool upgrade geulpu`)을 보인다. 릴리스에 그 휠이 함께 붙는다([문서/배포.md](배포.md)).

- **긴 대화의 생성이 틀리던 결함을 고침(4b단계, 2026-10-19)**: 대화가 10,240 토큰을 넘으면 생성 걸음(서버의 생성 · 추측 검증 · echo
  의 끝 덩이 · 생성 그래프)의 로짓이 프롬프트 길과 달라져 **오류 표시 없이 다른 토큰**이 나오고, 31,000 토큰 근처에서는 서버가 죽을 수
  있었다. 머리 크기 128 의 모델 모두(Qwen2.5-7B · 14B · Qwen3 · Llama 3.x · Mistral · R1-7B — 정밀 · 빠름, CUDA · Vulkan)에 있었고, 설정의
  문맥을 10,240 넘게 올렸을 때만 닿는다(기본 8,192). 생성 어텐션의 접기가 조각(키 64) 160 개 몫의 칸만 공유 메모리에 두던 것을 조각
  128 개씩 무리로 돌며 앞 무리의 최댓값을 잇는 꼴로 고쳤다 — 셈의 식과 차례는 그대로라 그 앞까지의 결과는 바이트까지 같고, 이제 32,768
  토큰까지 프롬프트 길 · CPU 참조와 비트까지 같다(시험: 커널 판 대 CPU 참조, 모델 끝에서 끝, 서버의 추측 켬 · 끔 · echo, CUDA ↔ Vulkan,
  교차검증 R1 32/32). **0.5.0 까지의 판에도 같은 결함이 있다**([문서/4b단계.md](4b단계.md) · [긴문맥재기.md](긴문맥재기.md)).
- **긴 프롬프트의 어텐션이 빨라짐(4단계, 2026-10-19)**: 빠른 모드의 프롬프트 어텐션 판에서 조각마다의 가중합을 곧바로 누적에 접고(분기
  없이 — 같은 비트) 조각을 올리는 주소를 줄여 레지스터 넘침을 1,092 → 336 바이트로. 8,192 토큰의 어텐션 −10.4 %, 프롬프트 8,192 가
  llama.cpp b11721 의 1.037 배(Qwen2.5-7B Q4_K_M) · 1.110 배(Llama-3.1-8B Q4_K_M) — 아직 llama.cpp 보다 조금 길다. 4,096 까지는 세 모델
  모두 llama.cpp 보다 짧다(0.81 ~ 0.99 배). 정밀 · Vulkan 모듈은 바이트 그대로([문서/4단계.md](4단계.md)).
- **추측 디코딩 — 같은 답으로 생성이 빨라짐(3단계, 2026-10-19)**: 설정에 **추측 디코딩**(켬 — 기본 · 끔)을 더했다. 서버가 슬롯의
  토큰열(프롬프트 + 앞의 답)에서 끝과 가장 길게 맞는 자리를 찾아 그 뒤 토큰들을 초안으로 한 걸음에 검증한다(초안 모델 없음 — 행
  여덟까지, 초안 길이는 받아들임의 어림과 잰 걸음 값으로). 이 엔진은 걸음의 행 수와 상관없이 같은 비트를 내므로 **답 · 로그확률 ·
  로짓 해시 · 연구 패널의 값이 끈 것과 비트까지 같다**(시험: 요청 열일곱 × 맞는 · 틀린 · 반쯤 틀린 초안, 슬롯 넷, CUDA · Vulkan).
  Qwen2.5-7B Q4_K_M(빠른 모드 · 슬롯 1)에서 코드 고치기 · 문서 고쳐 쓰기 · 요약의 생성이 3.5 ~ 4.1 배(329 ~ 389 토큰/초 — llama.cpp
  b11721 의 가장 빠른 추측 ngram-simple 보다 1.2 ~ 2.5 배), 보통 채팅 1.0 ~ 1.5 배, 번역 1.0 배([문서/3단계.md](3단계.md)). API: 요청의
  `geulpu.speculative`(참거짓), 응답의 `geulpu.speculative · draft_proposed · draft_accepted · draft_steps`, 서버 깃발 `--추측끔`.
  연구 패널의 답 머리에 받은 초안 수. 앱의 속도 측정은 추측을 끄고 잰다(지난 기록 · llama.cpp 와 견줄 수 있게).
- **행렬곱 판의 싼 고침(2c, 2026-10-19)**: 빠른 모드의 k-양자화 타일 판(Q4_K · Q5_K)과 SwiGLU — 같은 비트로 프롬프트 −1.5 ~ −1.9 %
  (Qwen2.5-7B Q4_K_M 2,048 토큰 llama.cpp b11719 의 0.906 배 · Llama-3.1-8B 0.940 배). 정밀 · Vulkan 모듈은 바이트 그대로. 교차검증
  기준의 `build.generator` 56b42099 → 180379cc([문서/2c단계.md](2c단계.md)).

- **빠른 모드 — 프롬프트 처리가 빨라짐(2단계, 2026-10-19)**: 설정에 **계산 방식**(빠름 — 기본 · 정밀)을 더했다. 빠름은 새 계약 F1 로
  셈한다 — 행렬곱(선형층)에 들어가는 활성값을 32 칸 블록마다 8 비트 정수(llama.cpp 의 활성값과 같은 급)로, 어텐션 · 정규화 등은 그대로.
  F1 도 CPU 참조가 있는 계약이라 결정성(길 · 묶음 · 동시 요청과 상관없이 같은 비트)과 CPU 참조와의 비트 같음, 연구 패널이 모드 안에서
  그대로 선다(계약.md 1.2). 7B · 8B 의 프롬프트가 정밀 모드보다 1.3 ~ 1.6 배 빠르고(512 · 2048 토큰), llama.cpp 최신 공식 판 b11719
  (같은 GGUF · 가장 빠른 설정)보다 2048 토큰까지 빠르다 — Qwen2.5-7B Q4_K_M 0.92 · 0.93 · 0.99 · 1.09, Q8_0 0.74 · 0.77 · 0.83 · 0.95,
  Llama-3.1-8B Q4_K_M 0.94 · 0.96 · 1.03 · 1.17 배 시간(512 · 2048 · 4096 · 8192 — 번갈아 세 바퀴의 가운데). 긴 문맥에서 늦어지는 것은
  어텐션(아직 자리 둘)의 몫이다. 정밀 모드 대비 다음 토큰 분포의 차이(KL)는 k-양자화 모델에서
  llama.cpp 의 0.65 ~ 0.98 배, Q8_0 에서 2.2 ~ 2.4 배다([문서/2단계.md](2단계.md)). 정밀 모드는 0.5.0 의 계약 그대로(모듈 바이트까지)이고,
  재현성 검증과 Vulkan 장치는 늘 정밀로 셈한다. 재현 캡슐은 계산 방식을 적고, 캡슐확인은 그 방식으로 확인한다. 생성기의 실행 파일이
  바뀌어 교차검증 기준의 `build.generator` 를 새로 적었다(22fa399e → 171c328a — 정밀 모듈 · 출력의 기준은 그대로).

## 0.5.0 — 연구 패널 · 영어 화면 (38단계, 2026-10-15)

- **API — 로그확률 · 점수 · 토큰화** — 채팅의 `logprobs` · `top_logprobs`, 완성의 `logprobs` · `echo` · `max_tokens: 0`, `/tokenize` ·

- **lm-evaluation-harness** — `local-completions` + `tokenizer_backend=remote` 로 그대로 붙는다(Hugging Face 토크나이저를 받지 않는다).

- **캡슐을 GPU 없이 확인** — `도구/캡슐확인.py`(저장소 · numpy)가 계약의 CPU 참조로 토큰 · 로짓 해시 · 로그확률을 다시 셈한다.

  답의 생각을 다시 보내지 않는다. 표 · 중첩 목록 · 코드 블록 복사 · 수식(LaTeX 의 흔한 꼴)을 그린다. 다시 생성 · 고쳐 보내기 · 이어서 생성(R1) ·
  길이를 늘려 다시 생성 — 메시지는 말풍선 자리에서 고치고, 고쳐 보내기 · 다시 생성은 앞 대화를 **버전**으로 남긴다(‹ n / m › 로 넘겨 봄).
  답이 흐르는 중에도 Enter 는 답을 멈추지 않고(중지는 단추 · Esc), 다른 채팅을 보거나 탭을 옮겨도 답이 이어진다. 메모리가 모자라면 같은
  모델의 더 작은 파일을 권한다.
- **모델**: 설치된 모델은 모델마다 머리 하나 + 양자화 줄, 목록은 모델마다 카드 하나 + 양자화 고르기(양자화마다 받는 상태) + 이 PC 의
  그래픽 메모리에 맞는지(맞음 · 빠듯함 · 부족 · 미지원), 처음 쓰는 사람에게 이 PC 에 맞는 추천. 상태 막대에서 다운로드 목록(받는 중 · 멈춤 ·
  실패 — 그 자리에서 멈추고 잇기 · 받은 것 지우기). 불러온 모델 내리기.
- **Hugging Face에서 찾기**: 모델 화면에서 Hugging Face 의 GGUF 저장소를 검색해 받는다. 받기 전에 파일 앞부분(GGUF 머리)만 받아 이 엔진 ·
  이 PC 에서 실행되는지 확인하고, 맞는 파일만 받는다(SHA-256 은 Hugging Face 가 알려 주는 값으로 확인). 엔진이 받는 구조는 그대로
  qwen2(Qwen2.5 · DeepSeek-R1-Distill-Qwen 과 그 미세조정 모델).
- **벤치마크**: 결과에 잰 모델 · 큰 숫자(KPI) · 하드웨어 한계 대비 %(높을수록 좋음 — 진단 요약도), 빠른 재현성 검증은 '앞부분 일치 — 전체
  검증은 아님'으로 따로 보인다.
- **설정**은 바꾸면 바로 저장된다(모델 폴더는 있는 폴더만 — 관리자가 확인). 연결이 끊기면 띠로 알린다. 좁은 창 · 휴대폰 배치.
- **관리자(GeulPU.exe)**: 화면에 나가는 문구 약 130 곳을 표준 한국어로, 결과 목록에 잰 모델, 속도 결과의 첫 줄은 생성 속도, 진단 요약은
  한계 대비 %, 설정의 모델 폴더 확인(없는 폴더면 400). 서버 · 생성기 · 뒷단 · 커널은 바이트까지 그대로다.
