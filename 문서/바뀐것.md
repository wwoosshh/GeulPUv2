# 바뀐 것

GeulPU 앱의 버전 — 0.7.0 부터 [버전 규칙](버전규칙.md)(MAJOR 호환되지 않는 변경 · MINOR 기능 추가 · PATCH 버그 수정)을 따른다. 버전은
`앱/판.gl` 하나에 적고, 릴리스 태그 `v<버전>` 과 같아야 한다(릴리스 CI 가 비교한다). 영어판은 [CHANGELOG.md](../CHANGELOG.md). 0.5.0 까지는 연구 저장소
[GeulPU](https://github.com/wwoosshh/GeulPU) 에서 냈고, 이 저장소(GeulPUv2)가 그 소스를 이어 받아 다음 판부터 여기서 낸다. 연구의 단계
기록은 [GeulPU 의 문서/단계기록.md](https://github.com/wwoosshh/GeulPU/blob/main/문서/단계기록.md).

## 0.10.2 — 고침: 정확성 · 재현성 · 안정성 (2026-10-22)

- **YaRN 배가 남은 그래픽 메모리에 따라 바뀌지 않는다**([#18](https://github.com/wwoosshh/GeulPUv2/issues/18)): 엔진이 그래픽 메모리에
  맞춰 줄인 문맥으로 배를 정해, 같은 설정이 그때 GPU 를 쓰는 다른 것에 따라 YaRN 없음 · 배 2 · 배 4 로 셈할 수 있었다 — 예: Qwen3-8B 에
  문맥 131,072 를 주면 35,328 토큰에서는 YaRN 없이, 59,392 에서는 배 2. 이제 배는 설정한 문맥(모델의 한도까지)으로 정한다 — 두 경우 모두
  배 4. 위치 수가 32,768 보다 작은 파일(Qwen2.5-Math-7B 의 4,096 등)은 32,768 을 가정해 늘이지 않는다. 서버 상태 · 디버거 실행 로그 ·
  재현 파일은 앱이 다시 셈하지 않고 서버가 적은 배(`yarn`)를 기록한다. YaRN 이 없는 출력은 그대로다. **출력 바뀜** — YaRN 을 켠
  문맥에서 0.10.1 이 같은 설정으로 다른 배를 고른 경우.
- **같은 경로의 모델 파일을 바꾸면 옛 SHA-256 을 쓰지 않는다**([#19](https://github.com/wwoosshh/GeulPUv2/issues/19)): 앱은 모델의
  SHA-256 을 프롬프트 캐시의 시드(`--모델해시`)로 서버에 넘기는데, 같은 경로의 파일을 다른 파일(같은 구조로 다시 양자화하거나 파인튜닝한
  파일 등)로 바꿔도 `모델목록.json` 의 옛 값을 그대로 써서, 옛 파일로 쓴 청크가 새 파일의 KV 로 복원되고 답이 경고 없이 틀릴 수 있었다.
  이제 목록이 해시와 함께 그때의 파일 크기 · 수정 시각(`sha256_size` · `sha256_mtime`)을 두고, 다르면 시작할 때나 다음에 불러올 때 해시와
  확인 표시를 버리고 프롬프트 캐시에 쓰기 전에 SHA-256 을 다시 계산한다. 무결성 확인이 계산하는 중이면 옛 값을 쓰지 않고 끝날 때까지
  기다리고, 재현성 검증도 파일이 바뀌었으면 다시 계산한다. 0.10.1 까지 쓴 목록의 해시에는 시각이 없어, 화면에는 그대로 두고 프롬프트
  캐시에 쓰기 전에 한 번 더 계산한다(바이트가 같으면 확인 표시도 남는다). 다른 빠른 비교(rsync · make)처럼 크기와 수정 시각이 모두 같은
  교체는 알아채지 못한다 — 그때는 '파일 무결성 다시 확인'을 누른다.
- **도구 결과 뒤의 잘못된 메시지가 서버를 멈추지 않는다**([#21](https://github.com/wwoosshh/GeulPUv2/issues/21)): Qwen2.5 · Qwen3 의
  채팅 틀이 `tool` 메시지 다음 말을 검사하기 전에 미리 보아, 그 원소가 객체가 아니거나 `role` 이 글이 아니면 서버가 널 포인터를 읽고
  끝났다(로컬 요청 하나로 진행 중인 요청을 모두 잃음). 이제 Llama 3 · Mistral 틀처럼 모든 메시지를 먼저 검사해 400 으로 답한다
  (`/v1/chat/completions` · `/tokenize`). 맞는 요청의 프롬프트는 그대로다.
- **DeepSeek-R1-Distill-Qwen-14B 가 파일의 RMSNorm eps 로 셈한다**([#16](https://github.com/wwoosshh/GeulPUv2/issues/16)): qwen2
  구조의 커널은 eps 10⁻⁶ 을 상수로 갖고, 엔진 · 앱 모두 파일의 값을 보지 않았다. 이 목록 모델은 10⁻⁵ 이라(같은 계열의 7B · Qwen2.5 는
  10⁻⁶) 경고 없이 불러와 모든 로짓이 모델과도, GeulPU 자신의 CPU 참조와도 달랐다. 이제 eps 10⁻⁵ 인 qwen2 파일은 RMSNorm 에 10⁻⁵ 을 쓰는
  모듈(`qwen2e5…` — 생성기 `qwen2e5큰`)로 셈하고, 엔진은 모듈이 파일과 맞는지 본다. 그 밖의 eps 는 까닭을 알리고 받지 않는다. 처음
  불러올 때 새 모듈을 한 번 만든다. 14B 의 답은 바뀌고(CPU 참조와 비트까지 같아진다), 다른 모델은 그대로다. **출력 바뀜** —
  DeepSeek-R1-Distill-Qwen-14B 만.
- **RoPE 늘이기 정보가 든 Qwen2 파일을 늘이지 않은 채 돌리지 않고 거부한다**([#17](https://github.com/wwoosshh/GeulPUv2/issues/17)):
  엔진과 앱이 qwen2 구조의 `rope.scaling.type` 을 버리고 파일의 위치 수까지 늘이지 않은 RoPE 로 셈해, 커뮤니티의 “128K” GGUF(위치
  131,072)는 파일이 요구하는 늘이기 없이 긴 문맥을 셈했다. 이제 qwen3 · llama · CPU 참조처럼 그런 파일은 까닭을 알리고 받지 않는다.
  늘이기 정보가 없는 같은 모델의 파일이면 7B 이상은 엔진의 YaRN 으로 131,072 토큰까지 쓴다.
- **SentencePiece 모델의 불러오기가 가끔 실패하지 않는다**([#20](https://github.com/wwoosshh/GeulPUv2/issues/20)): 불러오는 동안
  토크나이저 일꾼이 바이트 토큰 이름(`<0x00>` … `<0xFF>`)을 서식 함수로 지었는데, 그 전역 버퍼 하나를 같은 때 주 스레드가 텐서
  이름을 짓느라 써서 서로의 글을 덮을 수 있었다 — 불러오기가 '바이트 토큰 … 가 없다' · '텐서 … 없다'로 멈췄다
  (Mistral-7B-Instruct-v0.3). 이제 일꾼은 서식 없이 짓는다. 콘솔 실행기도 서버처럼 판 고르기 일꾼(판 기억의 파일 이름을 서식으로
  짓는다)이 끝난 뒤에 쓴다.
- **repro_check · CPU 참조가 서버의 YaRN 배를 쓴다**([#23](https://github.com/wwoosshh/GeulPUv2/issues/23)): 모델의 위치 수를 넘는
  문맥(YaRN 켬)으로 기록한 실행을 늘이지 않은 RoPE 로 다시 셈해, 맞는 실행도 '다름'으로 판정했다. 이제 실행 로그의 서버 `yarn` 과 재현
  파일의 새 `made_on.yarn` 을 CPU 참조에 넘기고, 점수 줄도 배까지 같은 것만 짝지으며, 재현 파일 확인은 배가 지금 서버와 다르면 알린다.
  재현 파일에 `top_p` · `min_p` 가 없으면 실행 로그처럼 서버의 기본값(0.95 · 0.05)을 쓴다.
- **하드웨어 진단이 어휘 안의 토큰만 쓴다**([#24](https://github.com/wwoosshh/GeulPUv2/issues/24)): 진단이 스스로 만든 토큰 번호가
  1,000 ~ 100,999 라, 어휘가 작은 모델(Mistral-7B-Instruct-v0.3 의 32,768)에서는 대부분이 어휘 밖이어서 임베딩이 표 밖을 읽었다 — CUDA
  오류나 뜻 없는 시간. 이제 번호를 어휘 수로 나눈 나머지로 쓴다. 어휘가 101,000 이상(Qwen · Llama 3)이면 번호도 재는 값도 그대로다.
- **앱과 서버가 켜 둔 동안 메모리를 흘리지 않는다**([#22](https://github.com/wwoosshh/GeulPUv2/issues/22)): 화면이 1 초마다 부르는
  `/api/state` 가 받을 모델 목록을 쓰며 항목마다 글 열둘을 복사만 하고 놓지 않았다 — 부를 때마다 약 14 KB, 하루 1 GB 남짓. 앱과 서버가
  함께 쓰는 JSON 파서는 글마다 작은 머리를 남기고, 본문이 틀리면 만들던 나무를 통째로 남겼다(잘린 16 MB 본문 하나가 1 GB 남짓). 둘 다
  고쳤고, GPU 없는 빠른 점검(`시험/앱누수.py`)이 /api/state · 올바른 본문 · 잘린 본문을 되풀이해 앱의 private 메모리가 1 MB 넘게
  늘면 진다.
- **견고성 셋**([#26](https://github.com/wwoosshh/GeulPUv2/issues/26)): `cache_prompt: false` 요청은 프롬프트의 KV 를 디스크의 문맥
  저장소에 쓰지 않는다(읽기만 꺼져 프롬프트가 자료 폴더에 남았다). `rope.freq_base` 가 1 보다 큰 유한한 수가 아닌 GGUF 는 불러오기가
  멈추는 대신 거부한다. k-양자화 모델의 망가진 판 기억(튜닝 캐시)은 커널 표 밖을 가리키는 대신 버리고 다시 잰다 — 잘못된 줄 하나가 '0으로
  나누기'로 끝났다.
- **한 번 할당 한도가 작은 GPU(Vulkan)에서도 긴 문맥을 올린다**([#25](https://github.com/wwoosshh/GeulPUv2/issues/25)): KV 캐시를 모든
  층을 아우르는 할당 하나로 잡아, 할당 하나가 2 GiB 까지인 AMD 에서는 메모리가 넉넉해도 긴 문맥이 올라가지 않았다 — 슬롯 둘이면
  Qwen2.5-7B 는 약 37k, Llama 3.1 8B 는 16k 토큰을 넘을 때. 이제 한도를 넘으면 가중치처럼 층마다 따로 잡는다 — 커널이 보는 바이트는 같다.
  나눌 수 없는 버퍼(캐시의 층 하나 · 어텐션의 중간 버퍼)가 한도를 넘으면 불러오기에 실패하는 대신 알리고 문맥을 줄인다.
- **CI 가 호스트 쪽 셈을 더 본다**([#27](https://github.com/wwoosshh/GeulPUv2/issues/27)): 빠른 점검이 글(geul) 판의 뽑기 · 로그확률을
  계약의 파이썬 참조와 견주고(합이 꼭 1 · 1 바로 위인 경우를 넣은 뽑기 12,000 경우), 계약 자체 시험이 빠른 계약의 자리 하나 행렬곱과 RMSNorm
  eps 상수를 보며, `도구/` 의 파이썬도 문법 · `--help` 로 보고, 커널 생성기가 포함하는 `엔진/파일.gl` 을 커널 파일로 친다.
- **안내 문서를 코드와 맞췄다**([#28](https://github.com/wwoosshh/GeulPUv2/issues/28)): 디버거 안내 · 버전 규칙의 같은 비트 조건(모델 파일 ·
  계산 방식 · 8비트 KV 캐시 · 빠른 어텐션 · YaRN 배, 빠른 모드면 백엔드), 개발 문서의 Vulkan 서버(터미널 실행기만 CUDA), 용어집의 `엔진/`,
  repro_check 안내의 numpy 는 가상 환경(venv)에(`python -I` 는 `pip install --user` 로 깐 패키지를 보지 않는다), 버그 양식의 버전 예시
  0.10.1.

## 0.10.1 — 보안 고침 (2026-10-22)

- **추론 서버가 웹페이지 · 다른 이름의 요청을 받지 않는다**
  ([GHSA-8jjh-hfp7-hg9p](https://github.com/wwoosshh/GeulPUv2/security/advisories/GHSA-8jjh-hfp7-hg9p)): 앱은 이미 막았지만, 앱이 띄우는
  추론 서버(127.0.0.1, 포트 44545 부터)는 둘 다 보지 않고 `Access-Control-Allow-Origin: *` 를 보냈다. 이제 Host 가 `127.0.0.1` ·
  `localhost` 일 때만 받고(DNS 리바인딩), `Origin` 머리가 있는 요청은 모두 거부하며, CORS 머리를 보내지 않는다. 프로그램(OpenAI SDK ·
  코딩 에이전트 · curl)과 앱의 `/v1` 은 Origin 을 보내지 않아 그대로 쓰고, 출력도 그대로다. 빠른 점검이 이 규칙을 GPU 없이 확인한다
  (`엔진/시험_요청지킴.gl`).
- **조작된 모델 파일이 엔진의 메모리 범위 밖을 읽거나 쓰지 못한다**
  ([GHSA-4v72-rvjg-8pvw](https://github.com/wwoosshh/GeulPUv2/security/advisories/GHSA-4v72-rvjg-8pvw)): 엔진의 GGUF 읽기가 모든 길이 ·
  개수 · 중첩 깊이 · 차원 · 텐서 범위를 파일 크기와 견주고, 어기면 죽지 않고 오류로 끝난다(alignment 0, 음수이거나 너무 큰 길이, 파일 끝을
  넘는 텐서 …). 가중치를 깔기 전에 모든 행렬 · 정규화 · 치우침이 모델 설정에서 나온 모양인지 보고, 어휘가 256 보다 작으면 거부한다(앱의
  모델 검사도). 유한하지 않은 로짓에서도 뽑기가 어휘 밖의 토큰을 고르지 않는다. 정상 파일의 출력은 그대로다. 빠른 점검이 조작한 GGUF
  32 개를 열고 NaN · ±Inf 가 섞인 행을 뽑아 본다(GPU 없이 — `시험/망가진입력.py`).
- **릴리스 · PyPI 워크플로 하드닝**([GHSA-4cgh-2775-jg3m](https://github.com/wwoosshh/GeulPUv2/security/advisories/GHSA-4cgh-2775-jg3m)):
  릴리스 워크플로는 태그 이름을 PowerShell 스크립트 글에 끼워 넣지 않는다 — '$(…)' 가 든 태그가 저장소 쓰기 권한으로 명령을 돌렸다. 태그는
  환경 변수로 받아 `v<MAJOR>.<MINOR>.<PATCH>` 꼴만 받고, checkout 은 토큰을 `.git/config` 에 남기지 않는다. PyPI 워크플로는 이 판의 휠
  하나만 받고, `SHA256SUMS.txt` 에 그 이름이 꼭 한 줄 있어야 하며, 그 파일만 올린다 — 전에는 릴리스에 덧붙인 다른 휠도 검사 없이
  올라갔다. 둘 다 태그를 밀거나 릴리스를 고칠 수 있는 사람만 쓸 수 있었다.
- **SECURITY.md**: 지원 판을 0.10.x 로(0.7.x 로 남아 있었다).

## 0.10.0 — 빠른 어텐션: 더 빠른 긴 프롬프트 (2026-10-22)

- **빠른 어텐션**(설정 — 기본 끔): KV 캐시 8비트(빠른 모드 · CUDA · k-양자화 모델)를 켰을 때만 쓴다. 어텐션을 더 가벼운 꼴로 센다(계약 F2 —

  정수). RTX 4070 Ti 에서 Qwen2.5-7B Q4_K_M 의 깊이 32k · 64k 새 입력 1,024 토큰이 KV 캐시 8비트만 켰을 때보다 22.6 % · 27.6 %, 빈 프롬프트

  llama.cpp 와 토큰이 모두 같다.
- **API**: 글 프롬프트에 BOS(Llama 3 · Mistral — llama.cpp · vLLM 과 같이), `/tokenize` 의 `add_special_tokens`, `/tokenizer_info` 의 bos ·
  `add_bos_token` · `eog_token_ids`. Qwen · R1 은 앞 버전과 같다.
- **받기 전 확인 · 모델 찾기**: llama 구조를 받는다 — 헤드 크기 64 인 작은 것(Llama 3.2 1B), 질의 폭이 너비와 다른 것(Mistral NeMo), MoE
  (Mixtral), 다른 채팅 템플릿(ChatML 등)을 쓰는 미세조정은 '실행 안 됨'으로 알린다.
- **터미널 실행기**: Llama 3 · Mistral 의 채팅 템플릿으로 채팅.
- **GeulPUv2 로 옮김(0단계, 2026-10-18)**: GeulPU `main` 160df6b 의 제품 닫힘(엔진 · 생성기 · 앱 · 계약 · 빠른 점검 · 워크플로)을 새
  저장소로. `호스트/` 는 `엔진/` 으로 이름을 바꿨고 포함 경로 · 꾸리기 · 빠른점검 · 워크플로의 경로만 고쳤다 — 꾸린 서버 · 생성기 · 백엔드의

  server-vulkan 784c31e6), 빠른 점검 모두 통과, 꾸린 앱으로 7B Q4_K_M 채팅 확인(모듈 만들기 포함 34 초). 기능은 모두 그대로다(연구 패널 ·
  교차검증 포함). 연구 기록(단계 문서 · 논문 · 재기 · 파이썬 엔진 · 공식 실행)은 GeulPU 에 남겼다 — [이관범위.md](이관범위.md).
