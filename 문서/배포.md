# 배포 — 0.5.1 릴리스 · PyPI (계획 2026-10-19 — 독립 검토 뒤 고침)

## 독립 검토 (2026-10-19 — 판정: 고쳐서 진행)

새 에이전트가 계획 · 워크플로 · 관리자 · 화면 · 꾸리기와 PyPI(warehouse)의 업로드 규칙을 읽었다(파일은 고치지 않음). 앱은 site-packages
안에서도 그대로 돈다(쓰기는 모두 자료 폴더 — 설정 · 모델목록 · 일 기록 · 모듈 · 판기억 · 임시 · 결과, 자식 프로세스의 작업 폴더도 자료
폴더, 경로 함수는 모두 W API). 받은 꼭 고칠 것:

1. `도구/*` 가 .gitignore 에 걸려 휠 스크립트가 커밋되지 않는다 → `!도구/pypi/`.
2. PyPI 에 올리는 일은 리눅스(ubuntu-latest — 게시 액션은 Docker)에서, `id-token: write` 는 그 일에만.
3. `release: types: [published]`(종류를 주지 않으면 edited 등에도 돌아 둘째부터 "File already exists").
4. 실행기 · 휠 만들기 · pypi.yml · 설치 방식 알림을 모두 v0.5.1 로 태그할 커밋에(release 이벤트는 태그 커밋의 워크플로로 돈다).
5. 휠 규칙: 핵심 메타데이터 2.4 · `License-Expression: MIT` + `License-File: LICENSE`(파일은 `dist-info/licenses/LICENSE`, License 칸 ·
   License 분류자와 함께 쓰지 않음), 빠짐없는 RECORD, 디렉터리 항목 없음, 올리는 폴더에는 .whl 만.
6. **올리는 휠 = 시험한 휠**: 같은 zip 이라도 파이썬(zlib)이 다르면 다른 바이트가 나온다 → 휠은 release.yml 이 꾸리기 바로 뒤에 한 번
   만들어 초안에 붙이고 SHA256SUMS 에 넣는다. 그 초안의 휠을 로컬에서 시험한 뒤 공개하고, pypi.yml 은 SHA 를 비교해 올리기만 한다.
7. pip 알림에 "앱을 끈 뒤"(켠 채로는 실행 파일이 잠겨 업데이트가 실패)와 설치 도구마다의 명령 — 실행기가 sys.prefix 로 pip · pipx · uv 를
   가려 `GEULPU_INSTALL` 에 넣는다.
8. 0.5.0 앱의 알림은 GeulPU 의 릴리스를 본다 — **사용자 결정: GeulPU 에는 이슈만 남긴다**(0.5.0 앱에는 알림이 가지 않고, 이슈가 GeulPUv2
   0.5.1 로 안내한다).

받은 고치면 좋은 것: 노트에 붙일 절이 없으면 멈춤 · 상대 링크를 그 태그의 절대 주소로, README 의 이슈 링크, 실행기의 콘솔 코드 페이지
되돌리기 · 파일 없음 안내, pip 설치본의 새 버전 확인은 PyPI JSON(아직 PyPI 에 없는 버전으로 올리라 하지 않게) · 확인 캐시 키를 출처별로,
설치 방식을 실행 폴더(`\site-packages\geulpu\app\`)로도 가리고 값은 허용 목록으로, USERPROFILE 이 없으면 LOCALAPPDATA, 게시 액션을 커밋
SHA 로 고정 · dispatch 입력의 형식 검사, 휠 만들기 안의 버전 대조(태그 = 판.gl = version.json) · 위험한 경로 거절 · 다 쓴 뒤 RECORD 검증. 계획의
"Windows 가 아니면 알기 쉬운 오류"는 지운다(리눅스의 pip 는 win_amd64 휠을 고르지 않는다 — 실행기의 안내는 남지만 닿지 않는다).

**고친 계획의 차례**: 고침 → 로컬 꾸리기(빌드 해시 [같음] 다섯) · 휠 · venv 시험 · 빠른점검 → 커밋 · CI → 태그 v0.5.1 → 초안(zip · 휠 ·
SHA256SUMS) 받아 SHA 비교하고 휠을 venv 에 깔아 작업 포트로 시험 → 공개 → GeulPU 이슈 → (사용자가 pending publisher 등록) → 저장소 변수
`PYPI_READY=true` · pypi.yml 을 dispatch → PyPI 에서 `pip install geulpu` 확인 → README 에 pip 설치 안내 · 릴리스 노트에 한 줄.

**되돌리기**: PyPI 는 같은 버전 번호의 같은 파일 이름을 다시 받지 않는다. 휠만 잘못됐으면 빌드 태그를 붙인 새 파일
(`geulpu-0.5.1-1-py3-none-win_amd64.whl`)을 같은 버전에 올린다(pip 는 높은 빌드 태그를 고른다). yank 는 약하다(버전이 하나뿐이면 경고만 하고
설치된다).

## 왜

사용자 요청(2026-10-19): 4b 고침까지 들어간 지금 버전을 **0.5.1** 로 GeulPUv2 에서 릴리스하고, 연구 저장소 GeulPU 에는 0.5.0 의 결함을
**이슈**로 남기고, **PyPI** 로 배포해 파이썬 설치 도구(`pip` · `pipx` · `uv`) 한 번으로 실행 파일을 받아 곧바로 실행하게 한다 — zip 을

## A. 0.5.1 릴리스 (github.com/wwoosshh/GeulPUv2)

1. `앱/판.gl` 0.5.0 → **0.5.1**. 모듈 캐시가 버전마다(`%USERPROFILE%\GeulPU\모듈\<판>\`)라 0.5.1 은 고친 생성기로 모듈을 새로 만든다 — 0.5.0
   때 만든 낡은 모듈(접기 결함)을 쓰지 않는다.
2. `문서/바뀐것.md`: "다음 판 0.6.0 … (아직 릴리스하지 않음)" → `## 0.5.1 — … (2026-10-19)`. 0.5.0 뒤의 바뀐 것 모두(Llama 3.1 · 3.2 ·
   Mistral, GeulPUv2 로 옮김, 빠른 모드, 추측 디코딩, 4단계, 4b 고침)가 0.5.1 에 든다 — 버전 번호는 사용자가 정했다(SemVer 로는 기능이 늘어
   0.6.0 감이지만 따른다).
3. 릴리스 워크플로(`.github/workflows/release.yml`) 고침: 노트에 붙일 바뀐것의 경로가 `GeulPUv2/바뀐것.md`(옮기기 전 자리 — 지금은 없음 →
   초안 단계가 실패)라 `GeulPUv2/문서/바뀐것.md` 로, 노트의 설치 링크(GeulPU#설치)를 GeulPUv2 로.
4. 앱의 새 버전 확인: GitHub API 주소를 GeulPU → **GeulPUv2** 로(0.5.1 부터 GeulPUv2 의 릴리스를 본다). 알림 글은 설치 방식마다 — 관리자가
   환경 변수 `GEULPU_INSTALL`(pip 실행기가 `pip` 을 넣음)을 `/api/state` 의 `app.installer` 로 넘기고(없으면 `zip`), 화면은 pip 면
   "`pip install -U geulpu`(pipx 면 `pipx upgrade geulpu`)"를, zip 이면 지금 글을 보인다(영어 사전에 새 글).
5. README 한 · 영: 받기 링크 → GeulPUv2/releases/latest, 버전 예시 0.5.1, zip 크기, 업데이트 절. `앱/읽어보기.txt`(zip 안내)의 새 버전 안내 주소.
6. 확인: 로컬 꾸리기(빌드 해시 [같음] 다섯) · 빠른점검 · CI 초록 → 태그 `v0.5.1` → 릴리스 워크플로(windows-latest)가 꾸려 **초안**(zip ·
   SHA256SUMS) → 초안의 zip 을 받아 SHA-256 을 비교하고, 작업 포트(44639) · 작업 자료 폴더로 띄워 `/api/state` 의 버전 0.5.1 · 모델 하나 불러
   채팅 한 번 → **공개**(사용자 요청 — 워크플로는 초안까지만 하고 공개는 사람이 정하는 규칙이라 공개는 내가 `gh release edit` 로).

## B. GeulPU 이슈 (github.com/wwoosshh/GeulPU)

## C. PyPI (패키지 이름 `geulpu` — 2026-10-19 비어 있음, `geul-pu` · `geulpu-app` 도 비어 있음)

- **패키지**: 플랫폼 휠 하나 `geulpu-0.5.1-py3-none-win_amd64.whl`. 릴리스 zip 의 `GeulPU-0.5.1/` 폴더(GeulPU.exe · bin · kernels · web ·
  data · version.json · LICENSE · README.txt)를 `geulpu/app/` 에 그대로 넣고, 파이썬 쪽은 실행기 하나 — 콘솔 명령 **`geulpu`**(그리고
  `python -m geulpu`)가 환경 변수 `GEULPU_INSTALL=pip` 를 두고 `geulpu/app/GeulPU.exe` 를 받은 인자 그대로 실행한다(표준 입출력을 물려받고,
  종료 코드 그대로, Ctrl+C 는 앱이 받는다). Windows 가 아니면 알기 쉬운 오류("지금은 Windows x64 만 — 리눅스는 소스 빌드").
- **자료**: 지금처럼 `%USERPROFILE%\GeulPU`(또는 `GEULPU_HOME`). 앱은 실행 폴더(site-packages 안)에서 읽기만 한다(관리자.gl — 쓰는 곳은
  자료 폴더뿐). `pip uninstall` 은 자료를 지우지 않는다(안내에 적음).
- **휠 만들기**: `도구/pypi/휠만들기.py` — 파이썬 표준 라이브러리만(zipfile · hashlib · base64 — METADATA · WHEEL · entry_points.txt · RECORD
  를 직접 씀, 파일 차례 · 시각을 고정해 같은 zip 이면 같은 휠). 입력은 릴리스 zip 과 SHA256SUMS.txt(비교). sdist 는 올리지 않는다(바이너리
  패키지 — 빌드에 글 컴파일러 · 고정 커밋이 든다; 소스는 GitHub).
- **올리기**: `.github/workflows/pypi.yml` — 릴리스가 공개되면(`release: published`) 또는 손으로(`workflow_dispatch` — 태그를 받음) 그 릴리스의
  zip · SHA256SUMS 를 받아 비교하고 휠을 만들어 **신뢰 게시(OIDC — 비밀 토큰 없음)** 로 PyPI 에 올린다(`pypa/gh-action-pypi-publish` — 버전을
  고정, `environment: pypi`, `id-token: write`). 휠도 릴리스 자산에 붙인다.
- **사용자가 할 일**(계정 · 로그인이라 내가 할 수 없음): pypi.org 에 로그인해 "pending publisher" 하나 — 프로젝트 `geulpu` · 소유자
  `wwoosshh` · 저장소 `GeulPUv2` · 워크플로 `pypi.yml` · environment `pypi`. 그 뒤 워크플로를 다시 돌리면 올라간다.
- **확인**: 로컬에서 같은 스크립트로 휠을 만들어 새 venv 에 `pip install <휠>` → `geulpu --포트 44639 --자료 <작업 폴더> --열지않음` 으로 떠서
  `/api/state` 의 버전 0.5.1 · `installer: pip` 를 보고 끈다. PyPI 에 올린 뒤 새 venv 에서 `pip install geulpu` 로 같은 확인.
- **설치 안내**(README 한 · 영 — PyPI 에 올라간 뒤): `pipx install geulpu` 또는 `uv tool install geulpu`(권장 — 따로 떨어진 환경 · PATH),
  `pip install geulpu`, 실행 `geulpu`, 업데이트 `pipx upgrade geulpu` · `pip install -U geulpu`.

## 위험

- 릴리스 워크플로의 바뀐것 경로(A3)를 고치지 않으면 초안이 생기지 않는다.
- CI 의 꾸리기가 기준 해시와 다르면 멈춘다 — 태그 앞에 로컬 꾸리기에서 [같음] 다섯을 본다.
- PyPI 는 같은 버전 번호를 다시 올릴 수 없다(지워도) — 로컬에서 휠을 먼저 시험하고, 휠 내용이 바뀌면 버전 번호를 올린다(0.5.1.post1 은
  앱 버전과 어긋나 쓰지 않는다).
- pip 가 푼 실행 파일에는 인터넷 표시(MOTW)가 없어 SmartScreen 창이 뜨지 않는다(서명이 없는 것은 그대로).
- pip 의 콘솔 명령이 PATH 에 없을 수 있다(사용자 site 의 Scripts) — pipx · uv tool 을 권하고 `python -m geulpu` 도 둔다.
- 사용자 앱(44544)과 겹치지 않게 시험은 작업 포트 · 작업 자료 폴더로.
