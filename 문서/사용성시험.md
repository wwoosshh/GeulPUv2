# 동등성 · 사용성 시험 — 앱 리디자인 단계 F (계획과 판정, 2026-11-09)

[앱리디자인.md](앱리디자인.md) §5 의 단계 F: 두 인터페이스(GUI · CLI)가 같은 일을 하고 같은 기록을 남기는지, 그리고 처음 쓰는 사람과 AI 가
연구 과제를 끝낼 수 있는지를 시험한다. 단계 E([화면구현.md](화면구현.md))까지 GUI 의 모든 호출이 기능 목록을 거치고 모든 기능이 화면에서
닿는다는 것은 CI 가 코드로 확인한다(E6). 이 단계는 실제 기록과 실제 사용으로 확인한다. 하위 단계마다 PR 하나이고, 판정은 그 하위 단계를
실행하기 전에 적는다.

## 0. 하위 단계 3 개

| 하위 단계 | 무엇 | 바뀌는 것 |
|---|---|---|
| F1 | 같은 명령, 같은 기록 — GUI 로 만든 실험의 명령 기록을 CLI 로, CLI 로 만든 실험의 명령 기록을 GUI 의 명령 창으로 다시 실행해 실험 기록이 같은지 비교한다. 기록 비교 도구, 서로 만든 실험을 열어 보기, 찾은 차이 고침 | 시험 · 웹(고침) |
| F2 | 사용성 시험 — 같은 연구 과제를 새 AI 세션이 CLI 로, 사용자 역할의 새 세션이 브라우저로 GUI 에서 한다. 과제마다 성공 · 걸린 시간 · 막힌 곳, 두 실험의 답과 실행 비교 | 시험 · 문서 |
| F3 | 고침 — F2 에서 막힌 곳을 고치고, 과제 수행에 닿는 고침이면 새 세션으로 그 과제를 다시 확인 | 찾은 것에 따라(웹 · 앱 · 안내 · 기능 목록) |

단계 F 의 판정(앱리디자인.md §5 — 두 인터페이스의 명령 목록과 실험 기록이 같다, 과제 성공률과 막힌 곳을 기록하고 고친다)은 F1(명령 목록과
기록)과 F2 · F3(성공률과 막힌 곳)이 나눠 맡는다.

**F1 을 먼저 하는 까닭(이 문서의 제안):** 두 세션이 같은 과제를 해도 고르는 인자(상위 후보 수 · 렌즈의 상위 k 처럼 보기에만 쓰는 인자)와
순서가 달라 두 명령 목록이 글자 그대로 같을 수는 없다. 그래서 "같은 명령이면 어느 인터페이스로 보내도 같은 기록"은 다시 실행으로
엄밀하게 확인하고(F1), 세션의 시험(F2)은 과제의 답과 그 답을 낸 실행의 결과를 비교한다. F1 은 GPU 만 쓰고 세션의 토큰을 쓰지 않으며,
기록의 차이를 세션을 돌리기 전에 고친다.

## 1. F1 — 같은 명령, 같은 기록 (설계와 판정)

**비교하는 것** — 실험 폴더 둘의 기록:
- **명령 기록**(`records/commands.jsonl`): 줄마다 `op` · `method` · `path` · `params` · `status` 가 같고 줄의 순서가 같다. `time` · `ms` ·
  `source` · `session` 은 비교하지 않는다(언제 · 어디서 보냈는가). `params` 안에 그 실험 자신의 폴더 경로가 있으면(`experiment.update` ·
  `experiment.check` 의 `path`) `<experiment>` 로 바꿔 비교한다.
- **실험 파일**(`experiment.json`): 계산 방식(`geulpu.mode`) · 모델(`models` — 이름 · 파일 · SHA-256 · 크기) · 실행 목록(`runs` — `id` ·
  `kind` · `operation` · `settings` · `base` · `intervention` · `check`, 요청에 시드가 있을 때의 `seed`) · 계획 · 판정 기준 · 판정 · 결과 ·
  파일 목록. 실험의 id · 제목 · 질문 · 만든 날 · 저자는 비교하지 않는다(다른 실험이다).
- **실행 기록**(`records/runs/<id>.json`):
  - 같아야 하는 것: `op` · `path` · `status` · `model` · `server`(모델 SHA-256 · 백엔드 · 계산 방식 · KV 8비트 · 빠른 어텐션 · 문맥 ·
    YaRN) · `app` · 요청(`request`) · 답 — 글, 토큰 id, 토큰마다의 로그확률, 상위 후보(id · 로그확률), 엔트로피, 로짓 해시, 프롬프트 토큰과
    echo 의 프롬프트 값, 끝난 이유, 토큰 수. 수는 비트까지(JSON 의 수 글자가 같다).
  - 비교하지 않는 것: `time` · `ms` · `source` · `session`, 응답의 `id` · `created`, 그때의 앱 상태에 따른 일의 통계 — 캐시에서 읽은 토큰 수
    (`prompt_tokens_cached` · `usage.prompt_tokens_details`) · 프롬프트 캐시(`store`) · 슬롯 · 걸린 시간(`first_token_ms` ·
    `generate_us`) · 추측 디코딩의 초안 수(`speculative` · `draft_*`), 그리고 요청에 시드가 없을 때 서버가 고른 시드. 계약은 이것들이 결과를
    바꾸지 않는다고 하고(캐시 없이 재실행 — E6-2 에서 토큰 · 로짓 해시 16/16 같음), 비교가 그 결과로 다시 확인한다.
  - 스트리밍: 채팅 화면의 답은 스트리밍(`stream: true`)이라 기록에 이벤트(`events`)가 남는다. 명령 창의 명령 복사는 E1 부터 `stream` ·
    `stream_options` 를 빼고 적는다(CLI 와 명령 창은 응답 전체를 받는다). 그래서 다시 실행도 그 둘을 빼고 보내고, 비교 도구는 요청에서 그 둘을
    빼고, 이벤트에서 답(글 · 토큰마다의 로그확률 · 상위 후보 · 확장 필드 · 끝난 이유 · 토큰 수)을 다시 모아 스트리밍이 아닌 답과 비교한다.

**도구 — `시험/기록비교.py`**(GPU 없음, 파이썬 표준 라이브러리만):
- `compare <A> <B>` — 위의 규칙으로 비교한다. 같으면 종료 코드 0, 다르면 1 과 다른 곳(파일 · 키 · 두 값)의 목록.
- `replay <A> --to <B> --app-port <p> --geulpu <GeulPU.exe>` — A 의 명령 기록을 줄마다 CLI 로 보낸다(`GeulPU <op> --json @<본문>
  --experiment <B>`, 작업인 기능은 `--wait`). 본문은 명령 창의 명령 복사와 같은 규칙으로 만든다(스트리밍 필드를 빼고, A 자신의 경로는 B 로).
  시작 상태(불러온 모델 · 계산 방식)만 A 의 첫 실행 기록에서 읽어 기록 없이(`--experiment` 없이) 맞춘다. 그 뒤로는 명령 기록만 보낸다 —
  기록에 없는 일(예: 모델 바꾸기)이 결과를 바꾸었다면 비교가 잡는다.
- `--self-test` — 같은 사본은 같다고, 일부러 바꾼 사본 열한 가지(토큰 하나 · 로짓 해시 하나 · 로그확률의 마지막 비트 · 요청 인자 하나 ·
  명령의 `op` · 실행의 `kind` · `base` · 개입 스텝 · 실행 하나 더 · 실행 하나 빠짐 · 명령 한 줄 더)는 다르다고 판정한다. 빠른 점검의 단계로
  넣는다.

**시나리오 A — GUI 로**(브라우저에서 화면의 단추와 입력만 쓴다): 시험 인스턴스(이 가지의 웹 · 기능 목록, 다른 포트와 임시 데이터 폴더, 정밀
모드, Qwen3-0.6B Q8_0 과 같은 어휘의 Qwen3-8B Q8_0)에서 새 실험 하나에, GUI 가 실험에 기록하는 동작을 모두 한 번씩 한다.
1. 계획 탭: 계획과 판정 기준 하나를 쓴다(`experiment.update`).
2. 새 실행 — 텍스트 생성: 프롬프트 P1, 24 토큰, 온도 0.8, 시드 7, 상위 후보 10(`run.complete`).
3. 그 실행 화면: 모든 스텝의 상위 후보(`run.score`), 재실행(같은 요청), 캐시 없이 재실행, 마진이 가장 작은 스텝에서 2 위 토큰으로
   분기(`run.branch`), 다른 모델로 점수(Qwen3-8B — `model.load` · `run.score`), 이 실행의 모델 불러오기(`model.load`).
4. 스텝 · 층 화면(그 스텝): 로짓 렌즈(`run.lens`), 글의 점수(`run.tokenize` · `run.score`), 문맥 없이 점수, 토큰 id 로 점수
   (`run.detokenize` · `run.score`).
5. 새 실행 — 프롬프트의 단어 하나를 바꾼 P2(같은 설정). 비교 탭에서 A 의 답을 B 의 프롬프트로 점수(`run.score`).
6. 새 실행 — 채팅(`run.chat`, 생각 끔), Anthropic Messages(토큰 수 세기 `run.messages.count_tokens` 와 `run.messages`), OpenAI Responses
   (`run.responses`).
7. 계산 방식: 위쪽의 계산 방식 단추로 빠름으로 바꾼 뒤(실험 밖 — 기록되지 않는다) 실행 화면의 '이 실행의 계산 방식으로'(`settings.set`).
8. 결과 탭: 판정과 결과를 쓴다(`experiment.update`). 기록 탭: 점검(`experiment.check`).
9. 채팅 화면(기본 실험 "대화"): 메시지 하나(스트리밍 — `run.chat`).

**다시 실행 둘과 열어 보기**
- **GUI → CLI:** A 의 명령 기록을 CLI 로 B 에(`replay A --to B`) — `compare A B`. 채팅 화면의 실험("대화")도 같은 방법으로.
- **CLI → GUI 의 명령 창:** B 의 명령을 명령 창의 입력 줄에 하나씩 입력해 C 에(C 의 실험 화면을 연 채로 — 그 동안 친 명령은 그 실험에
  남는다) — `compare B C`. 채팅 화면의 실험도.
- **열어 보기:** CLI 로 만든 B 를 GUI 에서 연다 — 실행 목록, 실행마다 실행 화면(요약 수치 · 스텝 상세 · 정보 줄), 스텝 · 층 화면, 비교 탭.
  A 의 같은 실행과 보이는 값이 같아야 한다. A · B · C 는 CLI 의 `experiment check` 로 점검한다.

**이미 아는 차이(설계하며 찾음 — 이 PR 에서 고친다):** 실행 화면 · 스텝 · 층 화면의 '이 실행의 모델 불러오기'와 '다른 모델로 점수'의 모델
불러오기, '이 실행의 계산 방식으로'(설정 저장)는 실험 헤더 없이 불러 그 실험의 명령 기록에 남지 않는다. CLI 는 `--experiment` 를 붙이면
남는다. 그래서 GUI 로 한 실험은 명령 기록만으로 다른 모델의 점수를 다시 만들 수 없다. 고침: 실험 안의 화면에서 부른 이 둘에 그 실험의 헤더를
붙인다. 모델 화면 · 설정 화면처럼 실험 밖에서 부른 것은 그대로 둔다.

**F1 의 판정(실행 전에 적음)**
1. 비교 도구: `--self-test` 가 같은 사본은 같다고, 일부러 바꾼 사본 열한 가지는 모두 다르다고 판정한다. 빠른 점검에 넣는다.
2. GUI → CLI: 시나리오 A 의 명령이 모두 CLI 로 다시 실행되고 `compare A B` 가 같다. 채팅 화면의 실험도 같다.
3. CLI → GUI 의 명령 창: B 의 명령이 모두 명령 창에서 다시 실행되고 `compare B C` 가 같다. 채팅 화면의 실험도 같다.
4. 열어 보기: B 의 실행이 GUI 의 실행 · 스텝 · 층 · 비교 화면에서 A 의 같은 실행과 같은 값으로 보이고 페이지 오류가 없다. A · B · C 가
   `experiment check` 를 통과한다.
5. 고침과 점검: 찾은 차이(위의 이미 아는 차이를 포함)를 이 PR 에서 고치거나, 큰 것은 까닭과 함께 F3 으로 넘긴다. 기능 목록 점검 · 명령줄
   점검 · 빠른 점검이 통과한다.

판정 2 ~ 4 는 GPU 를 쓴다 — 시험 인스턴스 하나를 GPU 줄 안에서 띄운다. 앱(글) 코드는 바꾸지 않는다(바꿔야 하는 차이가 나오면 결과에 적는다).

**F1 이 하지 않는 것:** 세션의 시험(F2). 기록된 명령으로 다시 실행하는 기능을 앱에 넣는 것(실험대 2단계 — 여기의 `replay` 는 시험
도구다). 새 기능(`check.repro` · `check.same_bits` · `replay.branch` → 실험대).

1. **(설계하며 찾음) 실험 안의 화면에서 바꾼 모델 · 계산 방식이 명령 기록에 없음** → 실험 헤더를 붙인다 — '이 실행의 모델 불러오기' · '다른
   모델로 점수'의 모델 불러오기(ui/research.js), '이 실행의 계산 방식으로'의 설정 저장 · 모델 내리기 · 다시 불러오기(app.js). 반대 시험: 고치기
   전과 같은 명령 기록(그 다섯 줄을 뺀 것)으로 다시 실행하면 다른 곳이 218 곳이고, 모두 r6(다른 모델로 매긴 점수가 Qwen3-0.6B 로 계산됨 —
   217 곳)과 실험의 모델 목록(1 곳)이다.
2. **명령 창의 명령 글이 줄바꿈이 든 글 인자를 줄바꿈째 적음** — `--plan '…'` 를 명령 창의 입력 줄(한 줄 입력)에 넣으면 줄바꿈이 지워진다
   (계획 · 결과 글). → 줄바꿈이 든 글은 `--json` 으로 적는다(JSON 이 `\n` 으로 적어 한 줄이 된다 — ui/command.js). 명령 창 점검에 그 경우와
   '명령 쓰기는 한 줄' 검사를 더했다.
3. **명령 창이 `experiment create` 를 보던 실험에 남김** — 실험 화면을 보는 동안 친 POST 명령에는 그 실험이 붙는데(E3), 새 실험을 만드는
   명령도 보던 실험의 명령 기록에 남았다(채팅 실험을 만들며 찾음). → 새 실험을 만드는 명령과 `path` 로 다른 실험을 가리키는 실험 명령에는
   붙이지 않는다(ui/console.js). 고친 뒤 CLI 실험을 보며 `experiment create` 를 쳐도 그 실험의 명령 기록은 25 줄 그대로다.
4. 비교 도구: OpenAI Responses 의 응답 시각은 이름이 `created_at` 이다 — 비교하지 않는 값에 더했다(도구의 고침).

- **시험:** 시험 인스턴스 하나(포트 44670, 임시 데이터 폴더, 정밀 모드) — E6 의 패키지(main 의 GeulPU.exe)에 이 가지의 웹 · 기능 목록,
  Qwen3-0.6B Q8_0 과 Qwen3-8B Q8_0. GPU 줄 1,099 초. 앱(글) 코드는 바꾸지 않았다.
- **설계에 더한 것:** (1) 시나리오의 분기 — 마진이 가장 작은 스텝(3)에서 샘플링된 토큰이 2 위("I")라, 두 후보 가운데 샘플링되지 않은 1 위
  토큰("The")으로 분기했다. (2) Anthropic Messages · OpenAI Responses 는 시드를 받지 않아 온도 0 으로 했다 — 온도가 0 보다 크면 서버가
  시드를 골라 어느 인터페이스로든 다시 실행한 답이 다를 수 있다(새 실행 창이 그렇게 알린다). (3) 스텝 · 층 화면의 '상위 후보 계산'도
  시나리오에 넣었다 — GUI 가 기록하는 동작이다. (4) 명령 창으로 다시 실행할 때의 명령 글은 명령 창의 '명령 복사'와 같은 함수(toCommand)로
  만들었다.

## 2. F2 — 사용성 시험 (안 — 판정은 실행 전에 확정)

- **세션 둘:** (가) 새 AI 세션 — CLI 만 쓴다(`GeulPU guide` 에서 시작 — C3 과 같은 조건). (나) 사용자 역할의 새 세션 — 브라우저로 GUI 만
  쓴다(앱의 주소와 과제만 받고, 화면의 설명으로 한다). 둘 다 이 대화의 맥락이 없고 저장소의 코드를 읽지 않는다.
- **과제(값을 정해 두 세션에 같은 답이 나오게):** R1 마진이 가장 작은 스텝과 두 후보 · 마진, R2 그 스텝에서 2 위 토큰으로 분기한 글,
  R3 · R4 프롬프트의 단어 하나를 바꿨을 때 처음 달라지는 스텝과 두 토큰의 확률, R5 샘플링된 토큰이 1 위가 되는 첫 층, R6 재현 파일을 만들고
  확인 — 모델 더하기 · 불러오기부터.
- **잴 것:** 과제마다 성공(내가 따로 낸 기준값과 같은가) · 걸린 시간 · 도구 호출 수 · 막힌 곳(오류 · 설명이 없어 헤맨 것). 두 실험에서 과제의
  답을 낸 실행의 결과가 같은가(F1 의 도구).
- **비용(어림):** CLI 세션은 토큰 15 ~ 25 만 · 10 분 안팎(C3 은 16 만 · 7 분). GUI 세션은 화면을 읽느라 더 든다(50 ~ 100 만 · 30 ~ 60 분).
  시험 인스턴스는 GPU 줄 안에서.

## 3. F3 — 고침 (F2 뒤)

F2 의 막힌 곳마다 고칠 곳(화면 · 안내 · CLI · 기능 목록)과 고침. 과제 수행에 닿는 고침이면 새 세션으로 그 과제를 다시 한다.

## 4. 하지 않는 것(단계 F)

- 다른 AI 로 하는 시험 — 같은 모델의 새 세션으로만 한다(C3 과 같이 남긴 것).
- 사용자 안내서 고침 — 단계 G(릴리스)에서.
