# 실험대 — 실험 기록과 PyTorch 모델 시험 (계획, 2026-11-08)

사용자 요청(2026-11-08): "실험기록을 중심에 두기위해서 저장소에 여러 실험기록들을 함께 저장하도록 폴더구조를 만들어야할것 같아. pytorch에서
모델을 만들면 그것을 geulpu플랫폼에서 실험하는 실험대가 되도록 하는게 좋을것 같아." 이 문서는 그 계획이고, 결정은
6 절에 있다. 화면과 명령 쪽은 [앱리디자인.md](앱리디자인.md). 각 단계의 판정 기준은 그 단계를 실행하기 전에 확정한다.

## 0. 요약

- **바탕:** 실험 하나 = 폴더 하나. 모델 · 설정 · 난수 · 개입 · 판정 기준 · 결과 · 기대값(해시)을 한곳에 두고, 그 폴더만 있으면 누구든 다른
  GPU 에서 같은 비트로 다시 낸다. 저장소에 이 폴더들을 모으는 최상위 폴더를 둔다.
- **PyTorch 에서 GeulPU 로:** 연구자가 PyTorch 로 만든 모델을 GGUF 로 내보내고, PyTorch 원본과 같은 결과를 내는지 먼저 대조한 뒤, GeulPU 에서
  관찰 · 개입 · 비교 실험을 하고 그 기록을 남긴다. 학습과 기울기가 드는 분석은 PyTorch 의 몫으로 두고, GeulPU 는 forward 계산의 실험대가 된다.
- **이미 있는 것이 많다.** 연구 패널 · 디버거 · llama 재현 영수증 · 모델 평가(Hugging Face 폴더 → GGUF) · 파이썬 API · 층 렌즈 · F16/BF16/F32
  GGUF 가 있다. 빠진 것은 이것들을 실험 단위로 묶는 형식과 자리, PyTorch 원본과의 대조, 직접 짠 모델을 내보내는 길, 활성값을 읽고 바꾸는 개입이다.
- **단계 일곱.** 1 ~ 4 는 엔진의 계산을 바꾸지 않아 1.0.0 작업과 함께 갈 수 있고, 5 · 6 은 엔진 · 계약을 바꾼다.

## 1. 이미 있는 것과 빠진 것

| 있는 것 | 하는 일 | 기록이 남는 곳 |
|---|---|---|
| 연구 패널(38단계) | 답 하나 — 스텝마다 확률 · 분기 · 비교 · 점수 · 층 렌즈, 재현 파일 내보내기 | 브라우저 안(최근 60 개), 내보낸 재현 파일 |
| 디버거 v1 | 실행(요청 여럿) 단위의 기록 · 재생 · 중단점 · 분기 · 비교, `도구/debugger.py`, GPU 없는 확인 `도구/repro_check.py` | 앱 자료 폴더의 실행 로그(JSONL) |
| llama.cpp 재현(1 ~ 39단계) | llama-server 실행을 영수증으로 기록하고 비트 단위로 다시 계산 | 앱 자료 폴더의 영수증 · 결과 폴더. `repro-kit/llama-replay/receipts/` 에 영수증 6 개(0.25 ~ 0.6 MB씩)를 저장소에 둔 선례가 있다 |
| 모델 평가(0.17.0) | 작업 공간(기준 모델 + 비교할 GGUF 들), Hugging Face 폴더(config.json · safetensors) → BF16 · F16 · Q8_0 GGUF 만들기(llama.cpp 의 변환 스크립트), 양자화 비교 | 앱 자료 폴더 |
| 파이썬 API | `load` · 생성 · `score` · `branch`(원래 난수로 잇는 토큰 분기 — `step_offset`) · `compare` · `info(provenance=True)` | 호출한 쪽이 저장 |
| 층 렌즈 | 계약 5.3 · CPU 참조 · 서버 `geulpu.layer_lens`. Jacobian lens 는 진행 중 | 연구 패널 · API |
| 블록 조합 · 구조표 | 층을 블록(어텐션 · GDN · SwiGLU · MoE · Gemma 4 의 블록)의 조합으로 짓는다. 구조 하나 = `구조/<이름>/` 폴더와 등록 두 줄 | — |

**빠진 것**
1. 기록 형식이 넷(재현 파일 · 실행 로그 · 영수증 · 모델 평가 작업 공간)이고 저장 위치가 흩어져 있다. 실험 단위로 묶는 형식과 자리가 없다.
2. 실험의 물음 · 가설 · 판정 기준과 결과가 기록과 함께 있지 않다(지금까지의 연구 기록은 저장소 밖의 문서 · 작업 폴더 · 일회용 스크립트에 흩어져 있다).
3. PyTorch 원본과 GeulPU 의 결과를 대조하는 기능이 없다(디버거 계획의 v2 (가)).
4. 직접 짠 PyTorch 모델(Hugging Face 형식이 아닌 것)을 GGUF 로 내보내는 길이 없다.
5. 활성값(activation)을 읽어 내거나 바꿔 넣는 개입(activation patching)이 없다(디버거 계획의 v2 (나)).
6. llama 재현 실행에서 같은 난수로 설정만 바꾼 반사실(counterfactual)은 아직 재현 호스트를 직접 부르는 스크립트로만 된다.

## 2. 실험 기록의 형식

**실험 하나 = 폴더 하나.**

```
<실험 폴더>/
  experiment.json   기계가 읽는 기록(형식 geulpu-experiment/1)
  plan.md           물음 · 가설 · 판정 기준 — 실행 전에 커밋한다
  results.md        결과 · 판정
  records/          다시 내는 데 필요한 기록 — 실행 로그(.jsonl.gz) · 영수증(.json.gz) · 재현 파일
  expected.json     실행 · 분기마다 토큰과 로짓 해시
  scripts/          쓴 스크립트(정식 기능으로 옮기기 전까지만)
```

**experiment.json 의 필드**(키는 영어 — 영수증 · 실행 로그처럼 바깥 연구자가 읽는다)

| 필드 | 뜻 |
|---|---|
| `format` | `geulpu-experiment/1` |
| `id` · `title` · `question` | 폴더 이름과 같은 번호, 제목, 한 줄 물음 |
| `status` | `planned` · `running` · `done` |
| `created` · `authors` | |
| `geulpu` | 판 · 커밋 · 계산 방식 · 모듈 해시 — 파이썬 API `info(provenance=True)` 그대로 |
| `devices` | GPU · 드라이버 |
| `models` | 이름 · 파일 · SHA-256 · 크기 · 형식 · 출처(Hugging Face 저장소 · revision · 파일, 또는 PyTorch 에서 내보낸 스크립트와 입력의 해시) |
| `engines` | 다른 엔진(llama.cpp 빌드 등) — 재현 실험일 때 |
| `runs` | 실행마다 번호 · 종류(생성 · 점수 · 렌즈 · 재현 · 평가) · 기록 파일 · 설정 · 시드 · 바탕 실행(분기면) · 개입(종류 · 스텝 · 값) |
| `criteria` | 판정 기준(실행 전에 적음)과 결과 |
| `reproduce` | 다시 내는 명령과 `expected.json` |
| `links` | 관련 실험 · 문서 · 논문 |

**무엇을 저장하나**
- 다시 계산할 수 있는 것(스텝마다 확률 · 상위 k · 엔트로피)은 저장하지 않고 해시로 확인한다 — 디버거 v1 의 원칙 그대로.
- 모델 파일은 저장하지 않는다. SHA-256 과 출처로 가리킨다.
- **크기 기준:** 실험 하나는 압축해서 5 MB 이하. 넘는 원자료는 릴리스 첨부나 바깥 저장소에 두고 SHA-256 으로 가리킨다(6 절의 결정 2).
- **기준이 먼저:** `plan.md` 와 `criteria` 를 실행 전에 커밋하면, git 이력이 "판정 기준을 결과보다 먼저 적었다"를 보여 준다.

## 3. 저장소 폴더

```
experiments/
  README.md                  실험 기록이 무엇이고, 어떻게 더하고, 어떻게 확인하나(README.ko.md 함께)
  index.md                   실험마다 한 줄: 번호 · 제목 · 모델 · 상태 · 결론 · 폴더
  _template/                 새 실험의 틀
  <YYYY-MM-DD>-<이름>/        실험 하나(2 절의 폴더)
  …
```

- 최상위에 두는 까닭: 계약 · 교차검증 · repro-kit 처럼 저장소의 다른 부분과 같은 위치에서, 실험이 코드의 버전과 함께 남는다.
- `repro-kit/` 은 바깥 사람이 돌리는 키트로 그대로 두고, 그 결과(독립 시험 등)는 나중에 실험 폴더로 가리킬 수 있다.
- 확인 도구 `도구/experiment_check.py`(안): 형식 · 필드 · 크기 · 포함 파일의 SHA-256 · 링크를 GPU 없이 확인하고, `--rerun` 이면 앱(GPU)이나 CPU
  참조(작은 모델)로 다시 돌려 `expected.json` 과 견준다. CI 의 `check` 에는 GPU 없는 확인만 넣는다.

## 4. PyTorch 모델을 GeulPU 에서 시험하는 길

| 연구자가 하는 일 | GeulPU 가 주는 것 | 지금 |
|---|---|---|
| 1. PyTorch 로 모델을 만든다(Hugging Face 형식, 또는 직접 짠 `nn.Module`) | — | — |
| 2. GGUF 로 내보낸다(학습 직후라 F32 · F16 · BF16) | Hugging Face 형식 + 지원 구조: 모델 평가의 'GGUF 만들기'. 직접 짠 모델: 내보내기 도구 | 앞은 됨, 뒤는 없음(단계 5) |
| 3. PyTorch 원본과 대조한다 | 같은 토큰열로 위치마다 분포 비교 — KL · 1위 일치 · 최대 로그확률 차 · 크게 갈라진 자리. "GeulPU 가 내 모델을 제대로 계산하나"의 확인이 그 모델의 첫 실험 기록이 된다 | 없음(단계 4) |
| 4. 실험한다 | 관찰: 스텝마다 확률 · 층 렌즈. 개입: 토큰 분기 · 같은 난수 설정 반사실 · 활성값 바꾸기. 비교: 체크포인트 · 양자화 | 관찰 · 토큰 분기 · 비교는 됨, 설정 반사실은 스크립트(단계 3), 활성값은 없음(단계 6) |
| 5. 기록을 남기고 나눈다 | 실험 폴더 — 누구든 같은 비트로 다시 낸다 | 없음(단계 1 ~ 3) |
| 6. 기울기가 드는 분석(SAE · 기여도)을 한다 | 활성값을 numpy · safetensors 로 내보내 PyTorch 에서 | 없음(단계 6) |

**경계:** 학습과 기울기는 PyTorch 에 둔다(디버거 계획과 같은 경계 — forward 의 관찰 · 개입 · 정확한 재현 · 비교). GeulPU 에 없는 연산을 쓰는 모델은
그 연산을 블록으로 더해야 시험할 수 있다(구조 더하기 — 계약 · CPU 참조 · 커널). 지금은 GeulPU 개발자가 더하는 길만 있다.

## 5. 단계

| 단계 | 무엇 | 엔진 · 계약 변경 | 판정(안 — 실행 전에 확정) |
|---|---|---|---|
| 1 | 실험 기록 형식(`문서/실험대.md` + 영어), `experiments/` 의 README · index · 틀, 확인 도구, CI 의 GPU 없는 확인 | 없음 | 틀이 확인을 통과하고, 일부러 망가뜨린 기록 셋(해시 틀림 · 크기 넘음 · 필드 빠짐)을 모두 잡는다. CI 에서 10 초 안 |
| 2 | 지금의 기록(재현 파일 · 실행 로그 · 영수증)을 실험 폴더로 감싸는 도구, 첫 실험 폴더 | 없음 | 실험 폴더만으로 다시 돌린 결과가 `expected.json` 과 같다(토큰 · 로짓 해시 — GPU, 작은 모델은 CPU 참조로도) |
| 3 | 파이썬 API 의 실험 기록(`geulpu.Experiment` — 생성 · 분기 · 점수 · 렌즈 · 비교 호출을 폴더에 적음, 기준을 먼저 적는 필드), 같은 난수 설정 반사실을 정식 기능으로(GeulPU 자체 실행과 llama 재현 모두) | 서버 · 앱 API | 같은 설정의 분기는 원래와 같다. 스텝 0 부터 설정을 바꾼 분기는 그 설정의 실제 실행과 같다 — 같은 난수 반사실의 두 점검을 정식 기능으로 |
| 4 | PyTorch 대조 — 파이썬 패키지의 선택 기능(torch · transformers 가 있을 때). Hugging Face 형식 모델 먼저 | 없음 | 기준 모델 둘(F16 GGUF 대 PyTorch fp32)에서 끝까지 돌고 값을 낸다. 일부러 틀리게 변환한 파일 둘(예: RoPE θ · 정규화 eps 를 바꿈)을 모두 잡는다(음성 대조) |
| 5 | 직접 짠 PyTorch 모델 — (가) Hugging Face 의 지원 구조 클래스로 크기만 바꾼 모델(바로 됨 — 예시와 안내), (나) 지원 블록으로 쌓은 임의의 모델을 층 구성 메타데이터와 함께 GGUF 로 내보내기(먼저 가능성 확인), 그리고 PyTorch 로 학습한 작은 예시 모델 | (나)는 구조 하나 더하기 | 작은 모델이 단계 4 의 대조를 통과하고, 그 실험 폴더가 CUDA · Vulkan · CPU 참조에서 같은 비트 |
| 6 | 활성값 읽기 · 바꾸기 — 계약의 '읽어 내기 · 써 넣기' 항목, CPU 참조, 서버 · API, numpy · safetensors 내보내기 | 계약 · 엔진 | 자기 값으로 바꾸면 원래와 같다. GPU 와 CPU 참조가 비트까지 같다. 기준 모델에서 같은 개입의 효과가 TransformerLens 같은 원래 구현과 같은 방향이고 미리 정한 허용 오차 안 |
| 7 | 화면(실험 목록 · 열기 · 다시 내기 확인, 연구 패널과 디버거의 '실험으로 저장') · 안내서(한국어 · 영어) | 앱 | 릴리스 판정 |

- 차례: 1 → 2 → 3 → 4 → 5. 6 은 3 뒤라면 4 · 5 와 따로 갈 수 있다. 7 은 릴리스 때.
- 단계마다 PR 하나 이상, 저장소 규칙대로(가지 → PR → CI → 스쿼시 병합). GPU 를 쓰는 확인은 GPU 큐로.
- 단계 5 (나) 앞에서 확인할 것: 블록 조합의 일반 경로(헤드 크기 32 ~ 256 · 아무 너비)가 어디까지 됐는지. 2026-10 기준 개발 문서에는 헤드 크기 64 의
  작은 llama 가 아직 없는 것으로 적혀 있다.

## 6. 결정(2026-11-08, 사용자 "추천대로해")

1. **공개 범위:** 저장소(공개)에는 공개해도 되는 실험만 둔다. 바깥 프로젝트의 버그를 다룬 사례 연구는 올리지 않는다.
2. **크기:** 실험 하나는 압축해서 5 MB 이하. 넘는 원자료는 바깥에 두고 SHA-256 으로 가리킨다. Git LFS 는 쓰지 않는다.
3. **폴더 이름:** `experiments/`(바깥 연구자가 읽는 폴더라 repro-kit · docs 처럼 영어).
4. **1.0.0 과의 순서:** 단계 1 ~ 4 는 1.0.0 과 함께, 5 · 6 은 1.0.0 뒤.
5. **첫 실험:** 연구자안내의 실험 여덟(이미 공개된 내용)을 첫 실험 폴더로 만든다.

## 7. 앱 리디자인 계획과의 연결

같은 날 정한 [앱리디자인.md](앱리디자인.md)(연구용 GUI 와 AI 용 CLI, 둘의 동등성)와 한 계획으로 간다. 이 문서의 1단계(실험 기록 형식)는 그 계획의 B 단계에, 3단계(파이썬 API 의 실험 기록 · 같은 난수 반사실)는 B · C 단계의 기능으로, 4단계(PyTorch 대조)는 C 단계 뒤 기능 목록의 새 기능으로, 7단계(화면)는 D · E 단계로 들어간다. 5 · 6단계는 1.0.0 뒤 그대로다.
