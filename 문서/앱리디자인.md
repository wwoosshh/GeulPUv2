# 앱 리디자인 — 연구용 GUI 와 AI 용 CLI (계획, 2026-11-08)

사용자 요청(2026-11-08): "현재 앱디자인은 일반적인 추론엔진용으로 채팅을 하는것에 목적이 맞추어져 있는데 연구용이 되기 위해서 그것에 맞는 위계를
갖는 레이아웃과 UX를 구현하려고 해. 특히 UX가 중요해. … 여러 기능들이 사용자에게 노출되지 않고 명령어나 cli로 숨겨져서 일반사용자가 이해하거나
사용하기 어려운 기능이 되어버리는거야. … ai용 cli버전과 gui버전 두가지에 대한 작업이 필요하고 거기에 차이가 발생하면 안돼."

같은 날의 [실험대.md](실험대.md)(실험 기록 · PyTorch 모델 시험)와 한 계획으로 간다. 이 문서는 그 화면과 명령의 쪽이고, 결정은 6 절에
있다. 각 단계의 판정 기준은 그 단계를 실행하기 전에 확정한다.

## 0. 요약

- **기능은 하나, 인터페이스는 둘.** 모든 기능을 앱 API 의 기능 목록(operation registry) 하나에 등록하고, GUI 와 CLI 는 그 목록을 부르기만 한다. 어느 한쪽에만
  있는 기능이 생기지 않게 목록에서 CLI 를 만들고, GUI 의 모든 동작이 목록의 기능을 부르는지를 CI 가 확인한다.
- **같은 기록.** GUI 로 하든 CLI 로 하든 같은 실험 기록이 남는다. AI 가 CLI 로 한 실험을 사람이 GUI 로 열어 이어 하고, 그 반대도 된다.
- **화면을 좌우로 나눈다(사용자 제안).** 왼쪽은 GUI, 오른쪽은 GeulPU 명령 창이다. GUI 로 한 일은 오른쪽에 같은 일을 하는 CLI 명령으로 찍히고,
  AI 가 CLI 로 친 명령도 오른쪽에 그대로 보이면서 왼쪽 GUI 에 반영된다. 명령 창에 쌓인 명령 목록이 그 실험의 작업 기록이 된다(3 절).
- **연구의 위계로 화면을 다시 짠다.** 지금은 채팅이 중심이고 연구 패널이 채팅 옆에 붙어 있다. 새 화면은 실험 → 실행 → 스텝 → 층의 위계를 따르고,
  채팅은 실험 안의 도구 하나가 된다.
- **숨은 기능 0.** 지금 스크립트 · API 요청 필드로만 되는 기능(예: llama 재현의 반사실, 같은 비트 확인, Jacobian lens 맞추기)을 모두 화면에 올린다.
  오른쪽 명령 창이 같은 일을 하는 CLI 명령을 늘 보여 준다.
- **UX 를 먼저 검증한다.** 연구 과제(사용자 여정)를 먼저 정하고, 와이어프레임을 사용자가 검토한 뒤 구현하고, 새 사용자 역할의 세션이 GUI 로, AI 가
  CLI 로 같은 과제를 해 보는 사용성 시험으로 판정한다.

## 1. 지금의 앱

| | 지금 |
|---|---|
| 화면 | 왼쪽 레일의 보기 여덟 — 채팅 · 모델 · 벤치마크 · 디버거 · 모델 평가 · 에이전트 · 장치 · 설정. 연구 패널은 채팅 옆에 붙는다 |
| 웹 코드 | `앱/web/app.js` 677 KB · `eval.js` 243 KB · `app.css` 81 KB — 파일 하나에 거의 모든 화면이 들어 있다. 바깥 자원 없음, 한국어 · 영어(`DICT` — 한국어 열쇠) |
| 앱 API | `/api/…` 경로 61 개(모델 평가 17 · 디버거 7 · 모델 6 · llama 재현 4 · 벤치 4 · 결과 3 · Hugging Face 3 · 그 밖). 오래 걸리는 일은 `/api/job` |
| 서버 API | OpenAI 호환 `/v1/…` 과 GeulPU 의 요청 필드(`geulpu.logit_hash` · `echo` · `step_offset` · `layer_lens` …) |
| 명령 | `geulpu`(파이썬 꾸러미 — 앱을 띄움, `--검사` 로 화면 없는 검사 하나), 스크립트 `도구/debugger.py` · `repro_check.py` · `same_bits.py` · `jlens_fit.py` |
| 파이썬 API | `geulpu.start` · `load` · 생성 · `score` · `branch` · `compare` · `info` |

**보이는 문제**
1. 기능이 네 갈래(화면 · 앱 API · 서버 요청 필드 · 스크립트)에 흩어져 있고, 어느 기능이 어디서 되는지 한눈에 볼 표가 없다.
2. 일부 기능은 화면에 없다 — 서버 요청 필드, 스크립트로만 되는 확인 · 맞추기, llama 재현의 반사실처럼 재현 호스트를 직접 부르는 실험.
3. 화면의 위계가 채팅 중심이다. 연구의 단위(실험 · 실행)가 화면에 없고, 연구 패널의 기록은 브라우저 안에만 남는다.
4. 웹 코드가 큰 파일 하나라 화면을 나눠 고치기 어렵다.

## 2. 원칙

1. **기능 목록이 기준이다.** 기능마다 이름(예: `run.branch`), 인자(형 · 기본값 · 한국어 · 영어 설명), 결과의 형식, 오래 걸리는 일인가, 실험 기록에
   무엇을 적는가를 적는다. 앱 API 는 이 목록대로 받고, CLI 는 이 목록에서 만들어지고, GUI 의 동작은 이 목록의 이름을 부른다.
2. **동등성을 시험으로 지킨다.** CI 가 (가) 목록의 모든 기능에 CLI 명령이 있는지, (나) GUI 의 모든 동작이 목록의 기능을 부르는지 · 목록의 모든 기능이
   GUI 에서 닿는지(내부용으로 표시한 것은 까닭과 함께 빼기)를 확인한다. 연구 과제를 CLI 와 GUI 로 각각 해서 실험 기록이 같은지(시각 · 인터페이스 필드 빼고)를
   시험으로 둔다.
3. **AI 용 CLI 의 형식.** 묻지 않고 끝까지 돈다(대화형 입력 없음). 결과는 기본이 JSON, 사람용은 `--text`. 정해진 종료 코드. 오류도 JSON — 까닭과
   다음에 할 일. `geulpu 기능 목록 --json` 이 모든 기능과 인자를 설명해 AI 가 스스로 찾는다. 오래 걸리는 일은 일 번호를 돌려주고 `--기다림` 으로 끝을
   기다린다. 실험 폴더를 작업 맥락으로 받는다(`--실험 <폴더>`).
4. **GUI 의 형식.** 과제 중심(사용자 여정에서 출발), 점진적 공개(progressive disclosure — 기본은 단순하게, 고급 설정은 접어 두되 숨기지 않음), 쉬운 이름
   (질문형 · 비유형 이름 없음, 표준 용어), 숫자마다 뜻을 그 자리에서 설명, 출처 막대(계산 방식 · GeulPU 판 · 모델 해시 · 시드)를 늘 보이기, 오래
   걸리는 일의 진행 · 취소, 모든 결과의 명령을 오른쪽 명령 창에 보이기(3 절 — 복사할 수 있다), 창마다 따로 스크롤.
5. **리팩터링은 화면을 바꾸며 함께.** 큰 파일을 영역별 모듈(실험 · 실행 · 모델 · 비교 · 재현 · 설정)과 공통 구성 요소(토큰 표 · 확률 그림 · 출처 막대 ·
   일 진행 · 기록 보기)로 나눈다. API 를 부르는 클라이언트는 기능 목록에서 만들어 CLI 와 같은 것을 쓴다. 옛 화면은 새 화면이 그 일을 다 할 때까지 둔다.

## 3. 좌우 배치 — 왼쪽 GUI, 오른쪽 명령 창 (사용자 제안, 2026-11-08)

사용자: "화면을 좌우로 나누고 왼쪽에는 Gui를 두고 오른쪽에는 커맨드창을 그대로 보여주는 cli를 만들어서 자신이 gui로 돌릴때에도 뒷쪽 cli를
보여주고 외부 ai를 통해서 연구할때에도 ai가 입력하는 cli를 그대로 화면에 보이면서 gui로도 반영되는 구조"

| 경우 | 왼쪽(GUI) | 오른쪽(명령 창) |
|---|---|---|
| 사람이 GUI 로 | 누른 기능의 결과 | 같은 일을 하는 CLI 명령과 진행 · 결과 |
| 사람이 명령 창에 직접 입력 | 결과가 화면에 반영된다 | 입력한 명령과 진행 · 결과 |
| AI 가 자기 터미널에서 CLI 로 | 결과가 화면에 반영된다("AI 따라가기"를 켰을 때 그 실행으로 넘어감) | AI 세션 이름과 명령, 진행 · 결과 |

**정한 것**
1. **명령 창은 운영체제 셸이 아니다.** 앱이 받은 GeulPU 기능 호출만 보이고, 직접 입력하는 줄도 GeulPU 명령만 받는다. 로컬 웹 앱 안에 진짜
   셸을 열면 아무 명령이나 실행될 수 있어 위험하다. AI 는 자기 터미널에서 명령을 치고, 그 명령이 앱 API 를 부르므로 명령 창에 나타난다.
2. **보이는 것은 기능 호출만.** 계산하거나 기록을 바꾸는 기능 목록의 호출만 찍는다. 탭 열기 · 스크롤 · 토큰 눌러 보기 같은 보기 동작은 찍지
   않는다. 줄마다 출처(GUI · 사용자 CLI · AI 세션 이름 · 파이썬) · 명령 전체 · 진행 상태 · 결과 요약 · 기록 링크를 적는다.
3. **어디서 온 호출이든 GUI 가 따라 바뀐다.** 앱이 기능 호출마다 시작 · 진행 · 끝 · 기록 저장을 이벤트로 내보내고(event stream), 화면은 그것을
   받아 갱신한다. 기능 목록에 결과 형식마다 그것을 보여 줄 화면을 적고, 모든 결과 형식에 화면이 있는지를 CI 가 확인한다.
4. **사람과 AI 가 함께 움직일 때.** 명령은 늘 실험 · 실행 번호를 직접 가리킨다("지금 열린 실험" 같은 숨은 상태를 두지 않는다). GPU 작업은 GPU
   큐로 차례를 지킨다. 화면은 "AI 따라가기"를 켰을 때만 AI 의 실행으로 넘어간다 — 사람이 보던 화면이 갑자기 바뀌지 않는다.
5. **자리.** 명령 창은 폭을 조절하고 접을 수 있다. 좁은 화면에서는 아래쪽 창이 된다. 두 창은 따로 스크롤한다.
6. **기록과 이어짐.** 명령 창의 명령 목록은 실험 폴더의 작업 기록(`records/commands.jsonl` — 기능 이름과 인자, 화면 언어와 상관없음)으로 남고,
   "다시 내기"는 그 명령들을 다시 돌리는 일이다.

## 4. 새 화면의 위계(안 — 와이어프레임 단계에서 사용자와 확정)

| 층 | 화면 | 담는 것 |
|---|---|---|
| 1. 레일 | 실험 · 모델 · 재현 · 일 · 설정 | 실험(첫 화면 — 실험 목록 · 새 실험), 모델(파일 · 변환 · PyTorch 대조 · 양자화 비교), 재현(남의 실험 폴더 · llama.cpp 영수증 확인), 일(GPU 큐 · 진행 · 기록), 설정 |
| 2. 실험 | 실험 하나 | 머리(물음 · 상태 · 모델 · 출처), 탭 — 계획(가설 · 판정 기준), 실행(목록 · 새 실행), 비교, 결과(판정), 기록(파일 · 다시 내기 확인) |
| 3. 실행 | 실행 하나 | 토큰 줄(스텝마다 확률 · 마진 · 엔트로피), 개입(토큰 분기 · 같은 난수 설정 반사실 · 활성값 바꾸기), 다른 실행과 비교 |
| 4. 스텝 · 층 | 스텝 하나 | 상위 후보, 층 렌즈 · Jacobian lens, 활성값(내보내기) |

- 모든 층에서 화면은 좌우로 나뉜다 — 왼쪽은 위의 층, 오른쪽은 명령 창(3 절).
- 채팅은 실험의 '새 실행' 가운데 하나(대화형 생성)다. 가볍게 쓰는 대화는 기본 실험 하나에 실행으로 쌓인다.
- 지금의 벤치마크 · 디버거 · 모델 평가 · 에이전트 화면의 기능은 위 층들로 옮겨 간다(어디로 가는지는 조사 단계의 기능 지도에서 정한다).

## 5. 단계

| 단계 | 무엇 | 바뀌는 것 | 판정(안 — 실행 전에 확정) |
|---|---|---|---|
| A | 조사 — 기능 지도(기능마다 화면의 자리 · 앱 API · 서버 필드 · 스크립트 · 문서, 숨은 기능 표시), 연구 과제(사용자 여정) 열 안팎과 지금 드는 단계 수 | 문서 | 앱 API 61 개 · 서버 필드 · 스크립트가 모두 표에 있다 — **통과(2026-11-08, [기능지도.md](기능지도.md))** |
| B | 기능 목록의 형식과 첫 판(지금 기능을 감쌈), 실험 기록 핵심(실험대 계획 1단계), 기능 호출의 이벤트 스트림, 동등성 확인 도구와 CI | 앱 API · 문서 · CI | 지금의 기능이 모두 목록에 있고, 기능 호출마다 이벤트가 나오고, 확인 도구가 일부러 빠뜨린 경우(목록에 없는 경로 · CLI 없는 기능 · 화면 없는 결과 형식)를 잡는다 |
| C | AI 용 CLI 1판 — 목록에서 만든 명령, 일 · 오류 · 실험 맥락, 세션 이름(출처 표시), AI 를 위한 안내 한 쪽 | 앱(명령) | 목록의 모든 기능이 CLI 로 돈다. AI 의 명령이 세션 이름과 함께 앱의 이벤트로 나온다. 새 AI 세션이 안내 한 쪽만 읽고 연구 과제 셋을 CLI 로 끝낸다 |
| D | 정보 구조와 와이어프레임 — 좌우 배치(왼쪽 GUI · 오른쪽 명령 창)를 기본으로 연구 과제마다 화면 흐름, 정적 시안(HTML), 디자인 시스템(`앱/DESIGN.md`) 고침 | 문서 · 시안 | 사용자 검토로 확정 |
| E | GUI 리팩터링과 새 화면 — 모듈로 나누기, 명령 창과 이벤트를 받아 갱신하는 화면, 실험 · 실행 · 스텝 화면부터 차례로 | 웹 · 앱 | 화면마다 그 층의 기능이 모두 GUI 에서 닿고, 옛 화면과 같은 결과(같은 API 결과). 명령 창에 입력한 명령과 AI 의 명령이 GUI 에 반영된다 |
| F | 동등성 · 사용성 시험 — 연구 과제를 CLI(AI 세션)와 GUI(브라우저를 쓰는 사용자 역할 세션)로 각각 | 시험 | 두 인터페이스의 명령 목록과 실험 기록이 같다. 과제 성공률과 막힌 곳을 기록하고 고친다 |
| G | 안내서(한국어 · 영어, 단계마다 실제 화면 그림) · 릴리스 | 문서 | 릴리스 판정 |

**실험대 계획과의 연결:** 실험대 1단계(실험 기록 형식)는 B 에, 3단계(파이썬 API 의 실험 기록 · 같은 난수 반사실)는 B · C 의 기능으로, 4단계(PyTorch
대조)는 C 뒤 목록의 새 기능으로, 7단계(화면)는 D · E 로 들어간다. 5 · 6단계(직접 짠 모델 · 활성값)는 1.0.0 뒤 그대로.

**차례:** A → B → C 는 엔진의 계산을 바꾸지 않아 지금 시작할 수 있다. D 는 사용자 검토가 필요하고, E 는 D 가 확정된 뒤. F · G 는 E 뒤.

## 6. 결정(2026-11-08, 사용자 "추천대로 해")

1. **CLI 의 자리:** GeulPU 실행 파일의 하위 명령으로 만든다 — 글(geul) 언어로, 파이썬 없이 어느 설치에서나 된다. `geulpu` 파이썬 명령은 지금처럼
   인자를 넘긴다.
2. **채팅의 자리:** 실험 안의 실행 하나로 두고, 가벼운 대화는 기본 실험에 쌓는다.
3. **옛 화면:** 새 화면이 그 일을 다 할 때까지 함께 두고 하나씩 바꾼다(한 번에 바꾸지 않는다).
4. **AI 연결의 다른 길(MCP 서버 등):** CLI 뒤에, 같은 기능 목록에서 만든다.
5. **1.0.0 과의 순서:** A · B · C 는 1.0.0 작업과 함께 한다.
6. **명령의 언어:** 기록에는 화면 언어와 상관없는 기능 이름(예: `run.branch`)과 인자를 적고, CLI 는 한국어 · 영어 명령을 모두 받으며, 명령 창은
   화면 언어로 보여 준다.
