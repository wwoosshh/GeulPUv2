# 프롬프트 캐시 축출 정책 — 시뮬레이터로 재기 (이슈 #1)

[이슈 #1](https://github.com/wwoosshh/GeulPUv2/issues/1)의 질문: 프롬프트 캐시(prompt cache)가 한도를 넘을 때 지금은 오래 쓰지 않은 청크(chunk)부터
지운다. 지울 때 손해가 가장 적은 청크를 골라 지우는 축출(eviction) 정책이 더 나은가? 다른 오픈소스의 방식과 견주어 실제로 쓸모가 있는가?

이 문서는 GPU 없이 도는 시뮬레이터(재기/캐시축출.py)로 그 답을 잰다. **판정 기준(3절)과 작업 부하 · 비용 모델(4절)은 결과를 보기 전에 적고
커밋했다.** 결과와 판정은 5절부터다.

## 1. 지금 엔진의 방식

엔진/저장소.gl · 엔진/서버몸.gl 을 그대로 옮긴 것이다(시뮬레이터의 `지금` 정책).

- **청크**: 256 토큰. 이름은 앞의 모든 토큰을 품은 해시라서 청크는 사슬(트리)을 이룬다. 청크 파일 = 머리말 4,096 B + 256 × 토큰당 KV.
- **쓴 때**: 시계 × 2^20 − 청크 번호. 요청을 슬롯에 넣을 때 그 프롬프트의 청크 0 … k−1 중 있는 것을 지금 쓴 것으로 바꾸고(앞 청크일수록 늦은
  값), 새로 쓴 청크는 앞 청크보다 하나 이른 값을 받는다(앞 청크가 없으면 새 시계). 한도를 넘으면 쓴 때가 이른 것부터 지운다(같으면 색인에
  먼저 들어온 것부터). 그래서 같은 사슬에서는 꼬리부터 지워진다 — 사실상 리프(leaf) 먼저인 LRU 다. 차례는 색인.txt 에 남아 다시 켜도 이어진다.
- **슬롯 고르기**: 빈 슬롯 중 덮일 꽉 찬 청크가 가장 적은 슬롯, 같으면 프롬프트와 앞이 더 길게 같은 슬롯. 그 뒤 다른 슬롯에 더 길게 같은
  앞부분이 있으면 GPU 안에서 복사한다.
- **조회 · 복원**: 슬롯이 가진 앞부분(이 슬롯 · 다른 슬롯)이 끝나는 청크부터 프롬프트 캐시에 이어서 있는 데까지 SSD 에서 복원한다. 앞
  청크가 SSD 에 없어도 슬롯에 있으면 뒤 청크를 쓸 수 있다. 마지막 프롬프트 토큰은 늘 계산한다.
- **쓰기**(기본 `all`): 요청이 끝나 서버가 쉴 때 슬롯 내용(프롬프트 + 답)의 꽉 찬 청크 중 아직 없는 것을 쓰고, 슬롯을 덮기 전에는 덮일 청크를
  먼저 쓴다. 기본 한도는 20 GB(10^9 B 단위).
- 복원한 KV 는 다시 계산한 KV 와 같은 바이트다(계약). **축출 정책은 속도만 바꾸고 출력 비트는 바꾸지 않는다.**

## 2. 다른 오픈소스의 방식

| 엔진 | 기본 축출 | 다른 선택 |
|---|---|---|
| vLLM (자동 접두사 캐시, GPU 블록) | 참조 수 0 인 블록 중 LRU, 같으면 더 긴 접두사의 끝 블록부터 | 없음 |
| SGLang (RadixAttention) | radix 트리 리프의 LRU | `--radix-eviction-policy`: lfu · slru · priority |
| LMCache (CPU · 디스크 계층) | LRU | LFU · FIFO · MRU |
| Marconi (MLSys 2025, 연구) | 최근성 + α × FLOP 효율(바이트당 아끼는 계산) | 어텐션 + SSM 하이브리드 모델용. TTFT 최대 71 % 감소(논문 자체 보고) |

GeulPU 의 지금 방식은 vLLM · SGLang 의 기본(리프 먼저 LRU)과 같은 꼴이다. 다른 점은 GPU 메모리가 아니라 SSD 의 청크 파일을 다룬다는 것이고,
그래서 한도가 수십 GB 이고 복원에도 시간(청크마다 수 ms)이 든다.

## 3. 판정 기준 — 재기 전에 적음

**주 지표**: 작업 부하 전체의 **첫 토큰까지 시간(TTFT, time to first token)의 합**(Σ TTFT) — 사용자가 기다리는 시간이다. 시드마다 재고
가운데값을 쓴다. 생성 시간은 정책과 관계없어 빼되, 전체 시간에서 차지하는 몫은 따로 적는다.

**보조 지표**: 프롬프트 캐시가 아낀 시간(= 프롬프트 캐시 끔의 Σ TTFT − 그 정책의 Σ TTFT), 적중률(hit rate — 슬롯 뒤로 필요한 청크 중 복원한
청크의 몫), 쓴 바이트.

**견줄 정책**(파라미터는 모든 작업 부하에 하나로 고정):

| 이름 | 지울 청크 | 비고 |
|---|---|---|
| `지금` | 쓴 때가 가장 이른 청크 | 엔진 그대로(1절) |
| `LRU` | 마지막으로 쓴 때가 가장 이른 리프 | 같으면 깊은 청크 — `지금`과 거의 같아야 한다(확인용) |
| `LFU` | 쓴 횟수가 가장 적은 리프, 같으면 더 오래된 것 | SGLang 의 lfu 와 같은 꼴 |
| `SLRU` | 시험 구역(한 번 쓴 것)의 LRU 리프부터, 없으면 보호 구역의 LRU 리프 | 보호 구역은 한도의 80 %까지(넘치면 보호 구역의 LRU 를 시험 구역으로) |
| `GDS` | H = L + 아끼는 시간 / 바이트 가 가장 작은 리프 | GreedyDual-Size. L = 마지막으로 지운 H. 쓸 때마다 H 를 다시 |
| `Marconi` | 최근성 + α × (아끼는 시간 / 바이트)가 가장 작은 리프 | 두 항을 리프들 사이에서 0 ~ 1 로 맞춤(min-max). α = 1 (0.5 · 2 는 민감도로만) |
| `Belady` | 다음에 필요할 때가 가장 늦은(또는 다시 필요 없는) 리프 | 앞날을 아는 오프라인 기준 — 구현할 수 없다. 시간에 대해 엄밀한 최적은 아니지만 여유의 크기를 보인다 |

참고 행: 프롬프트 캐시 끔(슬롯만), 한도 없음(지울 일이 없음 — 어떤 정책도 넘을 수 없는 위).

**판정**(용량 5 · 10 · 20 · 40 GB, 작업 부하 4 개 — 4절):

1. **구현 제안** — 앞날을 모르는 정책 P 가 (a) 20 GB 이하의 어떤 용량 · 작업 부하에서 Σ TTFT 를 `지금`보다 **10 % 이상** 줄이고, (b) 모든 용량 ·
   작업 부하에서 `지금`보다 **2 % 넘게 나빠지지 않고**, (c) 색인의 청크마다 둘 수 있는 값(부모 · 깊이 · 횟수 · 때)만으로 계산될 때. 여럿이면
   가장 단순한 것. 엔진 변경은 사용자 승인 뒤 따로 한다.
2. **기록만** — 가장 나은 P 가 20 GB 이하에서 3 ~ 10 %이고 (b)를 지킬 때: 나중의 후보로 적고 지금은 바꾸지 않는다.
3. 그 밖에는 **지금 방식을 둔다.**
4. 여유: `Belady`가 20 GB 이하의 모든 경우에서 `지금`보다 10 % 미만이면, 지우는 차례는 시간이 가는 곳이 아니라고 적는다. 이때 용량(20 → 40 GB)의
   효과와 견주어, 한도의 기본값이 정책보다 중요한지를 함께 적는다.

## 4. 시뮬레이터 · 비용 모델 · 작업 부하 — 재기 전에 정함

### 시뮬레이터

- 표준 라이브러리만 쓰는 Python(재기/캐시축출.py). 토큰열은 조각(조각 번호 · 길이)으로 나타내고, 청크 이름은 앞 청크 이름과 그 청크에 든
  조각들로 정한다 — 같은 앞부분이면 같은 이름이다(엔진의 해시 사슬과 같음).
- 엔진의 흐름을 요청마다 그대로: 슬롯 고르기 → 덮일 청크 쓰기 → 다른 슬롯 복사 → 조회 · 쓴 때 바꾸기 · 복원 → 계산 → 쉴 때 쓰기(슬롯 0, 1 차례)
  → 한도 지키기. 슬롯 수 2. 다시 켜기 = 슬롯을 비우고(프롬프트 캐시는 남김) 색인의 차례를 이어 간다. 정책은 '어느 청크를 지우나'와 그 정책이
  청크마다 두는 값만 다르다.
- 슬롯의 내용 · 고르기 · 복사는 축출 정책과 관계없다. 그래서 요청마다 '슬롯 뒤로 필요한 청크'가 정해지고, `Belady`는 그것으로 다음에 필요할
  때를 안다.

### 비용 모델(이미 잰 값 — 새로 재지 않음)

- **프롬프트 계산**: 길이 L 까지의 누적 시간 T(L) = a·L + b·L². 빠른 모드 · RTX 4070 Ti · Q4_K_M, 문서/긴문맥재기.md 의 16k · 32k 프롬프트와
  깊이 d 에서 1,024 토큰을 더한 값에 맞춤:
  Qwen2.5-7B a = 0.1225 ms, b = 6.3 × 10⁻⁶ ms (T(16,384) 3,698 ms ↔ 잰 값 3,708.8 · T(32,768) 10,779 ↔ 10,800.4),
  Llama-3.1-8B a = 0.1339, b = 8.2 × 10⁻⁶ (4,395 ↔ 4,414.5 · 13,193 ↔ 13,230.5). 요청 하나의 계산 = T(P) − T(슬롯 · 복원으로 채운 길이).
- **복원**: 청크 바이트 ÷ 1.75 GB/s(차가운 SSD — 문맥저장소.md 4단계의 1.8 GB/s, Qwen2.5-7B 청크 14.7 MB 에 8.4 ms). 확인(W0)만 OS 캐시
  2.7 GB/s. 다른 슬롯 복사는 GPU 안이라 0 으로 둔다.
- **토큰당 KV**: Qwen2.5-7B 57,344 B(청크 14.68 MB), Llama-3.1-8B 131,072 B(청크 33.56 MB).
- **민감도**: 정밀 모드는 프롬프트가 1.16 ~ 1.47 배 느리다 — 계산 × 1.3 으로 한 번 더(R · 20 GB).

### 작업 부하(시드 1 ~ 5)

앞부분(llama-server 의 `cache_n`) · 답 길이를 틀로 쓴다(Qwen2.5 토큰으로 × 0.97 — t1 첫 요청 15,112 → 14,671). t1 의 20번째 요청은
`cache_n` 이 0 이지만 글은 시스템 프롬프트가 같고 도구 목록부터 달라서(t2 · t3 의 11번째와 같은 꼴) 5,383 × 0.97 로 둔다. 작업 하나를 새로

- **W0 — 확인용**: 녹화한 54 요청(t1 → t2 → t3)을 그대로. 4단계 ②의 네 실행(다시 계산 · 끔 · 켬 빈 폴더 · 켬 다시 켠 뒤)과 견준다.
