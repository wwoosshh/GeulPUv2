# 프롬프트 캐시 재현성

*영어판: [docs/prompt-cache-reproducibility.md](../docs/prompt-cache-reproducibility.md).*

캐시에 남은 프롬프트 앞부분을 다시 쓰면 서버가 내는 답이 바뀌는가. Aditi Patodiya 의 연구 *Same Request, Different Answer:
Quantization Amplifies Cache-Induced Divergence in LLM Serving*([arXiv:2609.04748](https://arxiv.org/abs/2609.04748))이 이것을
에이전트의 도구 사용 에피소드로 잰다. 앞부분을 다시 쓰면 부동소수점 더하기 차례가 바뀌어 토큰 하나가 달라질 수 있고, 거기서부터 에피소드의
나머지가 갈라진다 — 연구가 llama.cpp b10434 · Qwen2.5-7B Q4_K_M 으로 돌린 실행에서는 캐시를 켜고 끔에 따라 80 에피소드 가운데 60 개가
갈라졌다. 측정 도구(harness) · 자료 · 분석 코드는 연구의 저장소 [cache-divergence-study](https://github.com/aditi-p31/cache-divergence-study)에
있다.

그 측정 도구를 고치지 않고 GeulPU 와, 양성 대조군(positive control)으로 연구의 llama.cpp 빌드에 한 PC 에서 돌렸다. GeulPU 에서는 캐시가
아무것도 바꾸지 않았다 — 모든 비교에서 80 에피소드 가운데 0 개가 갈라졌고, 토큰마다의 로그확률까지 같았다. 원자료는 Zenodo 에 있다
([doi:10.5281/zenodo.23631969](https://doi.org/10.5281/zenodo.23631969)).

## 설정

- **측정 도구**: 커밋 `bc0551d`([doi:10.5281/zenodo.23633821](https://doi.org/10.5281/zenodo.23633821)) 그대로, 그 저장소가 고정한
  환경에서(`uv.lock` — bfcl-eval 2026.3.23). BFCL v4 `multi_turn_base` 의
  에피소드 0 ~ 79, 온도 0. 설정마다 서버 프로세스 하나로 두 번(`main` 다음 `repeat`) 돌고, 한 번마다 캐시를 켜고(`cache_prompt: true`)
  다음에 끈다. GeulPU 는 측정 도구의 llama.cpp 백엔드로 부른다 — GeulPU 의 서버가 요청마다의 `cache_prompt` 를 같은 이름으로 받는다. 채점과
  분석은 연구의 `harness/score_results.py` 와 `analysis/analyze.py:analyse_config`.
- **모델**: Qwen2.5-7B-Instruct Q4_K_M(bartowski, SHA-256 `65b8fcd9…` — [파일쌍.md](파일쌍.md) 의 `7b-q4km` 과 같은 파일).
- **PC**: NVIDIA GeForce RTX 4070 Ti 12 GB · 드라이버 616.56 · Intel Core i7-14700K · Windows 11. 슬롯 1, 문맥 16,384.

| 설정 | 엔진 · 빌드 | 값 |
|---|---|---|
| llama.cpp(양성 대조군) | llama.cpp b10434(`7e4c0a968`), 공식 Windows CUDA 12.4 빌드 | 연구의 `server_llamacpp.sh` 그대로: `--parallel 1 -c 16384 -ngl 99 --seed 42 --slots`, KV f16, 플래시 어텐션 자동 |
| GeulPU 0.11.0 기본 | GeulPU 0.11.0(`5d6d58c`) | 빠른 모드, 8비트 KV 와 빠른 어텐션(F2), 추측 디코딩(speculative decoding) 켬, SSD 프롬프트 캐시(`store`) 켬 — 빈 데서 시작 |
| GeulPU 조건 맞춤 | GeulPU 0.12.0 + `cached_tokens`(`1c1074d`, #88) | 빠른 모드, 16비트 KV(빠른 어텐션은 8비트 KV 에만 있어서 어텐션은 정밀도 계약 그대로), 추측 디코딩 끔, SSD 프롬프트 캐시 끔 — 앞부분은 슬롯의 RAM 에서만 다시 쓴다(llama.cpp 처럼) |
| GeulPU 기본 다시 | 같은 빌드 | 0.11.0 의 기본, 새 빈 SSD 프롬프트 캐시 |

## 결과

80 에피소드 가운데 갈라진 수(연구의 `analyse_config` — llama.cpp 는 토큰 번호로, GeulPU 는 토큰 문자열로 견준다):

| 설정 | 캐시 켬 ↔ 끔 | 캐시 켬: main ↔ repeat | 캐시 끔: main ↔ repeat | `cached_tokens` 평균(켬 / 끔) | BFCL 성공(켬 / 끔) |
|---|---|---|---|---|---|
| llama.cpp b10434 | 64 | 53 | 0 | 7,001 / 0 | 8 / 5 |
| GeulPU 0.11.0 기본 | 0 | 0 | 0 | 0.11.0 은 알리지 않음 | 6 / 6 |
| GeulPU 조건 맞춤 | 0 | 0 | 0 | 6,750 / 0 | 6 / 6 |
| GeulPU 기본 다시 | 0 | 0 | 0 | 7,036 / 0 | 6 / 6 |

연구의 저자 Aditi Patodiya 가 이 파일들을 연구의 분석 코드로 다시 돌려 같은 숫자를 얻었다(메일, 2026-10-25).

- **양성 대조군**: 같은 llama.cpp 빌드 · 모델을 연구가 RTX 4090 에서 잰 값은 60 / 62 / 0 이다(`analysis/revision_findings.json` 의
  `table1/lcpp-qwen7b-q4km`). 이 PC 에서는 64 / 53 / 0 이고, 처음 갈리는 요청은 가운데값으로 2 번째다. 이 측정이 이 PC 에서도 차이를 잡고,
  `cached_tokens` 는 캐시 켬 쪽이 앞부분을 다시 썼고(요청마다 평균 7,001 토큰) 끔 쪽은 쓰지 않았음을 보인다.
- **GeulPU 는 토큰마다**: 세 실행의 모든 비교에서, 나온 토큰마다 토큰 번호 · 로그확률 · 엔트로피가 같다 — 기본은 짝지은 요청 863 개의
  22,520 토큰, 조건 맞춤은 866 개의 22,433 토큰. 새 빌드로 다시 돌린 기본은 0.11.0 의 실행과 비트까지 같다.
- **답을 바꾸는 것은 설정이지 캐시가 아니다**: 조건 맞춤과 기본은 80 가운데 66 에피소드가 다르고, 캐시를 끈 GeulPU 와 llama.cpp 는
  68(기본) · 66(조건 맞춤)이 다르다. 한 설정 안에서는 캐시를 쓴 길과 다시 셈한 길이 같은 비트를 낸다.
- **`cached_tokens`**: #88 부터(다음 릴리스) GeulPU 가 `usage.prompt_tokens_details.cached_tokens` 를 알린다. 처음 요청 뒤의 캐시 켬
  요청은 다시 쓴 앞부분을, 캐시 끔 요청은 0 을 알린다. 프롬프트의 마지막 토큰은 늘 셈하므로, 같은 프롬프트를 되풀이하면
  `prompt_tokens − 1` 이다.
- **문맥 넘침 하나(조건 맞춤)**: `multi_turn_base_65` 의 18 번째 요청이 16,450 토큰으로 문맥 16,384 를 넘는다. 서버가 400
  `context_length_exceeded` 로 답하고 측정 도구가 그 에피소드를 오류로 센다 — main · repeat 의 켬 · 끔 네 실행 모두 같은 요청에서.
- **과제 성공은 바닥이다**(80 가운데 6 ~ 8): 7B 모델에게 이 벤치마크가 어려워서, 이 실행으로는 캐시가 과제 성공에 주는 영향을 말할 수
  없다. 연구도 결과에 대한 결론은 수학 문제(GSM8K) 실험에서 낸다.

## 다시 해 보기

이 측정은 앱에서 돌지 않는다 — 연구의 파이썬 측정 도구가 있어야 한다. GeulPU 서버(슬롯 1, 문맥 16,384)를 띄우고, 측정 도구의 저장소에서
`uv sync` 한 뒤:

```
PYTHONPATH=harness uv run python harness/run_episodes.py --model-hf-id Qwen/Qwen2.5-7B-Instruct --served-model geulpu \
  --base-url http://127.0.0.1:<포트>/v1 --backend llamacpp --family qwen --arm on --n-episodes 80 --out-dir <결과>/main
```

다음에 `--arm off`, 그리고 둘을 `<결과>/repeat` 로 한 번 더. `arm_on` · `arm_off` 폴더마다
`harness/score_results.py <폴더> --model-hf-id Qwen/Qwen2.5-7B-Instruct --category multi_turn_base` 로 채점하고, 결과 폴더를
`analysis/analyze.py` 의 `analyse_config` 로 분석한다. 조건 맞춤의 앱 설정(`/api/settings`)은
`{"precision": "fast", "kv8_cache": false, "fast_attention": true, "speculative": false, "slots": 1, "context": 16384, "context_store": "off"}`
였다(빠른 어텐션은 8비트 KV 가 없으면 저절로 꺼진다). 원자료의 `scripts/run_pat2.sh` 가 GeulPU 의 두 설정을 보인다.
