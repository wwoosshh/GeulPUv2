단계 E 의 판정(앱리디자인.md §5) — 화면마다 그 수준의 기능이 모두 GUI 에서 닿고 옛 화면과 같은 결과(같은 API 결과)이며, 명령 창에 입력한
명령과 AI 의 명령이 GUI 에 반영된다 — 은 하위 단계의 판정이 나눠 맡는다.

## 1. E1 — 명령 창

**서버(앱 — 글)**
- **이벤트의 인자:** `start` 이벤트에 `params`(요청 본문 — C2 의 명령 기록과 같은 것)와 `experiment`(요청 헤더 `X-GeulPU-Experiment` 가 실험
  폴더일 때 그 경로)를 더한다. 본문이 JSON 객체가 아니거나 16 KB 를 넘으면 `params` 대신 `params_bytes`(바이트 수)만 적는다 — 앱이 메모리에
  두는 이벤트 1024 개가 16 MB 를 넘지 않게. 명령 기록(`records/commands.jsonl`)은 지금처럼 본문 전체를 적는다.
- **기능 목록 내보내기:** `GET /api/operations` → `data/operations.json` 그대로. 기능 `system.operations`(내부용 — 명령 창이 명령을 해석할 때
  읽는다. CLI 에는 `ops` 가 있다).
- **모듈 파일:** `GET /ui/<이름>.js` → `web\ui\<이름>.js`(이름은 `[a-z0-9-]`, `text/javascript`).
- **출처는 그대로:** 입력 줄은 사용자가 친 CLI 명령이므로 `X-GeulPU-Source: cli`(세션 없음)로 보낸다.

**화면(웹)**
- **배치:** 지금 화면 8 개 모두의 오른쪽에 명령 창. 처음에는 열림(380px — 화면설계.md §10 결정 3), 접으면 폭 40px, 크기 조절 핸들로
  280 ~ 640px, 폭 768px 아래에서는 아래 창(높이 40%). 접힘과 폭은 이 브라우저에 기억한다. 왼쪽과 명령 창은 따로 스크롤한다.
- **줄:** 기능 호출 하나에 한 줄 — 출처(GUI · 사용자 CLI · AI · 세션 이름 · 파이썬 · 알 수 없음) · 명령(이벤트의 `params` 를 CLI 형식으로 다시
  쓴 것 — 긴 값은 줄여 보이고 줄을 누르면 전체) · 상태(실행 중 → HTTP 상태) · 걸린 시간 · 실험. `start` 가 오면 실행 중, `end` 가 오면 결과를
  적는다. 놓친 이벤트(`oldest > after + 1`)는 그 위치에 한 줄로 알리고, 앱이 다시 켜졌으면(`last < after`) 처음부터 받는다. 이벤트는 롱
  폴링(long polling, `GET /api/events?after=&wait=`)으로 받는다.
- **명령 복사:** 줄마다 CLI 에 그대로 입력할 수 있는 명령 — 기능 목록의 `cli.en` 과 인자. 목록에 없는 필드가 본문에 있으면
  `--json '<본문>'`.
- **입력 줄:** CLI 와 같은 문법 — 명령 이름(`cli.en` · `cli.ko` · 기능 id, 앞의 `GeulPU` 는 있어도 되고 없어도 됨), `--인자 값` ·
  `--인자=값`, `--json`, `--experiment`, `--wait`, `--dry-run`. 기능 목록에서 요청을 만들고, 사용법 오류는 CLI 와 같은 까닭과 다음에 할 일을
  보인다. `help <명령>` · `ops` 는 앱을 부르지 않고 명령 창에 보인다. 단축키: `/` 입력 줄로 · `Esc` 나오기 · `]` 접기와 펼치기 · `↑` `↓` 이전에 친
  명령.
- **모듈:** 새 코드는 `앱/web/ui/` 의 ES 모듈 — `ops.js`(기능 목록 클라이언트: 기능 id 와 인자로 요청을 만들어 보낸다), `command.js`(명령
  해석과 명령 쓰기), `console.js`(명령 창). 새 코드는 앱을 이 클라이언트로만 부른다. 옛 화면의 코드는 옮기지 않는다(`app.js` 는 출처
  헤더를 이미 적은 요청을 덮어쓰지 않게 한 줄과 새 문구의 영어 사전만) — 옛 화면의 호출은 이벤트로 명령 창에 나온다.

**E1 의 판정(구현 전에 적음)**
1. **CLI 와 같은 요청:** 명령 예 40 개 이상(영어 · 한국어 이름 · 기능 id, 인자 자료형 다섯, 점(.)이 들어간 인자 이름, `--json`, GET 의 쿼리
   문자열, 사용법 오류 열 가지 이상)에서 입력 줄이 만드는 요청(op · method · path · body)이 CLI 의 `--dry-run` 과 같고, 오류는 같은 경우에
   난다 — 예 파일 하나를 CLI(빌드한 GeulPU.exe)와 명령 해석 모듈(node)이 각각 통과한다. 명령 복사로 만든 명령을 다시 해석하면 같은 요청이
   된다.
2. **네 출처가 명령 창에:** 시험 인스턴스에서 GUI(옛 화면의 동작) · 터미널의 CLI(세션 없음 · 있음) · 파이썬 API · 입력 줄로 부른 POST
   기능이 각각 한 줄로, 이벤트가 난 뒤 1 초 안에 맞는 출처 · 명령 · 상태로 나온다. `--experiment` 로 부른 호출은 줄에 그 실험이 보인다.
3. **이벤트의 인자:** `start` 의 `params` 가 보낸 본문과 같고, 16 KB 를 넘는 본문은 `params_bytes` 만 있다. 기존 API 응답은 바이트까지
   그대로다(main 에서 빌드한 앱과 같은 요청 12 개).
4. **배치:** 실제 브라우저에서 — 처음에 열림 380px, 접기 · 펼치기와 폭 조절, 두 창이 따로 스크롤(실제 휠 이벤트), 375 × 812 에서 아래 창이고
   가로로 넘치지 않음, 지금 화면 8 개가 모두 열리고 브라우저 콘솔에 오류 없음.
5. **점검:** 기능 목록 점검(`system.operations` 내부용) · 화면 문구 점검(새 문구의 영어) · 빠른 점검이 통과하고, CI 가 명령 해석 시험(node)을
   돈다.

판정 2 · 3 · 4 는 GPU 를 쓰지 않는다 — 앱이 켜질 때의 장치 확인만 GPU 줄로.

## 2. E2 — 실험 화면

**서버(앱 — 글)**
- **실험 파일 읽기:** 새 기능 `experiment.read` — `GET /api/experiments/read?path=<실험 폴더|id>&file=<실험 폴더 안의 상대 경로>&root=` →
  `{"path","file","bytes","text"}`. 텍스트 파일(.md · .json · .jsonl · .txt · .csv · .py · .sh · .log · .yaml · .yml)만, 2 MB 까지. 절대 경로 ·
  `..` · 드라이브 문자는 받지 않는다(실험 폴더 밖의 파일을 읽지 못하게). CLI 에서는 `experiment read`.
- **실험 목록의 요약:** `experiment.list` 의 실험마다 `models`(모델 이름) · `runs`(실행 수) · `criteria`(`{"total","pass","fail"}`) ·
  `commands`(명령 기록의 줄 수)를 더한다 — 목록 화면이 실험마다 따로 묻지 않게. 지금의 필드는 그대로다.

**화면(웹)**
- **사이드바의 '실험':** 맨 위에 '실험'을 더하고, 앱을 열면 실험 목록이 첫 화면이다(화면설계.md §10 결정 2). 지금 화면 8 개는 그대로 있다.
- **실험 목록:** 실험 폴더 위치(폴더 선택으로 바꾸고 이 브라우저에 기억), 실험마다 한 줄(제목 · 상태 · id · 모델 · 실행 수 · 판정 통과 수 / 기준
  수 · 명령 수), 새 실험(이름 · 제목 · 연구 질문). 목록 끝에 '대화'(채팅 화면으로 — 채팅을 기본 실험으로 옮기는 것은 E5).
- **실험 화면:** 경로(실험 › id), 헤더(제목 · 연구 질문 · 상태 · 만든 날), 실행 정보 줄(모델 · SHA-256 앞 8 자 · 계산 방식 · GeulPU 버전), 탭 셋:
  - 계획 — 판정 기준(id · 내용 · 판정)과 plan.md,
  - 결과 — 판정 기준마다의 판정과 results.md,
  - 기록 — 명령 기록(records/commands.jsonl — 줄마다 출처 · 명령 · 상태 · 걸린 시간 · 명령 복사), 파일(experiment.json 의 files — 경로 · 크기 ·
    SHA-256 앞 8 자), 재현 명령(reproduce), 점검(experiment.check — 작업, 판정과 문제 목록).
  실행 · 비교 탭은 실행 화면(E3)과 함께 더한다.
- **실험 안의 호출은 실험의 기록에:** 실험 화면에서 부른 기능(점검)은 `X-GeulPU-Experiment` 를 붙여 명령 기록에 남는다. 다른 곳(CLI · AI
  세션)에서 이 실험으로 부른 호출이 끝나면 기록 탭이 바로 다시 읽는다(이벤트).
- **명령 창에서 실험으로:** 실험이 있는 줄의 '실험 …' 을 누르면 그 실험 화면이 열린다.
- **모듈:** `앱/web/ui/experiments.js`. 명령 창(console.js)이 받은 이벤트를 화면에 알린다(`geulpu:event`). app.js 는 사이드바 항목 · 화면 전환
  알림(`geulpu:view`) · 첫 화면 · 영어 사전만 바꾼다.

**E2 의 판정(구현 전에 적음)**
1. **목록과 CLI 가 같다:** 시험 인스턴스에서 실험 셋(CLI 로 둘, 화면의 새 실험으로 하나)이 목록에 모두 있고, 줄의 값(제목 · 상태 · 모델 · 실행
   수 · 판정 · 명령 수)이 `experiment list` 의 답과 같다. 화면에서 만든 실험은 점검 도구(`experiment check`)를 통과한다. 실험 폴더 위치를 바꾸면
   그 위치의 실험이 보인다.
2. **실험 화면이 파일과 같다:** 계획 · 결과 탭의 글이 plan.md · results.md 와 같고, 판정 기준이 experiment.json 과 같으며, 기록 탭의 명령 기록이
   records/commands.jsonl 의 줄과 같다(수 · 순서 · 기능 · 출처 · 상태).
3. **실험 안의 호출이 기록에 남는다:** 실험 화면의 점검이 작업으로 돌고 그 판정이 `experiment check --wait` 와 같으며, 그 호출이 명령 기록에
   `source: gui` 로 한 줄 남는다. 터미널에서 `--experiment` 로 부른 호출이 끝나면 기록 탭에 1 초 안에 나온다. 명령 창의 '실험 …' 을 누르면 그
   실험이 열린다.
4. **파일 읽기의 경계:** `experiment.read` 가 실험 폴더 밖(`..` · 절대 경로 · 드라이브 문자)과 텍스트가 아닌 파일 · 2 MB 를 넘는 파일을 거절하고,
   CLI 의 `experiment read` 가 같은 답을 낸다.
5. **화면과 점검:** 앱을 열면 실험 목록이고, 지금 화면 8 개가 그대로 열리며, 두 창이 따로 스크롤하고(실제 휠 이벤트), 좁은 화면에서 가로로 넘치지
   않고, 브라우저 콘솔에 스크립트 오류가 없고, 영어 화면 문구가 모두 바뀐다. 기능 목록 점검 · 명령줄 점검 · 화면 문구 점검이 통과하고, 실험 기능
   밖의 기존 응답 12 개는 바이트까지 그대로다.

**하지 않는 것(E2):** 실행 · 비교 탭과 실행 결과의 기록(E3), 계획 · 판정 기준 · 결과를 화면에서 쓰기(기록을 쓰는 기능과 함께 E3 에서 정한다),
채팅을 기본 실험으로(E5).

## 3. E3 — 실행 화면

**서버(앱 — 글)**
- **실행을 실험에 남긴다:** 실행 기능 일곱(기능 목록의 `records` 가 `run` · `branch` · `score` · `lens` 인 `run.complete` · `run.chat` ·
  `run.messages` · `run.responses` · `run.branch` · `run.score` · `run.lens`)을 `X-GeulPU-Experiment` 와 함께 부르고 답이 200 이면, 앱이 추론
  서버의 응답을 받아 두었다가 그 실험에 실행 하나로 남긴다. 출처(GUI · CLI · AI 세션 · 파이썬)와 상관없이 앱의 한 곳(호출이 끝날 때)에서 한다. 실험
  헤더가 없는 호출은 지금과 같다(응답을 받아 두지 않는다).
  - **기록 파일** `records/runs/<실행 id>.json`(JSON 한 줄): `run` · `op` · `path` · `time` · `ms` · `status` · `source`(· `session`) · `model`(서버의
    모델 id) · `server`(그 요청을 계산한 서버 — 모델 SHA-256 · 백엔드 · 계산 방식 · 8비트 KV · 빠른 어텐션 · 문맥 · YaRN 배, 디버거의 실행 로그와
    같은 것) · `app`(GeulPU 버전) · `request`(받은 본문 그대로) · `response`(추론 서버가 준 JSON 그대로 — 스트리밍이면 확장 필드 `geulpu` 가 든
    마지막 이벤트와 `"stream": true`). 16 MB 를 넘는 응답은 `response` 없이 `response_bytes` 만 적는다.
  - **`runs` 의 항목:** `id`(r1 · r2 … — 다음 번호) · `kind` · `operation` · `record` · `settings`(요청에서 프롬프트 · 메시지 · 입력 · 도구 · 스트리밍을
    뺀 값, `geulpu` · `chat_template_kwargs` 안의 필드는 `geulpu.top_logprobs` 처럼 점으로) · `seed`(응답의 `geulpu.seed`).
    - `kind`: 생성 넷은 `generate`, 분기 `branch`, 점수 `score`, 렌즈 `lens`. 요청이 앞의 한 실행과 같으면(JSON 으로 — 키 순서까지) `check` 와 그
      실행을 `base` 로 — 같은 요청의 재실행(docs/cli.md 의 규칙).
    - 분기는 `base` 와 `intervention` — 이 실험의 실행 가운데 분기의 프롬프트(토큰 번호)가 '그 실행의 프롬프트 토큰 + 답의 앞 k 토큰 + 다른 토큰
      하나'인 첫 실행을 찾아 `{"type": "token", "step": k, "value": <바꾼 토큰 번호>}`. 점수 · 렌즈는 프롬프트가 어느 실행의 '프롬프트 + 답'의
      앞부분이면 그 실행을 `base` 로.
  - **experiment.json 의 다른 필드:** 그 실행의 모델이 `models` 에 없으면 더한다(이름 · 파일 이름 · SHA-256 · 바이트 · `source: {"local": <파일
    이름>}` — 경로는 적지 않는다). 상태가 `planned` 이면 첫 실행에서 `running` 으로.
  - **`files` 는 앱이 맞춘다:** 앱이 쓰는 파일(기록 파일과 `records/commands.jsonl`)의 항목(SHA-256 · 바이트)을 쓸 때마다 고친다 — 명령 기록만
    남는 호출(점검 등)도. E2 의 판정 3 에서 본 실패('commands.jsonl 이 files 에 없음')가 앱이 쓴 파일 때문에는 나지 않게.
  - **쓰는 형식:** experiment.json 은 들여쓰기 1 의 JSON(파이썬 `json.dumps(indent=1, ensure_ascii=False)` 와 같은 텍스트)을 임시 파일에 쓰고 옮긴다(읽는
    쪽이 반쯤 쓴 파일을 보지 않게). 파일이 JSON 이 아니면 고치지 않는다(기록 파일 · 명령 기록은 남긴다).
  - **이벤트:** 실행을 남긴 호출의 `end` 에 `run`(실행 id) — 명령 창의 줄이 그 실행으로 가는 링크가 된다.
- **계획 · 판정 기준 · 결과 쓰기:** 새 기능 `experiment.update` — `POST /api/experiments/update {path, root, title, question, plan, criteria,
  results, status}`(준 것만 바꾼다) → `experiment.show` 와 같은 답. CLI 는 `experiment update`.
  - 제목 · 연구 질문 · `plan`(plan.md) · 판정 기준의 `id` · `text` 는 실행이 없을 때만 바꾼다 — 첫 실행 뒤에는 409 와 까닭(화면설계.md §3 의 '실행
    전에 적고 고정').
  - 판정 기준의 `result`(pending · pass · fail) · `note`, `results`(results.md), `status`(planned · running · done)는 언제든.
- **실험 파일 읽기의 한도:** 2 MB → 32 MB(긴 답과 상위 후보가 든 기록 파일도 화면이 읽게).

**화면(웹)**
- **실험 화면의 탭 다섯:** 계획 · 실행 · 비교 · 결과 · 기록.
  - 계획 — 실행이 없으면 '편집'(제목 · 연구 질문 · plan.md · 판정 기준 더하기 · 고치기 · 빼기). 첫 실행 뒤에는 읽기만 하고 까닭을 보인다.
  - 결과 — '편집'(판정 기준마다 판정과 메모, results.md, 상태).
  - 실행 — 실행 목록(id · 설명 · 토큰 수 · 걸린 시간 · 출처)과 '새 실행'. 설명은 종류마다: 텍스트 생성 · 채팅(시드 · 온도 · 토큰 수), 분기('r1 의
    스텝 3 에 "I"'), 재실행('r1 재실행 — 로짓 해시 40 / 40 같음'), 점수 · 로짓 렌즈.
  - 비교 — 아래.
- **새 실행:** 텍스트 생성 · 채팅 — 프롬프트(채팅은 시스템 프롬프트와 사용자 메시지), 최대 토큰 · 온도 · 시드 · top-p · top-k · min-p, 상위 후보
  수(기본 2 — 마진에 필요한 수). 요청에는 늘 `logprobs` · `geulpu.top_logprobs` · `geulpu.logit_hash` · `geulpu.prompt_tokens` 를 넣고 스트리밍하지
  않는다. 실험 헤더를 붙여 보내고, 끝나면 그 실행을 연다. 모델이 없으면 새 실행 창에 모델 화면으로 가는 안내(화면설계.md §8). 실행 화면의 '이 설정으로
  새 실행'은 그 실행의 설정을 채운 이 창을 연다(프롬프트의 단어 하나 · 온도만 바꾸는 비교 — R4).
- **실행 화면**(경로: 실험 › id › 실행 r1):
  - 헤더(실행 id · 설명)와 실행 정보 줄(모델 · SHA-256 앞 8 자 · 계산 방식 · GeulPU 버전 · 시드 — 기록 파일의 `server` · `app` 에서).
  - 토큰별 출력 — 프롬프트(흐리게) 뒤에 샘플링된 토큰을 텍스트 그대로 잇는다. 토큰 아래 막대는 마진(기본) · 샘플링된 토큰의 확률 · 엔트로피 가운데
    하나(화면설계.md §10 결정 4). 마진이 가장 작은 스텝을 표시하고, 분기한 실행은 바꾼 토큰을 표시한다. 토큰을 누르거나 ← → 로 스텝을 고른다.
  - 고른 스텝(오른쪽) — 상위 후보(토큰 · 로그확률 · 확률 막대, 샘플링된 토큰 표시) · 마진 · 엔트로피 · 로짓 해시. 샘플링되지 않은 후보마다 '이
    토큰으로 분기'(키 `b` 는 그 가운데 가장 높은 후보), 그리고 '재실행' · '이 설정으로 새 실행'.
  - 분기 — `run.branch`: 프롬프트 = 원래 실행의 프롬프트 토큰 + 답의 앞 k 토큰 + 고른 후보, `max_tokens` = 원래 − (k + 1), 같은 시드 · 샘플링
    설정 · 상위 후보 수, `echo` 와 `geulpu.echo_from` = 원래 프롬프트의 길이(분기 앞부분의 로짓 해시를 원래 실행과 비교하게), `geulpu.step_offset` =
    k + 1 — docs/cli.md 의 분기 요청 그대로.
  - 재실행 — 그 실행의 요청을 그대로 다시 보낸다. 분기 · 재실행이 끝나면 비교 탭에서 원래 실행과 나란히 본다.
  - 프롬프트 토큰이나 상위 후보가 없는 실행(CLI 에서 그 필드 없이 부른 것)은 있는 것만 보이고, 분기는 까닭과 함께 막는다. 점수 · 로짓 렌즈 실행은
    헤더 · 실행 정보 줄 · 설정 · 응답(JSON)만 보인다 — 표는 스텝 · 층 화면(E4)에서.
- **비교:** 실행 둘(기본: 마지막 실행과 그 `base`, 없으면 바로 앞 실행)을 프롬프트를 포함한 토큰열의 위치로 맞춰 —
  - 두 답을 나란히(같은 앞부분은 흐리게, 처음 다른 토큰부터 밑줄),
  - 토큰이 처음 다른 스텝과 로짓 해시가 처음 다른 스텝(두 실행 모두 해시가 있는 위치만), 같은 토큰 수 · 같은 로짓 해시 수,
  - 처음 다른 스텝 앞뒤의 로짓 해시 칩('같음'은 판정의 초록, 처음 다른 스텝은 흰 표시 — 화면설계.md §9),
  - 요청에서 다른 설정, 계산 방식이 다르면 실행 정보 줄에 경고.
- **AI 실행 자동 열기:** 명령 창 헤더의 스위치(기본 꺼짐, 이 브라우저에 기억). 켜면 AI 세션(세션 이름이 있는 CLI)의 호출이 실행을 남길 때 왼쪽이 그
  실행으로 간다. 꺼져 있으면 줄의 '실행 r3' 링크로만 연다.
- **명령 창의 실험:** 실험 화면을 보는 동안 입력 줄 위에 그 실험이 보이고, 친 명령에 `--experiment` 가 붙는다(화면설계.md §5 — 명령에 이미 있으면
  그것).
- **모듈:** `앱/web/ui/runs.js`(실행 탭 · 새 실행 · 실행 화면 · 비교). experiments.js 는 탭 · 경로 · 편집을, console.js 는 실행 링크 · 스위치 · 실험
  표시를 더한다.

**E3 의 판정(구현 전에 적음)**
1. **실행이 실험에 남는다:** 시험 인스턴스(Qwen3-0.6B Q8_0)에서 화면의 새 실행(텍스트 생성 · 채팅), 터미널 CLI 의 `run complete --experiment`(세션
   없음), AI 세션 이름을 붙인 CLI 의 `run branch` · `run score` · `run lens`, 같은 요청의 재실행이 각각 실행 하나로 남는다 — 기록 파일의 `response` 가
   클라이언트가 받은 응답과 JSON 으로 같고, `runs` 의 `kind` · `base` · `intervention` · `seed` 가 맞으며, `models` 에 모델이 하나 들고, `experiment
   check` 가 통과한다. 실험 헤더 없는 호출은 실험에 아무것도 남기지 않는다.
2. **실행 화면이 기록과 같다:** 토큰별 출력의 토큰(수 · 글)이 기록의 토큰과 같고, 고른 스텝의 상위 후보 · 마진 · 엔트로피 · 로짓 해시가 기록의
   `geulpu` 값과 같으며, 마진이 가장 작은 스텝 표시가 마진이 가장 작은 스텝에 있다. 막대를 확률 · 엔트로피로 바꿀 수 있다.
3. **분기 · 재실행 · 비교:** 화면에서 마진이 가장 작은 스텝 k 의 2 위 후보로 분기하면 `kind: branch` · `base` · `intervention`(스텝 k, 그 후보)이 맞고,
   같은 본문을 CLI `run branch --json` 으로 보낸 답과 토큰 · 로짓 해시가 같다. 분기 앞부분(echo)의 로짓 해시가 원래 실행의 스텝 0 ~ k 와 같다.
   재실행은 `kind: check` 와 로짓 해시 n / n 같음. 비교 탭이 분기에는 '처음 다른 스텝 k', 재실행에는 '모두 같음'을 보인다.
4. **쓰기 · 명령 창:** 실행 전에 화면에서 쓴 계획 · 판정 기준이 plan.md · experiment.json 에 남고, 첫 실행 뒤에는 앱이 409 로 거절한다(CLI 의
   `experiment update` 도 같은 까닭으로 종료 1). 결과 탭에서 판정 · results.md · 상태 '끝'을 쓰면 `experiment check` 가 통과한다. 스위치를 켜면 AI
   세션의 실행이 끝나고 1 초 안에 왼쪽이 그 실행으로 가고, 끄면 그대로다. 실험 화면에서 입력 줄에 친 `run complete` 가 그 실험에 남는다.
5. **화면과 점검:** 사이드바의 화면 9 개가 열리고, 두 창이 따로 스크롤하며(실제 휠 이벤트), 375 × 812 에서 가로로 넘치지 않고(토큰별 출력은 줄을
   바꾼다), 브라우저 콘솔에 스크립트 오류가 없고, 영어 화면 문구가 모두 바뀐다. 기능 목록 점검 · 명령줄 점검 · 화면 문구 점검이 통과하고, 실험 밖의
   기존 응답 12 개가 main 에서 빌드한 앱과 바이트까지 같다.

판정 1 ~ 4 는 GPU 를 쓴다 — 시험 인스턴스에 Qwen3-0.6B Q8_0 을 불러(GPU 줄), 실행마다 1 초 안. 앱을 켜 둔 동안 GPU 줄을 잡는다.

**하지 않는 것(E3):** 스텝 · 층 화면(상위 후보 더 보기 · 로짓 렌즈 표 · Jacobian lens · 점수 — E4), 실행 지우기, 스트리밍하는 새 실행, 실행 여럿을 한
번에(테스트 세트 — R7), 활성값 개입, 파이썬 API 의 실험 헤더, 채팅을 기본 실험으로(E5).

## 4. E4 — 스텝 · 층 화면

실행 하나의 스텝 하나를 자세히 보는 화면(화면설계.md §3 의 수준 5 · §9 의 로짓 렌즈 표 · 시안의 '스텝 3 의 로짓 렌즈'). 이 화면의 계산은 모두
실험의 실행으로 남고(E3 의 실행 기록), 화면은 그 실행의 기록 파일에서 읽는다 — 다시 열면 이미 기록된 실행을 보이고 다시 계산하지 않는다.

**화면(웹)**
- **경로:** 실험 › id › 실행 r1 › 스텝 k. 실행 화면에서 스텝을 고르고 `Enter` 또는 고른 스텝 패널의 '스텝 · 층 화면'(화면설계.md §8). 스텝 번호는
  실행 화면과 같다(분기는 원래 실행의 번호를 잇는다). `←` `→` 와 이전 · 다음 스텝 버튼으로 옮긴다.
- **헤더:** 스텝 k 와 샘플링된 토큰, 마진 · 샘플링된 토큰의 확률과 순위 · 엔트로피 · 로짓 해시, 실행 정보 줄, 스텝 k 앞의 텍스트 몇 토큰과 그
  토큰(표시).
- **상위 후보:** 실행의 기록에 있는 후보(새 실행의 기본은 2 개)를 먼저 보인다. '상위 후보 N 개 계산'(N = 1 ~ 128, 기본 20) → `run.score` — 프롬프트
  = 실행의 프롬프트 토큰 + 답의 스텝 0 ~ k, `echo: true`, `max_tokens: 0`, `logprobs: min(N, 20)`, `geulpu: {echo_from: P + k, top_logprobs: N,
  logit_hash: true}`(P = 프롬프트 토큰 수). 응답의 `prompt_top_ids` · `prompt_top_logprobs` 로 N 줄(순위 · 토큰 · 로그확률 · 확률 막대, 샘플링된
  토큰 표시)을 보이고, echo 의 로짓 해시가 실행의 스텝 k 와 같은지 표시한다. 후보마다 '이 토큰으로 분기'(E3 의 분기 그대로).
- **로짓 렌즈 표:** '로짓 렌즈 계산'(층마다 상위 3 · 5 · 10 · 20, 기본 5) → `run.lens` — 같은 프롬프트, `echo: true`, `max_tokens: 0`,
  `logprobs: 1`, `geulpu: {echo_from: P + k, logit_hash: true, layer_lens: {top_k, jacobian}}`(`jacobian` 은 서버가 J 파일을 열었을 때만 — 상태의
  `server.jlens_sha256`). 표는 층마다 한 줄(0 이 위, 마지막 층이 아래) — 1 위 · 2 위 · 3 위(토큰과 로그확률), 샘플링된 토큰의 순위와 로그확률,
  엔트로피. 줄을 누르면 그 층의 상위 후보가 모두 보인다. 마지막 층의 1 위가 끝까지 1 위로 남는 첫 층부터 아래를 흰 선으로 묶고(화면설계.md §9),
  표 아래에 그 층과 샘플링된 토큰이 1 위였던 층들을 적는다. 마지막 층의 로짓 해시가 실행의 스텝 k 와 같은지 표시한다(같은 모델 · 같은 계산 방식이면
  같다 — docs/cli.md). 모델이 로짓 렌즈를 받지 않으면(모델의 `layer_lens_ok` 거짓) 계산 버튼 대신 까닭을 보인다.
- **Jacobian lens:** 응답에 `jacobian_lens` 가 있으면 표 위의 '로짓 렌즈 | Jacobian lens' 로 바꿔 본다(같은 형식 — J 파일의 SHA-256 앞 8 자와 함께,
  마지막 층은 두 렌즈가 같다). 서버에 J 파일이 없으면 J 파일을 두는 방법(모델 파일 옆의 `<이름>.jlens.safetensors` — `도구/jlens_fit.py` 로 만든
  것, 모델을 다시 불러오면 함께 읽는다)을, 서버가 J 파일을 받지 않았으면 그 까닭(`server.jlens_reason`)을 보인다.
- **점수:** 텍스트를 넣고 '점수 계산' → `run.tokenize`(특수 토큰 없이)로 토큰 번호 → `run.score` — 프롬프트 = 실행의 프롬프트 토큰 + 답의 스텝
  0 ~ k − 1 + 그 토큰들, `echo: true`, `max_tokens: 0`, `logprobs: 1`, `geulpu: {echo_from: P + k, top_logprobs: 20, logit_hash: true}`(echo
  스코어링). 결과는 토큰마다 로그확률 · 확률 · 순위(상위 20 안이면)와 합(그 텍스트가 스텝 k 부터 이어질 로그확률). 이 스텝의 점수 실행을 최근
  것부터 보인다.
- **이미 기록된 실행 찾기:** 이 실험의 점수 · 렌즈 실행 가운데 `geulpu.echo_from` 이 P + k 이고 프롬프트의 앞 P + k 토큰이 이 실행의 것과 같은
  실행이 이 스텝의 계산이다(같은 앞부분의 행은 그 뒤 토큰과 상관없이 같은 분포를 낸다 — 그래서 어느 점수 실행이든 상위 후보를 준다). 렌즈의 스텝
  k 토큰이 샘플링된 토큰이 아니면(CLI 로 다른 후보를 넣은 것) 표 아래에 그 실행으로 가는 링크만 둔다. 다른 모델(SHA-256)로 계산한 실행은 그
  모델을 표시한다.
- **모델:** 불러온 모델이 실행의 모델과 다르면(SHA-256) 계산 버튼 옆에 경고 — 결과는 불러온 모델의 값이다(막지 않는다 — 다른 모델로 같은 스텝을
  보는 비교도 실험이다).
- **실행 화면 · 목록:** 점수 · 로짓 렌즈 실행의 실행 화면은 요청 · 응답 대신 그 표(점수 표 · 로짓 렌즈 표)와 원래 실행의 스텝 화면으로 가는 링크를
  보인다(응답 JSON 은 접어서). 실행 목록의 설명 — 로짓 렌즈 'r1 의 스텝 3 · 28 층', 점수 'r1 의 스텝 3 · 상위 후보 20 개' · 'r1 의 스텝 3 에
  " The" · 로그확률 −2.31'. AI 실행 자동 열기로 열리는 점수 · 렌즈 실행도 그 표다.
- **좁은 화면:** 섹션이 세로로 쌓이고, 로짓 렌즈 표는 표만 가로로 스크롤한다(화면설계.md §8).
- **모듈:** `앱/web/ui/steps.js`(스텝 · 층 화면 · 로짓 렌즈 표 · 점수 표). runs.js 의 기록 읽기 · 실행 부르기 · 분기를 함께 쓴다.

**서버(앱 — 글)**
- **점수 · 렌즈의 원래 실행:** E3 은 프롬프트가 어느 실행의 '프롬프트 + 답'의 앞부분일 때만 `base` 를 적었다. 이제 프롬프트가 그 실행의 프롬프트
  토큰을 모두 담고 답의 스텝 k 부터 다른 토큰이면(점수의 텍스트 · 다른 후보의 렌즈) `base` 와 `intervention`(`{"type": "token", "step": k,
  "value": <처음 다른 토큰>}`)을 적는다. 맞는 실행이 여럿이면 같은 앞부분이 가장 긴 실행(같으면 먼저 남은 실행). 앞부분이면 지금처럼
  `intervention` 없이.
- **개입의 스텝 번호:** 원래 실행이 분기면(요청의 `geulpu.step_offset`) 그 수를 더해 화면의 스텝 번호와 같게 한다 — 분기의 `intervention.step` 도.
  E3 은 원래 실행의 답 안의 위치를 적어, 분기에서 다시 분기하면 화면의 번호와 달랐다.

**기능 목록:** `run.lens` 의 제목 · 설명 · 인자 설명의 '층 렌즈'를 '로짓 렌즈'로(2026-11-09 용어 검토의 표준 용어 — 화면설계.md §10). `run.lens` ·
`run.score` · `run.tokenize` 와 결과 형식 `lens` · `score` · `tokens` 의 화면에 '스텝 · 층 화면'.

**E4 의 판정(구현 전에 적음)**
1. **상위 후보:** 시험 인스턴스(Qwen3-0.6B Q8_0)에서 실행 r1 의 마진이 가장 작은 스텝 k 의 스텝 화면이 기록과 같은 후보 · 마진 · 엔트로피 · 로짓

   분기하면 E3 의 분기와 같다(`kind: branch` · 스텝 k · 그 후보).
2. **로짓 렌즈 표 · Jacobian lens:** '로짓 렌즈 계산'이 렌즈 실행으로 남고(`kind: lens` · `base` r1), 표의 층 28 줄(토큰 · 로그확률 · 순위 ·
   엔트로피)이 기록의 `layer_lens` 와 같고, 흰 선이 마지막 층의 1 위가 끝까지 1 위로 남는 첫 층부터이며, 마지막 층의 로짓 해시가 r1 의 스텝 k 와
   같다. 같은 본문을 CLI `run lens --json` 으로 보낸 답의 `layer_lens` · `jacobian_lens` 가 기록과 같다. 모델 옆에 J 파일을 두고 불러오면 같은

   `jacobian` 이 없다.
3. **점수:** 스텝 k 에서 텍스트를 넣어 '점수 계산'하면 점수 실행이 `base` r1 · `intervention`(스텝 k · 그 텍스트의 첫 토큰)으로 남고, 화면의
   토큰마다 로그확률 · 합이 기록과 같다. 첫 토큰이 상위 20 안이면 그 로그확률이 상위 후보 표의 값과 같다. CLI(AI 세션 이름)로 다른 후보를 넣은
   렌즈 · 점수도 같은 규칙의 `base` · `intervention` 으로 남고, 분기한 실행의 스텝에서 한 계산의 `intervention.step` 이 화면의 스텝 번호와 같다.
   `experiment check` 가 통과한다.
4. **이동 · 실행 화면:** 실행 화면에서 `Enter` 로 스텝 화면이 열리고 `←` `→` 로 스텝을 옮긴다. 스텝 화면을 다시 열면 이미 기록된 실행을 보이고 새
   실행이 생기지 않는다. 실행 목록에서 렌즈 · 점수 실행을 열면 그 표와 스텝 화면 링크가 보이고, AI 실행 자동 열기를 켜고 AI 세션이 렌즈를 부르면
   1 초 안에 그 표가 열린다.
5. **화면과 점검:** E3 의 판정 5 와 같다 — 사이드바의 화면 9 개, 브라우저 콘솔에 오류 없음, 두 창이 따로 스크롤(실제 휠 이벤트), 375 × 812 에서
   가로로 넘치지 않음(로짓 렌즈 표는 표만 가로로 스크롤), 영어 화면, 기능 목록 점검 · 명령줄 점검 · 화면 문구 점검 · 빠른 점검 통과, 실험 밖의
   기존 응답 12 개가 main 에서 빌드한 앱과 바이트까지 같음.

## 5. E5 — 옛 화면 옮기기

옛 화면의 코드는 그대로 쓰고(정리는 E6), 화면이 놓이는 곳을 새 위계(화면설계.md §3 · §6)로 옮긴다. 사이드바는 실험 · 모델 · 재현 · 작업 · 설정
다섯이고(화면설계.md §10 결정 1), 그룹마다 화면 위에 탭이 있다. 채팅은 기본 실험 "대화"에 들어가 답마다 실행으로 남는다(앱리디자인.md §6 결정 2).

**사이드바와 탭(웹)**

| 사이드바 | 탭 | 옛 화면에서 |
|---|---|---|
| 실험 | 탭 없음(실험 목록 · 실험 · 실행 · 스텝 · 층) | 채팅(경로 실험 › 대화), 디버거(실험 화면의 기록 탭에서) |
| 모델 | 파일 · 평가 · 성능 | 모델(설치된 모델 · 받는 중 · Hugging Face 받기), 모델 평가, 벤치마크의 속도 측정 |
| 재현 | llama.cpp · 검사 · 검사 결과 | 벤치마크의 llama.cpp 재현 검증, 재현성 검증과 파일 쌍 재현성, 최근 결과 |
| 작업 | 탭 없음 | 새 화면 — 화면마다 있던 작업 카드를 한곳에 |
| 설정 | 앱 · 장치 · 프롬프트 캐시 | 설정(프롬프트 캐시를 뺀 것), 하드웨어와 벤치마크의 하드웨어 진단, 설정의 프롬프트 캐시 |

- 사이드바의 단추는 그 그룹에서 마지막으로 연 탭으로 간다(이 브라우저에 기억). 지금 화면이 속한 그룹에 흰 표시. 옛 화면 안의 링크(상태 막대의
  GPU → 하드웨어, '벤치마크로', '모델 화면', '설정 열기' 등)는 그 기능의 새 탭으로 간다.
- 사이드바에 없는 화면 셋: 채팅(실험 › 대화), 디버거(실험 › 디버거 — 실험 화면의 기록 탭의 '디버거의 실행 로그'에서), 에이전트(명령 창 › AI 세션 —
  명령 창 헤더의 'AI 세션' 단추). 탭 대신 그 경로를 보인다(누르면 그 화면으로).
- 벤치마크의 카드는 탭마다 나눠 그린다 — 속도 측정(모델 › 성능), 하드웨어 진단(설정 › 장치), 재현성 검증 · 파일 쌍 재현성(재현 › 검사), llama.cpp
  재현 검증(재현 › llama.cpp), 결과 목록(재현 › 검사 결과). 측정할 모델 고르기는 성능 · 장치 탭에. 설정은 프롬프트 캐시의 줄들을 따로 그린다.
- 새로 고침하면 마지막 화면 그대로(지금처럼). 좁은 화면의 아래 막대도 다섯.

**작업 화면(새 화면 — `ui/jobs.js`)**
- 지금 작업(앱의 작업은 한 번에 하나 — 상태의 `job`): 제목 · 단계 · 진행 막대 · 걸린 시간, 작업 로그(`job.log`), 중지(`job.cancel`).
- 지난 작업: 이 브라우저가 본 작업 30 개까지(종류 · 제목 · 끝난 상태 · 걸린 시간 · 결과 요약 또는 까닭)를 이 브라우저에 기억한다 — 앱은 지금 작업
  하나만 알려 준다.
- 실행 중인 작업이 있으면 사이드바의 '작업'에 강조색 점(화면설계.md §2).
- 앱에는 작업의 대기열이 없다(작업이 있으면 새 작업은 409). 화면설계의 'GPU 큐'는 이 안내 한 줄로 대신한다.

**작업의 진행을 명령 창의 줄에(E1 에서 넘어옴)**
- 앱(글): 작업을 시작하는 기능(기능 목록의 `job: true`)이 200 으로 답하면 그 호출의 `end` 이벤트에 `job`(작업 번호).
- 명령 창: `job` 이 있는 줄은 그 작업이 끝날 때까지 단계 · 진행(%)을 보이고, 끝나면 끝난 상태 · 걸린 시간(실패면 까닭)을 적는다. 줄을 누르면 작업
  화면.

**채팅 → 기본 실험 "대화"**
- 기본 실험: 실험 폴더 위치(E2 의 root)에 제목 "대화" · 이름 `chat` 인 실험(`<날짜>-chat`)을 처음 보낼 때 만들고(`experiment.create`), 그 경로를
  이 브라우저에 기억한다. 같은 위치에 이미 있으면(제목 "대화"인 `*-chat`) 그것을 쓴다.
- 채팅이 보내는 요청에 `X-GeulPU-Experiment` 를 붙여 답마다 실행으로 남긴다(E3 의 실행 기록 — 출처 GUI, `run.chat` · R1 채팅 템플릿이면 `run.complete`).
  요청에 `logprobs` · 상위 후보 2 개 · `geulpu.logit_hash` 를 더해 실행 화면의 막대와 스텝 · 층 화면이 그 답에도 된다.
- 실험 목록의 "대화" 줄은 채팅 화면을 연다(E2 와 같다 — 이제 실행 수가 보인다). 채팅 화면 위에 경로 '실험 › 대화'(누르면 그 실험의 화면 — 실행
  탭에 답들), 답마다 '실행 rN' 링크(그 실행의 실행 화면).
- 채팅 목록(방)은 지금처럼 이 브라우저에 남는다(보이는 대화). 실험에 남는 것은 답마다의 요청과 응답이다.

**스트리밍 실행의 기록(앱 — 글)**: 스트리밍 응답의 실행 기록에 `events`(받은 SSE 이벤트의 JSON 모두, 받은 순서대로)를 더한다. E3 은 확장 필드가 든
마지막 이벤트만 남겨 답의 텍스트와 토큰마다의 로그확률이 기록에 없었다. 실행 화면은 `events` 로 텍스트 · 로그확률을 모아 보인다(스트리밍하지 않은
응답과 같은 값).

**명령 창 › AI 세션 · 실험 › 디버거**: 명령 창 헤더에 'AI 세션' 단추 — 에이전트 화면(코딩 에이전트 시작 · 모델 · 작업 폴더)을 왼쪽에 연다. 실험
화면의 기록 탭에 '디버거의 실행 로그' — 실험 밖에서 기록한 실행 로그(디버거 v1 — 기록 켜기 · 가져오기 · 비교)를 디버거 화면에서 본다.

**기능 목록**: 옮긴 기능의 화면(`gui.view`)을 새 위치로(화면설계.md §6 의 표 — 예: `bench.speed` → 모델 › 성능, `system.devices` → 설정 › 장치,
`agents.*` → 명령 창 › AI 세션).

**모듈**: `ui/nav.js`(사이드바 · 그룹의 탭 · 경로), `ui/jobs.js`(작업 화면), 채팅의 기본 실험은 `ui/experiments.js`. 옛 코드(app.js · eval.js)는
화면을 나누는 곳만 고친다 — 벤치마크 · 설정 화면을 탭마다 그리기, 작업 카드의 갱신을 그 화면 안에서, 채팅 요청의 헤더와 필드, 화면 이름과
그룹의 표.

**E5 의 판정(구현 전에 적음)**
1. **사이드바와 탭:** 사이드바가 실험 · 모델 · 재현 · 작업 · 설정 다섯이고, 탭 아홉(모델 셋 · 재현 셋 · 설정 셋)과 작업 화면이 열려 옛 화면의
   내용이 표의 탭에 있다(옛 화면 아홉의 카드 · 줄을 하나씩 대조 — 빠진 것 없음). 옛 화면 안의 링크(show 를 부르는 곳 모두)가 새 탭으로 가고 사이드바의
   표시가 맞으며, 채팅 · 디버거 · 에이전트는 사이드바 없이 경로로 닿는다.
2. **같은 요청:** 옮긴 화면에서 한 일이 main 에서 빌드한 앱의 옛 화면과 같은 기능을 같은 인자로 부른다 — 설정 하나 바꾸기(`settings.set`), 모델
   불러오기 · 내리기(`model.load` · `model.unload`), 속도 측정(`bench.speed` — 작업), 장치 확인(`system.device_check`)을 두 앱에서 하고 이벤트의
   `op` · `params` 를 견준다. 작업 화면이 실행 중인 작업의 단계 · 진행 · 로그를 보이고 중지가 되며, 명령 창의 그 줄이 진행과 끝을 보인다.
3. **대화:** 채팅 화면에서 보낸 메시지가 기본 실험 "대화"(처음이면 만들어진다)의 실행으로 남는다(`run.chat` · 출처 GUI · `stream: true` ·
   `events`). 실행 화면이 그 답의 토큰과 스텝마다의 값을 보이고 기록과 같으며, 그 요청을 스트리밍 없이 같은 시드로 보낸 답과 토큰 · 로짓 해시가
   같다. 답의 '실행 rN' 링크가 그 실행을 열고, "대화"의 `experiment check` 가 통과한다.
4. **E1 ~ E4 그대로:** 실험 · 실행 · 비교 · 스텝 · 층 화면과 명령 창이 그대로 되고, 실험 밖의 기존 응답 12 개가 main 에서 빌드한 앱과 바이트까지
   같다(`events` 와 `job` 은 실험에 남기는 호출 · 작업을 시작한 호출에만).
5. **화면과 점검:** 사이드바의 다섯과 사이드바 없는 화면 셋이 열리고 브라우저 콘솔에 오류가 없으며, 두 창이 따로 스크롤하고(실제 휠 이벤트),
   375 × 812 에서 가로로 넘치지 않고(사이드바는 아래 막대), 영어 화면 문구가 모두 바뀐다. 기능 목록 점검 · 명령줄 점검 · 화면 문구 점검 · 빠른
   점검이 통과한다.

판정 2 ~ 4 는 GPU 를 쓴다 — 시험 인스턴스에 Qwen3-0.6B Q8_0(GPU 줄), 속도 측정은 앱마다 1 ~ 3 분. 앱을 켜 둔 동안 GPU 줄을 잡는다.

**하지 않는 것(E5):** 옛 코드 정리(E6), 새 기능(실험 폴더 확인 `check.repro` · 같은 비트 `check.same_bits` · llama.cpp 분기 `replay.branch` ·
연구 패널의 기록 `panel.records` — 기능 목록에 계획으로 남는다), 채팅 안의 연구 패널 빼기(E6), 디버거의 실행 로그를 실험으로 옮기기(형식이
다르다 — 앞으로), 작업 대기열.

- **시험:** 시험 인스턴스 둘(main 빌드와 이 빌드 — 포트 44657 · 44658, 임시 데이터 폴더, Qwen3-0.6B Q8_0). GPU 줄 874 초(화면 시험 동안 두 앱을
  켜 둔 시간)와 응답 비교 1 초.
- **설계에 더한 것:** (1) 설정을 한 탭에서 저장해도 본문은 옛 설정 화면과 같다 — 다른 탭의 필드는 지금 설정값으로 채운다. (2) 끝 토큰으로 멈춘 답은
  확장 필드의 상위 후보 · 엔트로피가 토큰 수보다 하나 적다(그 스텝의 값이 없다 — 채팅의 logprobs 도 그렇다). 실행 화면이 이것을 받는다(채팅 실행에서
  찾음). (3) 한 글자의 바이트가 나뉜 토큰은 토큰별 출력에서 글자 사이에 틈을 내지 않는다. (4) 기본 실험은 id(`-chat`)와 제목 대화 · Chat ·
  Conversations 로 찾는다 — 만들 때의 화면 언어로 제목이 붙는다. (5) 이 화면이 끝을 못 본 작업(새로 고침 뒤 등)의 명령 창 줄은 작업 화면이 남긴 지난
  작업에서 끝난 상태를 가져온다. (6) 상태 막대의 작업은 그 작업의 탭(속도 측정 → 모델 › 성능 등)이나 작업 화면으로 가고, 벤치마크 화면을 가리키던 문구
  셋(연구 패널의 링크, 디버거의 llama.cpp 안내, 앱의 파일 쌍 안내)은 새 위치를 가리킨다.

## 6. E6 — 동등성 점검과 마무리

앱리디자인.md §2 의 원칙 2(나) — GUI 의 모든 동작이 기능 목록의 기능을 부르고, 목록의 모든 기능이 GUI 에서 닿는다 — 를 CI 가 확인하게 하고, 옛
화면의 코드를 그 규칙에 맞춘다. 일이 커서 PR 둘로 나눈다: **E6-1 동등성 점검**(1 ~ 4)과 **E6-2 연구 패널 옮기기와 옛 코드 정리**(5 ~ 6). 판정도 PR
마다 따로 적고, E6-2 는 E6-1 의 점검 아래에서 한다(연구 패널을 빼도 모든 기능이 화면에서 닿는지를 CI 가 본다).

**1. 모든 호출을 기능 목록 클라이언트로(웹 — E6-1)**
- 옛 코드(app.js · eval.js)는 경로로 앱을 부른다 — `api(path, body)` 87 곳(app.js 59 · eval.js 28), `postJ` · `labApi` · `dbgSend` · `dbgFetchRun` ·
  `getFile`, 채팅의 스트리밍 fetch, 검사 결과의 zip 내보내기 링크. 이것을 모두 기능 id 로 `ui/ops.js` 를 거치게 바꾼다 — 경로는 기능 목록에만 있다.
- `ui/ops.js` 에 더하는 것: 오류면 던지는 호출(옛 `api` 와 같은 메시지 — `callJ`), 이미 만든 본문 글을 그대로 보내기(2⁵³ 위의 시드 · 큰 정수 —
  `body` 옵션), 응답을 읽지 않고 fetch 의 Response 를 돌려주기(스트리밍 — `open`), 기능 id 와 인자로 주소 만들기(링크 — `urlFor`, 기능 목록을 읽은
  뒤). app.js · eval.js 는 고전 스크립트라 동적 import 로 부른다.
- 요청은 옛 코드와 같다: 같은 메서드 · 경로 · 본문(같은 `JSON.stringify`). GET 의 쿼리만 기능 목록 클라이언트의 % 인코딩이다(`! ' ( ) *` 도
  인코딩 — 앱이 풀면 같은 값).
- 앱 밖의 주소(PyPI · GitHub · Hugging Face)는 그대로 — 앱의 기능이 아니다.
- 전달 경로(`/tokenize` · `/detokenize`)를 쓰던 곳은 서버에서 같은 분기(엔진/서버몸.gl — `/tokenize` 와 `/v1/tokenize` 를 함께 받는다)인 기능
  `run.tokenize` · `run.detokenize` 로 부른다. 이제 이 호출도 이벤트가 나와 명령 창에 줄로 보인다(지금까지는 내부용 경로라 보이지 않았다).

**2. 기능 목록의 화면 필드(기능 목록 — E6-1)**
- 맨 위에 `screens` — 화면 id 마다 `{ko, en}` 이름과 종류: `view`(사이드바 · 탭으로 여는 화면 — 웹 코드의 `VIEW_GROUP` 과 같은 id) · `part`(화면의
  부분 — 실행 화면 · 스텝 · 층 화면 · 명령 창 · 모든 화면의 공통 부분).
- 기능의 `gui` 를 `{screens: [화면 id …], note}` 로 — 지금의 자유 글 `view` 대신(사람이 읽는 이름은 `screens` 표에서). 앞으로의 기능은
  `{planned: 단계}`. 결과 형식의 `gui_view` 도 `screens` 로.
- 화면이 다른 기능들로 같은 일을 하는 기능은 `gui.via`(기능 id 목록)와 `note` 의 까닭 — `model.hf.pull`(실행기의 한 줄 설치 `--hf` 를 떠 있는 앱에
  맡기는 경로. 화면은 같은 일을 `model.hf.check` · `model.hf.add` · `model.download.start` 로 한다).
- 단계 E 에 남겨 둔 표시를 고친다: `system.events` → 명령 창, `run.tokenizer_info` → 모델 › 파일. 앞으로의 기능은 그 단계로 — `check.repro` ·
  `check.same_bits` → 실험대 7(화면의 재현 확인), `replay.branch` → 실험대 3(같은 난수 설정 반사실), `lens.jacobian_fit` → 실험대.

**3. 화면에서 닿지 않던 기능(웹 — E6-1)** — 지금 웹 코드가 부르지 않는 기능 7 개:
- `run.models` · `run.tokenizer_info` → 모델 › 파일: 불러온 모델 줄의 '서버 정보' — 서버가 알리는 모델 이름 · 문맥 길이(`/v1/models`), 토크나이저의
  끝 토큰 · 채움 토큰 · 어휘 수 · 문맥(`/v1/tokenizer_info`).
- `run.messages` · `run.messages.count_tokens` · `run.responses` → 실험 › 새 실행: 종류에 'Anthropic Messages' · 'OpenAI Responses'. 이 두 형식은
  서버가 시드와 GeulPU 확장 필드를 받지 않는다(엔진/서버몸.gl 의 `앤바꾸기` — temperature · top_p · stream 만 옮긴다). 그래서 실행 화면은 답의 텍스트 ·
  도구 호출 · 사용량만 보이고, 토큰별 값이 없는 까닭과 '온도 0 이면 같은 답'을 화면에 적는다. Messages 에는 '토큰 수 세기'(count_tokens).
- `model.hf.pull` → 2 의 `via`.
- `system.events` → 명령 창(이미 부른다 — 표시만).
- `run.detokenize` · `system.provenance` 는 1 의 바꿈 뒤 연구 패널이 부른다. 연구 패널을 빼는 E6-2 에서 새 화면으로 옮긴다(5).

**4. CI 의 동등성 점검(시험/기능목록점검.py — E6-1)** — 점검 4 · 5 를 바꾸고 자체 시험에 잘못을 더한다:
- **4 화면:** 내부용이 아닌 있는 기능마다 `gui.screens`(또는 `gui.via`)가 있고, 화면 id 가 `screens` 표에 있으며, 표의 `view` 가 웹 코드의 화면
  (`VIEW_GROUP`)과 같다(빠짐 · 남음 0). `via` 의 기능은 있는 기능이다. 결과 형식마다 `screens` 가 있고 어느 기능의 결과다.
- **5 웹 코드:** (가) `ui/ops.js` · `ui/command.js` 밖의 웹 코드에 앱 · 서버 경로의 글(`/api/` · `/v1/` · `/tokenize` · `/detokenize` ·
  `/tokenizer_info` · `/llama/`)이 없다. (나) 기능 목록 클라이언트를 부르는 곳의 첫 인자는 글 그대로의 기능 id 이고, 목록에 있는 있는 기능이다.
  (다) 내부용이 아닌 있는 기능의 id 가 모두 화면 코드(`ui/ops.js` · `ui/command.js` 밖)에 있다 — 아니면 그 기능의 `via` 가 모두.
- **자체 시험:** 지금의 일곱(그 가운데 '웹 코드가 부르는 목록 밖 경로'는 '화면 코드의 경로 글'로)에 더해 — 목록에 없는 기능 id 를 부름, 화면에서
  닿지 않는 기능, 없는 화면 id, 기능 목록에 없는 화면(`VIEW_GROUP`), 어느 기능의 결과도 아닌 결과 형식.

**영어 화면 문구:** E5 에서 새 문구는 모두 영어다. E6 은 바꾸거나 더한 문구를 화면 문구 점검(시험/화면사전.py)으로, 화면마다 남은 한국어를
브라우저에서 본다(데이터 — 폴더 경로 · 사용자의 글 · 모델의 답 — 와 'Language · 언어' 만 남는다).

**E6-1 의 판정(구현 전에 적음)**
1. **클라이언트:** 웹 코드에 앱 · 서버 경로의 글이 없다(점검 5 가). 바꾸기 전(main)에서 빌드한 앱과 이 빌드에서 같은 동작을 하고 이벤트의 `op` ·
   `params` 가 같다 — 설정 저장, 모델 불러오기 · 내리기, 장치 확인, 하드웨어 진단(작업 · 중지), 모델 평가 화면, 디버거의 기록 켜기 · 끄기, 채팅 한 번,
   연구 패널의 관찰 · 점수 · 재현, 검사 결과의 zip 링크. 전달 경로였던 토큰화는 `run.tokenize` 로 새로 보인다(그 밖의 차이 0).
2. **닿기:** 점검 5 다 — 내부용이 아닌 있는 기능 모두가 화면 코드에서 불린다(빠짐 0, `via` 1). 새로 닿게 한 기능을 화면에서 한 번씩: 모델 › 파일의
   서버 정보(모델 이름 · 문맥 길이 · 토크나이저 — CLI 의 `run models` · `run tokenizer-info` 와 같은 값), 새 실행의 Messages · Responses(실행으로
   남고 실행 화면이 답의 텍스트를 보인다, Messages 의 토큰 수가 CLI 와 같다).
3. **기능 목록:** 점검 1 ~ 6 통과, 화면 id 와 웹 코드의 화면이 같다, 자체 시험 12/12.
4. **화면과 점검:** 화면 14 개 · 실험 탭 · 실행 화면이 브라우저 콘솔 오류 없이 열리고, 영어 화면에 바꾸거나 더한 문구가 모두 영어다. 화면 문구 점검 ·
   명령줄 점검 · 빠른 점검 통과.

판정 1 · 2 는 GPU 를 쓴다 — 시험 인스턴스 둘(main 빌드 · 이 빌드)에 Qwen3-0.6B Q8_0(GPU 줄). 앱(글) 코드는 바꾸지 않는다(웹 · 기능 목록 · 시험만).

**5 · 6. 연구 패널 옮기기와 옛 코드 정리(E6-2)** — 연구 패널(채팅 옆 — app.js 의 약 1,100 줄)의 기능을 하나씩 새 화면(실행 · 비교 · 스텝 · 층)과
대조해, 새 화면에 없는 것(예: 재현 파일 · 출처 · 내보내기)을 새 화면으로 옮긴 뒤 연구 패널과 그 코드를 뺀다. 옮긴 옛 화면에서 쓰지 않게 된 코드도
뺀다. 대조표 · 설계 · 판정은 E6-2 를 시작할 때 이 절에 적는다(구현 전에).
