## 컴파일러 선택과 옵션

검토 대상은 글 1.4.0, `0899bd753e1626e31c3094f5787d0f46ad4f7cc4`다. `ref/geulc.py`의 명령줄과 `ref/geul/driver.py`의 호출 흐름을 확인했다. 별도의 `-O2`/고급 최적화 모드는 없으며 정상 빌드에 작은 함수 인라인과 코드생성기의 핍홀·레지스터 할당이 적용된다. `--핫스왑`은 인라인을 끄고 호출 방식을 바꾸므로 속도 최적화 옵션으로 쓰지 않았다.

`ref/geul/inline.py`는 본문 12명령 이하, 분기·점프·호출 없는 작은 함수만 한 겹 인라인한다. `ref/geul/codegen.py`에는 상수 즉시값, 임시값 전달, 주소 접기, 직접 지역 접근, 선형 스캔 레지스터 할당, 비교-분기 결합이 구현돼 있다. 이 벤치마크의 GL 처리 함수에서는 패킹된 SIMD 정수 연산이 관측되지 않았다.

## 적용한 소스 최적화

`optimize_sources.py`가 같은 의미의 GL/C 소스를 생성한다. 원본은 보존했다.

- 복사/변환의 모드 분기를 원소 루프 밖으로 이동.
- 복사/변환 루프를 4개씩 펼침, 나머지 원소 처리 포함.
- 합산에 독립된 누산기 4개 사용, 나머지 처리 포함.
- 타일 전치의 순회를 출력 연속 쓰기 순서로 변경.
- GL의 누산·색인 `+=`를 같은 의미의 `x = x + ...`로 표현해 생성 코드를 확인.

이는 소스 최적화 후보다. 실제 실행 검증과 측정이 막혔으므로 더 빠르거나 최적으로 확정한 구현은 아니다. C도 같은 작업 분리·펼치기·누산기·순회 변경을 적용하고 `/O2 /W4`로 빌드했다. GL 참조 컴파일러를 실행한 Python은 이전 개발 환경이 앱 제어로 막혀 사용 가능한 Codex 제공 Python 3.12 런타임으로 바꿨다. 컴파일러 Python 교체는 벤치마크 실행 언어 교체가 아니며 원본 실행 파일도 동일했다.

## 기계어에서 확인한 차이

원본 GL 합산 루프:

```asm
mov r14,qword ptr [r13]     ; 누산값 읽기
mov r12,qword ptr [r15+r12*8]
add rax,r12
mov qword ptr [r13],rax     ; 누산값 쓰기
...
mov rax,qword ptr [r12]     ; 색인 읽기
add rax,1
mov qword ptr [r12],rax     ; 색인 쓰기
```

MSVC `/O2` 원본 합산 루프는 `movdqu`와 `paddq`로 여러 int64를 함께 처리한다:

```asm
movdqu xmm0,XMMWORD PTR [r11+rdx*8]
paddq xmm2,xmm0
movdqu xmm0,XMMWORD PTR [r11+rdx*8+16]
add rdx,4
paddq xmm1,xmm0
```

최적화 GL에서는 누산기 3개가 r13/r14/r15에, 색인이 rsi에 유지되고 `add rsi,4`가 관측됐다. 네 번째 누산기는 여전히 스택에 있고 입력 포인터/길이도 스택에서 다시 읽는다. 즉 소스 표현에 따라 레지스터 사용은 개선됐지만 SIMD와 스필 문제는 남는다.

처리 함수 범위는 원본 `0x14000a98d..0x14000acd8`(843바이트), 최종 최적화 `0x14000a98d..0x14000b08f`(1794바이트)다. 루프 펼치기로 원본보다 커졌다. 중간 최적화 버전 2132바이트에서 단순 대입 표현으로 1794바이트로 줄었으며, 이를 원본보다 작아졌다는 뜻으로 해석하면 안 된다. 스택 프레임 예약량도 원본 0x488에서 최종 0xCE8로 증가했다. 정적 크기나 명령 수만으로 실제 속도를 판단하지 않는다.

## 측정 차단과 제외한 대조군

일반 실행 환경에서 `geul-opt.exe` 시작 시 `WinError 4551: 애플리케이션 제어 정책에서 이 파일을 차단했습니다`가 발생했다. 샌드박스 승인 거절이 아니라 Windows 실행 정책 오류다. 실행 파일을 변형·재포장하거나 정책을 해제하는 방식으로 우회하지 않았다. 원본 GL의 첫 실행은 검증을 통과했지만 비교 라운드가 완성되지 않아 성능 결과로 집계하지 않았다.

자동 벡터화를 끄는 대조군을 위해 시도한 `/Qvec-`는 설치된 MSVC가 알 수 없는 옵션으로 무시했다. 따라서 그 바이너리를 스칼라 C 대조군으로 사용하지 않았고 최종 실행기에서도 제외했다.

재측정하려면 장치의 앱 제어 정책에서 해당 파일의 실행이 적법하게 허용되거나, 해당 실행 파일을 허용하는 측정 환경이 필요하다. 허용 후 다음 명령으로 원본/최적화 GL/C를 4라운드 교차 측정한다:

```powershell
& 'C:/Users/junso/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe' -X utf8 재기/language/audit_run.py
```

성공 시 `audit-results.json`, 차단 시 `audit-blocked.json`을 기록한다. 최적화 프로그램의 전체 원소 검증도 실행기에 포함된다. 현재 `audit-results.json`은 생성되지 않았다.

## 현재 판단

이전 측정은 GL의 최적 성능을 증명한 시험이 아니었다. GL에 더 적합한 소스 표현이 존재하며 생성 코드도 달라진다. 반면 이 저장소에 별도의 고성능 컴파일러 선택지가 있다는 근거는 발견하지 못했고, 확인한 두 컴파일러 출력은 같다. 현 시점에는 GL 최적화 후 C를 앞서는지 판단할 수 없다. 다음 성능 개선 후보는 주소를 거치는 복합 대입 하강, 레지스터 압박/스필, 루프 최적화, 정수 SIMD 코드 생성이다. 실제 컴파일러 수정에는 참조와 자체 구현을 함께 수정하고 교차검증해야 한다.
