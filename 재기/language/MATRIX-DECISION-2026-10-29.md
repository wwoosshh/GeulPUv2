# 계약 행렬곱 실측과 GeulNPU 구현 언어 결정

## 결정

현재 시스템은 **NPU 커널: C++ + MLIR-AIE, CPU 성능 핵심부: C/C++, 모델·실행 계획 제어: GL, 시험/참조: Python**으로 구성한다. 이는 측정과 현재 구현 가능성에 근거한 기술 권고이며, 미래의 모든 GL 컴파일러보다 C가 항상 빠르다는 주장이 아니다.

기존 GL 엔진과 수치 계약을 보존하되 행렬 계산·대량 패킹·FP32 후처리·장치 버퍼 수명 관리를 GL의 스칼라 원소 루프로 옮기지 않는다. 장치 연산은 현재 실제 실행이 검증된 C++/MLIR-AIE 경로를 사용한다. GL에는 아직 AIE 장치 코드 생성 백엔드가 구현돼 있지 않으므로, 그 컴파일러를 새로 만드는 일을 현재 성능 개선의 선행 조건으로 삼지 않는다.

## 새 벤치마크

단순 복사 대신 GeulPU 정수 선형층의 정확한 핵심인 **INT8 자리 두 개 × INT8 가중치의 깊이32별 INT32 행렬 부분합**을 측정했다. 입력은 정수계약.자리로(x,2)로 만들고, 스케일은 FP16로 반올림한 FP32, bias는 FP32다. 가중치는 [-128,127], 활성값은 고정 시드 난수 FP32다. 실제 모델 파일에서 추출한 가중치는 아니며 Qwen3 선형층에 나타나는 입력/출력 폭을 포함하는 합성 시험이다.

두 언어는 같은 INT8 저장형·INT32 누산형·행/블록/열 순회·사전 패킹한 가중치 배치를 사용한다. 깊이32 내부에 4개 누산기와 4개씩 펼친 루프를 사용한다. GL의 누산과 인덱스는 단순 대입으로 표현했다. C 함수는 noinline이며 외부 BLAS나 행렬 라이브러리를 사용하지 않았다. GL의 산술도 외부 C 함수에 위임하지 않았다. 파일 읽기/쓰기는 CRT를 사용하지만 타이머 밖이다.

| 조건 | M×K 입력 / N×K 가중치 | GL | C /O2 | C /O2 /arch:AVX2 | C /O2의 GL 대비 속도 |
|---|---|---:|---:|---:|---:|
| 한 토큰형 | 1×1024 / 1024×1024 | 2.730 ms | 0.913 ms | 0.830 ms | 2.99배 |
| 여러 토큰형 | 32×1024 / 256×1024 | 21.674 ms | 7.130 ms | 6.782 ms | 3.04배 |
| FFN 폭 조건 | 16×3072 / 1024×3072 | 129.164 ms | 44.643 ms | 45.185 ms | 2.89배 |

활성값 두 자리를 모두 처리하므로 실제 정수 행 수는 2M이다. 가장 큰 조건에서는 한 번에 100663296개의 정수 곱과 그 누산을 수행하고 3145728개의 INT32 부분합을 출력한다. 서로 다른 블록을 합쳐서 계약을 바꾸지 않았다.

3라운드에서 구현 실행 순서를 회전했고, 구현/조건마다 예열 1회와 측정 4회씩 실행했다. 표는 12표본 중앙값이다. 처리 함수 내부 시간만 측정하며 준비·패킹·검증·파일 I/O·FP32 후처리는 제외한다. 전체 모델 TPS나 NPU 전송 성능이 아니다.

AVX2 빌드는 모든 조건에서 유리하지 않았다. 따라서 AVX2 플래그만으로 항상 빨라진다고 판단하지 않으며, CPU 기본 경로는 정확성을 검증한 /O2로 두고 ISA별 구현은 개별 측정해 선택한다.

## 정확도 검증

- 독립 NumPy INT32 행렬 부분합 기준을 생성했다. 피연산자 크기상 오버플로가 없으며 모든 중간합이 INT32 범위다.
- GL/C 실행 파일은 매 반복마다 전체 부분합을 기준 파일과 비교한다. 총 135회 커널 실행이 모두 통과했다.
- 각 프로세스 종료 후 저장된 부분합 파일의 바이트 전체를 다시 비교했다.
- 저장된 부분합을 GeulPU의 자리 지수 복원 → 자리 합 → 블록 순서 FMA → bias 처리에 넣었다. 정수계약.행렬곱블라스의 FP32 결과와 uint32 비트로 비교해 모든 조건·구현·라운드에서 일치했다.
- 최종 FP32 후처리는 공통 Python 참조에서 수행했으므로, 이 시험은 **C/GL 자체 FP32 후처리 성능이나 정확성 구현을 검증한 것은 아니다.**

## 시스템에 적용할 역할

| 계층 | 선택 | 이유 |
|---|---|---|
| NPU 장치 커널 | C++ / MLIR-AIE | 이미 실제 XDNA2 실행·정수 정확성 검증 완료. 전용 타일·DMA·AIE 명령을 표현하는 경로가 있음 |
| CPU 수치/데이터 핵심부 | C/C++ | 이번 계약 행렬 부분합에서 /O2가 GL보다 약 3배 빠름. 향후 패킹·후처리는 각각 실측·비트 검증 후 이식 |
| GL 엔진 | 모델 구조, 실행 계획, 계약 버전, 오류/수명 주기 제어 | 기존 GeulPU 구조를 보존하며 대량 연산을 네이티브 API 단위로 호출 |
| Python | 참조·시험·측정 | 제품 실행 경로의 원소별 루프에서 제외 |

GL↔네이티브 경계는 타일 하나가 아닌 준비된 선형층/더 큰 실행 계획 단위로 잡는다. NPU 장치 실행에는 CPU용 MSVC /O2가 아니라 AIE 전용 컴파일러를 사용한다. 현 CPU 행렬 실측으로 장래 GL 생성 NPU 커널보다 C++ 생성 NPU 커널이 빠르다고 증명한 것은 아니다. **현재 구현 가능한 경로와 실측된 비용에 따라 선택한 것이다.**

가장 먼저 이식할 대상은 이전 NPU 프로파일에서 약 5.95초를 차지한 CPU FP32 후처리다. 이것을 C++로 옮길 때는 현재 반올림·비정규수·FMA 의미를 명시적으로 보존하고 비트 회귀시험을 통과시켜야 한다. 이번 행렬 시험의 3배를 후처리나 전체 모델에 그대로 적용하지 않는다. 그다음 NPU 네이티브 행렬 명령·다중 코어·전송 중첩을 구현한다.

## 제한과 재현

코어 고정·전력·클록·외부 부하는 통제하지 않았다. 예를 들어 여러 토큰형 GL의 라운드 중앙값은 50.67/21.67/20.59 ms로 변동이 크지만, 가장 빠른 GL 표본도 가장 느린 C /O2 표본보다 느렸다. 세 조건 모두 관측된 GL/C 범위가 분리됐으며 이 작업에 대한 선택 방향은 일관적이다. 다른 모델·크기·알고리즘의 보편적인 언어 우열로 확장하지 않는다.

소스/입력 생성: `matrix_generate.py`, 생성된 `matrix.gl`, `matrix.c`. 실행/검증: `matrix_run.py`. 전체 표본·검증·소스/실행 파일 해시: [matrix-results.json](matrix-results.json). 입력/참조/원시 출력: `빌드/matrix/`.

컴파일은 `geul-lang/ref/geulc.py matrix.gl -o gl.exe`, MSVC `cl /O2 matrix.c` 및 `cl /O2 /arch:AVX2 matrix.c`다. 실행기는 위 파일들을 `빌드/matrix/{gl,c,c-avx2}.exe`에서 찾아 실행한다. Python은 현재 사용 가능한 Codex 제공 런타임을 사용했다. 기존 컴파일러·언어를 변경한 시험은 아니다.
