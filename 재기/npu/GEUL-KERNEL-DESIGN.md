# GL의 특성을 이용하는 계약 기반 NPU 커널 설계

2026-10-29. 현재 코드 분석과 정확성 시험에 근거한 설계 제안이다. NPU 뒷단 구현이나 새로운 NPU 속도 결과를 뜻하지 않는다.

2026-10-30 후속: 두 자리 결합을 실제 AIE 커널에 구현하고 검증했다. 새 구현·측정 범위와 제한은 [실제 NPU 검증 결과](FUSION-RESULTS-2026-10-30.md)를 참조한다. 아래는 최초 설계 시점의 설명이며 GL→AIE lowering은 아직 구현하지 않았다.

추가 후속: 제한된 정적 정수 커널에 대해 공식 GL 앞단의 typed AST → AIE 백엔드를 구현했다. 불변 벡터 적재 이동, 중복 적재 재사용, 두 자리 결합을 적용하고 네이티브 C 및 AIE C++와 실제 장치에서 비교했다. 현재 구현 범위와 결과는 [GL/AIE 비교](gl_aie/README.md)를 참조한다. 아래 본문의 미구현 표시는 최초 설계 시점의 상태다.

## 결론

GL을 범용 x86 스칼라 루프로만 쓰는 대신 **계약 의미를 유지하는 커널 작성 언어**로 사용한다. GL 앞단 → 계약 연산 IR → 장치별 배치/융합 → MLIR-AIE 또는 AIE C++로 내리는 구조다. 커널 소스가 GL이라는 것과 장치 코드 생성에 C++/MLIR를 이용한다는 것은 양립한다.

현재 제품 경로를 빠르게 만드는 선택은 C++/MLIR-AIE이고, 기존 GL 엔진을 남긴다. GL로 커널을 작성하는 중기 경로에서는 아래의 의미 있는 연산만 지원하는 작은 뒷단부터 만든다. 범용 GL 전체를 NPU에 옮기는 컴파일러를 먼저 만드는 것은 권하지 않는다.

## 실제 GL에서 확인한 특성

1. 조사로 인자 역할을 구별한다. 입력/출력/스케일/누산기를 명확하게 표현하고 잘못된 인자 대응을 검사하는 데 쓸 수 있다. 다만 현재 조사는 버퍼 비중첩이나 소유권을 증명하지 않으므로 별도의 분석·런타임 검사가 필요하다.
2. 앞단이 타입 IR을 내고 별도 뒷단이 이를 사용한다. GeulPU `백엔드/PTX/PTX.gl`은 `self/하강.gl`을 포함하며, 범용 x86 컴파일러와 다른 경로다.
3. GPU 내장을 실제 장치 명령으로 변환한다. 같은 파일의 `정수텐서곱`은 `mma.sync...s32.s8.s8.s32`, `바이트넷곱더하기` 계열은 dp4a, `곱해더하기`는 명시적인 fma.rn, 비동기 복사는 cp.async로 내린다. 실제 외부 CPU 함수를 호출하는 것이 아니다.
4. 기존 PTX 뒷단에는 값 범위·주소 공간·정렬 관련 분석이 있다. CPU 단순 루프 벤치마크는 이 GPU 특화 경로의 성능을 측정하지 않았다.
5. 범용 x86 생성기는 작은 함수 인라인, 즉시값/주소 접기, 선형 스캔 레지스터 할당을 쓴다. 자동 SIMD가 나온 C와 같은 최적화 범위를 가정할 수 없다.

따라서 GL 커널의 장점을 살리려면 **높은 수준의 계약 연산을 앞단에서 너무 일찍 스칼라 load/mul/add로 분해하지 않아야 한다.**

## 먼저 넣을 연산 단위

다음은 새 뒷단의 의미 정의이며 현재 GL에서 바로 컴파일되는 문법 예제가 아니다.

- `정수블록곱32`: signed INT8 × signed INT8 → 정확한 INT32 부분합. 깊이 32와 오버플로 상한을 보존한다.
- `두자리결합`: 같은 활성값·가중치·블록의 S0/S1을 정확하게 `256*S1+S0`로 만든다.
- `계약지수복원`: INT32 → FP32 RN-even 한 번, 양의 2의 거듭제곱으로 스케일 복원.
- `계약블록누산`: 블록 오름차순의 규칙 R FMA. 재결합 금지.
- `타일적재/제출/완료`: 정렬·버퍼 길이·읽기/쓰기 영역·완료 이벤트를 명시한다.

`정수블록곱32`는 CPU SIMD, GPU MMA, NPU 행렬 명령에 서로 다르게 매핑한다. 동일한 스칼라 루프를 세 장치에 전달하지 않는다. NPU의 지원 타일/누산 폭은 해당 도구와 실제 장치에서 확인해 선택해야 한다.

## 검증한 최적화: 두 자리 부분합 결합

현재 두 자리 계약은 각 깊이32 블록에서 다음 값을 계산한다.

```
v1 = FP32(S1) * 2^(E - 5)
v0 = FP32(S0) * 2^(E - 13)
u  = RN32(v1 + v0)
```

이를 다음처럼 내릴 수 있다.

```
T = 256*S1 + S0                 # 정확한 INT32 연산
u = FP32_RN_even(T) * 2^(E - 13)
```

성립 근거:

- 두 자리 활성값 정수 n = 256*D1+D0이며 |n|≤2^14, |q|≤128, 블록 깊이32이므로 |T|≤2^26. INT32 누산과 자리 결합이 안전하다.
- S0/S1 각각은 FP32에 정확하게 표현된다. 따라서 원래 식의 유효한 반올림은 자리 합에서 한 번이다.
- E∈[-98,100]일 때 최종 비영 값은 최소 2^-111, 최대 약 2^113 범위로 이 자리 합에는 서브노멀/오버플로 문제가 없다. 이 범위의 2의 거듭제곱 스케일은 반올림 위치를 이동할 뿐이다.
- 정확한 상쇄 결과는 RN-even의 +0이며 정수 0 변환과 일치한다. 이후 스케일 d와 누산 y의 FMA 규칙은 전혀 바꾸지 않는다.

199개 지수 전체에서 무작위/경계 부분합 1646327조합을 검사해 비트 차이 0이었다. 세 행렬 조건의 최종 FP32 출력 25600개도 기존 정수계약.행렬곱블라스와 같았다. 기록은 `results/2026-10-29-digit-fusion.json`, 재현 코드는 `test_digit_fusion.py`다. 이것은 CPU에서의 변환 규칙 검증이며 실제 NPU 구현 시험은 아니다.

이 규칙을 NPU 안에 넣으면 **유효한 블록 부분합 결과를 두 INT32에서 한 INT32로 줄여 논리적 출력량을 8바이트→4바이트로 줄일 수 있다.** 실제 DMA 패딩·정렬·다른 전송은 별도이며 전체 시간이 2배 빨라진다는 뜻은 아니다. INT8 두 자리 곱 자체는 여전히 두 번 필요하다. 네이티브 INT16×INT8 연산 사용 여부는 별도 하드웨어 검증 없이는 가정하지 않는다.

안전한 구현에서는 음수 signed 정수의 왼쪽 shift에 의존하지 않고 `S1*256 + S0`를 범위 검증된 연산으로 표현한다. C++ 타깃에서도 동일 규칙을 적용할 수 있다.

## 추가로 성능을 얻을 구조

### 정적 특수화

모델 로딩 시 K/N, 블록32, 자리수2, 타일 배치, 정렬, 지원 입력 행 범위를 계획에 고정한다. 내부 루프에서 반복되는 모드 분기·나눗셈·주소 계산을 제거하고, 마지막 부분 타일은 별도 경로로 만든다. 비중첩/정렬은 실제 버퍼에 대해 확인한 후에만 최적화 근거로 쓴다.

### 출력 타일을 유지하며 블록 진행

입력 활성값 타일을 여러 출력 채널에 재사용하고, 가중치 타일을 여러 입력 행에 재사용한다. 한 블록의 두 자리 계산 직후 T로 결합한다. 장치에서 정확한 FP32 후처리가 가능해지면 출력 y를 장치 안에 유지해 블록 순서대로 갱신하고 최종 출력만 반환한다. 후처리 구현 전에는 T를 CPU로 전달하되 전체 K를 먼저 합산하지 않는다.

### 행렬곱 뒤 연산 결합

별도 커널 경계와 중간 메모리 저장을 줄이는 것은 허용한다. 그러나 bias, residual, 활성화 연산을 결합할 때도 기존 FP32 반올림 지점을 남겨야 한다. 중간 FP32 값을 넓은 누산기에 계속 보관하면 계약이 달라질 수 있다. 연산 합성 자체와 반올림 제거는 다른 최적화다.

### 비동기 실행

이중 버퍼·명시적 완료 이벤트·읽기/쓰기 소유권을 계획에 포함한다. in-flight 입력 변경, 완료 전 결과 읽기, CPU 쓰기 후 H2D 동기화 누락은 오류로 취급한다. 이미 경험한 동기화 버그 때문에 이 부분은 속도보다 먼저 명시해야 한다.

## 범용 x86 GL에 필요한 개선

`ref/geul/lower.py`의 복합 대입은 같은 주소에 load/store를 내고, `codegen.py`의 지역 승격은 직접 접근으로 인정된 주소만 레지스터 후보로 남긴다. 이 상호작용이 단순 누산에서도 스택 접근을 만들 수 있다.

- 주소가 탈출하지 않는 **단순 지역 변수**의 복합 대입을 값 갱신으로 정규화한다.
- `a[f()] += g()`를 무조건 `a[f()] = a[f()] + g()`로 바꾸면 f()가 두 번 실행되는 등 의미가 달라질 수 있으므로 일반 치환은 금지한다.
- 루프 단위 생존 구간·레지스터 압박을 고려한다. 많이 펼치면 오히려 스필이 늘어나므로 무조건 펼치지 않는다.
- 범위가 증명되는 색인/부분합만 좁은 정수형을 쓰고, 실제 포인터와 큰 오프셋은 필요한 폭을 유지한다.
- CPU SIMD를 원한다면 명시적 벡터 내장 또는 벡터화 단계를 추가해야 한다. 소스의 반복문 모양만으로 없는 SIMD 기능이 생기지 않는다.

이 변경은 참조/자체호스팅 구현 양쪽에 반영하고 바이트 교차검증해야 한다. 현재 이 문서는 해당 컴파일러 수정을 수행한 것이 아니다.

## C보다 빠르고 정확하다는 주장에 대한 기준

GL이 형상·블록·정밀도·반올림·데이터 수명을 명시하는 커널 언어가 되면, 이런 정보가 없는 일반 C 루프보다 좋은 실행 계획을 만들 기회가 있다. 하지만 같은 특수화와 계약을 적용한 C++도 같은 기계어를 만들 수 있다. 언어만으로 그 최적화된 C++보다 항상 빠르다고 주장하지 않는다.

같은 계약을 지키는 C와 GL은 같은 비트를 내야 한다. 목표는 올바른 C보다 숫자적으로 더 정확해지는 것이 아니라, **위험한 변환을 거부하고 비트 일치를 유지하면서 더 적은 전송·호출·중간 메모리로 실행하는 것**이다. 활성값 양자화 정밀도 자체를 높이는 것은 별도 계약 변경이다.

채택 조건은 (1) 정수 범위/반올림 정당화, (2) 경계값과 실제 행렬의 비트 회귀, (3) 같은 계약·타일·전송 조건의 C++ 기준과 비교, (4) 프리필/디코드 전체 지연 및 메모리 측정이다. 성능 향상이 없는 규칙은 채택하지 않는다.

## 실행 우선순위

1. 검증한 두 자리 결합을 기존 NPU 커널에 구현하고 출력/전송량과 지연을 측정.
2. 같은 의미를 GL 커널 내장으로 표현하고, 작은 GL→계약 IR→AIE 변환기로 기존 커널을 생성.
3. 타일 재사용·장치 FP32 계약 후처리·연산 결합을 순서대로 추가.
4. 전체 모델 비트 검증과 CPU/NPU 프로파일 후 CPU GL 레지스터/SIMD 개선의 우선순위를 결정.

이 경로에서는 GL을 커널 작성 언어에서 배제하지 않으면서 현재 검증된 AIE 도구를 활용한다. 지금까지 CPU GL 벤치마크에서 진 것을 무시하지도 않고, 그것으로 GPU/NPU용 GL 뒷단의 가능성을 부정하지도 않는다.
