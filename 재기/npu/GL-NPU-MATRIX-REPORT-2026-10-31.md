# GeulLang(GL) 행렬 커널 최적화와 NPU 벤치마크 종합 보고서

작성일: **2026-10-31, 한국 시간**  
대상: GeulPU 정수 선형층의 비트 일치 계약을 유지하는 GL 기반 NPU 실행 경로  
성격: 기존 코드·실험 로그·원시 JSON을 대조한 종합 보고서. 이 문서 작성 과정에서 성능을 새로 측정하지 않았다.

## 1. 결론과 현재 판단

**GL을 정밀도 계약을 표현하는 NPU 커널 작성 언어로 사용하는 방향은 실제 장치 시험에서 성립했다.** 공식 GL 파서와 타입 검사기를 사용하는 제한된 AIE 백엔드를 구현했고, 두 자리 정수 부분합 결합·입력 벡터 재사용·중복 적재 제거를 적용했다.

같은 NPU에서 비교한 최종 결과는 다음과 같다.

| 비교 범위 | 결과 | 해석 |
|---|---|---|
| 2,048프레임 타일 묶음 호출 | GL 19.39 ms, 최적화 C 127.13 ms | 측정한 C 4누산기 구현 대비 GL 약 **6.56배** |
| 호스트 후처리를 포함한 세 선형층 | 최적화 C 대비 GL **3.31~5.78배** | NPU 계산 외 비용이 포함되면 향상 폭이 달라짐 |
| Qwen3 모델의 warm 선형층 시간 합 | GL 11.49초, 최적화 C 51.99초 | 관측 속도비 **4.52배**. 생성 TPS 또는 전체 프로그램 실행시간 아님 |
| 동일 내장을 쓰는 수작업 AIE C++ | GL과 커널 기계어 구간이 동일 | GL의 추가 장치 실행 오버헤드 없이 같은 코드에 도달 |
| 정확성 | 타일·선형층·모델 시험에서 비트 불일치 0 | 시험한 범위에서 기존 계약 및 반복 재현성 유지 |

따라서 **커널 소스는 GL로 작성하고, 검증된 장치 연산으로 내려 AIE 도구로 컴파일하는 구조**를 권한다. 현재의 일반 C 루프보다 빠른 결과를 얻었지만, 같은 내장을 사용하는 최적화 C++보다 GL 자체가 본질적으로 빠르다는 증거는 아니다.

현재 구현은 정적 정수 타일에 한정한 실험 백엔드다. 일반 GL 전체의 NPU 지원, GL 제품 엔진 통합, 장치 FP32 후처리, 다중 코어 및 비동기 파이프라인까지 완성한 상태는 아니다.

## 2. 무엇을 비교했는가

### 2.1 형상과 수치 계약

입력 활성값은 `X[M,K]`, 가중치는 `Q[N,K]`, 출력은 `Y[M,N]`이다.

- `M`: 입력 행 수. 모델의 고정 prefix 시험에서는 토큰 수에 해당한다.
- `N`: 출력 채널 수.
- `K`: 입력 채널 수. 이번 커널은 32의 배수를 사용한다.
- 깊이 방향을 32개씩 나눈 블록마다 별도의 정수 부분합과 스케일을 유지한다.
- 활성값을 두 INT8 자리로 분해하고 INT8 가중치와 곱한다.
- INT32 정수 부분합을 FP32로 복원한 뒤, 블록 오름차순으로 계약에 맞는 FMA 누산을 수행한다.
- 마지막 bias 처리의 반올림도 유지한다.

여기서 정확성의 목표는 수학적 실수에 더 가까운 값을 만드는 것이 아니라 **기존 GeulPU 계약과 같은 FP32 비트를 출력하는 것**이다. 활성값 양자화 정밀도를 높이거나 블록 누산 순서를 바꾸는 일은 별도 계약 변경이다.

### 2.2 서로 다른 세 가지 측정 범위

| 실험 | 실행 장치 | 시간에 포함 | 시간에서 제외 |
|---|---|---|---|
| 과거 GL 대 C CPU 행렬 시험 | CPU | 정수 부분합 처리 함수 | 패킹, 파일 I/O, FP32 후처리, 검증 |
| 최종 NPU 타일 호출 시험 | NPU + 호스트 | 입력 복사·동기화, NPU 실행, 결과 수신 | 컴파일·예열, 독립 기준값 검증 |
| 최종 NPU 선형층 시험 | NPU + CPU | 패킹, 장치 호출·전송, FP32 후처리, bias | 예열·계획 생성 준비, 독립 기준값 검증 |

Qwen 모델 표는 추적기가 기록한 **각 선형층 호출 시간의 합**이다. 기준 CPU 계산을 별도로 실행하는 검증 프로그램이므로 프로그램 전체 wall-clock 시간과 같지 않다. KV 캐시 기반 자기회귀 생성 TPS도 측정하지 않았다.

**CPU 행렬 표의 2.73 ms와 NPU 선형층 표의 29.92 ms를 직접 비교해 CPU/NPU 우열을 계산하면 안 된다.** 포함하는 작업이 다르다.

## 3. CPU GL 시험에서 배운 점

### 3.1 먼저 시도한 소스 수준 최적화

범용 CPU GL 코드에서는 다음 변경을 시험했다.

1. 작업 모드 분기를 반복문 밖으로 이동.
2. 반복문을 4개 원소 단위로 펼침.
3. 합산을 4개 독립 누산기로 분리해 의존성 완화.
4. 타일 전치의 순회 순서 변경.
5. 단순 지역 변수의 `s += x`를 `s = s + x`로 표현.

마지막 변경은 당시 GL 생성기의 주소 접근과 지역 변수 레지스터 승격 방식에 대응한 것이다. `a[f()] += g()`처럼 부작용이 있는 일반 좌변을 무조건 치환한 것은 아니다. 그렇게 하면 `f()`의 평가 횟수가 바뀔 수 있다.

1,048,576개 INT64 원소의 warm CPU 배열 시험 결과:

| 작업 | 원본 GL | 수정 GL | 수정 C `/O2` | GL 자체 개선 |
|---|---:|---:|---:|---:|
| 복사 | 1.607 ms | 0.481 ms | 0.237 ms | 3.34배 |
| 산술 변환 | 1.439 ms | 0.673 ms | 0.457 ms | 2.14배 |
| 타일 전치 | 3.117 ms | 2.923 ms | 1.165 ms | 1.07배 |
| 합산 | 0.999 ms | 0.329 ms | 0.138 ms | 3.04배 |

4라운드, 구현·작업당 28표본 중앙값이다. 512회 실행이 정확성 검사를 통과했고, GL 참조/자체호스팅 컴파일러의 출력 바이트 일치도 확인했다. 각 최적화의 효과를 독립적으로 분리한 실험은 아니다. C 전치는 원본 0.748 ms에서 수정 후 1.165 ms로 오히려 느려졌다.

**배운 점:** 소스 최적화는 유효하지만, 같은 변경이 모든 언어·작업에 유리하지 않다. 현재 CPU GL 생성기의 스칼라 연산·스택 접근과 C의 SIMD 생성 차이는 남아 있었다.

### 3.2 복잡한 CPU 행렬 시험

단순 배열 연산의 한계를 확인하기 위해 실제 정수 계약에 맞춘 INT8 dot32 행렬 부분합을 비교했다. 두 언어 모두 4개 누산기, 같은 순회 및 가중치 배치를 사용했다. GL 산술을 외부 C 함수에 위임하지 않았다.

| M,N,K | GL CPU | C `/O2` | C `/O2 /arch:AVX2` |
|---|---:|---:|---:|
| 1,1024,1024 | 2.730 ms | 0.913 ms | 0.830 ms |
| 32,256,1024 | 21.674 ms | 7.130 ms | 6.782 ms |
| 16,1024,3072 | 129.164 ms | 44.643 ms | 45.185 ms |

3라운드, 조건·구현당 12표본 중앙값이다. 총 135회 커널 실행의 정수 부분합이 일치했고, 공통 참조 후처리로 복원한 FP32 출력도 일치했다. 가장 큰 조건은 약 1억 개 정수 곱과 누산을 수행했다.

이때 C `/O2`가 GL보다 약 2.89~3.04배 빨랐다. 그러나 이는 **기존 x86 CPU 백엔드**에 대한 결과였다. 당시 NPU GL 백엔드가 없다는 사실까지 합쳐 GL을 제어 계층 중심으로 권고했지만, 이후 제한된 AIE 백엔드를 구현했으므로 현재 권고는 GL 커널 소스까지 포함하도록 확장됐다. 과거 CPU 측정값 자체가 뒤집힌 것은 아니다.

## 4. NPU에 맞게 바꾼 구조

### 4.1 CPU 스칼라 코드 생성을 우회한 별도 장치 백엔드

GeulPU의 PTX 백엔드는 이미 GL의 전용 연산을 GPU MMA, DP4A, 명시적 FMA 등으로 내리는 구조를 갖고 있었다. 같은 관점에서 NPU도 범용 GL 스칼라 반복문을 그대로 실행시키기보다 장치 연산을 명시하는 경로가 필요하다고 판단했다.

실제 구현 경로:

```text
GL 원본 tile.gl
  ↓ 공식 GL lexer / parser / sema
타입과 조사별 인자 대응이 확인된 AST
  ↓ 제한된 정적 정수 커널 검사
범위·오버플로·벡터 오프셋 정렬 검사
  ↓ 입력 적재 위치 조정 / 중복 적재 재사용
AIE C++ 생성 코드
  ↓ Peano -O2
AIE2p 오브젝트
  ↓ 공통 FIFO / XRT 런타임
실제 NPU 실행
  ↓
CPU의 기존 순서 고정 FP32 후처리
```

현재 백엔드는 **typed AST에서 직접 AIE C++를 생성**한다. 별도의 범용 계약 IR, 일반 목적 GL→NPU 컴파일러를 완성한 것은 아니다. 기존 GL 앞단의 원본을 수정하지 않고 별도 실험 백엔드를 연결했다.

중간 산출물이 C++라고 해서 NPU 실행 중 C++ 인터프리터나 추가 함수 호출 계층이 생기는 것은 아니다. 최종 장치 기계어로 컴파일된다. Python은 현재 호스트 런타임과 시험을 담당하며 NPU 정수 계산의 대체 경로가 아니다.

### 4.2 실제 GL 커널 소스

다음은 [tile.gl](gl_aie/tile.gl)의 핵심이며 실제 파싱·타입 검사·변환에 사용한 소스다.

```text
외부 "dot32" [작은정수 참조 a에서 중간정수 ai를 작은정수 참조 b로 중간정수 bi 점곱32]는 -> 중간정수.

[작은정수 참조 a에서 작은정수 참조 b로 중간정수 참조 dst에 결합타일]는 {
    반복 (중간정수 r = 0: r < 4: r = r + 1) {
        중간정수 ai = r * 32.
        중간정수 ah = (r + 4) * 32.
        반복 (중간정수 n = 0: n < 32: n = n + 1) {
            중간정수 bi = n * 32.
            중간정수 s0 = 점곱32(a 에서, ai 를, b 로, bi).
            중간정수 s1 = 점곱32(a 에서, ah 를, b 로, bi).
            dst[r * 32 + n] = s0 + 256 * s1.
        }
    }
}
```

`점곱32`는 이번 백엔드가 지원하는 정확한 signed INT8×INT8→INT32 내장이다. 기존 GL 표준 라이브러리의 일반 NPU API가 새로 생긴 것으로 해석하지 않는다. `외부` 선언은 타입·역할 인터페이스를 제공하며 이 백엔드에서는 장치 벡터 코드로 내려간다.

GL 소스의 `256`을 바꾸면 생성 코드의 식도 바뀐다. 조사로 표시한 인자 순서를 바꾸어도 의미 분석이 같은 인자 순서로 정규화한다. 이 두 가지를 시험해 고정된 C++ 본문을 반환하는 단순 래퍼가 아님을 확인했다.

### 4.3 최적화 A: 두 자리 부분합을 NPU에서 결합

기존 경로는 블록마다 두 INT32 부분합을 CPU에 반환하고 각각 실수로 복원했다.

```text
v1 = FP32(S1) × 2^(E - 5)
v0 = FP32(S0) × 2^(E - 13)
u  = RN32(v1 + v0)
```

바꾼 경로:

```text
NPU: T = S0 + 256 × S1        # 정확한 INT32 결합
CPU: u = FP32_RN_even(T) × 2^(E - 13)
```

현재 두 자리 계약에서는 다음 이유로 이 변환이 가능하다.

- `n = 256·D1 + D0`, `|n| ≤ 2^14`, `|q| ≤ 128`, 블록 길이는 32다.
- 따라서 실제 계약 입력의 `T = Σ(n·q)`는 `|T| ≤ 2^26`으로 INT32에 들어간다. 구현에서는 중간 곱셈·덧셈도 범위를 검사한다.
- 각 자리 부분합은 FP32에 정확하게 표현할 수 있다. 기존 자리 합의 반올림을 정수 결합 뒤 FP32 변환으로 옮길 수 있다.
- 계약의 지수 `E∈[-98,100]`에서 해당 복원 범위에 오버플로·비정규수 문제가 없고, 이진 지수 스케일링으로 같은 반올림 결과를 보존한다.
- 이후 가중치 스케일 적용, 블록 간 FMA 순서, bias의 반올림은 바꾸지 않는다.

음수 signed 정수의 왼쪽 시프트에 의존하지 않고 `256*S1` 곱셈으로 표현한다. 이 규칙을 일반 부동소수점 합의 재결합에 적용해서는 안 된다.

검증은 199개 지수와 경계·무작위 부분합 1,646,327조합에서 비트 차이 0이었다. 이 검증과 수치 범위 논거를 바탕으로 장치 구현을 진행했다.

### 4.4 최적화 B: 타일 배치와 출력량 축소

| 버퍼 | 형상 | 의미 |
|---|---|---|
| a | INT8 `[8,32]` | 앞 4행은 낮은 자리, 뒤 4행은 높은 자리 |
| b | INT8 `[32,32]` | 출력 32채널의 깊이32 가중치 |
| dst | INT32 `[4,32]` | 두 자리를 결합한 출력 4행×32채널 |

한 프레임의 입력 버퍼는 1,280바이트, 출력 버퍼는 512바이트다. 두 부분합을 각각 반환하던 출력 1,024바이트에서 절반으로 줄었다.

2,048프레임 묶음에서는 입력 2.5 MiB, 출력 1 MiB다. 이전 출력 2 MiB에 비해 출력 버퍼가 50% 줄었지만, 입력까지 포함한 버퍼 합은 4.5→3.5 MiB이므로 약 22.2% 감소다. **이 수치는 할당·동기화 대상 버퍼 크기이며, 하드웨어 버스 카운터로 측정한 실제 트래픽이 아니다.** 전체 실행시간이 두 배 빨라진다는 뜻도 아니다.

### 4.5 최적화 C: 불변 벡터 적재와 중복 적재 제거

동일 입력 행의 낮은/높은 자리 벡터는 출력 열 32개를 계산하는 동안 바뀌지 않는다. 따라서 그 적재를 열 반복문 밖으로 이동했다. 같은 열의 가중치 벡터는 두 자리 곱에서 재사용한다.

생성된 코드의 형태:

```cpp
for (int32_t r = 0; r < 4; ++r) {
    auto lo = aie::load_v<32>(a + r * 32);
    auto hi = aie::load_v<32>(a + (r + 4) * 32);
    for (int32_t n = 0; n < 32; ++n) {
        auto w = aie::load_v<32>(b + n * 32);
        int32_t s0 = dot_loaded(lo, w);
        int32_t s1 = dot_loaded(hi, w);
        dst[r * 32 + n] = s0 + 256 * s1;
    }
}
```

이는 생성 코드의 설명용 표기다. 실제 산출물은 [generated.cc](gl_aie/generated.cc)에 있다. `dot_loaded`는 AIE 벡터 곱과 INT32 변환·합산으로 인라인된다.

백엔드는 적재 위치를 옮길 때 해당 오프셋 변수가 바깥 범위에서 이미 정의됐는지 확인한다. 입력 버퍼는 읽기 전용이고 출력은 별도 버퍼라는 실행 ABI가 전제다. 임의 포인터 별칭이 있는 일반 GL 프로그램에 적용하는 보편적인 최적화는 아니다.

적재 이동 전후는 별도 세션에서 측정했으므로 이 변경만의 독립적인 속도 향상을 확정하지 않는다. 최종 네 비교군을 같은 세션에서 측정한 결과를 판단 기준으로 사용한다.

### 4.6 최적화 D: 기존 실행 계획 재사용

호스트에는 이미 검증한 `PlannedLinear`를 공통으로 사용한다.

- 형상·가중치 내용 해시를 키로 하는 불변 가중치 패킹 계획.
- 768 MiB 상한 LRU 캐시. 가중치의 제자리 변경 시 이전 계획을 재사용하지 않음.
- 최대 2,048프레임의 묶음 제출과 채널 청크 처리.
- 타일 결과 재배치의 배열 연산화.
- 입력 쓰기 후 명시적 H2D 동기화.
- 블록 오름차순 FP32 FMA 후처리.

이 캐시는 **호스트 패킹 캐시**이며 NPU에 가중치를 계속 상주시킨 구현은 아니다. 모든 비교군에 공통으로 적용했으므로 최종 GL/C 차이를 이 캐시의 효과로 설명하지 않는다.

## 5. 단계별 실측 결과

### 5.1 언어 비교 전, 두 자리 결합 자체의 효과

먼저 AIE C++ 실험 커널로 결합 규칙을 검증했다. 예열 후 두 경로를 번갈아 각 6회 측정한 중앙값이다.

| M,N,K | 기존 planned | 결합 경로 | 기존 / 결합 |
|---|---:|---:|---:|
| 1,1024,1024 | 24.94 ms | 20.33 ms | 1.23배 |
| 32,256,1024 | 150.13 ms | 127.52 ms | 1.18배 |
| 16,1024,3072 | 298.14 ms | 254.15 ms | 1.17배 |

세 조건의 호출 수는 양쪽 모두 각각 1/8/8이었다. 출력량과 후처리를 줄여 얻은 개선이며, 이 단계에는 GL 백엔드가 아직 없었다.

이전 세션의 결합 경로 20.33 ms와 후속 GL 세션의 29.92 ms를 비교해 GL의 오버헤드로 해석하지 않는다. 세션·장치 코드·실행 환경이 다르며, 언어 비교의 통제군은 후속 세션의 수작업 AIE C++다.

### 5.2 최종 언어 비교군

| 이름 | 작성 방식 | 장치 연산 |
|---|---|---|
| GL | GL 소스 + 새 실험 백엔드 | 명시적 AIE 벡터 내장, 적재 재사용 |
| 일반 C | C11 루프, `-O2` | 컴파일러가 최적화하는 정수 dot32 |
| 최적화 C | C11, 4방향 펼치기·독립 누산기, `-O2` | C 버전 중 실측상 더 빠른 후보 |
| AIE C++ | 같은 벡터 내장을 수작업으로 작성 | GL 생성 코드와 동등한 장치 최적화 대조군 |

최종 타일·선형층 비교는 각 경로 12표본, 실행 순서를 순환 및 역순으로 교차한 warm 측정이다. 컴파일과 첫 호출 시간은 별도 기록했다. 일반 C와 최적화 C도 CPU가 아니라 **동일 NPU에서 실행**했다.

### 5.3 NPU 타일 묶음 호출

| 프레임 수 | GL | 일반 C | 최적화 C | AIE C++ | 최적화 C / GL |
|---|---:|---:|---:|---:|---:|
| 128 | 2.873 ms | 10.304 ms | 9.686 ms | 2.937 ms | 3.37배 |
| 2,048 | 19.393 ms | 138.703 ms | 127.127 ms | 19.098 ms | 6.56배 |

2,048프레임에서 일반 C 대비 GL의 속도비는 7.15배다. 작은 묶음에서는 공통 호스트 호출·동기화 비용의 상대적인 영향이 커지므로 향상 폭이 작다. 순수 장치 계산 시간이나 TOPS를 측정한 결과는 아니다.

### 5.4 FP32 후처리를 포함한 선형층

| M,N,K | GL | 일반 C | 최적화 C | AIE C++ | 최적화 C / GL |
|---|---:|---:|---:|---:|---:|
| 1,1024,1024 | 29.92 ms | 149.74 ms | 139.61 ms | 31.65 ms | 4.67배 |
| 32,256,1024 | 183.34 ms | 1,145.65 ms | 1,060.19 ms | 179.16 ms | 5.78배 |
| 16,1024,3072 | 400.88 ms | 1,377.73 ms | 1,324.94 ms | 439.61 ms | 3.31배 |

세 입력은 고정 시드 합성 fixture이며 모델 파일에서 추출한 가중치가 아니다. Qwen 계열 선형층에서 나타나는 폭을 포함한다. 실제 모델 검증은 별도로 수행했다.

가장 큰 조건의 GL 표본 범위는 261.53~616.51 ms, AIE C++는 273.97~512.84 ms였다. 변동이 크므로 두 경로의 중앙값 차이를 GL 고유의 우위로 해석하지 않는다. 신뢰구간을 산출하지 않았고 코어 고정·클록·전력·외부 부하를 엄격히 통제한 실험도 아니다.

### 5.5 기계어 비교

| 경로 | 커널 기계어 구간 크기 |
|---|---:|
| GL | 320바이트 |
| AIE C++ | 320바이트 |
| 일반 C | 1,520바이트 |
| 최적화 C | 1,504바이트 |

GL과 AIE C++의 기계어 구간 SHA256은 같다.

```text
94761b62c6744a76f13a5f73a995098850c65a8f149ab5bd3ab14ec407562847
```

확인한 재배치 레코드도 동일했다. 다만 소스·심볼 메타데이터 등을 포함한 ELF 오브젝트 전체의 해시는 다르다. 기계어 크기 비율을 속도비로 해석하지 않는다.

이 결과는 **GL로 최적화 커널을 작성해도 수작업 AIE C++ 수준의 장치 코드를 얻을 수 있다**는 근거다. C/C++ 자체의 성능 상한을 입증하거나 동일 기계어보다 GL이 더 빠르다는 근거는 아니다.

### 5.6 Qwen3 실제 모델 결과

고정 prefix `[1,2,3]`으로 각 경로를 두 번 실행했다. 모든 해당 정수 선형층을 실제 NPU 커널에 보내고, 나머지 모델 연산은 CPU에서 처리했다. 장치 오류 시 CPU로 조용히 우회하는 fallback은 없다.

| 경로 | 첫 실행의 선형층 시간 합 | 두 번째 실행의 선형층 시간 합 |

두 번째 실행의 관측 속도비는 4.52배다. 각 경로는 별도 프로세스에서 순차 실행했고 warm 모델 표본은 각 1개다. 따라서 안정적인 전체 애플리케이션 개선율·생성 TPS로 확장하지 않는다. AIE C++ 전체 모델 시간은 이번 비교에서 따로 측정하지 않았다.

네 번의 모델 실행에서 공통으로 나온 최종 로짓 SHA256:

## 6. 정확성과 실패 사례

### 6.1 최종 GL/C 비교의 검증 수

| 검증 | 범위 | 결과 |
|---|---|---|
| GL 변환기 | 8개 테스트 | 통과 |
| NPU 정수 타일 | 128회, INT64 oracle 대조 | 불일치 0 |
| 최종 FP32 선형층 | 204회 | 비트 불일치 0 |
| 모델 선형층 | GL/C 합계 564회 | 비트 불일치 0 |
| 모델 잔차 | 합계 112개 | 비트 불일치 0 |
| 모델 최종 로짓 | 합계 4개 | 기준·반복·경로 간 비트 일치 |

타일 시험은 INT8 극단값, 입력 버퍼 갱신, 128/2,048프레임, 꼬리 프레임을 포함한다. 선형층 시험은 행/열 꼬리, 지수 -98/0/100, 4,096열 경계와 세 큰 fixture를 포함한다.

GL 변환기 테스트는 소스 변경의 반영, 조사 기반 인자 정규화, 불변 적재 이동·재사용, 배열 범위·정렬·오버플로·서명·알 수 없는 내장 거부를 확인한다.

별도의 선행 결합 커널 시험에서는 입력 길이 1·3·16의 Qwen 모델을 각각 두 번 검증했다. **최종 GL/C 비교의 전체 모델 입력은 길이 3이다.** 선행 AIE 커널의 길이 1·16 결과를 최종 GL 경로의 직접 검증으로 합쳐 세지 않는다.

### 6.2 실패를 통해 확인한 제한

| 사례 | 관측 | 처리와 의미 |
|---|---|---|
| CPU 전치 최적화 | C에서는 오히려 느려짐 | 동일한 소스 변형을 보편적인 최적화로 채택하지 않음 |
| 초기 입력 동기화 | 유지한 NumPy 뷰를 수정해도 장치의 기존 데이터가 사용될 수 있었음 | 명시적 `_sync_to_device()` 후 재검증. SDK 내부 API 의존은 남음 |
| FP32 최댓값 | 기존 자리 계약부터 표현 범위 밖으로 거부 | 값 잘라내기로 통과시키지 않고 기준/새 경로의 거부 동작을 검사 |
| C 벡터 확장 | `<32 x i32>` 곱의 AIE legalization 실패 | 실패 기록 보존, 성능값 없음. 모든 C 벡터 구현이 불가능하다는 뜻은 아님 |
| 사전 컴파일 오브젝트 연결 | 최초 링크 시 오브젝트 경로를 찾지 못함 | 절대 오브젝트 경로 연결로 수정 후 실제 장치 시험 통과 |

테스트 통과는 시험한 입력·환경에 대한 관측이다. 모든 가능한 부동소수점 입력, 임의 버퍼 별칭, 모든 드라이버·컴파일러 버전에서의 보편적 보장을 뜻하지 않는다. 지원 계약의 범위와 변환의 정당화가 함께 필요하다.

## 7. 현재 병목과 아직 구현하지 않은 것

선행 결합 커널의 길이 16 모델 두 번째 실행에서 선형층 시간 합은 38.7231초였다.

| 구간 | 시간 | 의미 |
|---|---:|---|
| CPU FP32 후처리 | 24.8390초 | 전체 선형층 시간의 약 64% |
| 장치 및 전송 | 11.7649초 | 순수 NPU 계산과 전송을 아직 분리하지 않은 구간 |
| 패킹 | 1.7087초 | 나머지는 bias·호출 부대 비용 등 |

이 프로파일은 **선행 AIE 결합 경로의 측정**이며 최종 GL 길이 16 실행을 측정한 값이 아니다. 그래도 공통 후처리를 사용하는 현재 구조의 다음 병목을 찾는 근거가 된다.

현재 남아 있는 제약:

- FP32 지수 복원·순서 고정 FMA·bias는 CPU에 있다.
- 가중치는 호스트에서만 패킹 캐시하며 장치 상주 재사용은 구현하지 않았다.
- 계산과 전송의 비동기 중첩, 이중 버퍼 소유권 프로토콜이 없다.
- 단일 코어 벡터 dot32이며 다중 코어·전용 행렬 MAC 설계를 검증하지 않았다.
- 프레임 수와 타일 형상 지원이 제한적이고 작은 입력의 패딩 비용이 있다.
- GL 제품 엔진의 모델 로딩/계획/실행 API와 아직 통합하지 않았다.
- 정확성 검증과 성능 측정을 함께 하는 시험 런타임이지 완성된 추론 서비스가 아니다.

## 8. 미래 방향성과 실행 우선순위

다음 항목은 **구현 제안**이다. 아직 측정하지 않은 속도 향상을 약속하지 않는다.

### 8.1 우선순위 1 — 재현 가능한 기준선과 백엔드 계약 고정

현재 검증된 GL 커널, 생성 코드, 컴파일 옵션, 런타임 버전과 형상·정밀도 계약을 하나의 실행 계획으로 묶는다. AST 직접 변환을 늘리기 전에 작은 계약 IR로 연산 의미·입출력 범위·반올림 경계를 명시하는 방향을 권한다.

완료 조건:

- 여러 독립 세션에서 같은 입력·형상의 교차 측정, p50/p95와 표본 범위 기록.
- 모델/드라이버/컴파일러/전원·클록·외부 부하 조건 기록.
- cold 빌드, cold 실행, warm 실행을 구분.
- 지원하지 않는 형상·연산·정밀도는 컴파일/계획 생성 단계에서 명시적으로 거부.
- 입력 변경, 캐시 무효화, 버퍼 소유권, 컴파일러 업데이트 시 회귀 검사 자동화.

### 8.2 우선순위 2 — CPU FP32 후처리 비용 축소

가장 근거가 강한 다음 작업이다. 먼저 동일 의미를 보존하는 네이티브 CPU 후처리를 기준 후보로 만들고, 장치에서도 계약을 재현할 수 있는 연산부터 이동한다. 하드웨어 기본 FMA가 계약과 같다고 가정하지 않는다.

완료 조건:

- RN-even, FMA, 비정규수 처리, signed zero와 기존 계약의 입력 범위를 명시.
- 블록 누산 순서와 bias 반올림 경계 유지.
- 경계값·무작위 값·실제 모델의 uint32 비트 대조 통과.
- 후처리 단독 시간뿐 아니라 전송을 포함한 선형층 전체 시간 감소 확인.

실수 덧셈 재결합, 무조건적인 fast-math, 넓은 누산기로 중간 FP32 반올림을 생략하는 최적화는 계약을 확인하지 않고 적용하지 않는다.

### 8.3 우선순위 3 — 장치 내부 재사용과 전송 중첩

가중치·입력 타일의 장치 내 재사용을 늘리고, 버퍼 두 개와 명시적 완료 이벤트로 전송/계산 중첩을 시험한다. 모델 불변 핸들·버전을 사용해 매 호출 가중치 전체 해시 비용을 줄이는 방안도 포함한다.

완료 조건:

- 제출 중인 버퍼 변경, 완료 전 읽기, 잘못된 계획 재사용을 탐지.
- 연속 호출·다른 입력·꼬리 타일·캐시 축출 시험에서 비트 일치.
- 실제 전송량 또는 장치 계측을 도입해 계산/전송/대기 비용을 분리.
- 메모리 사용량 증가와 p95 지연까지 포함해 이득 확인.

### 8.4 우선순위 4 — 형상 특수화, 다중 코어, 행렬 연산 매핑

decode형 작은 M과 prefill형 큰 M을 나누어 타일·프레임 수를 선택한다. 현재 4행 결합 배치를 모든 크기에 고정하지 않는다. 1자리 계약도 별도 경로를 고려한다. 1자리에서 높은 자리를 0으로 채우는 구현은 정확성은 유지해도 호출 수가 늘 수 있다.

정수 부분합 계산은 독립 출력 타일별 병렬화를 우선한다. NPU 행렬 연산 명령이나 다중 코어를 적용하더라도 깊이32 블록별 스케일과 최종 블록 누산 순서를 합쳐 없애면 안 된다.

완료 조건:

- 여러 M/N/K, Q8/Q4 범위, 꼬리 크기, 1/2자리 모드의 별도 시험.
- 단일 코어 대조군 대비 총 지연·메모리·전송량 개선.
- 장치 누산 폭과 오버플로 상한 확인, 최종 비트 일치.
- 작은 입력에서 CPU 경로가 유리하다면 명시적인 선택 정책을 별도 측정해 결정. 오류를 숨기는 fallback과 구분.

### 8.5 우선순위 5 — GL 엔진 통합과 실제 생성 벤치마크

GL 엔진에 원시 장치 주소나 타일별 호출을 노출하기보다 다음 수명 주기를 제공한다.

```text
모델 준비 → 계약/형상에 맞는 실행 계획 생성
          → 입력 제출 → 완료/오류 확인 → 자원 해제
```

권하는 역할 분담:

| 계층 | 방향 |
|---|---|
| 모델 구조·계약·커널 소스 | GL |
| 계약 검증·정적 배치·연산 변환 | GL용 장치 백엔드 및 향후 계약 IR |
| 최종 장치 명령 생성 | AIE/LLVM 도구 체인 |
| 장치 호출·메모리 수명 관리 | 안정된 네이티브 런타임 ABI |
| 참조·회귀·차이 추적 | Python 및 독립 정수/FP32 oracle |

완료 조건은 고정 prefix를 넘어 실제 토크나이저 입력, KV 캐시, prefill/단일 토큰 decode, 여러 출력 길이에서 TTFT·토큰당 지연·TPS·p95·메모리를 측정하는 것이다. 정확성 기준에 맞춘 CPU/GPU 경로와 비교해야 실용적 채택 여부를 판단할 수 있다. CUDA 단독 GeulPU 대비 우위는 현재 자료만으로 주장하지 않는다.

## 9. 결과를 해석할 때 지켜야 할 경계

1. **관측:** 이번 GL NPU 경로는 시험한 일반 C/4누산기 C보다 빠르다.
2. **관측:** 같은 내장을 사용하는 AIE C++와 GL의 커널 기계어 구간은 같다.
3. **해석:** 이득은 장치에 맞는 연산 표현·배치·코드 생성에서 나온다. GL이라는 이름만으로 생기는 이득은 아니다.
4. **관측:** 현재 CPU GL 행렬 백엔드는 이전 시험에서 C보다 느렸다. NPU 결과와 모순되지 않는다.
5. **제한:** 현재 비교는 NPU 커널 생성 경로의 비교이며 호스트 전체를 GL/C로 다시 작성한 비교가 아니다.
6. **제한:** 같은 비트 재현성과 실수 정답에 대한 수학적 정확도는 다르다. 이번에는 전자를 보존했다.
7. **제한:** 동시 세션·모든 입력·모든 하드웨어에서의 보장이나 제품 성능 상한은 측정하지 않았다.

### 10.2 재현 명령

저장소 루트에서 실행한다. 기존 MLIR-AIE/XRT 환경과 VS 개발 도구, 사용자 NPU JIT 캐시 쓰기 권한이 필요하다.

```powershell
& ./재기/npu/gl_aie/run.ps1 -Mode test
& ./재기/npu/gl_aie/run.ps1 -Mode build
& ./재기/npu/gl_aie/run.ps1 -Mode bench
& ./재기/npu/gl_aie/run.ps1 -Mode model -Backend gl
& ./재기/npu/gl_aie/run.ps1 -Mode model -Backend c_unrolled

# NumPy가 설치된 Python으로 실행
python ./재기/npu/gl_aie/summarize.py
```

실행기는 현재 결과 파일을 갱신하므로 새 실험을 보존하려면 기존 결과 폴더를 먼저 별도 이름으로 복사한다. 새 비교에서는 소스·오브젝트 해시와 모델 해시를 함께 기록하고, 다른 세션의 수치를 같은 조건의 표본으로 섞지 않는다.
