# GeulNPU 시험·벤치마크 종합 기록

작성일: 2026-11-03. 기존 보고서와 저장된 결과를 통합한 작업 공유용 문서다. **이 문서를 만들기 위해 벤치마크를 재실행하지 않았다.** 초기 실험부터 최종 통합 경로까지 조합·조건·지연시간·정확성 결과·실패 사례를 파트별로 수록한다.

## 먼저 읽을 현재 결론

- 현재 완성된 것은 **NPU 정수 내적＋CPU의 계약 후처리·모델 연산**을 사용하는 연구용 통합 경로다. Geul 계약 전체를 NPU 내부에서 실행하는 백엔드는 아직 미완성이다.
- 비압축, 장치 작업자 4개, CPU 후처리 중첩, 가중치 타일 재사용, 제출 용량 자동 선택, 용량별 실행 핸들 재사용, 연속 입력 준비, 출력 중간 복사 제거가 통합 후보다. 전역 기본 실행 경로를 제품 NPU 백엔드로 교체한 것은 아니다.
- INT24 압축은 무손실 정확성을 확인했지만 같은 세션 진단에서 256행 FFN이 비압축 550ms 대 압축 712ms로 느려 채택하지 않았다.
- 최종 동일 Q8 계약 비교에서 16토큰 요청은 CPU 12.28초 대 분담 14.06초, 64토큰은 36.56초 대 36.27초, 256토큰은 145.75초 대 145.73초였다. **각 요청은 출력 총 4토큰**이며 조건별 2회다. 전체 지연·순차 처리량의 뚜렷한 우위를 확보하지 못했다.
- 256토큰에서 분담의 첫 출력은 약 5% 짧았지만 총 CPU 사용 시간은 약 16% 더 컸다. 메모리는 약 0.6GiB 더 사용했다. 전력 도구 실패로 에너지 효율은 미측정이다.
- 별도 FastFlowLM은 Qwen 0.6B Q4 계열에서 64토큰 생성에 1.65~1.76초, 런타임 디코드 61.5~65.7토큰/초를 기록했다. **다른 양자화·가중치·입력·계약이므로 Q8 엄격 계약과 직접적인 가속 배수로 비교하지 않는다.**
- 다음 핵심 개발은 기존 Geul 계약의 변환·반올림·FMA·규칙 R을 NPU에서 구현하고, CPU로 부분합을 반환하지 않는 완결된 NPU 선형층을 만드는 일이다. 기존 FMA 링크 실패·벡터 MAC 불일치는 시험한 구현의 실패이며 하드웨어에서 계약 구현이 불가능하다는 증명이 아니다.

**비교 규칙:** 같은 절 안의 교대·동일 세션 비교와, 다른 날짜·세션의 이전 기록을 구분한다. 각 단계의 최고 기록을 이어 붙여 누적 가속률을 만들지 않는다. 중첩된 CPU 후처리 시간과 NPU 시간을 더해 전체 시간으로 해석하지 않는다. GPU 피크 대비 50~70%, NPU 50 TOPS, 가정한 대역폭으로 계산한 하한 등은 이번 실측으로 확인한 활용률이 아니므로 벤치마크 표에 섞지 않는다.

**원문 보존 방식:** 아래 세부 절은 해당 단계의 기존 보고서를 수록한다. 절별 결론은 당시 시점의 판단이므로 현재 채택 상태는 위 요약 및 마지막 파트를 우선한다. 예를 들어 초기 문서의 “GL NPU 백엔드 미구현”은 이후 제한된 정수 커널 변환기 구현으로 일부 진전됐으며, 현재도 일반 GL 전체와 계약 전체의 NPU 백엔드는 아니다. 원문 코드 블록의 상대 경로·재현 명령은 해당 원본 보고서의 실행 위치를 따른다.

## 파트 1. 초기 실행 기준과 정확한 NPU 선형층

### 1.1. 외부 NPU 런타임 초기 기준

원본 보고서: [2026-10-27.md](results/2026-10-27.md). 아래 조건·결론은 해당 단계의 기록이다.

#### 결론

이 PC에서 NPU 추론의 첫 실측 기준을 확보했다. Qwen3-0.6B를 FastFlowLM 1.0.10으로 실행했으며,
엄격 greedy 요청 조건에서 15/15 요청이 성공했다. 생성 속도 중앙값은 짧은 입력에서 75.67 tok/s,
약 12K 입력에서는 22.67 tok/s였다. 큰 모델이나 GeulPU 자체 NPU 엔진의 성능을 예측하는 숫자는 아니다.

동일 요청 반복에서 중간 입력은 출력 2종, 긴 입력은 3종이 관측됐다. 샘플링 필드를 모두 고정하고
새 서버에서 재측정해도 현상이 남았다. 원인은 이번 실험으로 특정하지 못했으며, NPU 하드웨어 자체의
결정성 문제라고 단정할 수 없다. 현재 구성은 GeulPU의 비트 동일성 계약을 통과했다고 볼 수 없다.

#### 환경과 방법

- HP OmniBook X Flip 14-fk0xxx, AMD Ryzen AI 7 350, Radeon 860M, RAM 32GB급.
- Windows, NPU 드라이버 32.0.203.329. 런타임 validate: amd_device_found=true, npu_driver_ok=true, ready=true, aie2p.
- 공식 Windows FastFlowLM v1.0.10 휴대용 배포본. 시스템 설치/드라이버 교체 없이 작업 폴더에서 실행.
- Qwen3-0.6B-NPU2 (`qwen3:0.6b`), 카탈로그 Q4_1, 실제 가중치 `model.q4nx` 약 684MB.
- NPU performance, Windows 균형 조정 전원 계획. 최초 수집 시 BatteryStatus=2, 잔량 91%.
  배터리 상태 코드만으로 전체 실험 동안의 AC/충전 상태를 확정하지 않는다.
- 문맥 용량 32768, 동시 요청 1, 최대 생성 128토큰. 모든 측정 응답은 실제 128토큰, finish_reason=length.
- 한국어 합성 자료 세 종류. 각 종류 워밍업 1회 후 5회 측정. 실행 순서는 라운드별 순환.
- 엄격 요청: temperature=0, top_k=1, top_p=1, presence/frequency penalty=0,
  repetition_penalty=1, think=false. seed=7도 보냈지만 FLM의 시드 보장을 전제로 하지 않는다.
- 모든 측정에서 서버가 보고한 cached_tokens=0. 외부에서 내부 캐시를 강제 초기화했다는 의미는 아니다.
- 원시 API 이벤트와 시각, 요청, 모델/실행 파일 해시를 저장했다. NPU 이용률 카운터·전체 전력은 측정하지 않았다.

prefill/decode는 **FLM이 보고한 내부 시간 기준**이다. 첫 출력은 HTTP 클라이언트가 최초의
content/reasoning 델타를 받는 시간이며 토크나이저의 제어 토큰 생성 시각과 다를 수 있다.
5회 표본으로 안정적인 운영 p95를 추정하지 않는다. 원시 요약의 p95는 이 표본에서는 최댓값이다.

긴 입력에서 prefill 처리량과 decode 속도가 함께 낮아지는 관측은 문맥 길이를 독립 축으로
관리해야 한다는 근거다. 대역폭·KV 읽기·커널 분할 중 무엇이 지배적인지는 프로파일링 전에는 특정할 수 없다.

#### 반복 출력 확인

종류별 5개 요청의 JSON SHA-256은 각각 동일했다. request ID, timestamp, 무작위 system_fingerprint는
출력 비교에서 제외했고, 실제 content/reasoning/finish_reason만 비교했다.

- 짧은 입력: 동일 텍스트 5회.
- 중간 입력: 서로 다른 텍스트 2종.
- 긴 입력: 서로 다른 텍스트 3종.

이 결과는 **텍스트 반복성 검사**다. raw token IDs와 logit hash는 받지 않았으므로 비트 일치 여부는 null이다.
동일 텍스트가 나온 짧은 입력도 CPU 참조와 같은 로짓이라는 뜻이 아니다.
샘플링 적용 방식, 런타임 상태, 계산 경로 등 원인을 나누는 후속 실험이 필요하다.

이전 탐색 실행(temperature=0/seed=7만 지정)도 종류별 1/2/3개의 출력이 관측됐다.
탐색 실행은 엄격 조건 기준표와 합산하지 않았다. 원시 결과는 `빌드/npu/results/performance/`에 남겼다.

#### 메모리와 측정하지 않은 항목

탐색 실행 도중 시작한 89개 프로세스 표본에서 working set 최대 5,207,891,968바이트(약 4.85GiB),
private bytes 최대 5,198,233,600바이트가 관측됐다. 이는 32K 문맥으로 띄운 FLM 프로세스 전체다.
가중치 파일 크기, NPU 로컬 메모리, 모든 요청 구간을 포함한 최대값으로 해석하면 안 된다.
엄격 조건 재실행의 별도 메모리 기준은 아직 없다.

전력/J-per-token, 온도, 장시간 열 포화, 콜드 로드 반복, 4B 이상의 모델, 동시 요청,
GeulPU Vulkan 대비 성능, 한국어·코딩 정확도는 미측정이다. 128토큰으로 잘린 합성 답변으로 품질 점수를 만들지 않았다.

#### 이 기준을 GeulPU에 적용하는 방법

##### 우선: 외부 런타임 어댑터와 관측 체계

GeulPU 관리자와 웹 UI, 요청 기록은 재사용할 가치가 높다. NPU 실행은 별도 FLM 프로세스에 맡기고
`앱/일.gl`의 실행기 선택과 `앱/웹.gl`의 /v1 전달 지점에 런타임 어댑터를 추가하는 방식이 첫 단계다.
현재 모듈생성·--ptx 인자·GGUF 메타데이터 경로를 FLM에 그대로 적용하지 않는다.

상위 인터페이스는 `load / unload / health / capabilities / generate / cancel`을 중심으로 잡는다.
모델 구조(qwen3 등), 실행 런타임(geulpu/flm), 장치(cuda/vulkan/npu), 수치 계약을 서로 다른 필드로 둔다.
현재 구조/등록.gl은 모델 구조 등록이므로 NPU 장치를 여기에 추가하는 것은 적절하지 않다.

기록 헤더에는 runtime version, model/tokenizer/kernel hashes, driver, device, context, sampling options,
cache policy를 넣는다. 관측하지 못한 raw tokens/logits는 null로 남긴다. `앱/디버거.gl`의
geulpu 전용 요청 자동 삽입과 `도구/debugger.py`의 재생 판정은 capabilities에 따라 분기해야 한다.
기존 CPU/GPU와 동일한 비트를 보장하는 exact 표시는 외부 FLM 경로에 적용하지 않는다.

##### 이후: NPU 전용 정밀도 계약 실험

계약/정수계약.py의 CPU 참조를 기준으로 Q8_0 선형층 하나부터 IRON/MLIR-AIE 커널로 옮긴다.
정수 부분합, 스케일, 누산 순서, 반올림까지 단계별로 비교한다. 이 검증이 통과해야
엔진/서버몸.gl 수준의 GeulPU 자체 NPU 실행기와 커널 생성 백엔드로 확장할 근거가 생긴다.

기존 NPU 런타임을 연결하는 작업과 GeulPU 정밀도 계약을 NPU에서 구현하는 작업은 별도 단계다.
첫 단계에서 얻는 것은 즉시 활용 가능한 실행과 기록이고, 두 번째 단계의 목표는 기존 계약의 보존이다.

#### 다음 변경을 판단할 기준

- 동일 환경·모델·요청으로 이 기준을 다시 실행한다. 런타임/가중치/계약이 달라지면 새 기준군을 만든다.
- 지연 변화율 = 새 중앙값 / 기준 중앙값, TPS 변화율 = 새 중앙값 / 기준 중앙값으로 각각 보고한다.
- 어댑터 전송은 고정 응답 서버로 무손실 검증하고, 실제 NPU 직접/경유의 지연도 별도 비교한다.
- 성능 합격과 재현성 합격을 분리한다. 현재 기준은 성능 측정 성공, 전체 조건 텍스트 재현성은 미충족이다.

### 1.2. 정확한 선형층 초기 검증

원본 보고서: [2026-10-28-exact.md](results/2026-10-28-exact.md). 아래 조건·결론은 해당 단계의 기록이다.

**검사한 범위에서 CPU 계약 참조와 다른 비트 0.** AMD Ryzen AI 7 350의 XDNA2에서 정수 내적을 실행하고 GeulPU CPU 계약으로 FP32 후처리를 수행했다. 모델 전체가 NPU에서 실행된 것은 아니다. 제품 앱의 백엔드도 아직 바꾸지 않았다.

모델: 공식 Qwen3-0.6B Q8_0 GGUF, 28개 블록, 출력 어휘 151936.
SHA256 `9465e63a22add5354d9bb4b99e90117043c7124007664907259bd16d043bb031`.

| 시험 | 범위 | 결과 |
|---|---|---|
| 정수 커널 | 16384개 dot32 × 3회, INT8 극값 포함 | 모든 INT32 일치 |
| 입력/배치 변경 | 작업 수 16384 → 17 → 1024 → 16384, 각각 3회 | 모두 일치 |
| 선형 경계값 | 활성값 지수 −98, −30, 0, 30, 100; 자리 1/2 모드 | 기본 `정수계약.행렬곱`과 비트 일치 |
| 모델 A | 고정 토큰 `[1,2,3]`, 2회 순전파 | 매회 141개 선형 호출 모두 일치 |
| 모델 B | `Hello world.` 토큰 `[9707,1879,13]`, 2회 순전파 | 매회 141개 선형 호출 모두 일치 |
| 모델 B 잔차 | 28개 블록 × 3행 × 1024차원 × 2회 | 172032개 FP32 모두 일치 |
| 최종 로짓 | 매회 3 × 151936개 FP32, 총 4회 | CPU 참조 및 입력별 반복 간 모두 일치 |

전체 모델 시험에서 선형 출력 5,952,000개를 비교했고 실제 NPU 호출은 27,872회였다. 최대 절대 차이는 0이다. 같은 입력의 선형 호출별 SHA256도 반복 간 동일했다. 서로 다른 두 입력의 해시는 달라 정상적으로 입력 변화가 반영된다.

| 입력 | 최종 로짓 SHA256 | 위치별 greedy 토큰 |
|---|---|---|
| A | `3942df4c34d105117006a99831baa9ea86ac511e8471530f692897861bdc2838` | `[1479,1096,16]` |
| B | `7086db93d0958747cb113f2a88c8586b9e408230cffd03746515e41bbbdf0e52` | `[1479,0,1096]` |

이는 고정 입력 각 위치의 다음 토큰 선택이며, 세 토큰을 연속 생성한 결과가 아니다. 긴 문맥·자기회귀 생성·지속 KV 캐시는 시험하지 않았다. 임의의 모든 입력, 재부팅, 다른 드라이버·다른 NPU의 재현성을 실측으로 보장한다는 뜻은 아니다.

#### 시간과 해석

계약 대조 하네스 안에서 측정한 **선형 호출 시간의 합계**다. 전체 순전파 시간이나 생성 TPS가 아니다. CPU 참조를 바로 앞에서 계산하는 검증 부하가 있으며 전력과 실행 순서를 통제한 성능 벤치마크도 아니다.

| 입력/실행 | CPU 참조 | NPU 정수 내적 + CPU 후처리 |
|---|---:|---:|
| A 첫 회 | 8.40초 | 52.19초 |
| A 둘째 회 | 7.85초 | 43.28초 |
| B 첫 회 | 7.84초 | 50.86초 |
| B 둘째 회 | 7.75초 | 42.79초 |

첫 회에는 JIT/장치 준비 비용도 포함된다. B 둘째 회는 약 5.52배 느리다. 단일 코어 dot32, 반복 데이터 전송, 많은 장치 호출, CPU 후처리 때문에 현재 구현에 속도 이점은 없다. 앞서 FLM으로 측정한 Q4NX와는 모델 형식과 실행 구조가 달라 직접 비교하지 않는다.

결과는 **GeulPU의 정수 부분합과 FP32 후처리 경계를 유지하면서 NPU를 사용하는 구현이 이 장치에서 동작한다**는 근거다. 다음 단계는 블록별 부분합을 보존한 타일 재사용·다중 코어 구현이며, 이 추적 시험을 정확도 회귀 기준으로 사용한다. 구조와 실행 방법은 [EXACT.md](EXACT.md)에 정리했다.

### 1.3. 초기 최적화

원본 보고서: [2026-10-28-optimized.md](results/2026-10-28-optimized.md). 아래 조건·결론은 해당 단계의 기록이다.

**동일 입력에서 출력 비트를 유지하면서 예열 후 선형 연산 합계를 42.75초에서 15.15초로 줄였다. 2.82배 속도, 시간 64.6% 감소다.** CPU 참조 약 8.06초보다는 여전히 약 1.88배 느리다.

#### 구현

- `tiled_kernel.py`: 8개 활성값 자리·행 × 32개 출력 채널을 타일 안에서 재사용한다. 타일마다 깊이 32의 정확한 INT32 부분합을 출력하고, 128개 타일을 한 번에 실행한다.
- `tiled_linear.py`: 입력 버퍼의 호스트 뷰를 재사용하여 불필요한 역방향 동기화를 없애고, 최대 1024개 출력 채널 단위로 CPU 후처리를 수행한다.
- 서로 다른 깊이 블록을 먼저 합치지 않으며, GeulPU의 블록 순서·자리 합·FP32 FMA·bias 규칙을 유지한다.
- 기존 dot 경로도 남겨 `-Backend dot` / `-Backend tiled`로 같은 측정 코드를 사용한다. 모델에 전달되는 정수 부분합은 실제 NPU 결과이며 CPU 대체 경로는 없다.

다중 코어, 네이티브 행렬 MAC, 호출 간 가중치 캐시, 비동기 실행 중첩은 아직 구현하지 않았다. 단일 NPU 코어와 CPU 후처리의 혼합 백엔드이며 제품 앱에는 연결하지 않았다.

#### 시험과 값 추적

AMD Ryzen AI 7 350 / XDNA2, 기존 드라이버·도구 환경을 사용했다. 공식 Qwen3-0.6B Q8_0 GGUF 및 SHA256은 [앞선 정확도 보고서](results/2026-10-28-exact.md)와 같다.

- 실제 NPU 타일 시험: 128, 1, 17, 128개 타일로 입력을 바꾸며 각각 2회 실행. INT8 최악값 −128 × −128 포함, 모든 INT32 부분합이 정수 참조와 같았다.
- 선형층 시험: `(M,N,K)` = `(1,9,32)`, `(3,35,96)`, `(5,67,160)`, `(2,1031,96)`. 자리 1/2 모드와 지수 −98/0/100 조합 24건. 행 그룹·출력 타일·1024채널 청크 경계를 포함하며 기본 `정수계약.행렬곱`과 비트 일치.
- 처음 사용한 정규분포 경계 입력 일부가 계약 범위를 넘어 CPU 참조에서 거부됐다. 커널 불일치는 아니었으며, 균등분포 `[−1,1)`로 범위를 바로잡아 전체 경계 시험을 다시 통과했다.
- 전체 모델: `Hello world.` 토큰 `[9707,1879,13]`, 28개 블록, 각 경로 2회 실행. 경로당 282개 선형 호출, 2,976,000개 출력이 CPU 참조와 비트 일치했다.
- 28개 블록의 잔차, 최종 로짓, 반복별 결과도 일치했다. 기존 경로와 최적화 경로의 **모든 대응 선형층 SHA256**이 같으며, 저장된 전체 로짓 파일도 uint32 표현으로 직접 비교해 일치했다.

최종 로짓 SHA256은 양쪽 모두 `7086db93d0958747cb113f2a88c8586b9e408230cffd03746515e41bbbdf0e52`, 위치별 greedy 토큰은 `[1479,0,1096]`이다. 최적화에 따른 관측된 값 변화는 0이다.

#### 측정

| 측정 | 기존 dot | 최적화 tiled |
|---|---:|---:|
| 첫 실행 선형 시간 합 | 51.25초 | 22.83초 |
| 둘째 실행 선형 시간 합 | 42.75초 | 15.15초 |
| 둘째 실행의 CPU 대조 시간 합 | 7.98초 | 8.06초 |
| NPU 호출 수, 모델 2회 합계 | 13936회 | 9094회 |

최적화 경로 둘째 실행의 세부 시간:

| 구간 | 시간 |
|---|---:|
| 자리 분해·패킹·결과 재배치 | 1.68초 |
| NPU 호출·전송·동기화 | 8.58초 |
| CPU FP32 후처리 | 4.71초 |

전체 합과 세부 합 사이 약 0.18초는 입력 검사·bias 처리 등 세부 타이머 밖의 비용이다. 기존 경로의 세부 구간은 계측하지 않았다. NPU 구간은 순수 장치 계산 시간이 아니며 Python/XRT 오버헤드와 전송이 포함된다.

이는 동일 하네스에서 최적화 경로를 먼저, 기존 경로를 다음에 순차 실행한 결과다. 각 첫 실행에는 장치 준비 비용이 포함된다. 표의 예열 후 수치는 각 경로의 둘째 실행 1회이며 통계적 신뢰구간을 구한 벤치마크는 아니다. 선형 연산 시간 합계이므로 전체 추론 TPS로 환산하면 안 된다. 긴 문맥·지속 KV 캐시·자기회귀 생성 성능과 전력은 측정하지 않았다.

### 1.4. 계획·가중치 준비 캐시

원본 보고서: [2026-10-28-planned.md](results/2026-10-28-planned.md). 아래 조건·결론은 해당 단계의 기록이다.

글 저장소 `0899bd753e1626e31c3094f5787d0f46ad4f7cc4`와 GeulPU의 PTX 뒷단·CUDA 외부 선언을 확인했다. 언어 문법/x86 코드 생성기를 변경하는 대신 **NPU 실험 백엔드의 준비·실행·완료 경계를 분리**했다. 글 IR→AIE 변환이나 글 엔진용 네이티브 DLL은 아직 구현하지 않았다. 설계 근거와 연결 계획은 [ARCHITECTURE.md](ARCHITECTURE.md)에 있다.

#### 구현한 변경

1. 불변 `WeightPlan`으로 타일 가중치를 준비하고 호스트 LRU 캐시에 재사용한다. 가중치 내용 해시와 형상으로 식별하므로 원본 제자리 수정에도 이전 패킹을 쓰지 않는다. 상한은 768 MiB, 모델의 실제 캐시 사용량은 595984384바이트(약 568.4 MiB)였다.
2. 작업당 타일 수를 128→2048로 늘리고 후처리 청크를 최대 4096 출력 채널로 확장했다. 입력 행 수에 따라 청크를 줄인다.
3. 타일별 Python 결과 복사 반복을 배열 배치 변환으로 바꿨다.
4. 호스트 입력 버퍼를 쓴 후 **명시적으로 H2D 동기화**한다. 원래 dot/tiled 경로에도 적용했다.

동기화 수정은 정확성 수정이다. 작업 크기 확장 시험에서 불일치를 발견했고, 설치된 런타임은 텐서가 이미 NPU에 있으면 `to('npu')`에서 동기화를 생략한다는 것을 확인했다. NumPy 뷰 쓰기 후 명시적 동기화를 추가한 뒤 실패했던 시험을 통과했다. 앞선 작은 입력 시험의 통과는 모든 버퍼 크기의 동기화 보장이 아니었다. 수정 전 실패 결과로 모델 성능을 보고하지 않았으며, 아래 기준 경로에도 같은 수정을 적용했다.

#### 정확도

- 계획 경로: 부분 타일·8행 초과·4096채널 경계, 자리 1/2, 지수 −98/0/100 조합 24건과 가중치 제자리 수정 4건을 실제 NPU에서 기본 정수 계약과 대조해 통과했다. 캐시 상한·LRU 퇴출도 통과했다.

#### 구현 범위

`fused_kernel.py`는 AIE C++로 두 INT8 dot32 부분합을 계산하고, NPU에서 `S0 + 256*S1`로 결합한다. 입력 8행을 낮은 자리 4행/높은 자리 4행으로 배치하여 INT32 결과 4행만 반환한다. `planned_linear.py`는 이 배치와 한 번의 FP32 지수 복원을 지원한다. 블록 간 FMA 순서와 bias 반올림은 유지한다. 기존 planned 경로와 기본 실행 옵션은 유지했다.

### 2.1. CPU 데이터 처리: GL/C/Python/NumPy

원본 보고서: [RESULTS.md](../language/RESULTS.md). 아래 조건·결론은 해당 단계의 기록이다.

2026-10-28, AMD Ryzen AI 7 350 Windows PC. 1048576개 int64 원소, 배열당 8 MiB. 작업별·구현별 예열 제외 28표본 중앙값이며 작을수록 빠르다. 원시 표본·라운드별 중앙값·소스 해시는 [results.json](../language/results.json)에 있다.

#### 정확성 및 측정 범위

4개 구현 × 4개 작업 × 4개 라운드 × 8회 = 512회 실행 결과를 검증했다. 복사·변환·전치는 매회 전체 원소를 예상값과 비교했고 합산은 정확한 정수 합과 비교했다. 모든 검사에서 오류 0이었다. 각 라운드 첫 실행을 제외한 448개 표본으로 집계했다.

입력 생성·할당·검증·프로세스 시작·출력·컴파일 비용은 타이머 밖이다. 네 구현의 실행 순서는 라운드마다 회전한다. GL은 글 1.4.0 Python 참조 컴파일러가 생성한 네이티브 x86-64 실행 파일이며, C는 MSVC 19.51.36257.0 `/O2 /W4`, Python은 CPython 3.13.18, NumPy는 2.5.4다.

CPU 고정·클록·전력·외부 부하는 통제하지 않았다. 변동이 상당하다. 예를 들어 GL 복사의 라운드별 중앙값은 1.31/1.71/2.64/1.35 ms, C 복사는 0.66/0.24/0.25/0.28 ms였다. 따라서 표의 배수를 정밀한 하드웨어 상수나 모든 데이터 크기의 보장으로 해석하면 안 된다. 한 크기의 예열된 배열 시험이며 통계적 신뢰구간은 산출하지 않았다.

#### GeulNPU에 대한 의미

- Python 원소별 반복을 GL이나 C의 네이티브 루프로 옮기는 데에는 큰 개선 여지가 있다.
- 이미 NumPy 또는 XRT 안에서 실행되는 네이티브 연산을 GL 루프로 바꾸면 반드시 빨라지는 것은 아니다.
- GL이 네이티브 기계어를 만든다는 이유만으로 최적화된 C와 같은 속도이거나 더 빠르다고 볼 수 없다. 정확한 원인을 자동 벡터화나 특정 기계어 하나로 단정하려면 별도 기계어 분석이 필요하다.
- 이번 시험은 CPU 메모리 처리다. GL의 FFI 작업 제출 비용·CPU↔NPU DMA 대역폭·동기화·모델 추론은 측정하지 않았으며 NPU 속도 개선 배수로 환산할 수 없다.

현 단계에서는 GL을 실행 계획·모델 관리에 사용하고, 성능이 중요한 패킹·후처리·장치 호출을 최적화된 네이티브 경로로 제공하는 설계가 타당하다. GL 자체 최적화가 목적이라면 이번 네 가지 작업을 컴파일러 회귀 벤치마크로 사용할 수 있다.

소스와 재현 명령, 비교 조건은 [README.md](../language/README.md)에 있다.

### 2.2. GL·C 소스 최적화 후 비교

원본 보고서: [AUDIT-RESULTS-2026-10-29.md](../language/AUDIT-RESULTS-2026-10-29.md). 아래 조건·결론은 해당 단계의 기록이다.

이전 Windows 앱 제어 차단 이후 사용자의 재실행 요청으로 같은 실행 파일과 실행기를 다시 실행했고 성공했다. 이 작업에서 보안 정책을 수정하거나 바이너리를 재포장하지 않았다.

1048576개 int64 원소, 배열당 8 MiB. 원본 GL, 수정 GL, 원본 C `/O2`, 수정 C `/O2`를 순서를 회전하며 4라운드 측정했다. 각 작업의 첫 실행은 예열로 제외해 작업/구현별 28개 표본의 중앙값을 비교했다. 준비·검증·프로세스 시작·출력은 타이머 밖이다.

수정 GL은 이번 측정에서 원본보다 빨랐지만, 네 작업 모두 C를 앞서지는 못했다. GL의 소스 표현에 따른 개선 여지가 컸다는 것은 확인됐다. C와 GL 모두 동일한 의미의 모드 분리, 루프 펼치기, 누산기 분리, 전치 순회 변경을 적용했다. GL에는 복합 대입을 단순 대입으로 표현하는 변경도 적용했다. 각 변경의 독립적인 기여도를 분리한 시험은 아니다.

전치에서는 동일한 소스 변경이 C를 오히려 느리게 했다. 따라서 수정본을 모든 작업에서 최적이라고 부르지 않는다. 특히 GL 전치의 약 7% 개선은 표본 변동이 커 확정적인 개선으로 일반화하기 어렵다. 모든 크기·입력에서 GL이나 C가 우세하다는 증거도 아니다.

#### 검증

- 4구현 × 4작업 × 4라운드 × 8회 = 512회 실행 모두 정확성 검사 통과.
- 복사·변환·전치는 전체 출력 원소를 예상값과 비교했다. 합산은 정확한 정수 합과 비교했다.
- 실행기는 출력 개수, 오류 0, 합 34359214080을 다시 확인했다.
- 원본 및 최적화 GL 모두 참조·자체호스팅 컴파일러 출력 SHA256 일치를 재확인했다.
- 최신 JSON은 `passed: true`, `selfhost_byte_equal: true`다. 예전 `audit-blocked.json`은 과거 실패 기록이며 최신 상태가 아니다.

#### 해석과 제한

이전 벤치마크를 GL의 성능 한계로 해석할 수 없다는 점은 이번 개선으로 확인했다. 동시에 현재 소스/컴파일러 조합에서는 C의 SIMD·루프 코드와 GL의 스칼라·스택 접근 차이가 남아 있다. 세부 기계어 증거는 [분석 기록](../language/AUDIT-2026-10-29.md)에 있다. 현재 자료는 GL의 추가 개선 가능성도, C보다 반드시 빠르다는 주장도 확정하지 않는다.

CPU 코어·클록·외부 부하는 고정하지 않았고 라운드별 변동이 있다. 신뢰구간은 산출하지 않았다. 한 크기의 예열된 CPU 배열 시험이며 NPU 데이터 전송, FFI 비용, 추론 TPS를 측정한 것은 아니다. 이번에는 Python/NumPy를 재측정하지 않았으므로 이전 날짜의 표와 새로운 정밀 비율을 계산하지 않는다.

결론적으로 GL은 모델·실행 계획 관리에 사용할 수 있지만, 성능 핵심부까지 GL로 옮길 근거는 작업별로 확보해야 한다. 컴파일러 개선 후보는 복합 대입의 주소 처리, 레지스터 스필, 루프 최적화, 정수 SIMD 생성이다.

### 2.3. CPU 정수 행렬 부분합: GL/C/AVX2

원본 보고서: [MATRIX-DECISION-2026-10-29.md](../language/MATRIX-DECISION-2026-10-29.md). 아래 조건·결론은 해당 단계의 기록이다.

#### 결정

현재 시스템은 **NPU 커널: C++ + MLIR-AIE, CPU 성능 핵심부: C/C++, 모델·실행 계획 제어: GL, 시험/참조: Python**으로 구성한다. 이는 측정과 현재 구현 가능성에 근거한 기술 권고이며, 미래의 모든 GL 컴파일러보다 C가 항상 빠르다는 주장이 아니다.

기존 GL 엔진과 수치 계약을 보존하되 행렬 계산·대량 패킹·FP32 후처리·장치 버퍼 수명 관리를 GL의 스칼라 원소 루프로 옮기지 않는다. 장치 연산은 현재 실제 실행이 검증된 C++/MLIR-AIE 경로를 사용한다. GL에는 아직 AIE 장치 코드 생성 백엔드가 구현돼 있지 않으므로, 그 컴파일러를 새로 만드는 일을 현재 성능 개선의 선행 조건으로 삼지 않는다.

#### 새 벤치마크

단순 복사 대신 GeulPU 정수 선형층의 정확한 핵심인 **INT8 자리 두 개 × INT8 가중치의 깊이32별 INT32 행렬 부분합**을 측정했다. 입력은 정수계약.자리로(x,2)로 만들고, 스케일은 FP16로 반올림한 FP32, bias는 FP32다. 가중치는 [-128,127], 활성값은 고정 시드 난수 FP32다. 실제 모델 파일에서 추출한 가중치는 아니며 Qwen3 선형층에 나타나는 입력/출력 폭을 포함하는 합성 시험이다.

두 언어는 같은 INT8 저장형·INT32 누산형·행/블록/열 순회·사전 패킹한 가중치 배치를 사용한다. 깊이32 내부에 4개 누산기와 4개씩 펼친 루프를 사용한다. GL의 누산과 인덱스는 단순 대입으로 표현했다. C 함수는 noinline이며 외부 BLAS나 행렬 라이브러리를 사용하지 않았다. GL의 산술도 외부 C 함수에 위임하지 않았다. 파일 읽기/쓰기는 CRT를 사용하지만 타이머 밖이다.

| 조건 | M×K 입력 / N×K 가중치 | GL | C /O2 | C /O2 /arch:AVX2 | C /O2의 GL 대비 속도 |
|---|---|---:|---:|---:|---:|
| 한 토큰형 | 1×1024 / 1024×1024 | 2.730 ms | 0.913 ms | 0.830 ms | 2.99배 |
| 여러 토큰형 | 32×1024 / 256×1024 | 21.674 ms | 7.130 ms | 6.782 ms | 3.04배 |
| FFN 폭 조건 | 16×3072 / 1024×3072 | 129.164 ms | 44.643 ms | 45.185 ms | 2.89배 |

활성값 두 자리를 모두 처리하므로 실제 정수 행 수는 2M이다. 가장 큰 조건에서는 한 번에 100663296개의 정수 곱과 그 누산을 수행하고 3145728개의 INT32 부분합을 출력한다. 서로 다른 블록을 합쳐서 계약을 바꾸지 않았다.

3라운드에서 구현 실행 순서를 회전했고, 구현/조건마다 예열 1회와 측정 4회씩 실행했다. 표는 12표본 중앙값이다. 처리 함수 내부 시간만 측정하며 준비·패킹·검증·파일 I/O·FP32 후처리는 제외한다. 전체 모델 TPS나 NPU 전송 성능이 아니다.

AVX2 빌드는 모든 조건에서 유리하지 않았다. 따라서 AVX2 플래그만으로 항상 빨라진다고 판단하지 않으며, CPU 기본 경로는 정확성을 검증한 /O2로 두고 ISA별 구현은 개별 측정해 선택한다.

#### 정확도 검증

- 독립 NumPy INT32 행렬 부분합 기준을 생성했다. 피연산자 크기상 오버플로가 없으며 모든 중간합이 INT32 범위다.
- GL/C 실행 파일은 매 반복마다 전체 부분합을 기준 파일과 비교한다. 총 135회 커널 실행이 모두 통과했다.
- 각 프로세스 종료 후 저장된 부분합 파일의 바이트 전체를 다시 비교했다.
- 저장된 부분합을 GeulPU의 자리 지수 복원 → 자리 합 → 블록 순서 FMA → bias 처리에 넣었다. 정수계약.행렬곱블라스의 FP32 결과와 uint32 비트로 비교해 모든 조건·구현·라운드에서 일치했다.
- 최종 FP32 후처리는 공통 Python 참조에서 수행했으므로, 이 시험은 **C/GL 자체 FP32 후처리 성능이나 정확성 구현을 검증한 것은 아니다.**

#### 시스템에 적용할 역할

| 계층 | 선택 | 이유 |
|---|---|---|
| NPU 장치 커널 | C++ / MLIR-AIE | 이미 실제 XDNA2 실행·정수 정확성 검증 완료. 전용 타일·DMA·AIE 명령을 표현하는 경로가 있음 |
| CPU 수치/데이터 핵심부 | C/C++ | 이번 계약 행렬 부분합에서 /O2가 GL보다 약 3배 빠름. 향후 패킹·후처리는 각각 실측·비트 검증 후 이식 |
| GL 엔진 | 모델 구조, 실행 계획, 계약 버전, 오류/수명 주기 제어 | 기존 GeulPU 구조를 보존하며 대량 연산을 네이티브 API 단위로 호출 |
| Python | 참조·시험·측정 | 제품 실행 경로의 원소별 루프에서 제외 |

GL↔네이티브 경계는 타일 하나가 아닌 준비된 선형층/더 큰 실행 계획 단위로 잡는다. NPU 장치 실행에는 CPU용 MSVC /O2가 아니라 AIE 전용 컴파일러를 사용한다. 현 CPU 행렬 실측으로 장래 GL 생성 NPU 커널보다 C++ 생성 NPU 커널이 빠르다고 증명한 것은 아니다. **현재 구현 가능한 경로와 실측된 비용에 따라 선택한 것이다.**

가장 먼저 이식할 대상은 이전 NPU 프로파일에서 약 5.95초를 차지한 CPU FP32 후처리다. 이것을 C++로 옮길 때는 현재 반올림·비정규수·FMA 의미를 명시적으로 보존하고 비트 회귀시험을 통과시켜야 한다. 이번 행렬 시험의 3배를 후처리나 전체 모델에 그대로 적용하지 않는다. 그다음 NPU 네이티브 행렬 명령·다중 코어·전송 중첩을 구현한다.

#### 제한과 재현

코어 고정·전력·클록·외부 부하는 통제하지 않았다. 예를 들어 여러 토큰형 GL의 라운드 중앙값은 50.67/21.67/20.59 ms로 변동이 크지만, 가장 빠른 GL 표본도 가장 느린 C /O2 표본보다 느렸다. 세 조건 모두 관측된 GL/C 범위가 분리됐으며 이 작업에 대한 선택 방향은 일관적이다. 다른 모델·크기·알고리즘의 보편적인 언어 우열로 확장하지 않는다.

소스/입력 생성: `matrix_generate.py`, 생성된 `matrix.gl`, `matrix.c`. 실행/검증: `matrix_run.py`. 전체 표본·검증·소스/실행 파일 해시: [matrix-results.json](../language/matrix-results.json). 입력/참조/원시 출력: `빌드/matrix/`.

컴파일은 `geul-lang/ref/geulc.py matrix.gl -o gl.exe`, MSVC `cl /O2 matrix.c` 및 `cl /O2 /arch:AVX2 matrix.c`다. 실행기는 위 파일들을 `빌드/matrix/{gl,c,c-avx2}.exe`에서 찾아 실행한다. Python은 현재 사용 가능한 Codex 제공 런타임을 사용했다. 기존 컴파일러·언어를 변경한 시험은 아니다.

### 2.4. 실제 NPU 커널: GL/C/펼친 C/AIE C++

원본 보고서: [README.md](gl_aie/README.md). 아래 조건·결론은 해당 단계의 기록이다.

#### 구현

GL 커널 원본은 `tile.gl`이다. 공식 geul-lang 앞단(커밋 `0899bd753e1626e31c3094f5787d0f46ad4f7cc4`)의 파서와 의미 분석기로 읽고, 실험용 `lower_gl.py`가 타입이 붙은 AST에서 AIE C++를 생성한다. GL 소스의 루프·주소 계산·결합식을 실제로 변환하며, 고정된 C++ 함수 본문을 복사하는 래퍼가 아니다. 계수 변경은 생성 식에 반영되고, 조사에 따라 호출 인자를 정규화하는 테스트도 있다.

현재 지원 범위는 이 커널에 필요한 정적 INT32 반복문, 지역 변수, 정수 식, 출력 배열 저장, `점곱32` 내장이다. 일반 GL 전체의 NPU 컴파일을 지원하는 것은 아니다. 기존 GL 컴파일러 원본을 수정하지 않고 별도 실험 백엔드를 붙였다.

```
tile.gl
  → 공식 GL parser / sema
  → 정수 범위·버퍼 범위·오프셋 정렬 검사
  → 불변 벡터 적재를 루프 밖으로 이동 / 중복 적재 재사용
  → generated.cc (AIE 벡터 내장)
  → Peano clang++ -O2 → AIE2p object → 실제 NPU
```

입력 타일은 INT8 `a[8,32]`, `b[32,32]`, 출력은 INT32 `dst[4,32]`다. a의 앞 4행/뒤 4행이 낮은/높은 자리다. 각 출력은 `dot32(low,w)+256*dot32(high,w)`이며, 두 자리 부분합을 장치에서 결합해 출력 크기를 줄인다. 입력 재사용은 GL 백엔드가 수행한다. 고정 블록32, 정수 누산 폭, 두 자리 결합 및 이전 검증의 CPU FP32 순서 고정 후처리를 유지했다.

백엔드는 배열 범위를 넘는 접근, 정렬을 증명할 수 없는 벡터 적재 오프셋, INT32 오버플로 가능성, 알 수 없는 내장과 지원 밖 문법을 거부한다. 입력 읽기/출력 쓰기를 분리하며 런타임은 서로 다른 AIE FIFO 버퍼를 제공한다. 임의의 겹치는 버퍼에 이 코드를 적용하는 것은 지원 범위 밖이다. 반올림 순서를 바꾸는 실수 최적화는 하지 않는다.

#### 비교군과 공정성

| 이름 | 원본 | 장치 코드 |
|---|---|---|
| GL | `tile.gl` | 새 백엔드가 AIE 벡터 내장으로 변환 |
| C | `native.c` | C11 INT8 dot32 루프, 컴파일러 -O2 |
| C 4누산기 | `native_unrolled.c` | C11 수동 4방향 펼치기/독립 누산기, -O2 |
| AIE C++ | `native_aie.cc` | GL과 같은 벡터 내장을 수작업으로 작성한 대조군 |

모두 같은 Peano clang 22 빌드, `aie2p-none-unknown-elf`, `-O2`, 같은 단일 코어 FIFO 그래프, 같은 타일/프레임 수와 버퍼 크기를 쓴다. C는 실제 `clang -x c -std=c11`로 컴파일했다. C++로 C 코드를 컴파일한 비교가 아니다. CPU 측 전송, 캐시, 지수 복원, 블록별 FMA와 bias는 공통 Python/NumPy 구현을 쓴다. 따라서 전체 호스트 언어 GL 대 C의 비교가 아니라 NPU 커널 생성 경로의 비교다.

중요: C 루프에 없는 AIE 벡터 내장을 GL이 사용한다. 이 차이를 언어 자체의 보편적인 우위로 해석하지 않도록, 같은 내장을 쓰는 수작업 AIE C++ 대조군을 포함했다. C의 Clang 벡터 확장 구현 `native_vector.c`도 시도했으나 이 컴파일러의 `<32 x i32> mul` legalization 실패로 실행하지 못했다(`results/vector-experiment.json`). 모든 C 벡터 구현이 불가능하다는 뜻은 아니다.

#### 측정 결과

워밍업 후 각 백엔드를 12회씩 측정하고 실행 순서를 순환/역순으로 교차했다. 정수 출력 검증은 타이머 밖에서 INT64 oracle과 비교했다. 선형층 시험도 동일 fixture/기준 출력으로 수행했다. 측정 시간은 CPU에서 본 호출 시간이며 복사·동기화·결과 수신을 포함한다. NPU 코어의 순수 사이클 측정이 아니다.

#### 정확성 및 모델 검증

- GL 변환기 테스트 8개 통과: 소스 반영, 조사 정규화, 불변/중복 적재, 범위/정렬/오버플로/서명/알 수 없는 내장 거부.

모델의 두 번째 실행에서 계측한 선형층 시간 합계는 GL **11.4937초**, C 4누산기 **51.9872초**로 관측 속도비는 **4.52배**였다. 첫 실행은 각각 14.3629초/53.4655초다. 모델 프로세스는 순차 실행했고 warm 전체 모델 표본은 각 1개이므로 안정적인 생성 속도나 전체 애플리케이션 개선율로 확대하지 않는다. 모든 선형층에 대해 CPU 기준 계산도 추가 수행하므로 이 합계는 계측된 선형층 호출 시간이며 프로그램 전체 wall-clock 시간과 다르다. AIE C++ 모델 실행은 별도로 측정하지 않았다.

#### 채택 판단

GL을 계약 기반 NPU 커널 작성 언어로 사용하는 방향은 이 실험에서 성립했다. 범용 스칼라 GL CPU 코드로 비교할 때와 달리, 전용 내장과 정적 배치 최적화를 통해 수작업 AIE C++와 같은 장치 코드에 도달했다. 현재의 순수 C 루프 두 구현보다 빠르며 출력 비트도 유지했다.

권하는 구조는 GL 소스 + 검증 가능한 제한된 장치 연산 + AIE 코드 생성이다. 중간 C++ 사용 자체는 실행 오버헤드를 만들지 않는다. 다음 확장은 정확한 FP32 장치 후처리와 더 넓은 형상 지원이며, 현재 백엔드를 범용 컴파일러나 제품 수준 지원으로 표현하지 않는다.

## 파트 3. 정확 후처리·단계 분담·장치 병렬화

### 3.1. 네이티브 후처리·FMA 적합성·초기 중첩

원본 보고서: [RESULTS-2026-10-31.md](next_stage/RESULTS-2026-10-31.md). 아래 조건·결론은 해당 단계의 기록이다.

작성일: 2026-10-31. 대상은 Ryzen AI 7 350의 실제 NPU와 Qwen3-0.6B-Q8_0다. 앞선 GL 정수 커널을 유지하고 후처리·실행 중첩·캐시 생성 경로를 시험했다.

#### 1. 항목별 결과

| 항목 | 수행한 시험 | 결과 | 결정 |
|---|---|---|---|

| NPU 내부 FP32 후처리 | scalar FMA 컴파일·링크 및 AIE 벡터 MAC 실제 장치 시험 | scalar는 fmaf 링크 실패, 벡터는 256개 중 84개 비트 불일치 | 현재 경로로의 이동은 채택하지 않음 |

네 영역을 모두 시험했지만 모든 설계가 성공하거나 제품화된 것은 아니다. 특히 NPU FP32 경로는 계약 불일치를 발견해 제외했고, GL 엔진 통합은 DLL 연결 시험과 Python 기반 생성 프로토타입까지의 검증이다.

#### 2. 네이티브 CPU 후처리

##### 구현

`post.c`를 MSVC `/O2 /fp:strict /MD /LD`로 빌드하여 `post.dll`로 만든다. 단순한 곱셈·덧셈 대체나 fast-math는 사용하지 않았다.

- FP32 입력의 비정규수를 계약 모드에 맞게 처리.
- 정확한 FP64 곱, TwoSum 오차, FP32 중간값 경계의 보정으로 기존 `C.fma32` 의미를 재현.
- 결과가 규칙 R의 비정규수 경계 아래인지 확인해 부호 있는 0을 반환.
- 정수 부분합의 FP32 변환과 지수 복원, 깊이32 블록 순서 누산을 유지.
- 함수 진입 시 현재 스레드 MXCSR을 보존하고 RN/DAZ/FTZ 관련 설정을 명시한 뒤 복원.
- bias는 기존 공통 계약 경로에서 처리한다.

현재 경로는 참조 구현의 의미를 이식한 것으로, AVX FMA를 무조건 켠 구현이 아니다. NaN/무한대 입력을 포함하는 범용 수학 라이브러리 보장을 주장하지 않는다. 무작위 FMA 입력은 유한 FP32였으며 연산 결과의 오버플로도 비트 비교에 포함했다.

##### 단독 정확성과 속도

비정규수 버림 on/off 두 모드, 무작위 유한 비트 패턴 및 경계 조합을 합쳐 **403,456개 FMA 결과**를 검사했다. signed zero, 최소 비정규수, 최소 정규수, 상쇄 및 최댓값 조합 등을 포함하며 비트 불일치 0이었다.

각 조건은 12번 교차 실행하고 첫 회를 제외한 11표본 중앙값이다. 지수 복원과 블록 FMA까지 측정하며 NPU 전송과 bias는 포함하지 않는다.

| M,N,K | NumPy 참조 후처리 | 네이티브 후처리 | 속도비 |
|---|---:|---:|---:|
| 1,1024,1024 | 13.147 ms | 2.091 ms | 6.29배 |
| 32,256,1024 | 62.575 ms | 13.219 ms | 4.73배 |
| 16,1024,3072 | 257.498 ms | 69.152 ms | 3.72배 |

##### NPU 선형층 전체

동일 GL NPU 장치 경로에서 finalizer만 교체하고 각 8회 교차 측정했다. 전송·패킹·후처리·bias를 포함한다. 전체 48회 측정 출력이 동일 fixture의 FP32 비트와 일치했다.

| M,N,K | 기존 후처리 | 네이티브 후처리 | 속도비 |
|---|---:|---:|---:|
| 1,1024,1024 | 27.241 ms | 21.342 ms | 1.28배 |
| 32,256,1024 | 178.481 ms | 153.632 ms | 1.16배 |
| 16,1024,3072 | 369.419 ms | 233.738 ms | 1.58배 |

Qwen `[1,2,3]` 전체 forward를 두 번 실행해 선형층 282회, 잔차 56개, 로짓 2개 모두 CPU 기준과 일치했다. 반복 로짓 차이도 0이었다. 두 번째 선형층 시간 합계는 **8.3891초**, 그 안의 후처리 합은 **2.9457초**였다. 과거 GL 모델의 11.49초와는 다른 실행이므로 엄밀한 paired 모델 개선율로 계산하지 않는다.

#### 3. NPU 실수 후처리 시험: 현재 경로는 제외

##### 일반 scalar FMA

`__builtin_fmaf(a,b,c)`를 호출하는 AIE 커널을 실제 도구 체인으로 빌드했다. 외부 `fmaf` 기호를 찾지 못해 링크에 실패했다. 따라서 이 경로의 장치 실행시간이나 정확성 측정값은 없다. 다른 런타임/소프트웨어 FMA 구현까지 불가능하다는 의미는 아니다.

##### AIE 벡터 MAC

`aie::accum<accfloat,16>`와 `aie::mac(acc,x,y)`를 사용하는 벡터 커널은 컴파일·장치 실행에 성공했다. 그러나 256개 입력 중 **84개**가 기존 FMA 계약과 다른 비트를 냈다. 최대 절댓값 차이는 `2.384185791015625e-7`이었다.

대표적인 상쇄 사례:

```text
a = FP32(1 + 2^-23)
b = FP32(1 - 2^-23)
c = -1

계약 FMA: -2^-46   → 0xa8800000
AIE MAC: +0        → 0x00000000
```

설치된 AIE API 문서 `aie_doc.hpp`는 XDNA2의 float 곱셈을 native bfloat16 곱셈으로 에뮬레이션한다고 설명한다. 이번 실측도 계약과 같은 한 번의 FP32 반올림을 가정할 수 없음을 보여준다.

**결정:** 허용 오차로 검사를 바꾸어 통과시키거나 이 MAC을 그대로 후처리에 적용하지 않는다. 장치 이전을 다시 검토하려면 정수 기반 정확한 FP 연산 또는 오차 보정 방식의 별도 구현·증명·성능 시험이 필요하다. 당장은 검증된 CPU DLL을 유지한다.

#### 4. 실행 중첩

##### 두 독립 NPU 버퍼 슬롯

각 슬롯에 별도의 a/b/c 버퍼를 두고 입력 변경·짧은 꼬리를 포함한 8개 작업을 실행했다. 두 호스트 스레드의 동시 제출과 직렬 실행을 각 8회 교차 비교했다. 128개 정수 결과 검사에서 불일치 0이었다.

| 방식 | 8작업 묶음 중앙값 |
|---|---:|
| 직렬 | 64.495 ms |
| 두 슬롯 동시 제출 | 63.247 ms |

관측 속도비는 약 1.02배다. 유의미한 개선으로 확정하기 어렵다. 이는 호스트에서 본 동시 제출이며 실제 DMA와 계산이 겹쳤다는 하드웨어 추적 증거는 아니다. 기본 채택 대상으로 삼지 않는다.

##### CPU 후처리와 다음 NPU 청크 중첩

`PlannedLinear`에 선택적 `finalizer_executor`를 추가했다. 이전 출력 청크의 네이티브 후처리는 CPU worker에서 수행하고, 메인 스레드는 다음 청크의 NPU 작업을 진행한다.

- 청크별 sums 배열을 새로 할당하고 future가 완료될 때까지 소유하게 한다.
- 동시에 보관하는 후처리 청크는 두 개로 제한한다.
- 결과는 해당 출력 열 범위에만 기록한다.
- 모든 future가 완료된 뒤 bias를 적용하고 반환한다.
- 블록별 누산 순서는 청크 내부에서 그대로 유지한다.

두 형상에서 각각 warm 실행 후 6회 교차 측정했다. warm 검사를 포함한 28개 선형 출력에서 비트 불일치 0이었다.

| M,N,K | 네이티브 후처리 직렬 | CPU/NPU 청크 중첩 | 속도비 |
|---|---:|---:|---:|
| 3,8193,1024 | 70.501 ms | 53.328 ms | 1.32배 |
| 16,8193,1024 | 299.148 ms | 213.900 ms | 1.40배 |

이 개선은 CPU 후처리와 NPU 구간의 중첩이다. 모든 입력에서 유리하다는 뜻은 아니며 출력 청크가 하나뿐이면 겹칠 다음 작업이 적다. 중첩 시 프로파일 구간 시간의 합은 전체 wall-clock 시간과 같지 않다.

#### 5. GL 호스트 연결 및 KV 캐시 생성

##### GL → C DLL 연결

`host_smoke.gl`을 기존 GL x86 컴파일러로 실행 파일로 만들고 `post.dll`의 `geul_fma`를 직접 호출했다. GL에서 256개 출력의 비트를 기준 파일과 비교해 모두 일치했다. 일반 실행 환경에서 정상 실행됐으며 샌드박스에서는 초기 DLL 실행 오류가 있었다. 보안 정책이나 실행 파일을 우회 수정하지 않았다.

이는 GL FFI와 네이티브 후처리 연결의 시험이다. 전체 제품 GL 엔진의 NPU 모델 핸들 API를 구현한 것으로 표현하지 않는다.

##### 실제 cached decode 프로토타입

`CachedQwen`은 Qwen3 Q8/Q4 선형층용 별도 실행 프로토타입이다.

- 모델 가중치를 미리 읽고 FP32 RoPE K/V를 층별로 캐시한다.
- prefill 이후에는 새 토큰의 선형층만 계산한다.
- GL NPU 정수 커널 + 네이티브 CPU 후처리 + 청크 중첩을 사용한다.
- 어텐션은 기존 CPU 참조를 사용하며, 현재는 캐시 K/V를 매 단계 다시 양자화한다.
- 마지막 토큰의 로짓을 출력하고 argmax 토큰을 다음 입력으로 전달한다.
- 지원 범위는 Qwen3, 정렬된 full RoPE 헤드, 최대 256토큰이다.

입력 token IDs `[1,2,3]`에서 네 토큰 `[16,17,18,19]`를 생성했다. 첫 토큰은 prefill 출력이며 이어지는 세 번이 cached decode다. 독립적인 **전체-prefix 참조**로 각 단계의 로짓을 미리 계산한 뒤 비교했다. 두 번의 생성 실행, 총 8개 로짓 배열이 모두 비트 일치했다.

| 항목 | 첫 실행 | 두 번째 실행 |
|---|---:|---:|
| prefill → 첫 토큰 로짓 | 7.989초 | 5.577초 |
| decode 1 | 4.647초 | 4.583초 |
| decode 2 | 4.660초 | 4.613초 |
| decode 3 | 4.628초 | 4.660초 |
| decode 처리율 | 0.2153 tokens/s | 0.2165 tokens/s |

K/V 배열 크기는 마지막 단계에 1,376,256바이트였다. 프로세스 전체 또는 NPU 메모리 사용량이 아니다. 가중치 로딩은 위 prefill 시간 밖이며 첫 실행에는 계획·실행 준비 비용이 포함된다.

이제 고정 prefix forward만이 아니라 실제 캐시 생성 경로의 값을 확인했지만 **약 0.217 tokens/s는 실용적 속도라고 보기 어렵다.** 토크나이저, 채팅 템플릿, EOS 종료, 긴 문맥, 동시 요청을 포함하지 않았고 3개 decode 표본으로 p95나 서비스 성능을 주장하지 않는다.

#### 6. 추가 프로파일과 다음 병목

느린 생성의 원인을 확인하기 위해 같은 경로에 구간 계측을 추가하고 `[16,17,18]`까지 두 번 생성했다. 별도 프로파일 실행이며 다시 총 6개 로짓 배열이 전체-prefix 기준과 비트 일치했다.

warm 두 decode 단계의 관측값:

| 구간 | decode 1 | decode 2 |
|---|---:|---:|
| 전체 step | 4.583초 | 4.666초 |
| 선형층 전체 | 3.542초 | 3.595초 |
| 선형층 안의 장치 실행·전송 | 2.657초 | 2.692초 |
| 선형층 안의 패킹·계획 확인 | 0.466초 | 0.462초 |
| 선형층 안의 FP32 후처리 작업 합 | 0.651초 | 0.661초 |
| CPU 어텐션 | 0.826초 | 0.842초 |

선형층 안의 구간은 일부가 겹치므로 더해서 전체 시간으로 해석하면 안 된다. step당 선형층 호출은 141회였다. 후처리 개선 후에는 장치 실행·전송이 전체 step의 약 58%, CPU 어텐션이 약 18%를 차지한다. 따라서 더 이상 과거의 '후처리 약 64%' 프로파일만 보고 다음 작업을 정하면 안 된다.

#### 7. 개선 우선순위

##### 바로 사용할 수 있는 것

1. **네이티브 CPU 후처리:** 비트 계약과 모델 시험 통과. `finalizer=NativePost()`로 선택 가능하다. 기존 기본 경로를 자동 교체하지 않았다.
2. **CPU/NPU 청크 중첩:** 큰 출력 폭에서 실측 이득. `finalizer_executor`로 선택 가능하다. 캐시 생성 시험에서도 정확성을 확인했다.

##### 다음에 구현·측정할 것 — 아직 성능 이득을 측정하지 않은 제안

1. **decode 전용 행 수 특수화.** 현재 GL 타일은 출력 4행을 계산한다. M=1 decode에서는 1행만 유효하므로 불필요한 행 계산을 없애는 1행 커널을 우선 시험한다. 같은 논리 출력·순서·비트를 유지하고 M=1/3/4/꼬리 행을 각각 검증해야 한다. 단순히 4배 빨라진다고 가정하지 않는다.
2. **프레임 수와 제출 비용 축소.** 현재 최대 2,048프레임 버퍼의 패딩과 작은 호출 비용을 줄이도록 128/512/1,024/2,048 등의 계획을 형상별로 선택한다. compile/JIT 비용과 장치 버퍼 수 증가까지 함께 측정한다.
3. **가중치 재사용과 불변 모델 핸들.** 현재는 내용 해시·호스트 패킹 캐시 및 반복 전송이 남아 있다. 소유권이 보장되는 불변 모델 핸들로 해시 비용을 줄이고, 장치 내 재사용을 별도 설계한다. 임의 변경 가능한 배열에서 해시 검사만 빼서는 안 된다.
4. **CPU 어텐션과 K/V 표현 개선.** cached K/V를 매 단계 다시 양자화하는 비용과 CPU 참조의 배열 처리를 줄인다. 먼저 동일 계약의 양자화된 K/V 캐시를 설계하고 각 decode 위치의 로짓을 전체-prefix 기준과 비교한다.
5. **정확한 NPU FP32 연산은 별도 연구 항목.** AIE 기본 MAC으로 대체하지 않는다. 오차 보정/정수 기반 정확 연산을 구현한다면 반올림 경계와 실제 속도를 검증한 뒤 채택한다.
6. **제품 GL 엔진 통합.** 이번 GL FFI 시험과 Python 생성 프로토타입을 바탕으로 모델 준비·계획·제출·완료·해제 ABI를 설계한다. 현재는 완성된 제품 엔진 교체가 아니다.

우선순위는 **현재 NPU 정수 경로 + 검증된 CPU 후처리의 효율 개선**이다. 정밀도 계약을 느슨하게 바꾸어 NPU 실수 연산을 통과시키는 방향은 채택하지 않는다.

### 3.2. 초기 실용성 검증 질문

원본 보고서: [VIABILITY-2026-10-31.md](next_stage/VIABILITY-2026-10-31.md). 아래 조건·결론은 해당 단계의 기록이다.

Ryzen AI 7 350에서 같은 모델, 같은 디코더, 프롬프트 토큰 [1,2,3]으로 실행했다. 매 조건 두 회, 회당 prefill 한 번과 decode 세 번을 측정했다. 표는 두 번째 회 평균이다. 모델 로딩과 커널 준비 시간은 제외했다. 모든 단계의 전체 FP32 로짓 SHA-256을 CPU 기준과 비교했고 24개가 일치했다. 생성 토큰은 [16,17,18,19]였다. 이전 전체-prefix 참조에 일치했던 마지막 로짓 해시도 재현했다.

| 실행 | prefill 초 | 초/생성 토큰 | 토큰/초 | CPU초/토큰 | 평균 사용 코어 상당량 |
|---|---:|---:|---:|---:|---:|
| baseline | 8.273 | 6.644 | 0.151 | 3.833 | 0.58 |
| optimized | 5.631 | 3.216 | 0.311 | 2.745 | 0.85 |
| cpu_cached | 2.372 | 1.683 | 0.594 | 2.146 | 1.27 |

baseline은 GL 4행·고정 2048프레임 및 FP32 KV 캐시, optimized는 한 토큰 선형층에 GL 1행·512/1024/2048 가변 프레임과 양자화 KV 캐시를 사용한다. cpu_cached는 4개 워커의 네이티브 AVX2 정수 내적, 동일한 엄격 FP32 후처리 및 동일한 양자화 KV 캐시다. 공통 캐시 최적화는 길이 64 이하 기본 계약에서 단일 어텐션 조각을 재사용하며 기존 FP32 KV와 양자화 KV를 함께 보관한다. 각 조건을 순서대로 실행했으며 개별 최적화의 모델 수준 기여도와 장문 성능은 분리 측정하지 않았다. 고정된 짧은 요청에서의 선택 근거로 사용한다.

CPU초는 Python 프로세스 전체 스레드의 사용자·커널 시간이다. 이를 경과 시간으로 나눈 평균 코어 사용량과, 같은 토큰 하나에 소비한 CPU 시간은 서로 다른 지표다. 시스템 전체 및 드라이버 외부 작업은 포함하지 않는다. AC 전원 사용 중 배터리 방전율 0이며 조회한 에너지 카운터로 유효한 J/token을 얻지 못했다.

1행 커널은 유효 타일 128개를 512프레임에서 2.06 ms, 2048프레임에서 5.23 ms에 처리했다. 프레임 조건마다 5회 출력이 정수 참조와 일치했다. 시간은 첫 실행을 제외한 중앙값이다. 기존 4행 GL은 손으로 최적화한 AIE C++와 320바이트 기계어가 동일했다. GL 정적 검사 회귀시험 8개가 통과했고 범위 초과, 오정렬, 오버플로를 컴파일 때 거부했다. 개발 시간과 유지보수 비용은 측정하지 않았다.

#### 묶음 전송 개선

4행마다 따로 제출하던 GL 타일을 다음 행 묶음과 연결해 프레임을 채운다. 정수 내적과 블록 누산 순서는 유지하며, 호스트의 타일 배치와 결과 복원 순서를 변경했다. 입력 256행, 출력 3072열, 깊이 1024인 실제 FFN up projection에서 기존 형상의 제출 횟수는 768회이고 새 경로의 실제 제출 횟수는 96회다. 전송 프레임은 1,572,864개에서 196,608개로 감소한다. 여기서 프레임 수는 타일 단위이며 제출 한 번은 2048프레임이다. 새 경로의 해당 형상에서는 패딩 프레임이 없다.

### 3.4. NPU 작업자 1·2·4개

원본 보고서: [MULTIWORKER-2026-11-01.md](next_stage/MULTIWORKER-2026-11-01.md). 아래 조건·결론은 해당 단계의 기록이다.

### 4.1. 기본/중첩/재사용/결합 4조합

원본 보고서: [REUSE-OVERLAP.md](next_stage/REUSE-OVERLAP.md). 아래 조건·결론은 해당 단계의 기록이다.

NPU 4작업자와 CPU 후처리 4스레드를 고정했다. baseline은 순차 처리, overlap은 앞 출력 청크의 후처리를 다음 청크의 NPU 작업과 중첩, reuse는 장치 가중치 재사용, combined는 둘을 결합한 경로다. 최종 출력의 FMA 블록 순서는 유지한다.

재사용 그래프는 각 NPU 작업자가 32×32 INT8 가중치 FIFO 객체 하나를 acquire한 채 서로 다른 입력 4행 묶음 네 개에 같은 GL 커널을 호출한 뒤 release한다. 모델 전체 가중치가 장치에 상주하는 구현은 아니다. 그룹당 16입력 행 범위의 장치 내부 재사용이다. CPU 중첩은 단일 조정 스레드와 후처리 4스레드를 사용하며 보유 중인 후처리 청크를 최대 두 개로 제한한다. 각 청크의 부분합 저장소를 독립적으로 유지한다.

| 실제 Qwen FFN 입력 행 | 기본 ms | 중첩 ms | 재사용 ms | 둘 다 ms |

### 4.3. 제출 용량 2,048·4,096·8,192

원본 보고서: [BATCH-CAPACITY.md](next_stage/BATCH-CAPACITY.md). 아래 조건·결론은 해당 단계의 기록이다.

기존 2,048프레임 경로는 재실행하지 않았다. 새 4,096·8,192프레임 경로만 워밍업 후 각 3회 교대 측정했다. NPU 작업자 4개, CPU 후처리 4스레드, 장치 가중치 4회 재사용과 후처리 중첩을 유지했다. ReuseDevice의 프레임 용량을 선택 가능하게 했으며 기본값은 2,048이다. 장치 그래프 반복 횟수와 호스트 버퍼만 함께 늘리고 GL 정수 커널과 FMA 순서는 유지했다.

Qwen3-0.6B-Q8_0 첫 FFN up(K=1024,N=3072) 기준이다. 이전 자료와의 시간 차이는 서로 다른 세션의 관찰값이므로 통제된 속도 향상률로 해석하지 않는다. 이번 동일 세션의 두 새 용량끼리는 직접 비교할 수 있으나 각 3표본뿐이다.

전체 모델 64토큰은 선택한 8192프레임 경로에서 첫 출력 32.526초, 다음 CPU 출력 6.122초였다. 이전 2,048 경로의 첫 출력 중앙값은 32.938초다. 새 모델 경로는 정확성 통합 검증용 1회이며, 전체 모델의 안정적 성능 개선을 입증하는 반복 시험은 아니다.

홀수 크기와 깊이 꼬리를 포함한 선형층 20회에서 CPU 출력과 uint32 비트가 일치했다. 모델 첫·다음 출력 전체 로짓 해시 2개도 기존 CPU 기준과 일치했다. 실행 중 SetThreadExecutionState로 자동 절전을 억제하고 finally에서 해제했다. 덮개 닫힘이나 수동 절전을 막는 설정은 아니다.

#### 부분합 반환량을 유지한 이유

GL 커널은 깊이 32개마다 s0 + 256*s1을 반환한다. 임의 INT8 입력에서 각 내적의 절댓값 상한은 32×128×128=524,288이고 결합값 상한은 134,742,016이다. 따라서 범용 경로의 무손실 고정 폭은 보수적으로 부호 포함 29비트가 필요하며 INT16·INT24 축소는 안전하지 않다. 이 상한은 검증된 실제 데이터의 분포와 별개다. 여러 깊이 블록을 단순 정수 합산하면 블록별 스케일과 ordered FP32 FMA 반올림 지점이 사라지므로 기존 계약을 보존하지 못한다.

이번 변경은 제출 횟수를 줄였으며 반환 바이트는 줄이지 않았다. 고정 29비트 포장으로 줄일 수 있는 이론상 비율은 32비트 대비 9.375%뿐이며 장치 포장과 CPU 복원 비용을 추가로 검증해야 한다. 더 큰 반환량 절감은 데이터 의존 무손실 압축 또는 정확한 순차 FMA 후처리의 장치 구현이 필요하다. 어느 쪽도 이번에 구현·측정했다고 주장하지 않는다.

#### 적용 판단

이번 새 용량끼리의 결과로 큰 입력의 제출 용량 후보를 좁혔다. 작은 입력·꼬리에서는 큰 버퍼 패딩과 전송 낭비가 생길 수 있으므로 모든 호출에 큰 용량을 강제하지 않는다. 기본 경로는 그대로 유지한다. 다음 구현은 입력 프레임 수와 출력 청크 크기에 따른 제출 용량 선택이며, 이미 측정한 경로를 다시 벤치마킹할 필요 없이 새 선택 로직의 경계 정확성부터 검증할 수 있다.

### 4.4. 입력 크기별 자동 용량 정책

원본 보고서: [ADAPTIVE-REUSE.md](next_stage/ADAPTIVE-REUSE.md). 아래 조건·결론은 해당 단계의 기록이다.

`AdaptiveReuseDevice`를 `JoinedPrefill`의 장치로 전달하면 출력 청크마다 2,048·4,096·8,192 프레임 중 하나를 선택한다. 기존 고정 용량 경로와 기본값은 유지한다. CPU 후처리 중첩은 기존 `finalizer_executor`와 함께 사용한다.

#### 선택 기준

1. 입력 4행 그룹 수와 가중치 타일 수를 장치의 작업자·재사용 단위에 맞게 패딩한다.
2. 16그룹(최대 64행) 이하는 2,048·4,096을 후보로 사용한다. 큰 입력은 8,192도 허용한다. 이는 기존 FFN 시험을 바탕으로 한 초기 정책이며, 모든 모델에서 최적인 임계값은 아니다.
3. 후보마다 `ceil(필요 프레임 / 용량) × 용량`을 계산해 명시적 버퍼 전송량을 최소화한다. 같으면 제출 횟수가 적은 용량을 선택한다. 각 프레임의 A/B/C 바이트 비율은 후보 간 동일하다.
4. 장치 버퍼는 선택된 용량만 지연 생성하고 이후 재사용한다. 최대 세 용량의 A/B/C 버퍼 합계는 14MiB이며 런타임·컴파일 캐시와 호스트 임시 배열은 별도다.

예를 들어 20그룹×208타일은 4,160프레임이다. 8,192로 한 번 보내는 대신 2,048로 세 번 보내 총 6,144프레임을 전송한다. 20그룹×408타일은 8,160프레임으로, 세 후보의 총 전송량이 8,192로 같아 한 번 제출하는 8,192를 선택한다. 제출 비용과 전송 비용을 실측으로 모델링한 정책은 아니므로, 전송량 최소화가 항상 최소 지연을 보장하지는 않는다.

#### 검증 범위

`check_adaptive_reuse.py`는 성능 시간을 측정하지 않는다. 기존 벤치마크를 재실행하지 않고 새 선택 경로의 정확성만 확인한다.

- 정책 경계 8개와 잘못된 크기 3개.
- 모든 후보 용량과 용량 전환을 포함한 정수 부분합 8개. 전체 INT8 범위의 입력에 대해 독립적인 CPU INT64 내적과 비교한다.
- 단일 행 fallback, 홀수 행·열, 깊이 꼬리 및 64/65행 경계를 포함한 선형층 5개. CPU 출력과 uint32 비트를 비교한다.
- Qwen3-0.6B-Q8_0 64토큰 모델의 첫·다음 출력 전체 로짓 해시를 기존 CPU 기준과 비교한다. 이는 새 경로의 통합 정확성 검증이며 성능 재측정이 아니다.

실행: `viability.ps1 check_adaptive_reuse`. 결과는 [검증 원자료](next_stage/results/adaptive-reuse.json)에 저장한다. 실행 중 자동 절전을 억제하고 종료 시 해제한다.

부분합 형식, GL 커널, 깊이 블록별 FMA 순서는 바뀌지 않는다. 이 단계는 패딩 및 제출 용량 선택을 개선하며 유효 부분합 자체의 바이트 수를 줄이지 않는다. 장치 인스턴스의 호출은 기존과 같이 순차 실행하고 CPU 후처리만 중첩한다.

## 파트 5. 무손실 부분합 압축의 구현과 기각

### 5.1. 범위 분석·INT24 압축·넘침 재요청

원본 보고서: [PACKED-PARTIALS.md](next_stage/PACKED-PARTIALS.md). 아래 조건·결론은 해당 단계의 기록이다.

세 단계를 순서대로 실행했다. 이전 성능 벤치마크는 반복하지 않았고 새 압축 경로만 측정했다. 현재 구현은 채택하지 않는다. 반환량은 줄었으나 복원·재요청 비용이 크다.

#### 1. 범위 분석

실제 Qwen3-0.6B-Q8_0의 첫 FFN up/down 및 attention Q 가중치에 64행 난수 FP32 입력을 사용했다. 실제 모델 실행의 중간 활성값 분포를 수집한 것은 아니므로 모델 전체 압축률로 일반화하지 않는다. 세 선형층 모두 CPU 출력과 비트 일치를 확인했다.

부분합 16,777,216개, 128원소 타일 131,072개를 분석했다. INT16 원소 비율 1.8702%, INT24 원소 비율 99.9916%. 타일 전체가 INT16에 들어가는 비율은 0.0000%, INT24는 98.9433%다.

#### 2. 무손실 경로

기존 GL 정수 내적 객체 gl.o는 그대로 링크했다. 새 압축은 C++ ABI 래퍼 pack24.cc로 NPU 내부에서 수행한다. GL 언어로 작성된 압축 커널이라고 주장하지 않는다. 타일별 128개 INT32(512바이트)를 INT24 384바이트와 상태·정렬 헤더 32바이트, 총 416바이트로 전송한다. FIFO와 DMA의 실제 출력 크기를 변경했으므로 호스트에서 사후 압축한 결과가 아니다.

범위 초과 플래그가 있는 타일은 해당 입력·가중치만 모아 64프레임 INT32 NPU 경로로 재요청한다. CPU는 INT24 부호 확장 후 넘침 타일을 정확한 INT32 값으로 대체한다. 가중치는 재사용 순서에서 원래 타일 인덱스로 역매핑한다. 원래 순서의 부분합을 복원한 후 기존 ordered FP32 FMA 후처리를 실행한다. 넘친 값을 잘라서 계산에 사용하지 않는다. 모든 타일이 넘칠 경우도 정확성은 유지하지만 재요청 비용이 매우 커진다.

0·양수·음수 극단·무작위 INT8 입력의 정수 부분합 검사 4개, 홀수 크기·깊이 꼬리를 포함한 FP32 비트 비교 10개, 실제 16토큰 모델 첫·다음 출력 전체 로짓 해시 2개가 모두 통과했다. 단계 1의 별도 선형층 비교 3개도 통과했다.

#### 3. 추가 비용 포함 측정

NPU 작업자 4개, 가중치 재사용 4회, 4,096프레임 제출 및 CPU 후처리 중첩을 사용했다. 새 경로만 워밍업 후 각 3회 측정했다. 아래 값은 중앙값이다.

| FFN 행 | 압축 전체 ms | CPU 복원 ms | 넘침 재요청 ms | 넘침 타일 | 압축+재요청 횟수 | 반환 MiB | 이전 비압축 ms |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 64 | 320.38 | 84.03 | 40.68 | 548 | 12+12 | 19.875 | 152.56 |
| 256 | 1076.27 | 274.92 | 147.80 | 1995 | 48+48 | 79.500 | 595.09 |

이전 비압축 시간은 다른 세션의 기록이다. 동일 세션의 통제 비교가 아니므로 정확한 인과적 감속 배수는 확정하지 않는다. CPU 복원 시간은 언팩·플래그 검사 시간이고 재요청 시간은 추가 입력 준비·장치 실행·반환을 포함한다. 후처리와 일부 중첩되므로 세부 시간을 무조건 합산하지 않는다. NPU 압축 자체의 사이클 수는 별도 측정하지 않았다. 전체 시간에는 압축을 포함한 장치 실행, 전송, CPU 복원, 재요청, 기존 FP32 후처리가 포함된다.

256행에서 출력 버퍼 전송은 96→79.5MiB로 17.19% 감소한다. 재요청의 입력·가중치를 포함하면 A+B+C 명시적 버퍼 바이트는 192→179.25MiB로 6.64% 감소하는 데 그친다. 제출은 48회에서 압축 48회+재요청 48회로 늘어난다. 이 값은 실제 버퍼 크기와 호출 수의 집계이며 하드웨어 버스 카운터가 아니다.

#### 판단

무손실 압축은 정확성 측면에서 가능하지만 현재의 호스트 넘침 재요청 방식은 제출 최소화 방향과 충돌한다. Python/NumPy 복원도 상당한 비용이다. 기존 비압축 자동 용량 선택 경로를 유지하며 압축을 기본으로 활성화하지 않는다.

다음 개선을 한다면 CPU 복원의 native SIMD 구현과 NPU에서의 별도 넘침 버퍼 출력이 후보이다. 다만 가변 길이 DMA 또는 2단계 길이 전달이 필요하며, 최대 크기의 넘침 버퍼를 항상 전송하면 절감 효과가 사라진다. 이를 해결하기 전 추가 모델 성능 벤치마크를 반복할 이유는 없다.

### 5.2. SIMD 복원·헤더 내 넘침 보정

원본 보고서: [PACKED-PARTIALS-V2.md](next_stage/PACKED-PARTIALS-V2.md). 아래 조건·결론은 해당 단계의 기록이다.

새 v2 경로만 실행했다. 기존 벤치마크는 반복하지 않았다. 초기 파일 생성의 인코딩 오류로 발생한 컴파일 실패는 수정한 뒤 새 검증을 완료했다. 이전 v1 구현과 원자료는 보존했다.

#### 변경

CPU 복원은 NumPy 임시 배열 연산에서 네이티브 SSSE3 SIMD로 이동했다. 12바이트에서 4개의 INT24를 안전하게 읽고 바이트 셔플과 산술 시프트로 부호 확장한다. 마지막 원소에서도 버퍼를 초과하여 읽지 않는다. DLL은 MSVC /O2로 빌드했다.

NPU 압축은 기존 GL 내적 객체와 C++ 래퍼를 링크한다. 기존 32바이트 헤더에 넘침 개수와 최대 7개의 보정 정보를 넣는다. 보정 정보 하나는 원소 인덱스 7비트와 원래 INT32 상위 8비트를 저장한다. 하위 24비트와 합치면 원래 INT32를 복원할 수 있다. 타일당 전송 크기는 416바이트 그대로다. 8개 이상 넘치면 헤더를 -1로 표시하고 기존 INT32 재요청 경로를 사용한다. 모든 입력에서 재요청을 없앤 설계는 아니다.

#### 검증

정수 부분합 검사 7개, FP32 비트 비교 10개, Qwen3-0.6B-Q8_0 16토큰 모델의 첫·다음 로짓 해시 2개가 통과했다. 정수 검사에는 타일당 넘침 1·7·8개 경계를 포함하며, 8개에서만 재요청하는 것을 확인했다. 별도 SIMD 검사 8개(1024개 값)는 INT32 최소·최대 및 INT24 경계의 정확한 복원을 확인했다.

#### 성능과 반환량

각 새 선형층 경로는 워밍업 후 3회 측정한 중앙값이다. 동일 Qwen FFN up 가중치, NPU 작업자 4개, 4,096프레임, CPU 후처리 4스레드 중첩을 사용했다. v1과 비압축 수치는 저장된 이전 세션 결과이므로 통제된 동일 세션 속도 비교는 아니다.

| 행 | 비압축 이전 ms | v1 이전 ms | v2 신규 ms | v1 복원 ms | v2 복원 ms | v2 재요청 | v2 반환 MiB |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 64 | 152.56 | 320.38 | 194.90 | 84.03 | 7.96 | 0 | 19.50 |
| 256 | 595.09 | 1076.27 | 713.70 | 274.92 | 32.84 | 0 | 78.00 |

이번 대상 데이터에서는 64행의 548타일, 256행의 1,995타일을 헤더로 보정했고 모든 측정에서 재요청은 0회였다. 256행 출력은 비압축 96MiB→78MiB로 18.75% 감소했다. 입력·가중치를 포함한 명시적 버퍼 바이트는 192→174MiB로 9.375% 감소한다. 하드웨어 버스 카운터 계측값은 아니다.

전체 시간에는 NPU 압축, 반환, SIMD 복원, 기존 FP32 후처리와 중첩 비용이 포함된다. 복원 시간은 헤더 검사와 출력 배열 할당도 포함한다. NPU 압축의 독립 사이클 비용은 아직 분리 측정하지 않았으므로 남은 지연을 NPU 압축 하나로 단정하지 않는다.

#### 판단

v1의 주요 문제였던 CPU 복원과 흔한 넘침의 재요청은 줄였다. 그러나 새 전체 시간은 기존 비압축 기록보다 여전히 길다. 기본 경로로 채택할 근거가 없으므로 비압축 자동 용량 선택을 유지한다. 다음 후보는 NPU 압축 래퍼의 벡터화와 내적 결과 저장을 합쳐 임시 INT32 배열 및 별도 순회를 줄이는 것이다. 해당 개선 전 기존 전체 모델 벤치마크를 반복하지 않는다.

### 5.3. NPU 내적·압축 융합

원본 보고서: [PACKED-PARTIALS-V3.md](next_stage/PACKED-PARTIALS-V3.md). 아래 조건·결론은 해당 단계의 기록이다.

기존 v2는 GL 내적 객체가 128개 INT32 임시 배열을 채운 뒤 C++ 래퍼가 넘침 검사와 압축을 별도 순회했다. 새 v3는 내적 네 개를 계산할 때마다 넘침 정보를 헤더에 기록하고 즉시 세 개의 32비트 압축 워드로 저장한다. 소스에서 전체 128원소 임시 배열과 별도 압축 순회를 제거했다. 컴파일러의 레지스터 spill이 전혀 없다고 주장하지는 않는다.

이번 커널은 GL에서 낮춘 AIE 정수 내적과 같은 연산을 사용하는 수동 C++ 융합 시제품이다. GL 컴파일러 자체에 융합 최적화를 구현한 것은 아니다. 기존 gl.o와 기존 경로는 수정하지 않았다. 출력 ABI는 v2와 같아 타일당 416바이트, 헤더 내 넘침 보정 최대 7개, 8개 이상 INT32 재요청을 유지한다. SIMD 복원 구현도 그대로 사용한다.

#### 검증

새 v3 경로의 정수 부분합 검사 7개(넘침 1·7·8개 경계 포함), FP32 비트 비교 10개 및 Qwen3-0.6B-Q8_0 16토큰 첫·다음 로짓 해시 2개가 모두 통과했다. 기존 성능 벤치마크는 다시 실행하지 않았다.

#### 결과

#### 시간의 정확한 의미

설치된 IRON 소스를 확인했다. CallableDesign은 캐시·인자 검증 등을 거쳐 NPUKernel을 호출한다. XRTHostRuntime.run은 time.time_ns()로 kernel_handle.kernel(...)과 h.wait()를 감싸 npu_time을 반환한다. 따라서 이 값은 호스트에서 본 제출·완료 대기 시간이며 AIE 코어의 순수 연산 사이클 수가 아니다. 명령 처리, 장치 내부 DMA와 FIFO 대기, 스케줄링, 연산이 함께 들어갈 수 있다.

업로드는 A/B _sync_to_device, 다운로드는 C.numpy() 내부 _sync_from_device 시간을 각각 측정했다. 다운로드 후 명시적 copy는 별도로 측정했다. 동기화 호출이 짧다고 해서 물리적인 전체 데이터 이동 비용도 그 시간뿐이라고 결론 내리지 않는다. 장치 내부 전송은 실행 대기 구간에 포함될 수 있다.

런타임 반환값이 (핸들, 결과) 튜플인 점을 처음에 반영하지 못해 워밍업 계측이 중단됐다. 수정 후 위 진단 전체를 완료했다. 실패 실행에서는 성능 표본을 확보하지 않았다.

#### 판단과 우선순위

동일 세션의 진단에서도 압축의 전체 지연이 더 크다. 주요 증가 구간은 실행·완료 대기이며 CPU 복원도 추가된다. 이번 결과로는 반환 바이트 절약이 그 비용을 상쇄하지 못한다. 압축은 연구 경로로만 보존하고 비압축 자동 용량 선택을 유지한다.

CPU 후처리 작업은 약 0.3초지만 호출자가 실제로 기다리는 시간은 훨씬 짧다. 이미 중첩으로 상당 부분 숨겨져 있으므로 후처리 작업 시간 전체를 그대로 줄일 수 있는 지연으로 계산하면 안 된다.

다음 후보는 비압축 경로의 반복 호출 준비 비용 축소(미리 로드한 실행 핸들 재사용)와 호스트 패킹·출력 재배치 비용 축소다. 호출 전체와 실행 대기의 차이는 모두 순수 API 오버헤드라고 보장되지는 않지만 조사할 만한 구간이다. 순수 AIE 연산 대 DMA/FIFO 대기를 더 나누려면 장치 이벤트 트레이스가 필요하다. 이 진단만으로 GPU/NPU 성능 한계나 CPU 대비 우열을 일반화하지 않는다.

### 6.1. 핸들 재사용과 입력·출력 복사 축소

원본 보고서: [RETAINED-DEVICE.md](next_stage/RETAINED-DEVICE.md). 아래 조건·결론은 해당 단계의 기록이다.

기존 진단은 재실행하지 않았다. 새 handle 경로와 handle_lean 경로를 동일 세션에서 A/B/B/A/A/B 순서로 각 3회 측정했다. 기존 진단과 동일한 FFN up 가중치, M=256 K=1024 N=3072, 입력 seed=619, 4,096프레임, NPU 작업자 4개와 CPU 후처리 4스레드를 사용했다.

#### 구현

handle은 첫 CallableDesign 호출이 반환한 실행 핸들을 보유하고 이후 DefaultNPURuntime.run으로 실행한다. 반복 캐시 키 생성·컴파일 객체 준비·load 단계를 건너뛰되 runtime.run의 장치 확인과 완료 검사는 유지한다. 고정 형상과 버퍼를 가진 장치 인스턴스 내에서만 재사용한다. 명시적 clear_handle 뒤 재로딩도 검증했다. 알려진 XRT stale-context 오류에서는 핸들을 버리고 기존 CallableDesign 복구 경로로 돌아가도록 했지만 실제 절전 후 복구를 이번에 시험하지는 않았다.

handle_lean은 이에 더해 정렬된 그룹·가중치의 패딩용 복사를 생략하고, 장치 입력 버퍼를 전체 0으로 채우는 대신 사용하지 않는 꼬리만 초기화한다. 다운로드 후 중간 copy를 없애고 장치 호스트 버퍼 뷰에서 최종 청크 배열로 즉시 재배치한다. 다음 장치 실행 전에 재배치를 끝내며 CPU 후처리는 별도 소유 청크를 사용한다. 정수 연산과 FP32 FMA 순서는 바뀌지 않는다.

#### 검증

홀수 행·열, 깊이 꼬리, 버퍼 재사용 뒤 이전 출력 보존, 명시적 핸들 해제·재로딩을 포함해 CPU 기준 비트 비교 26회가 통과했다. handle_lean을 사용한 16토큰 Qwen 모델 첫·다음 전체 로짓 해시 2개도 일치했다. 6개 측정 구간에서 핸들 재로딩은 모두 0회다.

|---|---:|---:|---:|---:|---:|---:|
| 기존 진단(이전 세션) | 549.76 | 533.27–576.80 | 81.87 | 51.61 | 20.43 | 48.07 |
| handle | 500.14 | 473.63–564.82 | 8.92 | 55.86 | 21.33 | 49.40 |

호출 준비 잔여는 호출 전체 시간에서 런타임 제출·완료 대기 시간을 뺀 값이다. 스케줄링 등의 영향도 있으므로 순수 API 실행 시간이라고 단정하지 않는다. 기존 진단과의 차이는 서로 다른 세션의 관찰 비교다. 두 새 경로끼리는 같은 세션이지만 각 3표본이고 실행 후반에 시간이 줄어드는 변동이 있어 작은 차이를 확정적 우열로 일반화하지 않는다.

#### 판단

핸들 재사용은 호출 준비 잔여를 크게 줄였으며 유지할 가치가 있다. 다만 전체 모델의 성능 개선은 이번에 계측하지 않았고 기본 경로를 자동 교체하지 않았다.

복사 축소는 출력 중간 복사를 없앴지만 입력 패킹 시간이 늘었고 전체 중앙값도 handle 단독보다 좋지 않았다. 입력은 원래 전치된 strided 배열이므로 연속 복사를 생략하면 뒤의 gather 접근이 비효율적일 수 있다. 이는 코드와 계측에 따른 원인 후보이지 독립적으로 입증된 원인은 아니다. handle_lean을 일괄 채택하지 않는다.

### 6.2. 연속 입력 유지·출력 중간 복사만 제거

CPU 기준 비트 비교 16회와 16토큰 Qwen 모델의 첫·다음 출력 전체 로짓 해시 2개가 일치했다. 홀수 행·열 및 깊이 꼬리에서 최초 결과를 보존한 채 입력 부호를 바꿔 다시 실행하고, 이전 결과가 변하지 않는지 확인했다. 원래 입력으로 재실행한 결과도 비교했다. 명시적 핸들 해제 후 재로딩도 통과했고 성능 측정 구간의 추가 핸들 로딩은 모두 0회였다.

#### 판단

이 경로는 입력 연속 준비를 생략했던 handle_lean의 변경을 포함하지 않는다. 입력 패킹을 유지하고 출력 중간 복사만 없애는 후보로 보존한다. 기존 전역 기본값이나 모델 라우팅은 자동 교체하지 않았다. 전체 모델 실행은 정확성 검증이며 모델 전체의 가속률을 계측한 것은 아니다.

후속 적용 후보는 자동 용량 선택기의 용량별 장치로 OutputViewDevice를 사용하는 것이다. 통합할 때는 2,048·4,096·8,192 각 용량의 핸들을 독립적으로 보유하고, 용량 전환과 출력 수명을 검증해야 한다. 이미 완료한 고정 용량 성능 시험은 다시 실행할 필요가 없다.

### 6.3. 자동 용량＋핸들＋출력 뷰 통합

원본 보고서: [ADAPTIVE-OUTPUT-VIEW.md](next_stage/ADAPTIVE-OUTPUT-VIEW.md). 아래 조건·결론은 해당 단계의 기록이다.

AdaptiveOutputViewDevice를 추가했다. 기존 AdaptiveReuseDevice의 용량 선택 정책을 그대로 사용하고, 각 용량의 실행 장치를 OutputViewDevice로 생성한다. 2,048·4,096·8,192 프레임 장치는 서로 다른 버퍼와 실행 핸들을 보유한다. 연속 입력 준비를 유지하고 출력 중간 복사만 제거한다. 출력 재배치가 소유권이 독립적인 청크로 끝난 후 다음 장치 작업을 시작한다.

기존 기본 경로나 기존 결과 파일은 바꾸지 않았다. 새 통합 경로만 정확성 검사했고 성능 벤치마크를 재실행하지 않았다.

| 검사 | 결과 |
|---|---|
| 선택 경계·잘못된 크기 | 11개 통과 |
| 용량 전환 중 정수 부분합 | 16개 CPU INT64 기준과 일치 |
| 단일 행·홀수 크기·64/65행 경계 FP32 | 5개 CPU 출력 비트와 일치 |
| 이전 출력 수명 | 16개 결과를 후속 호출과 모델 실행 이후에도 보존 |
| 장치 출력 버퍼 alias | 없음 |
| 용량별 핸들 로딩 | 2,048·4,096·8,192 각각 1회 |
| 실제 모델 출력 | Qwen3-0.6B-Q8_0 64토큰 첫·다음 로짓 해시 2개 일치 |

용량 선택 순서: 2048 → 2048 → 4096 → 4096 → 4096 → 2048 → 8192 → 2048 → 2048 → 8192 → 2048 → 4096 → 4096 → 4096 → 2048 → 2048.

선택 순서를 정방향·역방향으로 바꿔 큰 용량에서 작은 용량으로 돌아가는 경우와 동일 용량 재방문을 모두 확인했다. 단순히 결과가 같은지만 보는 데 그치지 않고, 해당 용량의 핸들이 독립적이며 반복 호출 중 다시 로드되지 않는지 검사했다. 출력 원본을 계속 보유하고 이후 다른 입력 실행이 이를 덮어쓰지 않는지도 비교했다.

#### 사용

기존 JoinedPrefill의 device 인수에 AdaptiveOutputViewDevice()를 전달하고, CPU 후처리와 finalizer_executor는 기존과 같이 관리한다. 단일 행 모델 출력·디코드는 기존 CPU 라우팅을 유지할 수 있다. 하나의 장치 인스턴스는 순차적으로 호출해야 한다. 동시에 다른 요청에서 같은 장치 버퍼를 공유하는 서비스 동시성은 이번 검증 범위가 아니다.

성능은 앞선 고정 용량 시험 결과만 존재한다. 이번 통합 검증을 새 모델 가속률의 증거로 해석하지 않는다. 자동 용량 정책의 임계값도 전체 모델에 최적임을 보장하지 않는다. 절전·장치 리셋 후 핸들 복구는 별도 검증이 필요하다.

### 6.4. 상태 초기화·KV·분할 입력·연속 생성

원본 보고서: [MODEL-INTEGRATION.md](next_stage/MODEL-INTEGRATION.md). 아래 조건·결론은 해당 단계의 기록이다.

AdaptiveOutputViewDevice + JoinedPrefill + CPU 정확 후처리 중첩 경로를 Qwen3-0.6B-Q8_0 모델에 연결했다. 같은 모델 인스턴스와 가중치를 계속 사용하되 CPU 기준 실행과 통합 실행 사이에는 KV 상태를 초기화했다. 새로운 고정 난수 토큰 입력(seed=734)을 사용했다. 성능 시간은 측정하지 않았고 이전 성능 벤치마크도 반복하지 않았다.

| 시나리오 | 입력 방식 | 후속 디코드 | 일치한 단계 |
|---|---|---:|---:|
| prefill17 | 17토큰 | 3회 | 4 |
| prefill65 | 65토큰 | 3회 | 4 |
| chunked17 | 7 + 10토큰 | 3회 | 5 |
| reset_repeat17 | 17토큰 | 3회 | 4 |

#### 확인한 계약

총 17단계에서 전체 FP32 로짓을 uint32 비트 배열로 직접 비교했고 SHA256도 저장했다. 각 단계의 생성 토큰, 처리 위치, KV 바이트 수 및 모든 층의 FP32 K/V 캐시 해시가 CPU 기준과 일치했다. 단일 행 출력층과 연속 디코드는 공통 CPU 경로이며 여러 행의 프리필 선형층만 NPU 경로다. 따라서 이 결과를 NPU 단일 토큰 디코드 검증으로 해석하지 않는다.

초기화 7회 모두 위치=0, 모든 FP32 KV 캐시=None, 양자화 캐시 비어 있음을 확인했다. 17토큰 요청을 65토큰 요청 및 분할 요청 이후 재실행했을 때 처음의 CPU 기준 출력과 다시 일치했다. 각 요청 안에서 이전 로짓 배열을 보유하고 다음 실행 후에도 값이 변하지 않는지 확인했다.

7+10 분할 프리필은 동일한 분할 방식의 CPU 실행과 비교했다. 한 번에 17토큰을 넣는 방식과 분할 방식 자체의 동등성을 별도 계약으로 검증한 것은 아니다. 65토큰 요청과 후속 3회 디코드는 짧은 어텐션 캐시 경계(64)를 넘는 경로도 실행한다.

#### 자원 재사용

관찰된 용량별 선택 횟수: {"2048": 84, "4096": 1092}.
관찰된 용량별 실행 핸들 로딩 횟수: {"2048": 1, "4096": 1}.
통합 경로의 CPU/NPU 선형 호출 횟수: {"cpu": 1697, "npu": 700}.

이번 실제 모델 시나리오에서 선택된 용량의 핸들은 모두 1회만 로드됐다. 2,048·4,096·8,192 전체 용량 전환과 버퍼 수명은 앞선 ADAPTIVE-OUTPUT-VIEW.md의 별도 통합 검사로 검증했다. 실제 모델에서 선택되지 않은 용량까지 이번에 실행했다고 주장하지 않는다.

#### 범위와 판단

이번 모델·입력·CPU 기준 구현에 대해 상태 초기화와 반복 요청, 분할 프리필, 다단계 디코드가 비트 계약을 유지했다. 제품 전체의 보편적 정확성 증명은 아니며 다른 모델, 더 긴 컨텍스트, 동시 요청, 절전·장치 리셋 복구는 범위 밖이다. CPU 기준과 통합 경로는 모델 코드와 FP32 후처리를 공유하므로 공유 코드 자체의 오류까지 배제하는 독립 검증은 아니다.

기존 기본 실행 경로는 변경하지 않았다. 다음 배포·제품 통합 판단에서는 성능 주장과 정확성 결과를 분리하고, 동시 요청 및 장치 수명 관리를 별도 검증해야 한다.

## 파트 7. 최종 속도·효율·처리량과 NPU 전용 런타임 참고

### 7.1. CPU 단독 대 최종 분담 및 별도 FastFlowLM

원본 보고서: [SYSTEM-COMPARISON.md](next_stage/SYSTEM-COMPARISON.md). 아래 조건·결론은 해당 단계의 기록이다.

동일 Qwen3-0.6B-Q8_0 가중치, 동일 토큰 입력(seed=407), 동일 CPU 어텐션·정확 FP32 후처리로 비교했다. hybrid는 비압축 자동 용량 선택, NPU 작업자 4개, CPU 후처리 4스레드 중첩, 용량별 핸들 재사용, 연속 입력 준비, 출력 중간 복사 제거를 사용한다. 출력층과 디코드는 CPU다. CPU 단독은 기존 네이티브 AVX2 정수 내적과 정확 후처리 경로다.

각 입력 길이·모드마다 별도 프로세스를 사용해 다른 모드의 가중치 계획·장치 버퍼가 메모리 수치에 섞이지 않도록 했다. 모델 로딩과 3토큰 프리필·1토큰 디코드 워밍업은 제외했다. hybrid는 모든 제출 용량 그래프를 미리 실행해 JIT를 측정에서 제외했다. 같은 프로세스에서 KV를 초기화하며 요청 2개를 연속 처리했다. 길이별 실행 순서는 CPU→hybrid, hybrid→CPU, CPU→hybrid다. 완전한 열·전력 통제 실험은 아니다.

#### 속도와 순차 처리량

입력 길이별 요청당 출력은 첫 토큰을 포함해 4토큰이다. 첫 출력은 모델 step 시간으로 토큰화·서버 통신을 포함하지 않는다. decode tok/s는 후속 3토큰/그 시간이다. 요청/분은 두 요청의 측정 총시간으로 계산한 순차 처리량이며 동시 요청 또는 포화 서버 처리량이 아니다.

| 입력 | 모드 | 첫 출력 초 | 요청 전체 초 | 후속 생성 tok/s | 순차 요청/분 |
|---:|---|---:|---:|---:|---:|
| 16 | cpu | 7.051 | 12.282 | 0.574 | 4.885 |
| 16 | hybrid | 8.702 | 14.061 | 0.560 | 4.267 |
| 64 | cpu | 25.801 | 36.563 | 0.279 | 1.641 |
| 64 | hybrid | 25.451 | 36.274 | 0.277 | 1.654 |
| 256 | cpu | 119.649 | 145.745 | 0.115 | 0.412 |

#### 자원 효율

CPU 초는 프로세스의 모든 스레드가 사용한 user+kernel CPU 시간이다. 평균 코어 수는 CPU 초/벽시계 초다. 이 값이 작아도 요청이 오래 걸려 총 CPU 초가 늘면 계산 효율 개선으로 간주하지 않는다. RSS와 private 메모리는 요청 중 100ms 간격으로 샘플링한 최대값이다. 드라이버·장치 메모리 전체나 시스템 전력은 포함하지 않는다.

#### 전력과 NPU 단독의 범위

현재 OS 전원 구성표는 균형 조정이다. AMD 전력 도구는 권한을 높여 실행해도 LoadLibraryA 실패가 발생해 전력·에너지를 계측하지 못했다. CPU 시간 감소나 RSS 감소를 에너지 절감으로 환산하지 않는다. 에너지 효율 판정에는 지원되는 전력 센서 또는 외부 전력계가 추가로 필요하다.

Geul 정확성 계약을 지키는 NPU 단독 모델 실행 경로는 아직 구현되지 않았다. 따라서 NPU 단독을 0초·실패 성능으로 넣지 않고 미지원으로 표시한다. 아래 별도 FastFlowLM 실행은 NPU 기반 프리필·디코드의 실용적 참고이며 엄격 계약의 대체 경로가 아니다.

#### 별도 NPU 런타임 참고

FastFlowLM 1.0.10, Qwen3 0.6B Q4_1/model.q4nx, performance 모드, 문맥 1,024, 한국어/임의 토큰 대신 별도 영어 프롬프트, 출력 상한 64, 워밍업 후 서로 다른 프롬프트 2개를 사용했다. 같은 모델 계열이지만 가중치·양자화·프롬프트·출력 길이가 달라 위 결과와 공정한 속도비를 계산할 수 없다. prefix 캐시 재사용은 통제하지 않았다. NPU 전용 백엔드라도 서버·스케줄링에는 CPU를 사용한다.

- 256입력: hybrid/CPU 요청 시간 1.000배, CPU 사용 시간 1.160배. 1보다 작아야 각각 개선이다.

현재 엄격 계약의 분담 구현은 256토큰 첫 출력에서 약 5% 단축을 보였지만 요청 전체 지연과 순차 처리량의 실질적 우위를 확보하지 못했다. 256토큰에서는 총 CPU 사용 시간이 약 16% 더 크고, 메모리도 더 크다. 디코드는 두 모드 모두 같은 CPU 코드이므로 관찰된 디코드 차이를 NPU 연산의 직접 효과라고 해석하지 않는다. 실행 순서·열·메모리 상태 등의 원인은 분리하지 않았다.

별도 NPU 런타임에서는 빠른 생성이 가능했다. 따라서 이번 결과는 NPU 하드웨어가 본질적으로 모델 실행에 부적합하다는 근거가 아니라, 현재 엄격 계약 구현과 일반 NPU 추론의 성능 격차를 보여준다. 양자화·가중치·프롬프트·출력 길이 차이 때문에 그 격차를 특정 설계 하나의 비용으로 환산할 수는 없다.

이 결과는 현재 프로토타입과 CPU 기준 경로의 비교다. 최적화된 모든 CPU 런타임 또는 NPU 하드웨어 자체의 한계를 뜻하지 않는다. 동시 요청 포화 처리량, 긴 생성, 전력 효율은 이번 결과로 확정하지 않는다.
