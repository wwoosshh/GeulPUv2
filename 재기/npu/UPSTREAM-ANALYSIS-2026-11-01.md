# GeulPU 상위 변경의 GeulNPU 적용 분석

2026-11-01 원격 fetch 후 main은 e002c10eab3178c7c79d3dcf0c10c8eddc19d5a9다. 이전 확인 이후 추가 커밋은 없다. 로컬 eaef542 대비 37개 커밋을 대상으로 분석했다. 작업 브랜치에 병합하거나 새로운 NPU 성능 시험을 실행하지 않았다.

## 판단

정확한 연산 계약을 유지하면서 실행 계획, 데이터 재사용, 독립 작업의 배분을 바꾸는 설계 근거가 추가됐다. 즉시 가져올 수 있는 NPU 가속 커널은 발견하지 못했다. 특히 단일 요청 지연과 동시 요청 처리량을 따로 평가해야 한다.

## 1. 고정 실행 계획과 요청별 상태 표

#178(a377ecd)는 독립적인 여러 요청의 현재 토큰을 행으로 모아 선형층에 함께 넣는다. #179(b8ee622)는 위치와 슬롯 정보를 장치의 표로 옮겨 커널 인자를 고정하고 생성 한 걸음을 CUDA 그래프 한 번으로 실행한다. 엔진/엔진표.gl에서 행표칸은 16개 64비트 값이며 위치 8개와 슬롯 8개를 담는다. 계획에 행별 가변 인자가 남지 않으면 cuGraphLaunch를 사용한다.

상위 저장소의 RTX 4070 Ti, Qwen3.5-4B Q4_K_M 기록에서 #178 → #179의 동시 8요청 총 생성 속도는 467 → 615 tokens/s, 1요청은 116 → 116이다. 8행의 장치 걸음 시간은 14.2 → 10.2 ms이고 제출 시간은 4.9 → 0.09 ms다. 이 수치는 GPU의 보고값이며 GeulNPU에서 재현한 값이 아니다.

GeulNPU에서는 정해진 주소의 입력·출력 버퍼, 재사용 가능한 DMA/실행 계획, 작은 요청별 위치·슬롯 표를 연구할 근거다. 현재 Python이 선형층마다 패킹·제출·회수하는 비용과 연관이 있다. CPU의 계약 후처리가 매 단계 필요하면 그 경계까지 자동으로 없앨 수는 없다. CUDA 그래프 API와 NPU 런타임은 별도 구현이 필요하다.

여러 요청을 같은 행렬곱에 넣으면 한 가중치 읽기를 여러 행에 재사용할 기회가 생긴다. 이것은 현재 요청의 다음 토큰이 정해지기 전에 그다음 토큰을 계산하는 방식과 다르다. 서버 처리량과 요청별 p50/p95 지연을 함께 측정해야 한다. 최신 변경의 직접 적용 구조는 Qwen3.5 계열이며 현재 실험 대상 Qwen3-0.6B에는 별도 연결이 필요하다.

## 2. 정수 계산과 순서 있는 실수 누산의 분리

문서/생성행렬곱.md는 기존 커널의 생산·소비 구조를 명시한다. 독립 스레드가 정확한 정수 부분합과 스케일 관련 값을 만들고, 출력 열별 담당 스레드가 블록 순서대로 FMA 체인을 실행한다. 문서화된 이 구조 자체가 이번 커밋에서 처음 생긴 것은 아니다.

#165(bb673cb)의 새 최적화는 주소 계산을 반복 밖으로 이동하고, 중간값 저장을 묶고, 작은 정수 색인과 독립된 dp4a 체인을 사용하는 것이다. H100의 Llama-3.1-8B 생성 걸음은 6.290 → 4.613 ms, RTX 4070 Ti에서는 11.27 → 11.00 ms였다. 대상은 CUDA k-양자화 GEMV다. 현재 Q8_0 NPU 내적에 동일 배수를 기대할 근거는 없다.

GeulNPU의 적용 후보는 여러 NPU 작업자에게 독립 정수 부분합 생산을 맡기고, 정해진 순서의 후처리를 수행하는 소비자와 연결하는 구조다. CPU 소비자를 유지하는 경우 출력 열별 병렬 후처리와 버퍼 소유권을 명시해야 한다. NPU 소비자는 정확한 FMA 의미를 구현한 뒤 성능을 검증해야 한다. 이전 AIE 벡터 MAC은 계약을 통과하지 못했다.

## 3. 큰 타일의 효용과 비용을 함께 재기

문서/프롬프트행렬곱.md의 P0는 정수 내적 외에 블록별 실수 끝셈, 주소 계산, 읽기, 동기화가 필요한 점을 분석한다. SM당 명령 발행량으로 유도한 GPU의 처리량 상한은 NPU에 그대로 적용할 수 없다. GeulNPU에서는 DMA, NPU 정수 계산, 부분합 회수, CPU 후처리, 대기를 각각 측정해야 한다.

#162의 척도 변환 재사용은 정밀 Q8_0에서 소폭 개선을 보였지만 H100 회귀로 #164(b6fc8c9)에서 되돌려졌다. 최종 main에 남은 최적화로 소개해서는 안 된다. #165에서도 워프를 늘린 후보와 FMA 전담 워프 후보가 느려져 제외됐다. 작업자 수와 타일 크기를 늘렸다는 사실만으로 향상을 가정하지 않는다.

P2의 Hopper wgmma/TMA 경로는 문서의 계획이며 완료된 NPU 구현이 아니다. P3는 k-양자화 활성값 지수 단위를 변경해 빠른 모드의 출력 비트를 바꾸는 장기 후보다. 기존 계약을 유지하라는 현재 목표의 적용 대상에서 제외한다.

## 4. 검증 도구와 계약 변화

#172(283e107)의 도구/same_bits.py는 단독 요청과 동시 요청의 응답을 비교한다. HTTP JSON의 토큰과 제공되는 로그 확률 숫자를 비교하며 전체 로짓의 uint32 표현을 비교하지 않는다. 숫자 비교에서는 +0과 -0도 구별하지 못한다. 배치 불변성 회귀시험에 활용하고 내부 로짓·KV의 비트 검사는 유지해야 한다.

로컬 기준 대비 계약/정수계약.py와 시험/참조7B.py에는 변경이 없다. 계약/contract.md의 추가는 도구 호출 중 특수 토큰 후보 제외 규칙이다. 일반 Qwen forward의 선형층 계약 변경으로 해석하지 않는다. 향후 서버 출력을 맞출 때는 새 토큰 선택 규칙도 구현해야 한다.

## 실행 우선순위

1. 한 선형층에서 작업자 1·2·4개를 비교한다. 같은 정수 연산량과 계약 후처리를 유지하고 실제 전송량 및 작업자별 출력을 기록한다.
2. 가중치 타일을 장치 내부에서 여러 입력 행에 재사용한다. 이전 JoinedPrefill은 호스트 제출을 묶었지만 각 4행 묶음에 가중치가 반복 전송되는 문제를 남겼다.
3. 고정 버퍼와 실행 계획을 재사용하고 후처리를 출력 열별로 병렬화한다. 장치 연산만, 후처리만, 전체 시간을 따로 비교한다.
4. 여러 요청을 처리할 필요가 있을 때 위치·슬롯 표 기반 배치를 연결한다. 단독·배치 간 로짓과 KV 비트 일치, 총 처리량, 요청별 지연을 함께 판정한다.

동일 출력 비트, CPU 대비 전체 시간, 전송 바이트 수를 적용 판정에 사용한다. 상위 GPU 기록은 설계 후보를 정하는 근거이며 NPU의 성능 예측값으로 사용하지 않는다.
